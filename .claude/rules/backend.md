# SnowRaven backend conventions

Moved verbatim from CLAUDE.md (2026-08-26 context restructure). This file auto-loads when a session works on files matching the `paths` above; for related work that starts elsewhere, read it in full before changing anything it governs. Its rules carry the same force as CLAUDE.md.

- **The on-disk data directory is single-sourced in `backend/datadir.py` (`DATA_DIR`, overridable with `SR_DATA_DIR`) — a backend module that reads `data/` MUST import it, never re-derive `Path(__file__).parent…/"data"` (v0.5.77).** Four routers (`settings`, `settingskv`, `mapdefaults`, `taxonomy`) each derived it independently until the override was added; a **partial** override is worse than none — the app would read demo data on one route and real data on the next, which is precisely the privacy failure the override exists to prevent (it lets the website screenshot capture drive a throwaway synthetic dataset instead of `mv`-ing the user's real eBird export aside). `backend/tests/test_datadir.py` asserts every consumer resolves through the one module, so a new router that re-derives its own path fails the suite — extend that test rather than adding a parallel one.

- **An env var read at MODULE IMPORT time cannot be set in `backend/.env`, and fails SILENTLY when you try (v0.5.77).** Routers import while `main` is still importing, which is before `load_dotenv()` runs, so an import-time `os.environ` read never sees a `.env` value — the code just uses its default with no error. `SR_DATA_DIR` is the live example and must be set in the process environment before the backend starts. The API keys above are unaffected (they are read per-request, after `load_dotenv()`). The same import order is why a file write can never redirect the data root — the security-positive half of the same fact, so don't "fix" it by moving the read later. State both halves at the definition site (`backend/datadir.py`'s docstring is the reference).

- **Backend runtime and CI verification versions are exact security/reproducibility pins (v0.5.72).** Keep `backend/requirements.txt` at the audited compatible runtime set (`fastapi==0.141.1`, `starlette==1.3.1`, `python-multipart==0.0.32`, `python-dotenv==1.2.2`) until a deliberate, tested upgrade. Keep backend CI's development tools explicit too: `ruff==0.15.20` and `pytest==9.1.1`; never restore unconstrained `pip install ruff pytest`, which made a tagged release depend on whatever PyPI served that day.

- **Backend outbound HTTP goes through the shared pooled client — `get_client()` from `backend/http_client.py` (v0.5.55), NEVER `async with httpx.AsyncClient()` per call.** It is one process-wide keep-alive `httpx.AsyncClient` (pooled connections reused across requests), a **LAZY singleton created on first use — NOT lifespan-created** (the test suite mounts `TestClient(app)` at module scope without a context manager, so lifespan startup never runs; a lifespan-created client would be `None` under every test). `main.py`'s lifespan only *closes* it on shutdown; never close it per request. It carries **no default headers/cookies/auth/base-URL** — pass the per-request `timeout=` AND any auth (the eBird `X-eBirdApiToken` header, the OpenWeather `appid` param) at each `.get()`/`.post()` call site, so there is no cross-request state bleed. Test mocks patch the shared accessor, not the `httpx.AsyncClient` constructor.
