# SnowRaven map conventions (MapLibre layers, overlays, popups, FABs)

Moved verbatim from CLAUDE.md (2026-08-26 context restructure). This file auto-loads when a session works on files matching the `paths` above; for related work that starts elsewhere, read it in full before changing anything it governs. Its rules carry the same force as CLAUDE.md.

- **The maps run on MapLibre GL via `react-map-gl` (entry `react-map-gl/maplibre`); Leaflet has been fully removed.** All three maps (Map Explorer, Species Detail, Statistics) render through the shared `<SnowMap>` wrapper (`components/SnowMap.tsx`), with styles/providers in `lib/mapStyle.ts`. Import react-map-gl's `Map` as `MapGL` — it shadows the global `Map` constructor otherwise (that caused a blank-screen crash). Components inside a `<Map>` get the instance via `useMap().current` (a `MapRef` proxying the MapLibre `Map`). Popups are a single state-driven `<Popup>` per map (MapLibre has no per-marker `bindPopup`).
- **Map Explorer's high-count markers are GL layers, not DOM `<Marker>`s (v0.5.16).** Sighting pins are a `circle` layer (`sr-sight-circle`) and hotspot teardrops a `symbol` layer (`sr-hotspot`) with canvas-baked sprites — the count→radius/opacity model lives in `lib/mapPins.ts` as shared stop tables (function + step-expression from one source of truth; `mapPins.test.ts` locks the parity). Do NOT add a DOM `<Marker>` per feature for anything that can reach hundreds of instances; bounded, content-rich markers (Media Target chips, the user-location dot, Species Detail / Statistics pins) stay DOM. GL paint can't use CSS vars: colors are read from `--sr-*` tokens at runtime and refreshed on a `data-theme` change (a `MutationObserver`, same contract as the atlas hatch sprites). Clicks come from `map.on('click')` + `queryRenderedFeatures`; the canvas cursor must go through `updateMapCursor` in `lib/mapPins.ts` (overlapping interactive layers strand a stale cursor if each manages it independently). `AtlasLayer` ignores clicks where a marker layer is hit, so pin clicks don't also open the block popup.
- **Sighting-point sizing is single-sourced in `lib/mapPins.ts` — `POINT_SIZE_RADIUS_FACTOR` (normal:1, small:0.5) + a `factor` arg on `pinRadiusExpr`/`pinFillRadiusExpr` (factor-1 short-circuits so Normal is byte-identical), parity-locked by `mapPins.test.ts` (v0.5.53).** The Map Explorer "Point Size" control (Normal / Small / Off, `PointSize` in `lib/mapExplorerTypes.ts`; Pins-mode-only, under the Pins/Heatmap toggle; session-only `useState`, no `storage` seam) drives it via `SightingMarkers`' `pointSize` prop — **Off** returns null (removes the `sr-sight-circle` layer AND gates its click/hover handlers so a shaded breeding-block / county choropleth reads through), **Small** applies the 0.5 radius factor, **Normal** is unchanged. It **COMPOSES with the v0.5.47 shade auto-dim** (radius factor and opacity dim are independent axes — Small + an active shade multiplies opacity by the dim factor); the heatmap is untouched. Don't hardcode a second radius scale — thread the `factor` through `mapPins.ts`.
- **Sighting-pin maps use the shared `SightingsMap` (`components/SightingsMap.tsx`) — don't re-inline the Species Detail pins map (v0.5.26).** It owns the DOM `<Marker>` pins, the single state-driven `<Popup>` (its own `selectedCoord`), `MapBoundsFitter`, and the static `SP_PIN_HTML` sprite; **`MapBoundsFitter`'s `coordinates` prop MUST be memoized (v1.0.15).** Its effect deps are `[map, coordinates]` and its body calls `fitBounds(..., { duration: 0 })`, so a fresh array identity on every render re-frames the map on every render -- and that shipped: opening a pin popup sets `selectedCoord` in this very component, re-renders it, and snapped the map back to its starting view, discarding whatever the user had panned or zoomed to. Any state change in a component or its HOST re-frames a map fed an inline `.map(...)`. Guard it through the REAL fitter with a guard-the-guard asserting it still re-frames when the marker set genuinely changes. Species Detail and the Named Birds card both consume it. Build its `markers` with the pure `lib/sightingMarkers.ts` `buildSightingMarkers` (skip null coords, group by `lat,lng`, dates newest-first) so skip-null / empty→no-map / same-coord aggregation stays one tested function. The heatmap/intensity/map-mode toggle stay LOCAL to Species Detail — the extraction is the pins path only. Callers must gate on `markers.length > 0` (the empty guard is the caller's, so no WebGL context mounts for a no-coordinate entity). **Where a list can mount per-row maps, bound concurrent WebGL contexts structurally with a single-open accordion (one live map = one context), not an instance counter/queue** — the Named Birds tab does this via a `singleOpen` prop on `NamedBirdsTable` (Species Detail's map-less list stays multi-open).
- **Keep maplibre OFF the entry chunk — the per-row map and the map tabs stay lazy (v0.5.42).** Even though the map *tabs* are `React.lazy`, a single statically-imported component can silently drag the ~1 MB / 273 KB-gz maplibre vendor bundle onto first paint — `NamedBirdRow`'s static `import { SightingsMap }` did exactly this (latent regression, fixed in 0.5.42). Rule: NO component reachable from `App.tsx`'s STATIC import graph may statically import `SightingsMap` / `SnowMap` / `react-map-gl/maplibre`. The per-row `SightingsMap` and the map tabs (Map Explorer, Species Detail) stay `lazy()` + `<Suspense>`, warmed at idle via App's `requestIdleCallback` warmer — define the importer locally in App (`() => import('./components/SightingsMap')`) and keep the map component file component-only so `react-refresh/only-export-components` passes. Standing check after any map-touching change: a fresh `npm run build` must show `vendor-maplibre` ABSENT from `dist/index.html`'s modulepreload and no bare `import "./vendor-maplibre"` in the entry chunk. `chunkSizeWarningLimit` is 1100 because the isolated maplibre vendor chunk (~1 MB, off first paint) is legitimately over 500 KB. **This rule now has an automated guard — `frontend/src/lib/entryChunk.test.ts` walks `App.tsx`'s static import graph (asserting `SightingsMap`/`SnowMap`/maplibre and the on-demand `CountyLayer`/`us-counties.json` are not statically reachable) AND checks the built `dist/index.html` modulepreload for any county/maplibre entry. Extend `entryChunk.test.ts` when you add a new off-entry-chunk asset or component rather than relying on the manual build inspection alone.**
- **An asset that MUST ride the entry chunk can be compressed by shipping CORRECTIONS against a convention rather than the full set — and that is only sound because a test asserts the compressed form equals the full lookup member by member (v0.5.89).** Countability needed a verdict for all 17,891 published names on a module statically reachable from `App.tsx`. The full set is ~105 KB gz; eBird's own naming convention already reproduces the verdict on 17,722 of them, so the shipped artifact is the **169 corrections** in both directions (2.6 KB gz, +4.1% on the entry chunk rather than +32.5%), with the convention as the fallback for a name eBird does not publish. Three conditions make this a technique rather than a gamble, and dropping any one of them turns it into an unverifiable guess: the base convention is the DATA OWNER's own, not one we inferred; `countableForms.test.ts` re-derives eBird's verdict from the snapshot independently and asserts the shipped predicate against it **name by name over the whole snapshot**, pinning the count so the sweep cannot go vacuous and carrying a guard-the-guard that proves the sweep detects a named wrong compression; and the generator is called from `build-ebird-taxonomy.mjs` in the same run, so the annual Clements refresh cannot let the two files drift. Also state what compression buys nothing: listing the other 2,523 non-countable names would add ~19 KB gz and change no answer.
- **A test that walks an import graph by scanning SOURCE TEXT must strip comments FIRST — prose can hijack its matcher and invent an edge that does not exist (v0.5.87).** The word "import" or "export" inside a comment starts a lazy specifier match that runs forward to the next real `from '...'`, so a dependency-free module reported an import of `transport.ts`; it happened on `exoticProvenanceGraph.test.ts`'s first run, and it is the same class of defect the CSS guards' shared parser already fixes by stripping comments before its brace walk. **`entryChunk.test.ts` carries the same latent weakness** — strip comments there when it is next touched. Pair any such walker with a **guard-the-guard**: point it at a module that genuinely DOES have the forbidden edge and assert it reports one, so a broken matcher cannot return a clean result for everything (`exoticProvenanceGraph.test.ts` aims its walker at the controller for exactly this).
- **A deliberate "set a point on the map" gesture uses `contextmenu` (desktop) + a long-press timer (touch), NOT left-click (v0.5.43).** The Map Explorer maps already consume left-click/tap for pin/popup selection (sighting/hotspot GL layers + atlas fill via `map.on('click')` + `queryRenderedFeatures`), so a click-to-place gesture would ambiguate "open this pin" vs "set the point." Use a map child that binds `map.on('contextmenu', …)` plus a hand-rolled touch long-press timer — cancel the timer on `movestart`/`zoomstart`/`dragstart`, a `touchmove` past a ~10px slop, a 2nd touch (pinch), and `touchend`/`touchcancel`, and NEVER `preventDefault` before it fires (so a normal pan is untouched). Some touch platforms synthesize a `contextmenu` after a long-press, so dedup it (a short `lastTouchFire` window guarding the contextmenu handler). Render the result as a DOM `<Marker>` (one draggable instance, not a GL layer — avoids the base-switch / source-id pitfalls). Reference: `CenterPinDropper` / `CenterPin` in `components/map/MapControls.tsx` (the map-center pin). The `Date.now()` for the dedup lives in the event handler/effect, never in render.
- **Floating overlays (dropdowns, menus, popovers) that can appear over a map must use a `z-index` above the map's controls.** Use `z-index: 1200` (the phone navigation bar in `TabNav.tsx` sits exactly there; its More sheet goes above it at 1260 and the rail tooltip at 1250). **A FIXED element at 1200 that comes LATER in the DOM than `.sr-map-fullscreen-panel` will paint over a fullscreen map, and `inert` does not stop it** -- `inert` removes a subtree from focus and the accessibility tree, never from the paint. The phone nav bar is therefore not rendered at all while the map is fullscreen, rather than merely made inert like the header and footer, which are in normal flow and genuinely covered by the panel. The Map Explorer is reachable on most views, so any new overlay should assume a map may be beneath it.
- **A MapLibre `fill` layer with `fill-opacity: 0` is still hit-tested**, so a transparent fill makes a polygon's whole interior a click target. The atlas overlay (`AtlasLayer.tsx`) relies on this — unshaded blocks have `fill-opacity 0` yet still open the block popup, via a handler bound with `map.on('click', 'sr-atlas-fill', …)`.
- **The atlas overlay is viewport-capped (v0.5.16).** `AtlasLayer` generates blocks for the current view only — `blocksInBounds` + `padBounds(0.15)` from `lib/atlasBlocks.ts`, recomputed on `moveend`, cap 9000 — instead of materializing all ~17k block polygons. Over-cap views (roughly the full-state zoom-6 view) draw nothing and show a "Zoom in to see atlas blocks" hint chip. Tier fill colors read the `--sr-tier-N` tokens at render (theme-aware, matching the sidebar legend); the atlas layers insert *below* any marker layers present at mount (`beforeId`) so pins stay on top when the atlas is toggled on later.
- **The county overlay (`CountyLayer.tsx`) is the Map Explorer's SECOND viewport-capped GeoJSON overlay — the structural twin of the atlas (v0.5.46).** Same shape as `AtlasLayer`: a GeoJSON source recomputed on `moveend` from bundled boundary geometry (`countiesInBounds` + `padBounds(0.15)`, cap 800 → a "Zoom in to see counties" chip over-cap), a `line` layer for boundaries plus a `fill` layer whose unrecorded tier keeps `fill-opacity 0` but stays hit-tested for the popup, theme-aware fills (`--sr-county-N`) read at runtime with a `data-theme` MutationObserver re-resolve, a single state-driven `<Popup>`, and a keyboard "counties in view" disclosure for WCAG-AA parity. When you touch either overlay, remember BOTH now exist: the boundary *lines* may coexist, but the two SHADE fills are MUTUALLY EXCLUSIVE (v0.5.47) — turning on county shading clears atlas breeding shading and vice-versa, so only one choropleth ramp is ever active. The pure rule is `lib/shadingExclusion.ts` `nextShadingState(which, prev)` (an explicit cross-clearing helper wired into both shade toggles, NOT a `useEffect` mirror — that's ambiguous about which wins and adds a render); shade state stays session-scoped (plain `useState`, not persisted). The green county ramp and purple atlas ramp are still deliberately distinct hues — that distinctness now serves the coexisting boundary *lines*, no longer simultaneous fills (this reverses the v0.5.46 "designed to coexist so both can shade at once" contract).
- **County boundary LINES come from the basemap's OWN vector tiles at high zoom — the bundled GeoJSON is the fill/popup/join source and the below-z9 + offline LINE fallback (v0.5.49).** `CountyLayer` adds an `sr-county-line-hi` `line` layer on the SHARED `openmaptiles` vector source (the OpenFreeMap base tiles already fetched for the basemap — so NO new network, NO new provider, NO bundle growth, NO `PRIVACY_POLICY` change), `source-layer "boundary"`, filter `admin_level==6` (excluding maritime/disputed, matching the basemap's boundary family), `minzoom 9` (where OpenMapTiles starts emitting counties), `beforeId` below markers, gated on `map.getSource('openmaptiles')` via a `vectorReady` flag refreshed on `styledata` (the source is absent on a bare offline map). The bundled `sr-county-line` is **maxzoom-capped at `COUNTY_LINE_HANDOFF_ZOOM` (9)** so it draws only z4–9 (far out, where its blockiness is invisible) and as the offline-Tier-A / below-z9 fallback; the FILL, the (stusps,name) join, the popup, and the viewport windowing are UNTOUCHED. `mapStyle.ts` narrows the always-on `boundary_3` to `admin_level<=4` (states/provinces only) so counties are overlay-only and a faint dashed basemap line doesn't double-draw under the dedicated county line. Accepted tradeoffs: a residual shaded-fill sliver when shading is ON + zoomed past z9 (crisp tile line over the bundled fill edge — much reduced in v0.5.50 by sharpening the fill to 15% simplify, below visibility at practical zooms but not exactly zero at extreme zoom), and no county lines when fully offline at z10+ (no basemap tiles then — the bundled line is capped). Locked by `CountyLayer.test.tsx` (admin_level-6 line on `openmaptiles` + bundled maxzoom cap + the offline-omit) and `mapStyle.test.ts` (boundary_3 narrowed). This is the in-app realization of the basemap-anchored-boundary-line note below — the overlay line literally IS the basemap's own boundary. (NOTE: the "~1.04 MB-gz" figure below is the BUILT chunk size, verified at build — larger than the script's raw-json gz guard reading of 969 KB; v0.5.50 sharpened the bundled geometry to 15%-keep simplify, growing the on-demand chunk from ~751 KB-gz.)
- **The county shade ramp is 10 data-driven quantile classes (`--sr-county-1..10`), widened from 4 in v0.5.48.** `computeCountyTiers` (default `COUNTY_CLASS_COUNT = 10`, `lib/countyShading.ts`) maps each county's count onto equal-population quantile breaks; the green ramp is geometric-luminance-spaced so every adjacency clears the ≥1.2:1 legibility floor (10 single-hue green steps land at ~1.21–1.23:1 — intentionally subtle at the top; `lib/countyContrast.test.ts`, extended to tiers 1..10, is the guard, and the same monotonic/≥1.2:1/both-themes-identical/-rgb-present asserts apply). **Changing the class count means updating FOUR sites in lockstep or higher tiers paint the `#000000` fallback (black counties):** the `--sr-county-N`(+`-rgb`) tokens in BOTH `:root` and `[data-theme="dark"]` of `globals.css`, `CountyLayer.tsx`'s `CountyTier` union + `COUNTY_FALLBACK` + the `fill-color` `match` arms, the `computeCountyTiers` caller in `MapExplorer.tsx`, and `countyContrast.test.ts`'s `TIERS`. The legend (MapExplorer) and `tierFor`/dedupe already generalize to N. The bundled county geometry was resharpened again to **15%-keep Visvalingam** (`scripts/build-county-boundaries.mjs` `SIMPLIFY_PCT`; v0.5.50, up from 10% — ~54 verts/county, 969 KB raw-json gz / ~1.04 MB built-chunk-gz on-demand chunk, within the 1.3 MB gz guard with ~27% margin) so the FILL edge hugs the true boundary and the hair-thin shaded sliver under the crisp basemap-tile county line vanishes at high zoom when shading is on (the deferred v0.5.49 "option D", done by sharpening the one file that drives both the fill and the below-z9/offline line) — regenerate with `node scripts/build-county-boundaries.mjs` (release-time dev tool, needs network + `npx mapshaper`; NOT part of `npm run build`).
- **The county overlay's third metric, Completeness (v0.5.54), shades on FIXED percentage bands — an absolute-scale metric gets a parallel fixed-band tier path, never a `computeCountyTiers` extension.** A metric whose value has absolute meaning (a percent: "50% complete" means the same everywhere) supplies its own static band table (`COMPLETENESS_BANDS` / `completenessBand` in `lib/countyCompleteness.ts`, (lo, hi] semantics, FP-epsilon-guarded) and feeds the SAME tier property/`--sr-county-N` tokens/hatch sprites; the quantile machinery stays untouched (a `CountyLayer.test.tsx` parity test locks that the count metrics never consult the completeness controller, and the fill layer id stays `sr-county-fill` in every branch). A map layer that needs per-feature LIVE data takes a controller VIEW object — render-safe `summaryFor`/`resultFor` plus event-driven `onViewportCounties`/`requestCounty` (`CountyCompletenessView` from `lib/useCountyCompleteness.ts`) — keeping the layer presentational and the fetch policy (birded-in-view only, TTL-fresh skip, pool of 4, in-flight dedupe, never bulk) unit-testable in the hook. `GET /map/county-species` is dual-transport (`backend/routers/map.py` ↔ `mapService.getCountySpecies`), its Y-side taxonomy collapse twins are `routers/taxonomy.py` `collapse_to_species_list` ↔ `taxonomyService.collapseToSpeciesList` (keep in lockstep), and the route is deliberately NOT in `CACHED_GET_PATHS` — the 30-day `countyCompletenessCache` is its single caching layer. A fetched-but-0% county stays band 0 (plain outline = never birded survives click-to-fetch).
- **County shading has a colorblind "Use Textures" mode (`lib/countyTextures.ts`, v0.5.51) — the county analogue of the atlas hatch, bringing the two mutually-exclusive ramps to parity.** When county shading is on, an opt-in `useTextures` toggle (default OFF, session-`useState`, no persistence) paints each tier as ONE 45°/135° CROSSHATCH whose DENSITY rises with the tier (sprite ids `sr-county-hatch-1..10`): line SPACING carries tiers 1–6, line WEIGHT takes over 7–10 where the gap can't shrink further (`HATCH` table {gapPx 20→5, lineWidthPx 0.75→1.30}; tier 10 ~60% ink — never solid, tier 1 ~10% open-lattice floor); a faint 0.12 tint underlay + 0.80 strokes both read `--sr-county-N-rgb` at generation. `CountyLayer` gained the `useTextures` prop + a sprite-registration effect that EXTENDS the existing `themeRev` MutationObserver — registers all 10 sprites UNCONDITIONALLY (NO `isStyleLoaded` gate — the documented pitfall) with a `styleimagemissing` net scoped to its own ids via `countyHatchTierForImage`, exactly the atlas-hatch contract; `useHatch = useTextures && shadeOn` switches the paint to `fill-pattern` else the unchanged `fill-color`. **The fill layer id STAYS `sr-county-fill` in BOTH branches — load-bearing for the heatmap z-order + `BasemapDesaturation`; don't rename it.** The legend + the 11px "Counties in view" swatch swap to `CountyDensitySwatch` (`map/MapSidebarUI.tsx`), its geometry imported from `countyHatchSpec` so the legend can't drift from the map. Guard: `lib/countyTextures.test.ts` (strict-monotonic + adjacency ≥1.12 on the pure `countyHatchDensity(tier)=lineWidthPx/gapPx` proxy) — the density analogue of the UNCHANGED `countyContrast.test.ts` (which still guards the COLOR ramp). `nextShadingState`, `BasemapDesaturation`, the `shadingFillId` heatmap order, the boundary lines, the popup, the (state,county) join, the viewport cap, and the `--sr-county-*` tokens are all untouched.
- **A GL *boundary line* color may be a fixed, basemap-anchored literal — distinct from GL *fills*, which must still read `--sr-*` tokens at runtime.** Both `AtlasLayer` and `CountyLayer` hardcode the same slate boundary line (`rgba(71,85,105,~0.85)`) because GL paint can't read CSS vars and the line sits on the always-light Positron basemap regardless of app theme. This is the deliberate exception to the no-hardcoded-color rule; don't flag it as a token violation. Fills are NOT exempt — the county fills read `--sr-county-N` and re-resolve on a `data-theme` change.
- **While a shading ramp is active, the basemap's land fills mute to grey so the ramp pops (v0.5.47) — an extension of the basemap-anchored hardcoded-color exception above.** `components/map/BasemapDesaturation.tsx` (a `<SnowMap>` child driven by `active = shadeByCounty || shadeByBreeding`) greys the four Positron land-cover fills (`park`/`landcover_wood`/`landcover_grass`/`landuse_residential`) via `setPaintProperty('fill-color', …)` and pushes `raster-saturation` toward grey on the `sr-satellite`/`sr-topo` raster bases; water, roads, labels, and the `sr-trails` overlay keep their color, and everything restores when shading is off. The greys are DERIVED from the exported `TINT_*` HSL constants in `mapStyle.ts` (S→0, same lightness — one source of truth via `desaturateHsl`), so they are basemap-anchored literals, NOT a token violation (and theme-independent at S=0 — no `data-theme` observer needed). It is surgical MapLibre paint, NOT a CSS `filter: grayscale()` (which would grey the user's own pins/data and would not raise overlay-vs-basemap contrast). Every paint call is `getLayer()`-guarded and applied idempotently to BOTH paths (so the child needn't read SnowMap's private `base`), and re-applied on `styledata` (a style reload recreates layers with original colors); never gate on `isStyleLoaded()` (sprite-registration post-mortem). It is automatic on the existing shade toggles — NOT exposed as its own user control (a "Desaturate basemap" toggle would cross into New-Feature territory).
- **`computeGeo`'s per-county aggregation is keyed by a (state, county) composite, not county name alone (v0.5.46).** US county names collide across states (many "Washington"/"Jefferson"), so the county overlay's join and the Statistics geo rows key on `countyKey(stusps, normalizeCountyName(name))`. Any consumer of per-county data must key rows the same way — a name-only key silently merges same-named counties across states (a real, visible count shift for users who've birded them). The re-key is locked by a `birdingStats.test.ts` two-Washingtons regression test and a `countyShading.test.ts` parity test against `computeGeo`.
- **Heatmaps use MapLibre's native `heatmap` layer**, driven by one shared model in `lib/heat.ts` (`heatRadiusPx` / `heatIntensityFactor` / `heatWeight`) so the 1–10 intensity slider behaves identically on the Map Explorer and Species Detail maps — tune the curve there, not per-map (default is deliberately calm: `heatIntensityFactor(5) = 0.30`). When EITHER shading ramp is on (atlas breeding OR county — mutually exclusive since v0.5.47), the Map Explorer heatmap is re-ordered UNDER the active shade fill and dimmed, and the sighting pins fade, so the tier colors stay legible on top. `SightingMarkers` takes a `shadingFillId` STRING (generalized from the old `atlasShading` boolean) — the id of whichever fill is active (`sr-atlas-fill` or the county fill) — and uses it as the heatmap `beforeId`; an empty string means no active shading (normal z-order, full opacity, pins not dimmed).
- **To texture/pattern-fill a MapLibre layer, generate a raster sprite and `map.addImage(id, imageData, { pixelRatio })`, then reference it from `fill-pattern`** (MapLibre fills can't use SVG `<pattern>` fragments). The atlas hatches (`lib/atlasTextures.ts` → canvas `ImageData` per breeding tier; added by `AtlasLayer` on load) use this. Sprite colors are read from the `--sr-tier-N-rgb` tokens at generation time, so regenerate + re-add on a `data-theme` change (a `MutationObserver` in `AtlasLayer` handles it). The sidebar legend's hatch preview is a separate inline-SVG swatch (`TierHatchSwatch` in `MapExplorer.tsx`), theme-aware via CSS vars.
- **Never gate map sprite/image registration on `isStyleLoaded()` with a `once('load')` fallback (0.5.30 post-mortem).** `isStyleLoaded()` reads false during ANY tile/source churn (base switch, fitBounds, slow network), and MapLibre's `load` event fires once per map lifetime — the Map Explorer's map stays alive from first tab mount, so a listener armed later never fires and the sprites silently never register (invisible, unclickable pins; latent since 0.5.16). Register unconditionally at effect time (`addImage` needs the style present, not "loaded"; keep the `hasImage → updateImage : addImage` idempotency) AND keep a `styleimagemissing` safety net that bakes only the component's OWN hardcoded image ids — exact-match against the id constants (`HOTSPOT_IMAGE_ID` / `HATCH_IMAGE_ID`), `hasImage`-guarded, removed on unmount. The same ownership contract applies to any map-level event handler fed external ids: act only on your own hardcoded id set; never use the incoming id as an object key or regex input. `HotspotMarkers.tsx` / `AtlasLayer.tsx` are the reference implementation.
- **A react-map-gl `<Source>` whose `id` differs between render branches must be keyed (or conditionally mounted as separate components) so React remounts it (0.5.30 post-mortem).** MapLibre forbids changing a source's id in place: an unkeyed branch swap reuses the React instance, react-map-gl throws `Error: source id changed`, and the app error boundary takes the whole app down — the Map Explorer Pins→Heatmap toggle shipped that crash unnoticed from 0.5.18 through 0.5.29. `map/SightingMarkers.tsx` keys its two branch `<Source>`s (`key="sr-sight"` / `key="sr-heat"`); `SightingMarkers.test.tsx` is the mechanical check (proven to fail on pre-fix code).
- **A COSMETIC per-marker view-mode toggle (e.g. Labels/Dots) is a PROP-driven in-place re-render — NEVER folded into the marker layer's remount `key` (v0.5.59).** The Nearby Lifers / Media Targets "Marker style: Labels | Dots" toggle passes `markerMode` as a prop and is deliberately kept OUT of the marker set's `key`. Folding it in remounts every marker on each toggle, which re-runs the `fitBounds` effect (the map re-frames to the pins) and dismisses any open popup — a jarring reframe for a purely cosmetic restyle. Only genuinely structural inputs (dataset length, a view mode that changes *which* markers exist) belong in the `key`; a mode that only changes how the SAME markers look is a prop. (Dots mode hides the label via `display:none` while keeping the real focusable `<button>` + `aria-label` + popup; the locator dot is always-on ground truth.)
- **When a control's VISIBILITY is decided by state the app itself mutates as a RESULT of that control's action, you have built a feedback loop — and the cut belongs at the app's mutation, never in a cleverer predicate (v0.5.91).** "Search this area" offers itself when the viewport has moved away from the last searched area; a successful search re-framed the map onto its own results; and the re-fit reliably frames OUTWARD (a rectangle spanning the searched circle has a half-diagonal approaching `r*sqrt(2)`, and its centre lands away from the searched one). So one press moved the map out from under its own record, the control re-offered itself, and a second press spent another eBird lookup a rung wider — 5 to 10 to 25 mi, one unrequested lookup per step, on a map the user never touched. **No geometric predicate can separate that from a deliberate pan or zoom-out, because the two produce the identical viewport**; a containment predicate proposed as the fix was rejected by measurement for exactly that reason (the auto-fit zooms OUT, so containment never fires). The fix is an `autoFit` prop on the three marker layers, default `true` and false only for a press whose centre and radius were DERIVED from the framing. Every shipped route still frames its results and each genuinely needs to, because each can set a centre nowhere near the screen. Suppression is per RESULT SET rather than per press, so it also covers a filter-driven re-fit on the two views that pass a filtered derivative as `pins`. `searchArea.test.ts` carries a test naming the rejected predicate, so the fix cannot later be dropped back into the offer predicate. The same discipline settles two other measurements in that build — the fit hook measures a term the control cannot move, and the chrome measurement above excludes the box it sizes — and it is the one question to ask of any such reading: **can the thing being decided move the thing being measured?**
- **A MapLibre GL paint transition does NOT inherit the app's global reduced-motion collapse (v0.5.91).** `globals.css`'s `@media (prefers-reduced-motion: reduce)` block reaches CSS animations and transitions on DOM elements; `-transition` values are configured in JavaScript and rendered on the canvas, so no CSS rule touches them. Any GL layer that animates must read the shipped `prefersReducedMotion()` from `lib/scroll.ts` (do not re-inline `matchMedia`; its home in `scroll.ts` under-describes it) and pass duration 0, read at effect or state-initializer time and never in a render body. MapLibre's easing is also not configurable — `-transition` accepts `{ duration, delay }` only — so a GL fade can match a DOM one approximately and never exactly.
- **The map backdrop (area beyond tiles / before load) comes from the MapLibre style's `background` layer**, not a CSS container override. `SnowMap` shows a `VOID_COLOR` placeholder (`lib/mapStyle.ts`) only while the vector style is fetching; once loaded, the style paints its own background. (The old Leaflet `.leaflet-container` backdrop hack is gone.)
- **Map tiles come from keyless providers defined once in `frontend/src/lib/mapStyle.ts`, rendered via `<SnowMap switcher?>` — never hard-code a tile source in a map component.** Default base is the **OpenFreeMap** vector style (positron), tuned in `fetchTunedBaseStyle` (label size, country/state borders, land tints). Do NOT reintroduce `tile.openstreetmap.org` (OSMF policy forbids app/self-hosted use). Satellite (Esri) / Topo-US (USGS) / Trails (Waymarked) are raster layers toggled by `visibility` within the ONE persistent style — never `setStyle`-swap for base changes (it drops sources and resets pan/zoom). Base/overlay choice persists via the storage seam. **Adding or changing any tile provider MUST be reflected in `PRIVACY_POLICY.md` (the "Map Tiles" section)** — tiles, and the OpenFreeMap style/glyphs/sprites, are fetched browser→provider, exposing IP + viewport, so the provider list is a privacy disclosure. Flag this in security reviews touching the map basemaps.
- **Map fullscreen is a CSS overlay, not the browser Fullscreen API.** The Map Explorer panel becomes `position: fixed; inset: 0; height: 100dvh; z-index: 1200` driven by `mapFullscreen` in `App.tsx` (the Fullscreen API is unreliable in iOS Safari/WKWebView). **The three EMBEDDED maps expand through a second, separate mechanism with the same geometry (v1.0.15):** `lib/useMapFullscreen.ts` swaps `MAP_FS_PANEL_CLASS` (`.sr-map-fs-panel`) onto the host's OWN container, so the `<SnowMap>` keeps its place in the React tree and the MapLibre instance, its WebGL context, the viewport, an open popup, a dropped share pin and the county overlay all survive a round trip because nothing ever asked them not to -- never a portal, never a remount, never the Fullscreen API. One expanded class for all four mounts (Species Detail Pins and Heatmap, which share one state because the hook is called on the container wrapping the ternary; the Named Birds card; Statistics Geographic Stats), so "the surfaces are identical when expanded" is a property of the stylesheet rather than of anyone's discipline, and its first four declarations are byte-identical to the Map Explorer's panel: the app has ONE fullscreen geometry, not two. **Four traps, all of which cost a build here.** (a) `.sr-map-fs-panel` and the phone-tier `.sr-map-container { height: 300px }` are both ONE CLASS DEEP and the `@media (max-width: 640px)` block comes last, so unscoped the media rule wins and the expanded map is 300px tall on a phone with every other declaration correct -- hence `.sr-map-container:not(.sr-map-fs-panel)`, and any future phone-tier height override owes the same guard; raising the panel rule's specificity artificially would work and is the wrong shape. (b) The panel rule must sit BELOW the container rules in source order, since all four are one class deep. (c) **An inline declaration is specificity 1,0,0 and can never be beaten by a class**, so a container styled inline must be lifted to a class before it can be expanded at all (and the lifted class goes on the loading placeholder twin too, so zero-layout-shift stops being two hand-kept copies). (d) The panel must not animate: a scaling live canvas tears, a fade shows the page through a half-transparent map, and **a transform is the one property this feature is forbidden** because an ancestor transform makes `position: fixed` resolve against it. Animate the corner row instead, entrance only. The corner row is `.sr-map-corner-row` (share button first via a `display: contents` slot, then the toggle) mounted as a `<SnowMap>` CHILD so it has `useMap()` access, and `components/map/MapCornerControls.tsx` must stay OFF the entry chunk while `lib/useFocusTrap.ts` and `lib/useMapFullscreen.ts` must stay ON it and dependency-free (`NamedBirdRow.tsx` is on `App.tsx`'s static graph), guarded by `entryChunk.test.ts` plus `lib/mapFullscreenEntrySafe.test.ts`.
- **`react-map-gl`'s `MapRef` LIES about handler properties: `createRef` copies only the map's FUNCTIONS, so `mapRef.scrollZoom` is `undefined` at runtime while the type says otherwise (v1.0.15).** It typechecks and it fails. Methods (`resize()`, `fitBounds()`) are proxied and fine; handler objects (`scrollZoom`, `cooperativeGestures`, `dragPan`) are reachable ONLY through `getMap()`. Drive a gesture-posture change on the live instance with the JSX props held CONSTANT -- react-map-gl re-applies a handler prop only when its value changes, so constant props and imperative control do not fight and nothing remounts. **CAPTURE the in-flow posture per mount and restore what you captured; never hardcode a pair** -- the four mounts do not agree, and `SnowMap` forwards both props unconditionally, so a map that "passes neither" is constructed with `scrollZoom: undefined`, an own key that shadows maplibre's `true` default. **Measure the captured value once in a real browser anyway:** the Statistics map's posture is scroll zoom OFF and cooperative gestures OFF, and three artifacts said the opposite while the code was right, because capturing makes a wrong premise cost nothing at runtime and nothing at all in review. Also: a class swap needs an explicit `map.resize()` in a LAYOUT effect after the commit and before paint, plus one more on the next frame for WKWebView, where `100dvh` can settle a frame late; `resize()` preserves centre and zoom, so it is not a re-frame.
 The fullscreen toggle shows on ALL widths (bottom-right of the map, in `.sr-map-fab-cluster`); the **Filters** button in that same cluster is mobile-only (desktop keeps the sidebar visible). When adding state that hides app chrome, clear it on any in-component navigation that switches tabs, and lock `document.body` overflow only while the overlay is active.
- **Every circular map FAB is `.sr-map-fab` plus a size modifier (`--std` / `--compact`); the three hand-duplicated copies are gone (v0.5.84).** `.sr-map-fullscreen-btn`, `.sr-share-drop-btn` and `.sr-map-locate-btn` each carried the same twelve declarations, and `.sr-map-locate-btn`'s own comment named this extraction as its successor. The semantic classes survive as **state hooks only** (`.sr-share-drop-btn`'s `[aria-pressed]` tint, `.sr-map-locate-btn`'s busy rule, `.sr-map-center-share-btn`'s two states); `.sr-map-fullscreen-btn` and `.sr-share-drop-btn--compact` now carry no declarations at all and stay on their elements as handles. Three rules hang off this shape:
  - **A glyph's unit must match its box's unit, or the ratio breaks at scale.** lucide's `size={17}` renders a **px** `width`/`height` attribute, so a phone FAB growing 44px → 88px at 200% text scale kept a 17px glyph and the disc emptied out at exactly the condition this row is judged at. The glyph is now sized in rem through `--sr-fab-glyph`, declared on each size modifier and read by `.sr-map-fab svg` — measured constant at 0.3864 (phone) and 0.4722 (desktop) at both 1x and 200%. Deliberately NO `var()` fallback: a `.sr-map-fab` with no size modifier should fail visibly rather than silently pick a size. **Flagged consequence:** desktop FABs now grow with text scale (`2.25rem` = 36px at 1x, 72px at 200%), where the base was a fixed 36px. That is what these conventions ask for and what the phone tier already did; keeping 36px fixed would force a px glyph and re-open the ratio bug on the desktop side.
  - **A shared base plus a same-specificity modifier makes SOURCE ORDER behaviour, not tidiness.** `.sr-map-fab:hover` and `.sr-share-drop-btn[aria-pressed="true"]` are both (0,2,0) and both set `background`, so only source order keeps the green "holding a pin" tint on a hovered pinned button. Grouping the state rules above the base block — the natural tidy-up — silently drops it, and no value diff catches it. The same trap sits on `.sr-touch-target` (`display: inline-flex`) added to `.sr-map-filters-btn` (`display: none`), which resolves correctly only because the former appears ~190 lines earlier; moving either would reveal the Filters pill on desktop with nothing failing. **When a utility class is added to an element whose own rule declares the same property, record the order dependence beside the rule or pin it in the stylesheet guard** — and write that guard against `parseTopLevelRules`' insertion order, not a substring search, since `.sr-map-fab` is a prefix of `.sr-map-fab-cluster` and `.sr-map-fab-slot`.
  - **The row's fit is the binding constraint, and it is nearly spent.** Three discs plus two 10px gaps measure 284.00px against the cluster's `calc(100% - 32px)` = 288.00px at 320px and 200% text scale: **4.00px of slack** (136.00px at 1x). A fourth disc does not fit, and the pre-approved escape hatch is dropping the column gap to 8px in the ≤640 tier. `document.scrollWidth` read exactly `320` in every configuration, broken or not, so measure the row against the container's content box. **v0.5.91 added a fourth control without spending any of that slack, and the constraint it hit instead was VERTICAL.** A full-width row (`flex: 0 0 100%`, the cluster's own `row-gap` / `justify-content` / `max-width` doing the work) consumes none of the horizontal budget, so a labelled action belongs there rather than as a fourth disc. Three rules came out of placing it: **(a) no INTERACTIVE control may take the map's top-centre anchor** — at 320px it measures 206x31px at 1x and 294x148px at 200%, where it buries the layers switcher completely, so that anchor holds only `pointer-events: none` statements (the loading chip, the search-outcome region) and a tap-through claim about one is asserted with `document.elementFromPoint` naming what the tap actually reached, never merely that the overlay declares `pointer-events: none`; **(b)** the switcher grows downward from the top while the cluster grows upward from the bottom, so their collision is **scale-dependent rather than width-dependent** and must be measured at all four shipped text scales, not at three widths; **(c)** where a new row genuinely has nowhere to fit, the answer is to WITHHOLD it and leave its function reachable where it already was, measured (`lib/useSearchControlFit.ts`, against the shipped disc line's top, which is bottom-anchored and therefore invariant to whether the row is rendered) rather than gated at a fixed breakpoint — the same answer TabNav already gives.
- **AN APP CSS RULE AT THE SAME SPECIFICITY AS A `maplibre-gl.css` RULE IS DEAD, AND ANY CONSTANT DERIVED FROM IT IS WRONG (v1.0.5).** The vendor stylesheet is imported after the app's own, so at equal specificity source order hands it the win. `.maplibregl-popup-content { padding: 12px 14px }` in `globals.css` has never applied — maplibre's own `15px 10px` does — which is why `COUNTY_POPUP_CONTENT_CHROME_PX` is 30 where the shipped chrome is 22, in a constant whose comment claims exactness. Where a declaration must beat the vendor rule, mark it `!important`, as the background declaration in that same block already does. Where arithmetic depends on the vendor's geometry, read the **computed** value in a browser once and pin the measured number with the reading beside it — never re-derive it from the app declaration you can see in the file, because that declaration may not be the one in force.
- **A MapLibre popup's side anchors place an EDGE at the click point, so containment is a two-thirds rule, not a fits-the-map rule (v1.0.5).** MapLibre picks the anchor itself, and `left`/`right` put the popup's edge at the anchor point rather than centring it — so a popup is containable only while `width <= (mapWidth - offset) / 1.5`. Past two thirds the centred band between the two thresholds is empty and *every* click overflows, by nearly the popup's own width. Cap the popup at what its container can anchor (`lib/countyPopupFit.ts`), and below a readable minimum stop anchoring altogether and pin it to the container as a sheet; the sheet is what makes a 240px map usable at all, where an anchored cap alone would leave 153px of readable width. Because the three county mounts share one `CountyLayer`, a containment fix reaches all three, which is correct — Species Detail and the Map Explorer carry the same latent overflow at phone widths. **Verify in a browser against the BUILT stylesheets** (Tailwind's preflight `box-sizing` is load-bearing) and sweep every click position: the anchored form's absolute `min-width`/`max-width` on the popup BODY must stay absolute lengths, since the popup is shrink-to-fit and a `100%`/`min(…, 100%)` rewrite resolves against the width the content itself produced and silently collapses the floor. Only the sheet, pinned to a container that may be narrower than the floor, releases them — in its own rule, never by weakening the anchored one.
