# SnowRaven testing and verification methodology

Moved verbatim from CLAUDE.md (2026-08-26 context restructure). This file auto-loads when a session works on files matching the `paths` above; for related work that starts elsewhere, read it in full before changing anything it governs. Its rules carry the same force as CLAUDE.md.

- **`frontend/src/test-setup.ts` installs baseline `requestAnimationFrame`/`cancelAnimationFrame` shims for every test file** (wired via vitest `test.setupFiles` in `vite.config.ts`). Reason: recharts bundles `@reduxjs/toolkit`, whose autoBatch fallback timer (100 ms, calls bare `cancelAnimationFrame`) can outlive a jsdom test file and fire in a later DOM-less node-env file in the same worker — the source of the old ~11% full-suite flake. Never remove the shims or convert them to per-test `vi.stubGlobal` stubs (per-test stubs can't cover timers that fire after their file's environment is torn down). The shims are `typeof === 'undefined'`-guarded, so jsdom files keep their natives and a file's own stubs still win.

- **Component tests that stub a scheduling queue must wait on an observable stub-queue precondition before flushing.** A `waitFor` on rendered DOM resolves on the React commit, which under suite load can land BEFORE a passive effect queues into the stubbed queue — flushing then drains an empty queue and the test asserts against a frozen shell (the BirdingStats frozen-shell flake). After the DOM wait, add `await waitFor(() => expect(rafQueue.length).toBeGreaterThan(0))` (or the equivalent for the stubbed queue), then flush. Never assume effect timing relative to `waitFor`, and never substitute a wall-clock sleep. Reference: `renderAndLoad()` in `BirdingStats.test.tsx`.

- **A strict performance contract may sample complete executions to resist shared-runner scheduling noise, but may not weaken its threshold (v0.5.72).** Calendar QA-41 still requires one complete `buildDayCells` execution below 50 ms; it measures seven full executions and asserts their minimum. Do not time partial work, raise the limit, or discard the contract. Use this bounded repeated-measurement pattern only for deterministic work whose isolated baseline is comfortably below the threshold and whose one-off wall time is vulnerable to unrelated parallel test load. **A performance assertion needs margin AND repetition, and 2x is not margin (v0.5.84).** Where an isolated baseline sits within ~2x of the ceiling, a single measurement will breach under ordinary CI contention; measure the baseline against the ceiling explicitly before choosing the fixture size, and where a fix opens an enormous gap (bounded vs unbounded regex, scan vs backtracker) buy the margin from that gap rather than from a quiet machine. The two v0.5.84 guards sit ~30x and ~15,000x under their ceilings and 6x and 12-46x over the defect, a gap no shared runner closes in either direction. Each timed run must also defeat any memo on the path (a distinct input per run), or the guard measures a cache hit. **A performance assertion is anchored to a SAME-RUN QUOTIENT, never to an absolute wall-clock margin measured on the build machine (v1.0.5) — and this one reached production before it was caught.** `countyShadingPerSpecies.test.ts` asserted `best * 10 < 200`, which reads like the PRD's 10x margin requirement and is not: it encodes *this Mac's* 10.15 ms. CI measured 45.7 ms — comfortably inside the real 200 ms budget, a passing machine by the actual contract — and the suite went red on the feature commit after the release had shipped. Express the margin as the ratio the contract states (`ceiling / best >= 10`), so the assertion means the same thing on a laptop, a loaded shared runner, and whatever the fleet runs next year. The absolute ceiling stays as the separate, honest claim it is; what may never be hardcoded is the *headroom a particular machine happened to have*. Same family as the work-done rule below: pick a reference the hardware cannot move.

- **A FIXED-SIZE CACHE'S PERFORMANCE CLAIM MUST BE MEASURED AT CAPACITY PLUS ONE (v0.5.85).** At capacity it never evicts and every measurement after the first is a hit, so it reports its best case as if it were its typical case — and a hostile input set is chosen by whoever supplies the data, for whom one key more than the cache holds is the cheapest possible attack. This produced **both** High findings on `normalizeSpeciesName`'s memo bound, and then invalidated the remediation proposed to fix the first. Measured through the real module, min of interleaved rounds with rotating start order: the over-length **single slot** cost 3,493.7 ms on two alternating 40,000-character names against 2.4 ms uncapped (a one-entry cache is defeated by two keys, and it had been benchmarked on one repeated name); the short cache evicting **FIFO** cost 2,544.9 ms at capacity+1 on ordinary 24-character names, **167x worse than having no cache at all**, on 32,769 distinct names, which is 0.75 MB of name data in a CSV well under 5 MB. **Admission control — fill to the limit, then stop admitting, never evict — is identical below capacity and 34x, 11x and 85x better at capacity+1**, which is why the reviewer's recommended character-budgeted FIFO was not adopted unmodified: it had been measured at 8 rotating names against a capacity of 26, the same below-capacity class of measurement that let the slot through. Four rules follow, each of which was a live wrong turn:
  - **State the guarantee STRUCTURALLY (entry count, key length, slot occupancy, character budget), never as a byte product.** Three measurements of the same design gave 172, 208 and 173 B/entry; the first assertion built on one of them (`32,768 x 172 B < 6 MiB`) stated a ceiling the true worst case exceeds **and passed anyway**. A byte figure encodes one engine's heap accounting and can go false without ever failing.
  - **A retained-bytes figure kept as an annotation must name the STRING REPRESENTATION it assumed.** V8 stores one-byte and two-byte strings differently and a hostile key set picks the expensive one, so the ASCII-only replacement figure went out of range by a third on its second try. Either state the character width or drop the number and keep the structure.
  - **The property that matters is "never much worse than not caching", and it is what both defects violated. Assert it as WORK DONE, not elapsed time.** The elapsed-time form passed in isolation (1.60, 2.08, 2.50 across three machines) and failed the full-suite run at 5.69 against a ceiling of 4; repetition was not the fix and measurement proved it, reading 2.21 at min-of-3 and **2.70 at min-of-9** — worse with more rounds, the signature of a systematic effect rather than noise, because a hit is a Map lookup and a miss is recomputation, two kinds of work that lose CPU-cache locality at different rates. Counting misses gives "worse than no cache" an exact meaning (no cache recomputes on exactly 1.0 of calls) that no loaded machine can move, and the counter increments only on a miss so the hot path is untouched.
  - **A rule discovered in review must be applied to EVERY instance in the module, not only the one that failed.** The capacity+1 rule was correctly derived, correctly written into the source as a general statement, and then applied to one of the two caches — leaving the other evicting FIFO fifteen lines below the comment stating the rule. When a fix generalizes into a stated principle, sweep the module for other instances before closing and say which ones were checked. **Where a bound is enforced by a COUNTER rather than by the container's own size, assert the counter across repeated calls, separately from the contents** — the nastiest half of the third finding was invisible in both the cache's entries and its answers, and showed up only in the accounting variable silently inflating until admission closed permanently.

- **Capacity+1 is a measurement rule, not a universal eviction policy (v0.5.86).** Admission control is right for a hot memo whose miss is cheap and whose FIFO churn can be worse than no cache. The county-completeness and replay stores deliberately remain FIFO: their bookkeeping is dominated by network/storage work, and retaining the newest loaded data for offline use is the product contract. Their legacy 4 MB / 3 MB names are not byte ceilings: the implementation budgets `JSON.stringify(data).length` UTF-16 code units for payloads only, excluding keys, metadata, ordering and the document envelope, and deliberately allows one sole oversized newest entry.

- **Every jsdom test file that mounts recharts charts must end with `afterAll(() => new Promise((r) => setTimeout(r, 120)))`.** Toolkit's 100 ms autoBatch fallback timers armed during the file must fire before its jsdom environment is torn down — the `test-setup.ts` shims never install in jsdom files (the globals exist there), so a timer that outlives the file fires where `cancelAnimationFrame` no longer exists and fails a later file with all tests green. Currently applied in `BirdingStats.test.tsx` and `MediaStatsSections.test.tsx`; copy the pattern into any new chart-mounting jsdom file.

- **A PIPELINE REPORTS THE LAST COMMAND'S EXIT CODE, so `cmd | head` reads `exit=0` over a command that failed (v1.0.17).** Hit while verifying a security fix: the run was piped through `head` to keep the output short, `echo "exit=$?"` printed 0, and the real status was 1. `head` also closes the pipe early, so the producer can die on SIGPIPE and still leave a 0 behind it. **Capture the status from the command itself** -- run it to a file and check `$?` before piping, or set `pipefail` for the shell that runs it -- whenever the exit code is the evidence. Trimming output is fine; trimming output through the thing you are measuring is not.

- **jsdom returns the UNRESOLVED keyword `medium` for the root font size, so any derivation that reads it is silently inert in every component test (v1.0.17).** `getComputedStyle(document.documentElement).fontSize` is `"16px"` in a browser and `"medium"` in jsdom; `parseFloat("medium")` is `NaN`, so a threshold computed from it does not throw -- it quietly takes whichever branch `NaN` comparisons fall to, for the whole suite. The nav density arithmetic reads the root font size to track `--sr-text-scale`, and its jsdom tests were exercising a branch no user can reach until the keyword was mapped to its spec value (`medium` = 16px) in the test setup. **Grep any new `getComputedStyle(...).fontSize` consumer for a jsdom test that claims to cover it**, and treat a suite that goes green on a value the browser never produces as untested rather than passing.

- **A CSS-only fix is verified against a REAL RENDER, not a parsed stylesheet — and this repo already has the browser (v0.5.81).** A stylesheet test proves a rule exists and is scoped; only a browser proves it *wins* against the inline styles it must beat, and only measuring the element that owns the visible text proves what the user actually reads. Playwright is already a dependency in `website/tools/` for the screenshot pipeline, and there is a synthetic demo dataset: point the backend at it with `SR_DATA_DIR` (never the real export) and measure BOTH revisions on the same DOM nodes. When two builds differ only by a class, resolve blocks by structural DOM path from the build that HAS the class so the comparison is like-for-like, and guard the resolved node (tag, child count) rather than trusting the path. Geometric claims — whether focus lands under a sticky band, whether a band is opaque, what `elementFromPoint` returns inside it, whether a row wraps — are invisible to vitest/jsdom (no layout engine, no media queries, no computed font size, no cascade against React inline styles) and equally invisible to a built-CSS text assertion. A throwaway static HTML reproduction of the exact DOM and CSS settles them in about a minute; reach for it when a change's core claim is geometric. **Four v0.5.84 additions, each earned:** (1) prefer a genuine build A/B (stash, rebuild, measure, restore, then verify the restored patch byte-identical) over simulating "before" by toggling a class on the live page — the class toggle is a good like-for-like on the same nodes but by construction exercises only the DOM half of a change, and it cannot distinguish a defect this build introduced from one that was already there; (2) **a geometric harness's own exclusion logic must be sanity-checked against a configuration already known to be clean before any flagged number is trusted** — an off-by-one in a scroll-container ancestor walk let a by-design horizontally scrolling `<pre>` dominate every reading and report 44 of 104 configurations broken in *both* builds, plausible-looking numbers that would have masked the real signal entirely, and the tell was the same offender appearing at widths the brief had measured clean; (3) **a "measured clean at widths X through Y" claim must name the text scales it was measured at** — the v0.5.83 comment asserting 641px to 1440px clean was true at 100% only and never measured at 200%, which is exactly how the `help-overlay-641-leak` band survived a fix that had just been written for it; (4) when re-verifying, measure at least one case the original probe did not cover. **Three v0.5.85 additions, all from one build's probe going wrong before its numbers were used:** (5) **an ELEMENT-BOX measurement will certify a half-fixed build, so measure TEXT INK — client rects over a `Range` per text node, against the container's content box.** Two of five mutations on the Breeding Codes legend left `getBoundingClientRect()` on the element reading a clean **zero** while text hung 22.20px and 81.08px outside it: once a box is allowed to shrink to the line, an unbreakable run simply ink-overflows it and the element cannot see that. This is the same family as the `scrollWidth` rule below — the proxy does not merely under-report, it reports the bug as absent. (6) **A geometric probe over FLEX ITEMS cannot detect wrapping via `getClientRects()`.** A flex item is blockified, so it returns one border-box rect however many lines its text takes; the first cut of the "does a wrapped chip share a line with another chip" check reported a confident zero while structurally unable to see any wrap at all. Count line boxes through a `Range`, and give the check a per-partition non-vacuity assertion (the chips must be enumerated, and some configuration must actually wrap). (7) **A geometric fingerprint comparing two renders must use CONTAINER-RELATIVE coordinates, never raw `getBoundingClientRect()` values** — those are viewport-relative, so any scroll-position difference between runs makes every element look moved. It reported 17 false positives here, and the tell was that only `y` differed while `x`, width, height and line count were identical. Same family as the scroll-container off-by-one below; prove non-vacuity by checking the fingerprint still detects the configurations that genuinely changed. And **state a fixture dataset's composition by EXTRACTION, not description** — a brief, a design and a PR each described the synthetic demo dataset as omitting two breeding codes when it omits one, and a probe's stand-in dataset inherited the error; no measurement moved, but the argument for which declarations are load-bearing did. Three sharpenings from v0.5.82, each a wrong turn that was actually taken:
  - **A NUMERIC browser measurement is still not a render when the element is a native control with UA-drawn internals.** Neither `scrollWidth`/`scrollHeight` nor a canvas `measureText` is admissible evidence that a control clips, and both were wrong in OPPOSITE directions on the same elements: an `<input type="date">` reports `scrollWidth === clientWidth` while visibly cutting the year off (proxy under-reports), a `<select>` reports `scrollHeight > clientHeight` at 200% text scale while rendering perfectly (over-reports), and `measureText` on the value string declared a clipped `Longitude` placeholder a fit by 0.04px because it cannot see the picker icon, the spinner buttons, or the control's internal field spacing. Screenshot the control and look.
  - **Render the declarations PARSED from the real stylesheet, never retyped into a fixture.** Retyping is how a reproduction quietly stops testing the shipped code. Substituting a platform value (e.g. `env(safe-area-inset-top)` → a literal 59px) is fine and is the point; re-authoring the rule around it is not.
  - **Page `scrollWidth` alone is not a usable assertion for an overflow fix — measure the ELEMENT against its container.** A broken build can read a clean integer `scrollWidth` when the overflow is sub-pixel or absorbed by panel padding (a cluster 24.23px past its content box read exactly 320 on a 320px viewport), and the leak's size tracks the data (a count label reading `428 species` reproduced 3px, `1247 species` gave 12px, `88 species` gave none), so a dataset-dependent defect hides behind a viewport-width equality. **Sharpened twice in v0.5.83: it does not merely under-report, it can report the bug as ABSENT — a `scrollWidth` check will certify a broken build.** Two independent mechanisms, both measured: (1) an `overflow: hidden` ANCESTOR swallows the signal completely — the Help overlay's body was 186px draggable at 320px and 372px at 200% scale while page `scrollWidth` read exactly the viewport width in *every* broken configuration at every width and scale; (2) a **left** overflow on an absolutely positioned element never extends scroll width at all — the map FAB cluster's share button sat 62.92px off the left edge, unreachable, with `scrollWidth` reading exactly 320. **A THIRD mechanism, measured in v0.5.85: a CO-LOCATED LARGER OVERFLOWER masks the element you are measuring entirely.** On the 13-code dataset `scrollWidth` read **351 in both builds** — bit-identical across a change that took the Breeding Codes legend's leak from 64.17px to zero — because the out-of-scope filter pill row on the same tab sits further past the edge than the legend ever did. Neither of the first two mechanisms was in play; the signal was simply hidden behind a bigger one. Measure the element against its container's content box, always.
  - **A hand-built static reproduction is evidence about ELEMENTS, never about the PAGE, because its ancestor chain above the component is the author's invention (v1.0.14).** The `honest-load-failures` probe reproduced every box width to the hundredth and then reported a 47px page-scroll leak that does not exist: page `scrollWidth` measures 320 in every configuration of the real app, patched and unpatched, with no clipping ancestor, because the shell's padding absorbs the overhang (the box's right edge reaches 279.28 on a 320 viewport, 40.72px of clearance). The element numbers were right for exactly the reason the page number was wrong -- the DOM under the component was copied, the DOM above it was not. So read element-versus-container numbers off a repro if you like, but any claim containing `scrollWidth`, "page" or "viewport" comes from the real built app, and a repro that produces one has produced a QUESTION, not a finding. **Two corollaries.** (1) **When re-verifying a measurement, check which columns AGREE before concluding anything about the ones that do not -- agreement localizes the disagreement.** Six box widths matching to two decimals proved the DOM, CSS and font were identical, which is what made the non-matching `scrollWidth` column diagnostic rather than mysterious: same element, same geometry, different ancestors. (2) **State what a layout fix buys and do not upgrade it to an accessibility repair.** "47px of page scroll at 320px" reads as a WCAG 1.4.10 (Reflow) failure; "a box 23.28px past its column, absorbed by the shell" reads as tidiness. Same fix, same diff, and only one is true -- nothing scrolled and nothing clipped, so the AA bar at 320px/200% held before the change as well as after. A fix described as clearing a WCAG failure that was never failing makes the next reader trust every accessibility claim less, and `ACCESSIBILITY.md` is a published statement that has to stay worth trusting. Establish whether a geometric defect is visible to the USER before writing the sentence that will outlive the build.
  - **`elementFromPoint` and pixel sampling answer DIFFERENT QUESTIONS, and taking one for the other inverts the finding (v1.0.17).** `elementFromPoint` answers *what would receive this click* -- hit-testing, which `pointer-events` and `inert` participate in. Sampling the rendered pixel answers *what the user sees* -- paint, which neither of those touches. Asking whether a fixed overlay covers a fullscreen map, `elementFromPoint` returned the map and the pixels returned the overlay, and the pixels were right: `inert` removes a subtree from focus and the accessibility tree, never from the paint. **Name which question you are asking before choosing the instrument**, because each is a perfectly convincing answer to the other question.

  - **An interactive overflow probe measures every visible layer, not only boxes (v0.5.86).** Compare rendered text and icon ink and the complete hit-target rectangle with the intended container. The Breeding Codes name-column repair kept both external-link targets at least 24×24px across 48 Chromium/WebKit configurations; a box-only or page-`scrollWidth` assertion could not prove that the icons remained visible and the whole links remained operable.
  - **A guard-the-guard must run in a configuration where the guarded property can actually VARY, and the way to prove it is to neuter the mechanism it guards (v0.5.91).** The ResizeObserver fit probe was first run at 1x text scale and returned 0 disagreements against its independently written oracle — a clean number that was vacuous by construction, because no tested configuration flips at 1x. Re-run at 200% with `ResizeObserver` replaced by a no-op, it produced **6 stale decisions in Chromium and 6 in WebKit**, which is what makes the 40 live configurations evidence rather than an absence of evidence. This is the per-partition non-vacuity rule below, applied to a browser probe: pick the configuration by where the property moves, then break the mechanism on purpose and confirm the probe notices.
  - **A browser probe exercising the in-app text scale sets `--sr-text-scale` as an INLINE style on `documentElement`, never via an injected `html {}` stylesheet rule (v1.0.6).** The shipped declaration lives on `:root`, whose pseudo-class specificity beats an `html` type selector at any source order, so the injected override silently loses and the "200%" leg measures the same render as 100% -- a vacuous probe caught live this run. Same family as the guard-the-guard vacuity rule above, applied to the probe's own configuration: before trusting any number, prove the scale actually APPLIED by reading a computed size that must track it.
  - **Mutation-check a guard in the forms the defect could actually return in, and run the implementations that must stay GREEN as well as the ones that must go red.** The equivalent-but-different cases are what expose a dead branch in the guard's own matching logic, and two shipped this bundle before mutation testing caught them: a `/\b100%\b/` that can never match (`\b` adjacent to `%`, a non-word character — equally true of `)` in `min(100%, 680px)`), and a `decl()` helper blind to a declaration directly following `{`, which left a raw-rule scan inert against single-line rules. Where a guard has two scans covering different reach, mutate into **each scan's exclusive territory** (a top-level single-line form AND a media-tier form); where it is a paired positive/negative guard, mutate in both directions, because the negative case alone passes on a seam that has silently stopped working. And slice the rule's own block before mutating: `globals.css` is large enough that a common declaration (`flex-wrap: wrap`, five occurrences) makes a first-textual-match mutation exercise an unrelated rule and a sound guard look inert. **Three v0.5.84 extensions, each of which caught a guard that was already inert or already wrong:** (1) **where a guard's correctness depends on a CSS rule APPLYING, mutate the SELECTOR, not only the declarations** — every declaration-and-media-bound mutation across two builds behaved correctly, and the green-when-they-should-be-red cases appeared only once the selector itself was mutated; selector mutation is the axis that tests whether a guard is checking the rule it thinks it is. (2) **A guard that partitions its work into profiles, buckets, or passes needs a per-partition non-vacuity assertion, not one for the scan as a whole** — `mapFabCascade.test.ts` asserted only that its *disc* profile saw something, and its *glyph* half shipped structurally unable to match our own rule (`.sr-map-fab svg`, whose rightmost compound is a bare `svg`), so both of its glyph assertions passed against any stylesheet whatsoever. This is the "mutate into each scan's exclusive territory" rule applied to a scan's own internal split. (3) **Before recording a mutation as an untestable GREEN, try the cheapest mock.** A build argued that "the renderer stops calling the gate" could not be rejected without adding a content prop that would be actively wrong, and shipped that claim; `vi.mock('../../../docs/HELP.md?raw', …)` drives the real renderer with hostile content and needs no production change at all. The most obvious form a defect can return in is the one least worth conceding, and a documented GREEN is a claim to be tested rather than asserted. **Two v0.5.85 extensions.** (1) **The must-stay-GREEN group is where a guard's own matching logic gets caught, so never skip it as ceremony** — one guard was keyed on the literal selector spelling `.sr-bc-card > .sr-bc-legend`, so rewriting it with a descendant combinator (which selects the same element) turned it red; the guard was wrong, not the mutation, and only running the equivalent rewrites surfaced it. The converse also happens: an old guard went *red* on reordering a rule above one it cannot lose to on specificity, a change that alters nothing, because it had resolved to the wrong rule in the first place. (2) **When a review names a line as correct and load-bearing, that line needs a GUARD, not a compliment.** Round 1 of a review singled out `!== undefined` over a truthiness check as the right call; it went two more rounds unguarded and both truthiness mutants survived a 57-test suite. A detail worth praising in review is a detail worth pinning — the praise is itself evidence that a future reader might not see why it matters. **Also sanity-check the mutation harness against an UNMUTATED baseline before trusting a single result**: one run reported all eleven mutations GREEN, which would have been a serious false finding about the guards, and the cause was that zsh does not word-split unquoted parameters so vitest received one nonexistent path and never ran the suites at all. The same rule as for geometric harnesses, applied to any harness that reports a verdict rather than a measurement. **v0.5.87 extension: a mutation you EXPECTED to go red and which does not is a finding about the TEST, not a clean bill — and the answer is almost always that two mechanisms overlap and only one is guarded.** Making the escapee progress emitter ignore its `force` flag left all 26 controller tests green; the behaviour was correct, and the cause was that `lastEmit` starts at 0, so the first emission of any pass clears the throttle interval on its own and the opening figure is protected twice over. What `force` uniquely protects is a follow-up wave discovered *inside* the throttle window, where the sentence changes shape milliseconds after the opening emission — rendered and tested, emitted and not. Ask which mechanism absorbed the mutation, then guard the case only the mutated one covers. **v0.5.88 generalizes all three of the harness rules above into the one question worth asking of any check: a verification whose reference point is DERIVED FROM the thing being verified cannot fail when that thing is wrong.** It reported success twice in one run, in unrelated places. (1) Tests that pin a *compiled regex* cannot see a weakened *call site*: the fixture rows and the parity helper both exercised `CHECKLIST_ID_RE` directly, so mutating both routers to `.match(...)` left all 227 tests green while the mutation was behaviorally live and a trailing-newline id passed a guard shipped code refuses. Pin the call sites separately from the pattern, and per-consumer rather than in aggregate. (2) A restore-verification must compare against the INTENDED content, never against the snapshot used to perform the restore — the mutation harness diffed a restored file against the snapshot it had just copied back (identical by construction) and printed "restored byte-identical" while a stale snapshot had silently reinstated an earlier revision of a corrected comment. Before trusting any check, ask: **could this fail if the thing it is checking were wrong?** **Two v0.5.89 additions, both from a single run that hit this family four times.** (1) **A shell pipeline reports the LAST command's exit code, so piping a gate to `tail`/`head`/`grep` reports success no matter what the gate did** — two suite invocations that failed on their own tooling (a bad `--reporter`, `python` not on PATH) both printed exit 0. Run every gate with `set -o pipefail` and echo the explicit status, the same discipline as the zsh word-splitting trap above — and capture it as `rc=$?`, never `status=$?`: `status` is a READ-ONLY builtin in zsh, so that wrapper itself aborts with exit 1 after a green gate and mislabels it a failure (v0.5.90). (2) **A mutation you expected to go red that stays green has a THIRD possible answer beyond "the test is weak" and "two mechanisms overlap": the specified behaviour is ABSENT.** Reverting the Multimedia/Species Detail widening left the whole suite green because `mergeSubspecies` defaults to `true`, so the row key was the normalized base and `Brewster's Warbler (hybrid)` collapsed to something indistinguishable from a species — the predicate was judging the key, so the feature was half-delivered and no test *could* be written for it. When a test cannot be written for a specified behaviour, suspect the behaviour before the test.

- **A stylesheet test for a rule that must apply at ALL viewport widths parses exact top-level selectors and skips at-rule blocks WHOLE (v0.5.81).** A substring or regex match over the raw stylesheet cannot distinguish a top-level rule from one nested inside a media tier, so it passes silently on a DRY-consolidation that strands every width outside that tier — the concrete harm being the iPad Help-TOC case. The third arrived (`skip-link-safe-area`) and the helper was extracted as anticipated: **`frontend/src/lib/cssTopLevelRules.ts` (`parseTopLevelRules`) is now the one parser**, and `mapIosFullscreen.test.ts` (whose `stripMediaBlocks` + `iosRule` + `cssRule` trio it replaces) and `iosChrome.test.ts` (which hosts the skip-link guard) both read `globals.css` through it. **Recounted at v0.5.84: it has FIVE consumers** — `iosChrome`, `mapIosFullscreen`, `lifeListPinnedCss`, `mapFabClusterCss`, and (new this bundle) `breedingCodePinnedCss` — plus its own `cssTopLevelRules.test.ts`, which is what the previously recorded "five" had mistakenly counted; the true figure at v0.5.83 was four. A **fourth load-bearing property was found and fixed there: a selector ends at a top-level `;`.** Without it the parser sliced from the file start to the first `{`, producing the selector `@import "tailwindcss"; :root`, which starts with `@` and was skipped — so `:root` was UNREACHABLE in `globals.css` (which opens with `@import "tailwindcss";`) and any guard reaching for a token there got `undefined` and, under optional chaining, passed vacuously. Verified blast radius was exactly `:root`, and no previously-shipped guard was vacuous. Reuse it for a sixth; its four properties — exact selector keys, at-rule blocks skipped whole, comments stripped before the brace walk, top-level `;` terminates a selector — are asserted against fixtures in `cssTopLevelRules.test.ts`, so the guards assert about the stylesheet rather than about their plumbing. - **A COMMENT IN A TEST FILE CAN ADD A RULE TO THE SHIPPED STYLESHEET — a test file is a production input in this repo, which is exactly what nobody expects (v0.5.85).** Tailwind v4 uses **auto source detection with no config**: it scans the **build root** (`frontend/`, test files included), extracts bare words as class candidates, and emits a rule for every candidate that happens to name a real utility. It does not care that the word sits in a `//` comment, in prose, or in a file that never ships. Measured with a single-word controlled experiment: the word `invert` in one comment line of `filterControlSizeCss.test.ts` emitted `.invert{...}` and grew `dist/assets/index-*.css` from 45,506 to 45,725 bytes, **+219**, with a different content hash; changing that one word restored byte-identity at the same hash. Five things make this nastier than it sounds, all verified:
  - **The cost is per word NEW TO THE WHOLE CORPUS, not per use.** 16 of the 18 commonest single-word utilities (`container`, `block`, `hidden`, `flex`, `grid`, `table`, `contents`, `sticky`, `fixed`, `absolute`, `relative`, `static`, `italic`, `underline`, `truncate`, `visible`) are ALREADY emitted at HEAD from the existing corpus, so writing them in a comment costs nothing. It is the RARE utility name — `invert`, `isolate` — that bites. So the defect is intermittent, invisible to review, and cannot be predicted by reading the diff.
  - **Writing the warning can reproduce the defect.** The first repair here explained the mechanism and named the offending word inside the explanation, which re-emitted the identical rule. Describe such a word, never spell it.
  - **Impact is usually bounded but the CLAIM is what breaks.** No element carried `class="invert"`, so nothing rendered differently — but "test-only, no bundle change" and a changelog line reading "nothing about the app itself changed" were both false. Reword the comment so the claim becomes true again; do not weaken the claim.
  - **Verify by MEASUREMENT, never by inspection.** Build, then byte-compare `frontend/dist/assets/index-*.css` and its content hash against a HEAD build made in the same directory with the same toolchain, with a determinism control (build HEAD twice, expect identical) and a reproducibility control. Any change touching a `.test.ts`/`.tsx` file that claims "no bundle change" owes this check; a green suite and a clean lint say nothing about it.
  - **Bundled is not scanned, and `docs/HELP.md` is the case that separates them (v0.5.91).** The scanned tree is the directory the build runs in — `frontend/` — so a repo-root file that IS bundled into the app (through the `?raw` import) is nonetheless not a Tailwind source. Measured both ways in one session on clean builds with `dist/` and the Vite cache removed: the same rare utility word appended to `docs/HELP.md` emitted **no** rule and left the bundle byte- and hash-identical, while the identical word in a comment in a `frontend/src/lib/*.ts` file DID emit it and moved the bundle by 27 bytes. - **`vitest` + `eslint` are NOT a substitute for the production build as the pre-push gate (0.5.35 post-mortem).** vitest transpiles with esbuild (no type-check), and an `// eslint-disable-next-line @typescript-eslint/no-unused-vars` silences ESLint but NOT the TypeScript compiler. - **A canvas-bake byte-identity claim is guarded by op-stream equality on a recording 2D context (v1.0.2).** jsdom has no canvas, so pixel comparison is unavailable in the suite — but the sprite bakes (`mapPins.ts`, `countyTextures.ts`, `atlasTextures.ts`) are deterministic drawing programs, and two invocations that issue an identical operation stream against the same context semantics paint identical pixels by construction. - **A `vi.mock` FACTORY CANNOT COUNT DYNAMIC IMPORTS — count accesses to the namespace's `default` getter instead (v1.0.5).** vitest evaluates a mock factory once and caches the module namespace, so a counter incremented inside the factory reads 1 no matter how many times the subject `await import()`s it, and a test asserting "the geometry module is fetched once per session" passes identically against an implementation that fetches it on every call. - **A FUNCTION THAT MUST NOT RETAIN A LARGE STRING FINDS ITS OFFSETS WITH `indexOf` AND COPIES WITH A CHARACTER LOOP — never `.slice()`, never a regex METHOD — and no equivalence test can catch the difference (v1.0.13).** Measured on a 148.4 MB export, holding one 309-character header line with the source dropped and GC forced three times: the whole text 152.2 MB, `search`+`.slice` **152.2 MB**, `indexOf`+`.slice` **152.2 MB**, `search`+character copy **152.2 MB**, `indexOf`+character copy **3.8 MB**. - **SYMMETRY IN THE CODE IS NOT SYMMETRY IN THE EVIDENCE: when a change touches N paths, write N tests from ONE roster and mutation-check each against its own path (v1.0.14).** One bundle hit this four times -- three of four durable stores with an in-flight race test and the fourth with none, two half-tests each mocking the other with nothing on the composed seam, two clear paths with the failure surfacing guarded on only one, four cancel-guarded loaders. Each untested half looked safe *because* its sibling was tested and the code beside it read the same; reading two branches and seeing the same lines is what makes it feel covered, and the only check that settles it is to delete the second branch's behaviour and see whether anything goes red. **A roster from one template makes the path list itself the artifact** (`WRITE_RACES` beside the existing `LOAD_RACES`), so a fifth store with no row reads as a gap rather than as nothing at all -- reach for it at the FIRST instance, not the third. Five rules ride with it. (1) **Assert that the guarded path never RAN, not only that the observable outcome is clean:** the county row stayed green with its own guard deleted, because a downstream guard kept the disk clean while the deleted one was the only thing protecting a module-level byte total from permanent over-count; read it from the store's work-stats seam (`puts`/`merges` at zero). Four green rows are not four working guards, and a roster green for the wrong reason is the same failure as a roster with a row missing. (2) **Each mutation must ISOLATE ONE ARM.** Three mutations that each turn the same *pair* of rows red prove nothing about which arm is covered; the mutation that establishes independence is the one that guards the read arm and not the parse arm and turns exactly one row red. (3) **A roster carries each row's own re-trigger, not one assumed to be shared** -- `BirdingStats` re-runs on the files epoch and has no `filesVersion` prop, so a prop-driven roster would have left its effect never re-running and its row passing by never reaching the code it exists to test. (4) **A test that forces an interleaving must prove the interleaving it claims:** the first ordering test released the parked write before the purge could issue its own, so an unordered store passed on timing alone; it now asserts the disk is still untouched while the purge's write is queued, a state only an ordered writer can be in. (5) **A pair of guards that each mock the other needs one test of the COMPOSED SEAM** -- two half-tests can both stay green while the halves stop fitting together (the producer passing a value the consumer no longer reads, or the reverse). - **Three ways a green test in this repo proves less than it looks like, all from v1.0.14, all in the setup rather than the assertion.** (1) **A test that imports the constant it is checking proves DELIVERY, never CONTENT.** Nine per-surface rows importing `EBIRD_BACKUP_LOAD_ERROR` correctly stayed green through a mutation reverting that constant to the old, wrong sentence. - **A TOTALITY CLAIM NEEDS A TOTAL TEST: derive the subjects from the INTERFACE, sweep the nth call, and name the boundary the sweep cannot close (v1.0.16).** A guard that names its subjects in a literal array is a roster wearing a totality claim's clothes -- it cannot see what it does not name. `weatherBacklogLoad.ts`'s first "this promise never rejects" guard listed three of its four dependencies, and the omitted one was the single member with an unguarded call site; a designed mutation (an extra dependency called outside every `try`) produced **zero** failures across all 51 rows. Rewritten to iterate `Object.keys(deps())`, the same mutation goes red and names the offender. Three parts ride with it. **(1) Derive, don't enumerate** -- TypeScript already forces the fixture to carry every member for the call under test to compile, so a dependency added later brings its own rows whether or not anyone remembers the file. **(2) Sweep the nth call, not the first** -- a member called more than once has more than one site and they are not equally guarded, so make each member throw on each of its first N calls; a throw on a call that never happens leaves the healthy path intact, so the row asserts FULFILMENT and a legal value, with the member and call number in the assertion's own message. **(3) Assert non-vacuity and the bound** -- compare a counter against `keys x N` so an empty or partial key list fails loudly, and assert that the healthy path's real maximum call count is below N, or the ceiling silently narrows as the code grows (today: `NTH_MAX` 3 against a real maximum of 2, one call of headroom, and nothing asserted it). **A throw-sweep is structurally blind to a dependency that RESOLVES BADLY**, so add at least one row returning a hostile value beside the rows that throw.

- **A totality guard's subject may be a claim `return await` is what makes true.** In an async function, `try { return v } catch` catches neither a rejection of `v` nor a throw from its `then` getter, so a "never rejects" claim over a dependency that could ever return a promise needs `return await`; a throw-sweep cannot see either shape, because they make a dependency resolve badly rather than throw. The rule and its measurements are in CLAUDE.md (**Promise boundaries**), because it is a code rule an engineer meets before any test file.

- **`npm audit --offline` PRINTS "found 0 vulnerabilities" WITHOUT CONSULTING THE REGISTRY -- never use it as the dependency check (v1.0.16).** It does not fail; it manufactures a false clean, which is the worst shape a gate can take, because a green line then means *not run* and reads as *verified*. The two answer different questions, and reporting only one is how a dev-only High either blocks a release it should not or hides entirely. The same shape is why a harness that **skips when its dependency is missing is worse than no harness at all**; a skip that is silent is the shape that rots, so a gate that can skip fails when `CI` is set.

- **AN EXCLUSION ROSTER NEEDS CARDINALITY, NOT MEMBERSHIP (v1.0.16).** A roster row keyed on file-plus-attribute is a blanket pardon for its whole file: a second unmarked control added beside an already-rostered one is absorbed silently, and the guard stays green over the exact defect it exists to catch. That binds the row to its own site without pinning a line number an unrelated edit above would move, and the failure message names the offending row and its `why` rather than reporting a number that moved. - **THE FULL FRONTEND SUITE FLAKES AT HEAD UNDER ITS OWN SCHEDULING, AND THE KNOWN PROFILE IS AT LEAST FOUR DISTINCT IDENTITIES (v1.0.16).** A baseline sample of roughly 27 clean full-suite runs produced 5 failures across **at least three unrelated suites**, none of them reproducible in isolation (0 failures in 16 isolated runs, and 0 under six deliberate CPU spinners) -- the classic full-suite-scheduling signature. A fourth identity was added in the same bundle: a render-timing shape in `MapExplorerLocateFab.test.tsx > cluster order`, `kids[1]` undefined under load, 8/8 green in isolation and green on a clean full re-run. **A flake attributed from three runs is a hypothesis, not a finding** -- a two-file scoping held at n=3 and failed at n=27 -- so sample until the *set* of affected tests stops growing, then describe it. Before attributing any full-suite failure to the change in hand: re-run the file in isolation, then re-run the full suite clean, with nothing else compiling on the machine.

  - **"Nothing else compiling on the machine" is not the same as a QUIET machine, and the difference cost two stages of reasoning (v1.0.17).** A `mapCornerTabStops` failure -- one of the four identities named above, which is exactly what makes it convincing -- was reasoned about across two stages as though the change in hand had caused it. It had not: **six orphaned `/bin/zsh` busy-loops, PPID 1 and ten hours old, were pinning six of eight cores at load average 24.** Nothing in this session started them, `npm` reported nothing, and the suite simply ran 51s instead of 32s and failed a timing-sensitive file. They are consistent in count, shell and shape with the "six deliberate CPU spinners" the v1.0.16 baseline above ran, which is the second rule here: **a deliberate load experiment owns its teardown**, or it silently taxes every session that follows it on that machine. So before attributing a timing-sensitive failure to anything: check the load average and look for orphans (`ps -eo ppid,etime,pcpu,command | awk '$1==1 && $3>50'`), kill what does not belong, and only then judge the run. A green re-run after killing them is the evidence; a re-run without checking is a coin toss you will read as a finding.

- **A VISUAL "NOTHING CHANGED" CLAIM IS SETTLED BY MEASURING THE SAME BUILD TWICE FIRST (v1.0.15).** The Map Explorer loading view differed from HEAD by ~405-417 pixels, and the same build differed from ITSELF by ~511 -- the spinner's animation phase. The same discipline settles a CSS-change claim mechanically: a comment-stripped, declaration-sorted multiset diff of the stylesheet (blocks added / removed / changed), a rule-level diff of the BUILT `dist/assets/*.css`, and a cascade-competitor scan testing the rightmost compound of every selector in the bundle against an element carrying the new classes -- needed whenever a declaration moves from an inline style (1,0,0) down to a class (0,1,0), or a first-ever class lands on an element, because both make it newly reachable by selectors that were always there.
