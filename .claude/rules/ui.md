# SnowRaven UI construction conventions (colors, responsive layout, accessibility, display copy)

Moved verbatim from CLAUDE.md (2026-08-26 context restructure). This file auto-loads when a session works on files matching the `paths` above; for related work that starts elsewhere, read it in full before changing anything it governs. Its rules carry the same force as CLAUDE.md.

### Colors and theming

- **All colors must use `var(--sr-*)` CSS custom properties** — no hardcoded hex or RGB values in any component file
- The full token palette lives in `frontend/src/globals.css`: `:root` (light) and `[data-theme="dark"]` (dark)
- When inline styles need rgba() with a dynamic alpha, use the RGB triplet pattern: `rgba(var(--sr-tier-4-rgb), 0.08)`
- New tokens go in both `:root` and `[data-theme="dark"]` before use
- **On/off switch & toggle THUMBS use `--sr-switch-thumb` (fill) + `--sr-switch-thumb-shadow` (drop shadow) — theme-neutral: a white knob and the SAME subtle shadow in BOTH themes (post-0.5.67 consolidation).** The knob carries no text, so it's exempt from the on-surface AA rule above; `--sr-gray-400` (the off-track) is already contrast-tuned against this white (see its `:root`/dark comments). Do NOT re-inline `#fff`/`'white'` or an `rgba(0,0,0,…)` shadow on a thumb, and do NOT reuse `--sr-on-accent` for the fill — that token is dark-green (`#052E16`) in dark mode and would render a dark-green knob. `--sr-switch-thumb-shadow` is a full-value shadow token (same convention as `--sr-card-shadow`) and is deliberately identical across themes so the token migration is pixel-identical. Applied to every switch thumb app-wide: `ui/ToggleSwitch.tsx` (shared), `Calendar.tsx`, the six `MapExplorer.tsx` toggles, and `WeatherBacklog.tsx`'s widen-toggle.
- **A surface that is intentionally LIGHT in both themes must not host theme-following text or tokens — give dark mode its own tokens, and guard them with a parse-the-tokens AA test (0.5.44 post-mortem).** The milestone badges (`--sr-milestone-*`) had their near-white `:root` tiles copied verbatim into `[data-theme="dark"]` ("same light-tinted values as :root by design"); in dark mode they glared white AND the species name — the one badge element not bound to a milestone token, rendered via `<BirdName>` → `.sr-birdname-*` → the theme-flipping `--sr-text` — went near-white-on-near-white (~1:1, invisible). The fix gave the dark theme genuine dark tiles (deep green tiers 1–3, deep amber tier 4) with every element (number, date, white ✓, border, and the name via `--sr-text`) re-tuned to WCAG AA against BOTH gradient stops. Rule: never reuse a `:root` light-tinted fill in `[data-theme="dark"]` for a surface that also carries text; any token block marked "same as :root by design" must prove the on-surface text still passes AA in dark mode. `frontend/src/lib/milestoneContrast.test.ts` is the guard pattern — it parses the real `[data-theme="dark"]` tokens out of `globals.css` and asserts AA, so a regression fails the suite, not the user's eyes. (It reads the stylesheet with a file-scoped `/// <reference types="node" />` + `fs` because vitest stubs CSS `?raw`; node types live only in `tsconfig.node`, so keep the reference file-scoped, don't add `node` to `tsconfig.app`.)
- **A sequential shade ramp whose cells CARRY TEXT ON THE FILL must be sized so ONE on-fill text color clears ≥4.5:1 on EVERY tier in BOTH themes — a stricter bar than a fill-only ramp, and the reason a number-bearing ramp gets its OWN token family (v0.5.58 Calendar).** The county ramp (`--sr-county-1..10`, fill-only, guarded by `countyContrast.test.ts` for monotonicity/adjacency ONLY) cannot be reused for a cell that carries a number: no 10-class single-hue green ramp can satisfy both the ≥4.5:1-on-number rule AND the ≥1.2:1 adjacency floor at once (county tier 7 `#358758` is a dead zone — pure white only 4.41:1). The Calendar's day cells therefore use a distinct `--sr-cal-1..5` (+ `-rgb`) with a single white `--sr-cal-fg` — 5 deep-green theme-identical classes, class-count forced by the AA + adjacency math, `computeCountyTiers` reused with `maxClasses = 5`. Guard the pair with a parse-the-tokens test that asserts the on-fill text ≥4.5:1 on every tier in both themes: `frontend/src/lib/calendarContrast.test.ts` is the reference (it adds exactly the ≥4.5:1-on-fill assertion `countyContrast.test.ts` omits). Rule going forward: don't paint text on a fill-only ramp — mint a text-bearing ramp and guard the on-fill contrast, both themes, at the token.
- **A DOM heatmap/crosshatch reuses ONLY the pure density model, NOT the MapLibre sprite machinery (v0.5.58).** The map's colorblind texture mode (atlas/county) bakes canvas `ImageData` sprites via `map.addImage` + a `data-theme` `MutationObserver` — a path that exists *only* because MapLibre fills can't use CSS patterns. A DOM surface that wants the same density-coded crosshatch (the Calendar's cells + Year-Overview thumbnails) uses a CSS `repeating-linear-gradient` reading the `--sr-*-rgb` tokens directly (`lib/calendarTextures.ts` `CAL_HATCH`/`CAL_MINI_HATCH` + `calHatchCss`), reusing ONLY the pure monotonic density *shape* from `countyTextures.ts`, never `addImage`/`ImageData`/`MutationObserver`. Legend swatch and cell derive from the one spec so they can't drift, guarded by a single monotonic-density test.
- **The in-app brand mark is the shared `components/RavenGlyph.tsx` — never a lucide `Bird`, never a second inlined copy of the path (v1.0.3).** It is an inline single-path SVG with `fill="currentColor"`, a square `viewBox`, a `size` prop driving both width and height, and an unconditional `aria-hidden="true"` + `focusable="false"` (the mark is decorative at every site; the wordmark carries the name). The CALLER supplies the color as a token — both shipped sites pass `style={{ color: 'var(--sr-accent)' }}` — which is what keeps the no-hardcoded-hex rule intact inside the component. Shipped at `size={compactChrome() ? 20 : 30}` in the App header and `size={34}` on the welcome screen; those numbers are the design-approved slot sizes (a 90% optical trim was shown and declined) so don't re-tune them casually. It must stay dependency-free: it rides the App.tsx entry chunk and `entryChunk.test.ts` guards that. The component's master SVG is committed at `frontend/src/assets/snowraven-bird-glyph.svg` and is the source of truth for the path — the archival master deliberately keeps its baked `color="#2D8653"` and `<title>`/`<desc>`, which the component strips; it is artwork, not a component, and is exempt from the hex rule. This is a SEPARATE master from the app-icon artwork under `pipeline/ebird-cooldown-and-app-icon/icon-source/` (which regenerates the platform icons, web favicon, and website logo) — do not regenerate either from the other.
- The `data-theme` attribute on `<html>` is set by the anti-flash script in `index.html` and updated by `applyTheme()` in `src/lib/theme.ts`

### Responsive layout — standing conventions

The app is responsive from ~320px phones to large desktops (the 0.5.37 sweep, extended by the 0.5.55 mobile-prep pass with touch-target sizing and iOS input-zoom lenses). The rules:

- **Make layout responsive by LIFTING it to a class, never with an inline style.** React inline styles are specificity 1,0,0 and BEAT class rules, and an inline `display:grid`/`flex` can't be reached by a media query — that is exactly why `.sr-two-col`/`.sr-compare-panels` and the sweep's hooks exist. To make a container respond, REMOVE its inline `display`/`gridTemplateColumns`/`flex-direction`/`flex-wrap`/`gap` and add the class; keep colors/padding/borders inline (tokens only). The sanctioned inline exceptions are responsive-by-construction (no breakpoint math): px→rem width conversions and `minmax(min(<px>, 100%), 1fr)` self-collapse tracks so a fixed track shrinks below a phone width instead of overflowing.
  - **An inline `alignItems` on a flex container is a latent CROSS-AXIS WIDTH constraint on every child, which activates the moment a tier flips that container to `flex-direction: column` (v0.5.83).** The child then shrink-to-fits to its widest descendant's min-content, and the child's own `minWidth: 0` is powerless because it relaxes the MAIN axis. That is the Help overlay defect: `.sr-help-row`'s inline `alignItems: 'flex-start'` is load-bearing above 640 (the sticky TOC) and became a width rule below it, sizing the prose column to a `white-space: pre` coordinates block's longest line (494px at 1x, 955px at 200%). **Before adding a `flex-direction: column` override to a tier, check what the parent's `align-items` will start governing — and fix it at the CHILD** (`align-self: stretch` + `width: 100%`, `!important` to out-rank the child's own inline block), never by weakening the parent. Constraining the column is necessary but not sufficient: an unbreakable URL-shaped string or a long single word still leaks, so pair it with a wrap allowance (`overflow-wrap: anywhere; word-break: break-word`) written INTO the tier rule rather than by attaching the unconditional `.sr-wrap-anywhere` class, whose reach would extend past the tier the evidence covers.
- **The shared layout vocabulary (all in `globals.css`):** `.sr-action-row` (a label + trailing action(s) row that wraps instead of overflowing; give the growable child `.sr-min0`; add `.sr-action-row-stack` to stack ≤480), `.sr-grid-2/-3/-4` (fixed N-up that collapses 3/4→2 at ≤1024 and all→1 at ≤640), `.sr-grid-auto` (self-collapsing `auto-fill minmax(--sr-grid-min,1fr)` — no breakpoint math; best default for tile grids), `.sr-grid-chart-aside` (content + a pie/donut aside that stacks ≤640), `.sr-field-row` (inline form controls that stack ≤480 where native date inputs can't shrink), `.sr-scroll-x` (contained horizontal scroll for wide tables), leaf helpers `.sr-min0`/`.sr-truncate`/`.sr-wrap-anywhere`, `.sr-pad-x-trim` (trim component-local side padding on phones), and `.sr-map-explorer-panel`.
- **The 0.5.55 mobile-prep additions (also `globals.css`) — use these, don't re-inline:** `.sr-touch-target` (raises a dense fixed-height button/pill toward ~44px min-height, in the ≤640 tier ONLY — desktop density is untouched; it does not change the visible glyph/label size, and a control that must be 44px on desktop too needs its own rule), `.sr-map-popup-body` (wrap the inner content div of any map popup that can grow tall — `max-height: min(60dvh, 26rem)` + internal scroll + `overscroll-behavior: contain`, so it never runs off a short phone viewport), `.sr-input-16` (add to any `<input>`/`<select>`/date-time control carrying a sub-16px inline font-size — sizes it in the ≤640 tier to suppress iOS focus-zoom; **the one place a px font-size is correct**, since the iOS zoom threshold is an absolute px value, and it avoids a `maximum-scale` viewport clamp that would kill pinch-zoom. **The class must sit on the `<input>`/`<select>` element ITSELF and out-rank its inline font-size** — the rule carries `!important` precisely because the thing it must beat is an inline style (specificity 1,0,0); put it on a wrapper, or leave the rule non-`!important` against an inline sub-16px font, and the guard is silently inert. This was inert on ~25 inputs app-wide until fixed in v0.5.61), `.sr-ctl-row` (v0.5.81 — put it on a **filter block**, and every interactive descendant inside it gets one phone-tier text size; it sizes descendants, never the container), and `.sr-wrap-flex` (wrapping inline flex control groups / header rows — lift the inline `display`/`flex-wrap` here, keep gap/colors inline or via `--sr-wrap-gap`). The `index.html` viewport carries `viewport-fit=cover`.
- **A phone-tier size that must clear an absolute px floor AND stay consistent with a scale-tracking neighbour is written `max(<px floor>, <rem>)`, ONCE, as a single declaration covering both sides (v0.5.81).** The old flat `.sr-input-16` value satisfied the 16px iOS floor and nothing else: at 1x it left pills at 12px beside 16px selects in the same wrapping filter row, and at 200% in-app text scale it INVERTED (pills 24px, controls still pinned at 16px), so the controls became the small ones for exactly the user who enlarged their text. `font-size: max(16px, 0.75rem) !important` in the ≤640 tier is shared verbatim by `.sr-input-16` and `.sr-ctl-row :is(button, select, input)`; the two sides can never differ at any scale, which two rules holding two literals that agree today cannot promise. State the guarantee as a property of the FORMULA across the whole input domain (`max(16px, rem)` is ≥16px for every value of `rem`, including a browser/OS default font size the user has lowered), not as "it computes 16px at 1x and 24px at 200%" — sampling the four in-app text scales would have missed that `rem` also tracks the browser default. The two selectors deliberately differ in specificity ((0,1,0) vs (0,1,1), both `!important`), which is exactly why they must share one declaration and a test must lock the values identical: then which one governs a guarded control is moot rather than reasoned about. Guard: `frontend/src/lib/filterControlSizeCss.test.ts` (parses the real `globals.css`, same posture as `milestoneContrast` / `countyContrast` / `calendarContrast`). **Corollary for VERTICAL fit, which the formula answers structurally so it needs no measuring (v0.5.82):** `max(16px, <rem>)` never TIGHTENS a box whose inline size is already that rem. It raises only while the rem is below 16px (below ~133% text scale, where it pins to exactly 16px); above that it returns the rem, i.e. the inline value the box was already built for. So a fixed-height control guarded this way cannot start clipping vertically at any scale — which is why adding the guard to nine controls sitting in fixed 34px boxes needed no accommodation.
- **A phone-tier size guard that makes a row stop FITTING inside a fixed-width container needs a companion layout rule, and the companion belongs beside it in the same tier, scoped to the feature's own subtree (v0.5.82).** Raising a control to 16px can push a side-by-side pair past its container: the Map Explorer's Date Range pair renders `08/09/2026` at 12px and `08/09/202` at 16px in the 120.5px each gets from a 282px sidebar. The repair is a `.sr-field-row` stacking rule scoped to the map sidebar through the whole ≤640 tier — NOT widening `.sr-field-row`'s own 480 breakpoint, which has six consumers and would restack five surfaces that sit in the full-width main panel with 220px+ per field and have no problem. Never weaken the `.sr-input-16` guard to resolve a clip; the guard is the requirement and the layout is what yields. Same "prefer the rule that lives inside the feature's own subtree" principle as the scroll-margin case above.
- **Put a control's font size on the control ELEMENT, not on a label span nested inside it (v0.5.81).** A size on a descendant beats any class on an ancestor, so a container rule like `.sr-ctl-row` cannot reach it — and the two forms are visually indistinguishable until the container rule exists, so this is invisible in review. Calendar's local `Switch` declared its size on the label `<span>` and would have stayed small beside everything else in its strip; the declaration moved up to the `<button>` (the span inherits, so desktop is byte-identical) and a test pins it. Corollary when measuring: a font size read off a control's box is not the size the user reads — measure the text-owning element.
- **A `rem` cap inside a fixed-`px` container measures the wrong thing — measure the container (v0.5.80).** `--sr-text-scale` multiplies the root font size, but a `height: 220px` card (the Named Birds card map) does not follow, so a `rem` max-height GROWS on a container that did not, and at 200% text scale it can double. When a popup or panel must fit a px-measured box, compute the cap from container geometry and write it as a **px custom property from a ref side effect** (no `setState`, no render-time measurement), with a floor at the ~44px touch-target size so the cap can never shrink a control out of reach. `SharePopup.tsx`'s `COMPACT_BODY_MAX_PX` / `COMPACT_BODY_MIN_PX` / `COMPACT_CHROME_PX` / `COMPACT_EDGE_MARGIN_PX` are the reference. This does NOT replace `.sr-map-popup-body` (`min(60dvh, 26rem)`) — that one is correct because its constraint is the *viewport*, not a container. Known modelling limit: `COMPACT_CHROME_PX` is a fixed px estimate of partly rem-sized chrome, so it under-estimates at large text scales; the cap itself is sound. **The CONVERSE is the same rule and shipped as a defect for fourteen versions (v0.5.91): a fixed px constant standing in for TEXT-SIZED chrome cannot be right at any scale.** `.sr-map-explorer-panel` was `calc(100dvh - 178px)` (132px in the phone tier) where the real header + tab nav + footer measures **223px to 484px** across five widths and four text scales, so the map's corner FABs sat below the bottom of the window until the user scrolled. `lib/mapPanelChrome.ts` is the repair and follows this bullet exactly — measure, publish a px custom property from a ref side effect, keep the old constants only as the pre-measurement fallback so first paint is unchanged. Two properties make the measurement safe rather than circular, and both are worth copying: measure the elements AROUND the sized box (here `<main>`'s two offsets, never the panel's own height), so nothing observed can change when the published value does; and REJECT an unusable reading (non-finite, negative, or a zero-height footer) rather than clamping it to 0, since publishing 0 would size the panel to a full `100dvh` and be the same defect but worse. Round with `ceil`, never `round`, so a fractional chrome cannot leave a half-pixel page scroll behind. The floor that can act on the outcome belongs in the stylesheet with the outcome (`min-height: 340px`, 300px on iOS), which is why 320px at 200% text scale still overflows by 24px by design.
- **Two standing mobile checks for new UI (the 0.5.55 lenses beyond the 0.5.37 sweep):** (1) touch targets on fixed, dense controls must meet the ~44px posture in the ≤640 tier (reach for `.sr-touch-target`); (2) no form control may ship a sub-16px font-size on phone (reach for `.sr-input-16`) or iOS auto-zooms on focus. Both hold at 320px and 200% in-app text scale.
- **Any `position: fixed` OR `position: sticky` element escapes `.sr-ios-app body`'s safe-area padding and needs its OWN `.sr-ios-app`-gated inset — and therefore cannot keep its positioning in an inline style (v0.5.81, proven three times).** `.sr-ios-app body { padding-top: env(safe-area-inset-top) }` protects every in-flow surface; a fixed element is viewport-relative and a sticky one resolves `top` against its scrollport, so both sit ABOVE that padding and render under the status bar / Dynamic Island (and, in landscape, the sensor housing). An inline `inset: 0` / `top: 0` is specificity (1,0,0) and unreachable from a stylesheet, so the positioning must be **lifted into a `globals.css` class first** (values byte-identical), which is the only thing that gives the inset somewhere to hang. Shipped instances: `.sr-map-fullscreen-panel` (map fullscreen), `.sr-help-panel` + `.sr-help-toc` (the Help overlay), `.sr-bc-matrix--pinned thead th` (the pinned Breeding Codes band), and `.sr-skip-link:focus` (the "Skip to main content" link). Rules that hold:
  - **Gate on `.sr-ios-app`, NEVER a bare `env()`.** `index.html` ships `viewport-fit=cover` to browsers too, so `env(safe-area-inset-*)` is non-zero in iOS Safari on the **web** build; an ungated rule fixes the app and silently changes shipped web rendering on every notched phone. `.sr-ios-app` is set on `<html>` by `main.tsx` only when `isIOS()`, so desktop and web stay byte-identical. Assert in the test that the ungated base rule contains no `env(`.
  - **Pad, don't shrink; top/left/right only.** Tailwind preflight's global `box-sizing: border-box` keeps a `100dvh` panel exactly `100dvh` with only its content box moving inward. Mirror `.sr-ios-app body` and add no `padding-bottom` (the FAB cluster and each overlay's own bottom padding already clear the home indicator; adding one shrinks a `flex: 1` scrollport into a dead band).
  - **A viewport-height calc INSIDE such an overlay must subtract the top inset too**, or a child capped that way over-extends by exactly the inset — invisible on a phone, live on iPad. The Help TOC's `calc(100vh - 52px)` stranded its last entries there until the gated variant subtracted it. Same family as the v0.5.80 "measure what actually bounds it" rule.
  - **Each overlay gets its OWN sibling rule; do not generalize.** The two full-screen overlays share only the three-line inset block (the map panel additionally needs `height: 100dvh` and carries a landscape coupling where the sidebar overlay reaches the padded edge through `.sr-map-content`'s `position: relative`; Help has neither), so a shared utility would still need a per-overlay positioning class and buys one declaration block at the cost of a second class name on the element. **Revisit a shared utility at a third overlay, not at two.**
  - **Watch the containing block when an inset is expected to reach a descendant.** An absolutely positioned child resolves against its nearest *positioned* ancestor's **padding box** — so a fixed panel's own padding does NOT inset an `absolute; left: 0` child unless that panel is the containing block. Name the actual positioned ancestor and assert its `position`, since removing it fails nothing today.
  - **Pad only a full-viewport box; a POINT-ANCHORED element is RE-POINTED, and only in the state that is on screen (`skip-link-safe-area`, the last of the family).** The "pad, don't shrink" rule above is the two panels' shape *because* they are `inset: 0` boxes; padding a `width: auto` pill instead grows it by the inset and paints its own background across the Island. The precedent that fits a point-anchored element is `.sr-ios-app .sr-bc-matrix--pinned thead th`, which moves an offset. Three sub-rules, each of which was a live wrong turn:
    - **Gate on the on-screen state, not the element.** `.sr-skip-link`'s base `top: -100px` is an off-screen *park* and is load-bearing: the pill is 41px tall at 1x and 62px at 200% text scale (measured, not estimated), so adding a 59px inset to the parked state — by `calc()` or by `padding-top`, both fail identically — puts its bottom edge at +21px and the HIDDEN link becomes permanently visible in the Island band. The inset belongs on `:focus` alone. Generally: before insetting a fixed element, ask which of its states the offset is describing.
    - **Only the edges the element actually declares.** `left` yes (at risk in landscape, and self-correcting — in the rotation where the housing is on the far side `inset-left` is 0 and the `calc` collapses to the shipped 16px); `right` never, because the element declares none and adding one to a `width: auto` fixed box stretches it across the viewport. This is the deliberate deviation from the two panel rules, which need both edges only because `inset: 0` pins both. Say so in a comment beside the rule, or it reads as an omission.
    - **Anchor the `calc` to the shipped literal** (`calc(16px + env(…, 0px))`), so the rule degrades to today's exact geometry wherever the inset is 0, and keep the `0px` fallback or the whole declaration is invalid where the variable is unsupported.
  - **This does NOT make it three overlays.** The skip link shares the escape and the gate, not the pad block, so the "revisit a shared utility at a third overlay" count above still stands at two.
- **Breakpoint tiers:** ~480 (small phone), **640 (the established phone boundary — don't move it; lots hangs off it)**, ~1024 (tablet), and a `.sr-panel` max-width cap (1280px, centered) for large desktops. Prefer self-collapsing `.sr-grid-auto` so most grids need no breakpoint; reserve explicit collapses for column control. Do NOT add JS `window`/`resize`/`innerWidth` checks — TabNav's ResizeObserver and the CSS tiers cover it. **When a render BRANCH (which DOM mounts, not just styling) must change by breakpoint and pure CSS can't express it**, use a render-safe `useSyncExternalStore` over `matchMedia` (`lib/useIsPhone.ts`: subscribe to the `MediaQueryList` `change` event, `getSnapshot = () => mql.matches`, `getServerSnapshot = () => false`, old-Safari `addListener` fallback), NEVER a `window.innerWidth`/`resize` listener. This is the React-sanctioned external-store media pattern (no innerWidth arithmetic, no per-pixel handler, no impure render read), so it honors the spirit of the no-resize rule while doing what CSS cannot. (NOTE: the Calendar tab NO LONGER uses `useIsPhone` to force a view — as of v0.5.68 its Compact/Large toggle governs at ALL widths, so the two views are distinct on a phone too. Earlier docs describing a phone-forced Compact calendar view are obsolete; the hook remains blessed and is still used where a genuine render-branch must flip by breakpoint.)
- **A user-relabelable / swappable toggle stores label-AGNOSTIC internal state values — what the option renders semantically (e.g. `'months'` / `'overview'`), NOT value names that encode the visible label (`'large'` / `'compact'`).** The Calendar view toggle churned labels twice: v0.5.60 coupled the enum values to the labels for "code and UI agreement," so v0.5.62's label swap would otherwise have forced a lockstep value rename. Semantic, label-agnostic values let the labels and the code drift independently — a future relabel/swap touches only the option copy, never the state values or their consumers. (The values are session-only `useState` here, so there is no persisted string to migrate either way.)
- **When a child's legibility depends on its OWN cell size — not the viewport — gate it with a CSS container query, not a viewport breakpoint.** The same viewport width yields very different cell sizes (a desktop 3-up narrow panel and a phone single column are both "narrow" to a media query but sized oppositely), so a viewport tier can't decide whether an in-cell number fits. Give the sized element `container-type: inline-size` and reveal the number span under a `@container (min-width: …)` floor; below it, hide only the number span so the cell/grid never distorts and the shading still carries magnitude. The `.sr-cal-minimonth` (152px floor) day-number reference from v0.5.60 was RETIRED in v0.5.62 (the year-overview mini-cells reverted to shading-only, so both the numbers and the container-query CSS are gone) — the pattern remains the sanctioned approach when a cell-sized number genuinely earns its place. If you re-introduce it, the px floor is the same sanctioned legibility exception as `.sr-input-16`, and size everything else in rem so it holds at 200% text scale.
- **A `position:absolute` element wider than the viewport leaks PAGE horizontal scroll on a phone even when invisible.** Two such bugs were fixed in 0.5.37 (TabNav's `visibility:hidden` overflow probe; absolutely-positioned `.sr-only` spans inside a horizontally-scrolled table). **Standing check:** any wide / `max-content` element or off-screen measurement node must sit under an `overflow:hidden` / `position:relative` ancestor so it can't extend `document.scrollWidth` on a phone. Wrap any new wide table in `.sr-scroll-x` (which carries `min-width:0` + `position:relative`); don't add a blanket `body{overflow-x:hidden}` (it would break the tables' `wideMode` page-scroll). **THIRD INSTANCE, v1.0.4, and it arrived by a different route than the first two: a SELECTOR reached the element rather than the element being wrong.** A phone-tier `.sr-field-row > * { width: 100% }` matched the visually-hidden `<span class="sr-only" aria-live="polite">` in that row; because `.sr-only` is `position: absolute`, the percentage resolved against the containing block rather than the row, giving a 320px box at x=42 that leaked page scroll at EVERY text size while remaining invisible. Equal specificity (0,1,0) with `.sr-only`'s own rule meant source order decided it. **Standing rule: exclude `.sr-only` from any `> *` sizing rule** (`:not(.sr-only)`), including copies that merely re-state the same declarations at another tier -- `.sr-field-row`, `.sr-action-row-stack`, and `.sr-map-sidebar-overlay .sr-field-row` are all guarded, the last prophylactically, and `scrollLeakCss.test.ts` pins all three with a mutation check against the shipped selector. Fixes must hold at 200% in-app text scale — size in rem, never convert rem→px to "fix" overflow. Relatedly (v0.5.91): an absolutely positioned box with only `left` set **shrink-to-fits against the space from that edge**, so the shipped loading chip's `left: 50%; transform: translateX(-50%)` gives any WRAPPING occupant of that anchor half the container's width (measured as 8 lines where 4 were expected). The chip gets away with it because it is effectively single-line; anchor a wrapping one `left` AND `right` and centre its child.
- **`.sr-wrap-flex` is INERT on a cluster that also carries an inline `flexShrink: 0` — the class needs a width cap to bind (v0.5.82).** A pinned flex container is never narrowed, and a container that is never narrowed has no reason to break a line, so `flex-wrap: wrap` computes correctly and changes nothing: the Breeding Codes count-and-view cluster measured 475px inside a 296px box with the class applied and wrapping enabled the whole time, the single largest unclipped overflower on any tab at 320px/200%. Pair the class with `maxWidth: '100%'` (responsive by construction, no breakpoint math, the same pairing `.sr-scroll-x` already uses) — measured identical in effect to dropping `flexShrink: 0`, and preferred because it keeps the do-not-get-squeezed intent rather than discarding it. Write the TEST as the invariant (given an inline `flexShrink: 0`, a width cap must be present) so either measured-equivalent form stays green and neither-of-them does not. General shape: **adding a responsive class is not evidence the layout responds** — a stylesheet test passes on an inert class, which is exactly how this one shipped inert.
- **A wrapping flex row is not contained until EVERY nested automatic minimum on the overflow path is released (v0.5.86).** At 320px/200%, the Breeding Codes filter row wrapped yet measured 327.11px inside a 272px parent because both its pill and the pill's label retained `min-width: auto`. The repair uses feature-specific hooks — `.sr-bc-filter-row`, `.sr-bc-filter-pill`, `.sr-bc-filter-pill-label` — with `min-width: 0` on both nested flex items, phone-only `height: auto !important` plus the existing 30px minimum, and `overflow-wrap: break-word` for the emergency slash-run. Do not put these layout declarations on shared `.sr-ctl-row`; other filter surfaces and wider layouts are outside the measured repair.
- **A container that sizes itself INTRINSICALLY (`width: max-content` / `min-content`) takes the maximum over ALL its children's contributions, not just the one it was built around — so a wrapping sibling silently becomes the ruler (v0.5.84).** This is the Breeding Codes Unbounded card: it was built around the table and was in fact being sized by the tier legend beside it, a wrapping row of nowrap chips whose max-content is every chip on one unwrapped line (1749px against the table's 792px). Any wrapping sibling qualifies — a legend, a chip row, a footer strip, a filter cluster — and the symptom appears somewhere else entirely, on the child that was supposed to be doing the sizing. **Constrain the SIBLING with `width: min-content; min-width: 100%`**, which lets it floor the container but never dictate it: `min-content` makes it contribute only its widest single item to both intrinsic sizes, and the percentage stretches it back across the resolved container in layout without feeding back, because a percentage is indefinite while the container is being sized intrinsically. Two forms to reject: sizing the container from a different keyword (it is still the maximum over both children, so the defect shrinks rather than goes away and returns silently the first time the content shifts), and **zeroing the sibling's contribution (`width: 0`, `contain: inline-size`) — never do this where the sibling holds unbreakable `white-space: nowrap` content**, since the container can then fall below that content's own minimum and the content hangs outside its border, which is reachable on a phone at 200% text scale.
- **The Breeding Codes matrix is BY DEFAULT a NATURAL full-height, page-scrolling table at ALL widths — NOT a capped-height frozen-header data-grid (v0.5.69, amended v0.5.81).** A frozen title row + capped-height data-grid was built and live-tested during the mobile pass, then REVERTED at the user's request for the natural table (the reason is in DECISIONS: pure CSS cannot combine a page-frozen header + an unbounded-height table + contained horizontal scroll — `overflow-x:auto` forces the vertical axis to `auto`/`hidden`, binding a sticky header to the wrapper instead of the page). The tier legend sits in normal flow after the last row. **v0.5.81 adds an opt-in "Pin code labels" toggle (default off, session-only) that pins the header — offered ONLY in the "↔ Unbounded" view**, where neither the card nor the wrapper sets `overflow`, so a `position: sticky; top: 0` `<th>` anchors to the page for free and the table keeps its full natural height. Normal view is deliberately NOT given the capped box: at 200% text scale a row is ~68px, so `60dvh` leaves ~5 rows with the legend stranded (worse than what v0.5.69 reverted) and `26rem` (832px) exceeds the viewport, which puts the scrollport's top — and the pinned header with it — off-screen. That arithmetic, not preference, is why the v0.5.69 shape stays reverted. Invariant: **pinned implies Unbounded** (pinning from Normal switches and pins in one press; unpinning restores the view you came from; pressing `↔ Normal` clears the pin). `position: sticky` sits on each `<th>` individually, NEVER on `<thead>`/`<tr>` (WKWebView honors sticky on cells only), and `border-collapse: separate` is required. **Phone narrowing is single-sourced in `.sr-bc-code-col`** (`frontend/src/globals.css`): base ~44px on desktop, `@media (max-width:640px)` → ~30px dot-width columns + 0.625rem headers. Change the phone width THROUGH that class, never an inline width. Thin vertical column rules come from `--sr-border-subtle` right-borders on `.sr-bc-code-col` / `.sr-bc-name-col` (all widths). The species-name column is horizontally sticky ONLY (`left:0`, no `top`). Magnify is native viewport pinch — NO CSS `zoom` / `transform:scale` (unreliable in WKWebView, same reason the v0.5.64 ZoomableWideSurface was reverted). **The ≤640 dot-width narrowing holds in BOTH the Normal and the "↔ Unbounded" (wideMode) views (v0.5.70):** `.sr-bc-matrix` on the `<table>` (base `width:100%; min-width:max-content`; `@≤640` `table-layout:fixed; width:max-content; min-width:0`) makes the declared `.sr-bc-code-col` widths *authoritative* — under `table-layout:auto` a cell width is only a floor a wide/uncapped table never reaches — and `.sr-bc-card` on the wideMode card (base `max-content`; `@≤640` `min-content`) hugs the fixed-width table so there's no trailing whitespace. **CORRECTED at v0.5.84 — that "hugs the table" claim was TRUE on the phone tier and FALSE on desktop from v0.5.70 until this bundle, and the same false sentence sat in `globals.css`.** `max-content` on a column flex container is the maximum over ALL its children, and the card's other child is the tier legend, a wrapping row of "CODE Full Label" chips whose max-content is every chip on one unwrapped line: it measured 1749px against the table's 792px and won, the table's `width: 100%` then resolved against that inflated card, and `table-layout: auto` stretched every column to fill it (code columns 97px instead of their declared 44px, the card 519px past the panel). What makes the claim true now is one added top-level rule, `.sr-bc-card > .sr-bc-legend { width: min-content; min-width: 100%; }`, which lets the legend FLOOR the card but never dictate it. Keep it top-level (it must hold in the ≤640 tier too) and scoped under `.sr-bc-card` (Normal view never carries that class, which is what makes "Normal is untouched" a property of the stylesheet rather than of a measurement). **AMENDED at v0.5.85 — "Normal is untouched" is no longer the whole story: Normal view's legend now has its OWN phone-tier constraint, and the two rules are converses that must not be merged.** v0.5.84 stopped the legend *dictating* an intrinsic card width, which can only happen in Unbounded. In Normal the card is a stretched flex item at the panel's width, so an unbreakable `white-space: nowrap` chip is simply wider than it: at 320px/200% with all 23 codes the widest label ran **81.08px** past the legend's content box, out through the card's rounded border and off screen (the band reaches 390px and 1.5x). The Normal-view fix is three declarations in the ≤640 tier, each load-bearing and two of them invisible to a box measurement — `min-width: 0` on **both** `.sr-bc-legend--normal .sr-bc-legend-tier` and `.sr-bc-legend--normal .sr-bc-legend-chip` (both are flex items, whose `min-width: auto` floors them at their min-content width regardless of available space), plus `white-space: normal` and `overflow-wrap: break-word` on the chip, with the base `.sr-bc-legend-chip { white-space: nowrap }` lifted top-level byte-identical to the inline value it replaces. Three things must not be flattened: the **`.sr-bc-legend--normal` scope** (the component adds it exactly when it omits `.sr-bc-card`, so the two can never co-occur — unscoped, `min-width: 0` on the tier group would lower the legend's min-content, which is precisely the value v0.5.84's rule reads, and every CSS guard would stay green through it); **`break-word` into `anywhere`** (renders identically and would let both `min-width: 0` go, but collapses min-content to a single character, the zero-contribution shape v0.5.84 named and rejected — `break-word` never affects intrinsic sizing); and **`overflow-wrap` itself**, which a box-based test reports as unnecessary. No hanging indent is needed: flex collects items onto a line only while they fit, so a chip wide enough to wrap is always alone on its flex line, and every line opens with a bold code or continues the one above. **CSS caution:** `table-layout:fixed` needs a *definite* width (`max-content; min-width:0`), NEVER `width:100%` inside a `max-content`/shrink-to-fit container (a circular constraint that runs the table to the browser's ~500,000px element-width cap); and a `max-content` card over a fixed table sizes to the columns' *intrinsic* width (huge whitespace) — use `min-content` to hug it (both layout-only, caught only in live phone preview). Files: `frontend/src/components/BreedingCodeTable.tsx` (+ its test), `frontend/src/globals.css`.
- **PINNED LABEL ROWS ARE ONE PATTERN ACROSS TWO TABLES (Breeding Codes and Multimedia), and the pattern is a CONTROL, not just a mechanism (`freezable-label-rows`).** Both offer an opt-in pill (default OFF, session-only `useState`, no storage seam) that pins the header row, offered in the "↔ Unbounded" view, under one invariant: **pinned implies Unbounded**. Four things are deliberately shared, and a third pinnable table should reuse all four rather than re-inventing them:
  - **The state machine is `frontend/src/lib/pinnedLabels.ts` (`nextPinnedState` / `nextViewState`), used by BOTH tabs.** Same posture as `nextShadingState`: pure transitions wired into both toggles, never a `useEffect` mirroring one piece of state onto another. It also carries the `announce` flag (true only on the press that PINS) so the two surfaces cannot drift on when they speak. The invariant is proved once there, including over random walks; what each component test still owes is the WIRING.
  - **The sticky sits on each `<th>` individually, never on `<thead>`/`<tr>`** (WKWebView honors sticky on cells only), with `border-collapse: separate`. Multimedia's shipped on the `<tr>` from v0.0.29 and was therefore very likely dead in the macOS app and on iOS while alive in Chromium.
  - **Everything the band needs lives in the stylesheet, never inline** (`.sr-bc-matrix--pinned` / `.sr-ll-table--pinned`): an inline style is specificity (1,0,0), so the `.sr-ios-app` safe-area gate could never re-point `top` and the band would pin into the Dynamic Island. That gate is a gate, never a bare `env()`. The band's fill moves onto the `<th>` because a sticky CELL travels while its `<tr>` stays in flow, so a fill left on the row scrolls out from under the band.
  - **The focus guard is `scroll-margin-top` on the pinned body cells AND their descendants** (four selectors), because the focusables are not the cells: `BirdName` renders a `<button>` inside each row header. Read the computed value off the element that RECEIVES FOCUS before claiming WCAG 2.2 SC 2.4.11; a rule on the cells alone computes `0px` on everything that can actually take focus. Never `scroll-padding-top` on the root, which would outlive the tab (hidden tabs stay mounted).
  - The pinned-state note's classes are surface-neutral (`.sr-pinstatus` / `.sr-pinnote`) precisely because both tabs render them; a `.sr-bc-*` name on the Multimedia tab would be a name that lies.

### Accessibility — standing conventions

The app targets WCAG 2.1 AA (the 0.5.31 pass). These are the durable, enforceable contracts; the published statement is `ACCESSIBILITY.md` and must stay true to the shipped code (a wrong accessibility statement is a liability, same posture as the privacy policy).

- **Contrast is fixed at the token, in BOTH themes — with a typed naming system.** Three text-on-X cases have distinct token families in `globals.css`: `--sr-tier-N-fg` (tier-colored text ON an 8–15% tier tint), `--sr-tier-N-text` (text ON the solid tier fill), and the on-fill tokens for specific surfaces (`--sr-map-target-*-text`, `--sr-milestone-*`, `--sr-rank-pin-*`, `--sr-on-chart-blue-dark`, `--sr-border-input` for form-control boundaries at ≥3:1 non-text). Pick the family by what the text sits on; never reuse a fill token (`--sr-tier-N` / `-rgb`) as a text color (the fill palette is left untouched for atlas/hatch parity). Verify with the same WCAG luminance math, both themes, before shipping a new pair.
- **`--sr-text-disabled` is for genuinely disabled CONTROLS only** (WCAG-exempt). Informative text, empty states, and captions use `--sr-text-muted`. Do not use `text-disabled` for content.
- **A token whose underlying fill differs by theme may need OPPOSITE text colors per theme** — `--sr-on-chart-blue-dark` is `#FFFFFF` light / `#0A0A0A` dark for exactly this reason. A single value can't always pass on a light-in-one-theme, dark-in-the-other fill.
- **Filter controls follow the Checklists.tsx pattern: an explicit `aria-label` on every `<select>` / date input / search box** that would otherwise rely on a placeholder or a nearby caption. `Checklists.tsx` is the reference; the pattern is now applied app-wide.
- **`SegControl` and segmented/pill toggles carry `aria-pressed`** reflecting the selected state.
- **Overlays route EVERY close affordance (Escape, Close button, backdrop) through one close function that restores focus to the opener.** If the opener unmounts while the overlay is open (e.g. a FAB that only mounts when the panel is closed), run the restore in an effect AFTER the close render commits via a flag ref — not at close() time, when the ref is still null (the `closeSidebar` / `restoreFiltersFocusRef` pattern in `MapExplorer.tsx`). A focus trap must **re-query its focusables per Tab keydown**, not cache them once (collapsed/`inert` content changes the set); `HelpDocs.tsx` and `MapExplorer.tsx` are the references.
- **Wrap a decorative recharts chart in `inert` — recharts ignores `accessibilityLayer={false}` on `PieChart`** (its root `<svg>` stays focusable and leaves an axe aria-hidden-focus ghost). The same `inert` clamps collapsed filter panels so hidden controls aren't stray tab stops.
- **A CSS-COLLAPSED disclosure panel is not hidden — it needs `inert` while closed, plus a test asserting the LITERAL attribute in BOTH states (v0.5.87).** A panel collapsed with `grid-template-rows: 0fr`, `max-height: 0`, or `opacity: 0` is clipped, not unmounted, so its focusable descendants stay in the tab order and the accessibility tree while `aria-expanded="false"` says otherwise (WCAG 2.4.3, 4.1.2). The escapee account panel measured exactly 9 such focusables. The fix is `inert` on the clipped inner div — the same fix on the same grid-rows shape as the Map Explorer's collapsed filter panel. Assert the literal attribute in both states, because **React 19 emits `inert={false}` correctly as absent while pre-19 rendered the truthy string `inert="false"`**, which would pin the panel permanently inert. This is NOT the "Show all N counties" idiom, which conditionally renders and is only the source of the expander BUTTON's styling; say so in the component and the CSS so the two are not confused. **Corollary (v0.5.92): a live region consumed by a collapsing subtree renders OUTSIDE the `inert` boundary.** `inert` removes its subtree from the accessibility tree entirely, so a `role="status"` region inside the clipped panel re-enters the tree along with its first message — the insert-with-first-message trap by another route. Put the region outside the inert-able element; `HotspotModeControl` is the reference (its test asserts the literal `inert` attribute in both states). **Second corollary (v1.0.5): where the live region IS the collapsing content rather than something rendered inside it, drop the live semantics instead of relocating them.** Relocation answers the case of a small status line that a panel happens to contain; it has no answer for a panel whose whole body is the thing that would be announced. A county-shading legend moved outside its own disclosure is no longer a disclosure, and left inside with `aria-live` it announces the entire ramp — ten tiers of text — on every open, which is the insert-with-first-message trap paying out at its worst. Ask what the user needs told: a legend is reference material consulted after opening, not an event, and the state change that actually happened (the metric switch) is already announced by the `SegControl`'s own `aria-pressed`. So the panel opens silently and carries no live region at all. **A design spec asking for `aria-live` does not override this** — the county shading panel's did, and the repo rule won; say so in the component so the next reader does not restore it as an oversight.
- **`scroll-padding` goes on the SCROLLPORT, `scroll-margin` on the FOCUS TARGET — and in this app the focus target is almost never the cell (v0.5.81).** When a sticky band can obscure keyboard focus (WCAG 2.2 SC 2.4.11 Focus Not Obscured), the vertical guard is `scroll-margin-top` on the elements that actually receive focus. Table cells, rows, and list items are not focusable; the real target is the `<button>`/`<a>` inside them (`BirdName` nests one three levels deep in every species row), and `scroll-margin` neither inherits nor applies to an ancestor — so a rule on the cell computes `0px` on every focusable and is completely inert. Use the descendant combinator (`… tbody th *`), not a child combinator, and verify by reading the computed `scroll-margin-top` **off the element that receives focus** before claiming the SC. The `scroll-padding-top`-on-the-scrollport half is geometrically correct and is nonetheless the WRONG reach here: the scrollport is the page, and `mountedTabs` only grows with hidden panels at `display: none`, so a root-scoped rule (or a `:root:has(…)` variant — selectors match the DOM tree irrespective of computed `display`, verified in Chromium) stays in force on every other tab after the user pins and navigates away. **Prefer the rule that lives inside the feature's own subtree.** The same component's horizontal axis IS the genuine `scroll-padding` case (`BreedingCodeTable.tsx`'s `scrollPaddingLeft`), because there the wrapper really is a scrollport; the two axes are not symmetric. Scope any regression tripwire to the leak (a `:root`/`html`-scoped declaration), not to the property or selector vocabulary — a stylesheet-wide ban on `scroll-padding-top` or `:has(` fails unrelated future work under a test name that points at the wrong thing.
- **An overlay hosted INSIDE a map binds its Escape handler in the CAPTURE phase at `document`, with `stopPropagation` (v0.5.80).** `MapExplorer`'s shipped fullscreen-exit and sidebar-close Escape handlers are bubble-phase on `document`, so a bubble-phase handler on a new in-map overlay cannot beat them — one Escape would dismiss the overlay AND exit fullscreen. Capturing at `document` and calling `stopPropagation` makes the overlay the innermost dismiss layer and prevents the outer handlers firing at all. `SharePopup.tsx` is the reference; it stays one close path (the close control, Escape, and any maplibre dismissal all route through the same function, per the bullet above).
- **A live region whose text is set to the SAME string does not announce — put the message in a sequence-keyed child node (v0.5.80).** `aria-live` fires on DOM *mutation*, and React bails out when reconciling a text node to an identical string, so pressing the same control twice announces once while the visible confirmation re-renders both times and every `textContent` assertion stays green. The repo rule "render the region from the start, only change its text" is necessary but NOT sufficient. The fix is `{msg ? <span key={seq}>{msg}</span> : null}` inside the `role="status"` region, with `seq` advancing per announcement — each one is a real node replacement while the region's `textContent` stays exactly the message. Do NOT append an invisible character to force a diff: it makes every `textContent` assertion quietly false. Any such region needs a test that presses the same control twice and counts DOM mutations (`SharePopup.tsx` + `SharePopup.test.tsx` are the reference). **One nuance on that test, verified empirically in v0.5.81:** mutation-counting only discriminates against the wrong implementation when the message node stays **permanently mounted** and its text is toggled. Where the node unmounts while the region remains (the Breeding Codes pin note), the remount is already a real DOM addition, so an unkeyed child passes the same test. Still write the keyed child — but describe the guard by what it actually rejects, rather than banking a false confidence. **A guard whose discrimination has been shown to be absent should say so in its own comment and name the test that DOES reject the defect** (the Breeding Codes pin note is the reference: its mutation-counting test cannot reject an unkeyed child, the file says exactly that, and an adjacent test carries the real `aria-live` guarantee).
- **A live region driven by a PER-ITEM progress callback needs its announcement rate stated, bounded, and measured against a REAL-DURATION pass — never a fast mock (v0.5.87).** The escapee progress region announced 75 times over a 9.7 s pass, about 7.7 per second, because the sequence-keyed child fired per request; a fast mock would have let any throttle suppress everything and reported a rate the user will never see. **Throttle the EMISSION, not the announcement**, so the sentence, the progress bar and the `N / M` readout keep one source of truth and cannot disagree on screen. Never throttle a terminal status or the first definite figure, keep the region always rendered (never `display: none` while idle, per the rule below), keep the sequence-keyed child, and mutation-check in BOTH directions — removing the throttle must go red, and throttling the opening figure must go red. **v0.5.92 sharpening: the throttled emission must be a FROZEN SNAPSHOT of the progress accumulator, never the shared accumulator object itself — and the throttle is verified at the RENDER, by a timestamped text-change measurement over a real-duration pass.** Emitting the live accumulator lets every per-arrival re-render observe its in-place mutations, so the rendered text updates at arrival rate while the emission rate is nominally throttled; the defect shipped with the unit suite green because the suite asserted the emitted objects, not the rendered timeline. `useHotspotActivity`'s `flushEmit` is the reference (its regression test was proven red against the shipped defect on the mutation and frozen-snapshot assertions independently).
- **A CSS rule whose subject is an ARIA element must be checked against the ACCESSIBILITY TREE, not only against layout — and `display: none` on a live region is the specific trap (v0.5.83, caught in security review as a Medium).** `display: none` removes an element from the tree entirely, so a `role="status"` region hidden while idle is *inserted along with its first message*, which is the documented way to make a live region fail to announce. `.sr-map-geo-error:empty { display: none }` did exactly that to the map's location-failure region, and it broke **every** announcement rather than only the first, because the handler clears the message before each press (so each one was a `none` → `flex` transition) — and it defeated the sequence-keyed child from the bullet above, whose entire premise is a STABLE region whose child is replaced. It is invisible to every layout measurement, to a `textContent` assertion, and to jsdom (which loads no stylesheet), so the component test passes on the broken build and is necessary but not sufficient; pair it with a stylesheet scan over every rule whose subject is the region, asserting nothing sets `display`/`visibility`/`content-visibility` to a hiding value plus a positive `display: flex` so the scan cannot pass vacuously by the rule being deleted. Verify with Playwright's `ariaSnapshot` against a real render while the region is IDLE. **The same "use a real accessibility tree" instruction covers accessible NAMES, and the jsdom proxy has a specific known deviation (v0.5.84, and it cost a QA cycle).** `computeAccessibleName` from `dom-accessibility-api` — what testing-library uses — omits the inter-node space real engines insert per the accname algorithm, so it reports a spurious one-space delta between an `.sr-only` cue node and an `aria-label`; a build measured that, called it "measured, not reasoned about", and published a bold claim that the name had changed when Chromium and WebKit both render it byte-identical. jsdom has no accessibility tree, so there was never anything there to measure. Assert a name in a component test with `getByRole(..., { name })` (which pins the guarantee rather than the mechanism that carries it), and settle any claim that a name CHANGED against `ariaSnapshot` plus CDP `Accessibility.getFullAXTree` in Chromium **and** WebKit, the engine the macOS and iOS apps actually ship on. House posture, unchanged since `SharePopup.tsx`: the region is always rendered and only its child changes. A `.sr-only` duplicate announcer is the wrong repair where the announced text IS the visible card (it would put the same sentence in the reading order twice).
- **To portal a control into an EXISTING flex row, use `display: contents` on the slot — never `order` (v0.5.80).** `order` moves the box visually while leaving DOM order unchanged, which desynchronizes tab order from reading order (WCAG 2.4.3 Focus Order). `display: contents` makes the wrapper transparent to layout so DOM order IS visual order, and the new control simply takes its place in the sequence. `.sr-map-fab-slot` (the share pin's slot as the first item of `.sr-map-fab-cluster`) is the reference; it also means no shipped control in the cluster moves. **Its counterpart cost, found in v0.5.91: such a wrapper has NO BOX, so a `ResizeObserver` on it reports 0x0 and never fires.** Any layout observer walking the app shell's children must descend one level through a `display: contents` child or it silently misses exactly the case it exists for — `App` wraps the tab nav in one, so a tab strip collapsing into its dropdown (which an in-app text-scale change alone can trigger at an unchanged viewport width) would go unobserved. `chromeBoxes` in `lib/mapPanelChrome.ts` is the reference.
- **DOM map markers are real `<button>`s** via `neutralizeMarkerWrapper` (`lib/mapPins.ts`) on the `<Marker>` ref — never a clickable `<div>`.
- **The "open this checklist on eBird" affordance is the shared `components/ChecklistLink.tsx`, used for EVERY checklist link app-wide.** One visual signature (the lucide external-link icon) and one accessible-name formula, which is **label-aware**: with a visible date/count the name leads `{label} — open checklist on eBird (opens in a new tab)` (WCAG 2.5.3 Label in Name, so Voice Control can activate it by what's on screen); with no label it names the id directly; the functional suffix is identical everywhere (WCAG 3.2.4). A `compact` prop renders icon-only for dense spots (species pills, fixed-width cells, map popups) while keeping that same name; an optional `title` adds a hover tooltip without changing the accessible name. It keeps the `SUBMISSION_ID_RE` guard (junk id → plain text, never a styled 404 link).
- **Every NON-checklist external link goes through the shared `components/OutboundLink.tsx`** — it guarantees `target="_blank"` + `rel="noreferrer"` and an "(opens in a new tab)" cue (a clean spaced `aria-label` from string children / an explicit label, else an `.sr-only` cue node for JSX children). Canonical new-tab wording is "(opens in a new tab)". It is named `OutboundLink`, **not** `ExternalLink`, to avoid colliding with lucide-react's `ExternalLink` ICON; decorative ↗/→ glyphs beside a link are `aria-hidden`. Don't hand-roll an external `<a target="_blank">` — use `OutboundLink` (or `ChecklistLink` for checklists).
- **A location NAME that is a PUBLIC eBird hotspot renders through the shared `components/HotspotLink.tsx` (v0.5.40).** It turns the name into a link to `ebird.org/hotspot/{locId}` ONLY when the caller passes `isHotspot` true AND the id passes `LOCATION_ID_RE` (`/^L\d+$/`); a personal location, a junk/absent id, or a not-yet-resolved Set all render as plain text — never a styled 404 link (the pre-existing inline links gated on id-format ALONE, which wrongly linked personal locations; this is the fix). It wraps `OutboundLink` and reuses the `Open {name} on eBird (opens in a new tab)` name formula (`hotspotLinkAriaLabel`); `compact` = icon-only (map popups), `truncate` = ellipsis a long name while keeping the trailing icon (the link color is forced `var(--sr-accent)` so a caller's plain-text color can't bleed onto it). **Public-vs-personal is decided by `isPublicHotspot` against a region-scoped Set** (`lib/hotspotSet.ts`): one cached fetch per distinct `stateProvince` region in the backup via `GET /map/hotspot-region` (eBird `ref/hotspot/{regionCode}`) → union of locIds → O(1) membership, NOT one call per location. Tabs get it via the parameterless `useHotspotSet()` hook (loads the backup itself through `observationsCache`; the `getHotspotSet` module cache keys on the region list so all tabs share one build). No key / a failed fetch degrades to an empty Set (everything plain). When a list renders many rows, call `useHotspotSet()` ONCE in the parent and pass `isHotspot` down — don't call the hook per-row. The backend route and `lib/tauri/mapService.ts` `getHotspotRegion` are dual-transport parity — keep them in lockstep, and `/map/hotspot-region` is in `CACHED_GET_PATHS`.
- **The Calendar tab is deliberately OFFLINE / zero-network — render location names there as PLAIN TEXT, NOT through `HotspotLink` (v0.5.63).** The app-wide "a public-hotspot location name links to eBird via `HotspotLink`" convention above is **explicitly waived on the Calendar tab**: `HotspotLink` needs `useHotspotSet()`, whose region-scoped `GET /map/hotspot-region` fetch would add a live network dependency to a tab whose entire promise is that it computes purely from the already-loaded backup and works with no connection. The day-popup checklist rows show the checklist's location as escaped plain-text JSX (no anchor, no `OutboundLink`, no fetch); a code comment in `Calendar.tsx` marks this, and this note makes it a durable convention so a future dev doesn't "upgrade" those names into linked hotspots and silently break the tab's offline guarantee. Any new Calendar-tab surface follows the same rule.

### Display and copy conventions

- **No impure calls during render — `react-hooks/purity` is enforced by eslint (build-blocking).** Never call `Date.now()` / `new Date()` (or other impure functions) inside a component render body or a `useMemo`/`useCallback`. For a "now" reference in recency / time-window filters, use a module-level session constant (`const SESSION_NOW_MS = Date.now()` at module top) and read it in the memo, or thread a `nowMs` arg into a pure helper — the pattern in `MapExplorer.tsx` (the Time Range window) and `BirdingStats.tsx`. Event handlers may call `Date.now()` directly (they don't run during render).

- **A histogram whose bin count derives arithmetically from a data VALUE (not from row count or distinct values) must bound its ladder structurally in the compute layer (v0.5.78).** The CSV parser admits any `parseInt`-able integer, so one corrupt cell can otherwise mint millions of bins (~3 GB heap and a render-time `RangeError` from a `Math.max(...spread)` — the checklist-duration Medium, empirically confirmed). `computeDurationBins` (`lib/birdingStats.ts`) is the reference: a plausible-range input guard (`[0, 1440]`, eBird's 24 h checklist cap — out-of-range rows fall into the honest "N of M have a usable duration" coverage note) PLUS a structural `DURATION_MAX_BIN_INDEX` clamp so the ladder is bounded even if the guard is bypassed. Pair it with reduce-not-spread for any `Math.max`/`Math.min` over a data-length array (bounded spreads over fixed-size arrays are fine). A histogram bounded by distinct values (the observer-count chart) is a different, inherently bounded shape — do not generalize from it.

- **When a preference's copy multiplies combinatorially (N independent toggles means 2^N labels), GENERATE it from one ordered manifest plus pure functions — never a hand-written lookup table (v0.5.81).** `SHARE_PARTS` in `lib/shareLocation.ts` is the reference: one ordered table drives the payload lines, the switch labels, their accessible names, the popup button label, and the mode sentence, so adding a fourth destination is one row and zero new copy. Three properties are load-bearing:
  - **Keep the manifest noun its OWN column, never the visible label lowercased.** The one-column-plus-`.toLowerCase()` shortcut reads correctly on today's rows and silently produces "Bing maps link" on the next one. Same class of trap: a `countWord` ladder that stops at the shipped count and starts mixing a digit into a sentence of word forms.
  - **The generic functions take the driving table as a DEFAULTED parameter, and the suite proves the claim by actually adding a hypothetical extra row** and asserting every derived output from it. Extensibility asserted only against the shipped table is untested by construction; this is the mechanism that surfaced the noun trap before it shipped.
  - **Where a copy decision rests on a rendered measurement (a character ceiling, a wrap count, a fixed-width container), state the number AND keep a test that fails if the generated string exceeds it.** The prose figure alone drifted by one character here with nothing failing.
  A structural state (all toggles off) is a structural answer, not an extra string: **no control that looks pressable may put an empty string on the clipboard** — replace the control with a sentence rather than disabling it.

- **A ranked list that can degenerate renders a SENTENCE at one item and NOTHING at zero — never a ranking of one, never an empty-state box (v1.0.3).** Rank numbers, a count column, and a show-all expander all presuppose a comparison; with one row they are chrome around a single fact. State the fact instead (`Every sighting at {place}.`), and where there is nothing to rank omit the block heading and all, matching how the Named Birds card already omits its map for a bird with no coordinates. Test all three shapes (many / one / none), since the one-item case is the one a fixture of realistic data never produces.

- **A COPY GUARD STATES RULES OVER A GENERATED CORPUS — never a ban list of known-bad strings, and never two hand-picked samples (v1.0.5).** The pass that fixed "about 1 minutes" shipped "1 requests" and "The other 1 have not been asked about yet." straight past a guard that banned four named strings, because a ban list can only ever reject the defects someone already found. Replacing it with rules — no count of one takes a plural noun (`/\b1 [a-z]+s\b/`), no determiner takes a bare "1", and no plural verb follows a subject counted at one — found **seven** plural defects across the Projects section where reading the copy had found two, including `1 row … carry`, whose subject and verb sit four words apart and which no window-scoped or string-scoped check reaches (make the subject-verb check SENTENCE-scoped for exactly that reason). Two obligations ride it. **Generate the corpus from the shipped state function, not by hand** — the grid here is driven by `restingStatus`, so it covers every state the app can actually reach and nothing it cannot, and a new state joins the sweep for free. And **a helper that renders a count-bearing estimate must state its property over the whole input domain, not at two sample values** — sampling proves the two samples, which is how a singular slipped through a helper whose author had checked it. Mutation-restore each defect the sweep found and confirm each one turns it red. **Corollary already earned here:** a count-bearing string built OUTSIDE the copy module (`{n} {n === 1 ? 'checklist' : 'checklists'}` inline in a component) is invisible to the corpus sweep however correct it is today — put it in the module.

- **A displayed whole-percent share for a NONZERO count must never render a bare rounded "0%" (v0.5.79).** Route share display through `fmtSharePct(count, total)` (`lib/statsFormat.ts`) — "<1%" for a nonzero share that rounds to zero, honest "0%" only for a truly zero count — never raw `Math.round(count/total*100)`.

- **A share BREAKDOWN -- rows of one whole whose displayed percentages must sum to 100% -- reuses the shaped-rows contract in `lib/subspeciesExplorer.ts`, never a re-derived rounding (v1.0.6).** The shaping is one tested rule set: percentages in integer tenths computed from exact counts (no float accumulation), a 0.1% floor for every nonzero row, the rounding residue of either sign (including residue the floor creates) absorbed by the largest row so the display sums to exactly 100.0, and a single row rendered as a flat "100%". Today it is reached through that module's breakdown/explorer derivations; a new breakdown surface exports/extracts its `shapeRows` rather than re-deriving these rules. `fmtSharePct` above stays the contract for a LONE share figure -- two different jobs: a display-true partition versus one honest number.
