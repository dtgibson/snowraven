# SnowRaven release runbook

## Device boundary (user direction, 2026-09-26)

Agents work on the developer Mac and its local simulators only. Never
discover, query, pair, install on, or otherwise access any physical,
production, or personal device, including Hydra and Telesto; do not access
other machines for testing. Do not assume which devices the user has. The
historical exact-uploaded-build launch check before App Store submission is
performed by the user after an explicit request with exact steps, and the
result is recorded as the user reports it. It is not a prerequisite to a
TestFlight upload. The 1.0.37 splash release was authorized for TestFlight
only, with no App Store submission; 1.0.38 took it to the App Store as a
full all-platforms release. This direction overrides conflicting device
instructions below.

Moved verbatim from CLAUDE.md's release sections (2026-08-26, /doctor context cleanup) so the mechanics load at ship time instead of riding every session. The always-resident rules stay in CLAUDE.md's `## Versioning` section: bump BOTH version files, changelog on every bump, the dev-only exemption, run `release.sh` (never `gh release create`), the updater relaunch contract, the all-platforms rhythm, the cross-platform Rust deps rule, and the opaque iOS icon rule. Everything below is the how.

### macOS desktop (`release.sh`)

- **macOS ships a UNIVERSAL binary (v0.5.5+).** `release.sh` builds `--target universal-apple-darwin`, so one DMG (`SnowRaven_<ver>_universal.dmg`) and one updater bundle (`SnowRaven.app.tar.gz`) run on both Apple Silicon and Intel. With an explicit `--target`, Tauri nests the bundle under the target triple — `$CARGO_TARGET_DIR/universal-apple-darwin/release/bundle/...`, not `release/bundle/...`. The build needs BOTH Rust targets installed (`rustup target add aarch64-apple-darwin x86_64-apple-darwin`); `release.sh` preflights this and aborts with the install command if either is missing.
- **`release.sh` Intel arch:** `latest.json` maps BOTH `darwin-aarch64` and `darwin-x86_64` to the one universal updater bundle (same URL, same signature). The Intel key must be exactly `darwin-x86_64` — Tauri's `updater_arch()` returns `"x86_64"` on Intel, so mapping it to `"x64"` means Intel users never see any update as available.
- **`createUpdaterArtifacts: true` is required in `tauri.conf.json`** — `@tauri-apps/cli` v2.11.2+ defaults this to `false`. Without it, `tauri build` creates the `.app` and `.dmg` but skips the `.app.tar.gz` updater bundle entirely. The setting must be in `bundle.createUpdaterArtifacts`.
- **`release.sh` version guard:** After the build, `release.sh` reads `CFBundleShortVersionString` from the bundle's `Info.plist` and aborts if it doesn't match `tauri.conf.json`. This catches stale-artifact issues before anything is uploaded to GitHub.
- **The release machine MUST be on the pinned Node (`.nvmrc` = 24; `frontend/package.json` `engines.node >= 20.19`), and `release.sh` is self-healing (mac-release-build-blocked post-mortem).** A bleeding-edge/non-LTS Node (e.g. 25) crashes `npm ci` with npm's internal `Exit handler never called!` (npm/cli#8766) — this blocked the 0.5.45 release for days on a Mac that had drifted to Node 25, while the build VM (Node 24) and Windows CI (Node 20) installed the identical lockfile fine. `release.sh` now runs `npm ci` ITSELF at BOTH the repo root AND `frontend` (the **root** install provides the `tauri` CLI that `npm run desktop:build` resolves from root `node_modules/.bin` — a frontend-only install dies with `tauri: command not found`), and preflights — loudly, each naming its remedy — the required tools, the Node version against `.nvmrc`, `gh auth`, npm-registry + GitHub reachability, and a clean working tree, all BEFORE the slow build. Dev and releases now run on ONE machine — **Hephaestus**, the single dev+release Mac (the build VM and the old release Mac are retired); Node 24 is the nvm default wired into its `~/.zprofile`, which the `zsh -lc` login shell sources, so its whole release job is just `zsh -lc ./release.sh` — no manual `nvm use`, and no separate manual `npm ci` (release.sh runs the root + frontend installs itself). Homebrew's `node` on Hephaestus is 26 and is deliberately NOT used for this project. Dry-run the portable half (preflight + `npm ci`) with `CHECK_ONLY=1` (other knobs: `SKIP_NPM_INSTALL`, `ALLOW_DIRTY`, `ALLOW_NODE_MISMATCH`, `ALLOW_NPM_INSTALL_FALLBACK`). The signing/notarization/`latest.json` logic is unchanged. Bump `.nvmrc` deliberately (a logged decision) on any toolchain move.
- **`release.sh` forces Tauri's DMG build into `CI=true` itself** so non-GUI automation always passes `--skip-jenkins` and never enters Finder AppleScript (`osascript`), which otherwise times out with `failed to run bundle_dmg.sh`. The raw DMG is then styled headlessly by injecting the committed `.DS_Store` (`src-tauri/dmg/dmg-DS_Store`, captured from a prior styled release) with `hdiutil`. Regenerate that template only if the DMG's volume name or item names change. The release command is simply `zsh -lc ./release.sh`; `SKIP_NPM_INSTALL=1 zsh -lc ./release.sh` is the warm-tree shortcut.
- **iCloud entitlements and embedded profile (v1.0.11, icloud-sync).** The Mac app ships with the restricted iCloud entitlements (`src-tauri/entitlements.icloud.plist`: the three `com.apple.developer.icloud-*` / `ubiquity-container-identifiers` keys for the container `iCloud.com.dtgibson.snowraven`, plus the `application-identifier` / `team-identifier` keys Tauri's codesign does not inject) AND a Developer ID provisioning profile embedded at `Contents/embedded.provisionprofile`, which is what authorizes those keys on a Developer ID build. The two are PAIRED by a release-time overlay, never by the committed config: `release.sh` copies the profile from `~/.tauri/snowraven-developerid.provisionprofile` (never in the repo) to the gitignored `src-tauri/embedded.provisionprofile`, builds with `--config tauri.icloud.conf.json` (which points `bundle.macOS.entitlements` at the iCloud plist and maps the copy through `bundle.macOS.files`), and removes the copy on every exit path. A plain `npm run desktop:build` or a `tauri dev` binary therefore has neither and lands in Settings' "This build cannot use iCloud" state by design (the app probes its own entitlement with `SecTaskCopyValueForEntitlement` and checks for the profile file). Two checks guard the ship: the PREFLIGHT dies if the profile is missing, does not decode (`security cms -D`), is for an App ID other than `<TEAMID>.com.snowraven`, lacks the container, or has expired; the POST-BUILD check (before DMG styling, so it covers the updater `.app.tar.gz` too) dies if `Contents/embedded.provisionprofile` is absent, if `codesign -d --entitlements` does not list all three iCloud keys and the container, or if `codesign --verify --deep --strict` fails. The preflight reads the two dotted entitlement keys with `/usr/libexec/PlistBuddy -c 'Print :Entitlements:...'`, never `plutil -extract`, which reads every dot in a key name as a path separator and returned nothing for `com.apple.application-identifier`, so the first preflight died on the correct profile (QA round 1); any change to that block is run verbatim against the real profile before it ships, because `CHECK_ONLY=1` skips it and the suite never sees it. **Renewal rule:** the profile expires with the Developer ID certificate; when the preflight reports expiry, regenerate the "Developer ID Application" profile for `com.snowraven` in the portal (Certificates, Identifiers & Profiles), download it to the path above, and re-run. **Portal prerequisites (one-time, human; done before the first iCloud release):** the explicit macOS App ID `com.snowraven` registered (if the portal rejects it as taken by another team, STOP: a macOS bundle-id change moves the app data directory and breaks the shipped updater, and needs a decision); the iCloud container `iCloud.com.dtgibson.snowraven` created (portal UI only; no public ASC API creates a container); iCloud enabled on BOTH App IDs (`com.snowraven` and `com.dtgibson.snowraven`) with the container assigned to each (assignment is portal UI); the Developer ID Application profile created and downloaded. **iOS half:** `src-tauri/gen/apple/snowraven_iOS/snowraven_iOS.entitlements` carries the same three iCloud keys (no application-identifier keys; Xcode injects them), so the App Store profile must carry the iCloud capability, and on this account Xcode CANNOT regenerate it: the Xcode-managed "iOS Team Store Provisioning Profile: com.dtgibson.snowraven" predates the capability, and its automatic repair tries to mint a cloud-managed Apple Distribution certificate, which BOTH API keys are refused (hit with `BVVLBRRVL6` and again with `QJA25M7XHM` on the 1.0.11 ship). **The wording of that refusal has CHANGED and grepping for the old string finds nothing.** Through 1.0.15 it read `FORBIDDEN_ERROR` resultCode 7495, "You haven't been given access to cloud-managed distribution certificates"; on the 1.0.16 ship the same refusal, from the same cause and with the same remedy, surfaced only as **`Cloud signing permission error`** with no `FORBIDDEN_ERROR` and no resultCode anywhere in the log. Expect either wording; neither is new, and neither is worth chasing. **A third wording arrived at the 1.0.42 ship, from the same step and with the same remedy:** "No Account for Team" and "No profiles found". `-allowProvisioningUpdates` is therefore closed, not a convenience. The working path is a MANUAL App Store profile plus a manual-signing export, the "iCloud-era export" bullet in the iOS section below. `Info.plist` / `Info.ios.plist` deliberately carry NO `NSUbiquitousContainers` (the container is hidden from Finder and the Files app in v1). Windows CI (`windows-build.yml`) is untouched: `bundle.macOS.*` is ignored there and `src/icloud.rs` does not compile on Windows.
- **The final styled DMG bytes are signed before notarization (v1.0.28; reverses the v0.5.74 unsigned-container decision).** The `.DS_Store` styling step re-converts the image after Tauri's first signature and therefore removes that signature. Apple can still accept and staple the converted image because the app inside is signed, but Gatekeeper's `spctl -a -t open --context context:primary-signature` rejects the downloaded DMG as `source=no usable signature`. `release.sh` now signs the exact post-styling image with a secure timestamp, verifies it, and only then submits and staples it. After publish, independently download the GitHub asset and require all three checks: `codesign --verify --verbose=2`, `xcrun stapler validate`, and `spctl -a -t open --context context:primary-signature -vv` reporting `accepted` / `Notarized Developer ID`. The updater's separate minisign signature remains unchanged.

- **After a Hephaestus reboot, the login keychain is LOCKED for remote (SSH/tailnet) sessions — every signing step fails until the USER unlocks it (v0.5.73 ship).** Symptoms: `codesign`/`xcodebuild -exportArchive` dies with `errSecInternalComponent`, `security show-keychain-info` says "User interaction is not allowed," and git's osxkeychain helper fails with `-25308`. The fix is once per reboot: the user runs `security unlock-keychain ~/Library/Keychains/login.keychain-db` in THEIR OWN terminal on the machine (a second ssh is fine). Claude cannot collect the password — the in-chat `!` command has no interactive TTY, so `security` reads EOF and fails without ever prompting; never ask for the password in chat. Check `security show-keychain-info` before a ship to catch this up front. (For git pushes, `git -c credential.helper='!gh auth git-credential' push …` sidesteps the keychain entirely.)
- **`release.sh` builds into ONE fixed `CARGO_TARGET_DIR`, `~/.snowraven-build`, shared by every checkout on the machine, worktrees included, so two desktop releases must never overlap (v1.0.38, the first ship from a worktree).** The universal bundle directory and the fixed-name updater bundle `SnowRaven.app.tar.gz` and its `.sig` live under it, so a second run started while another is building, signing or uploading can overwrite the first run's artifacts. Run one desktop release at a time on the release Mac. The iOS build is not shared this way: it uses the checkout's own `src-tauri/target`, which is why a worktree's first iOS build compiles from cold (see the swift shim below).
- **`release.sh` runs `touch src-tauri/src/main.rs` to force a Cargo relink, so a running `npm run desktop:dev` watcher will rebuild and RELAUNCH the dev app mid-release (v0.5.74 ship).** Harmless — the dev app and the release build use separate target dirs, and the release is unaffected — but it looks alarming if unexplained, and it matters when a live preview is being shown to the user during a ship: their app window will disappear and come back on its own. Either quit the dev watcher before releasing, or tell the user to expect the relaunch. Don't chase it as a crash.

### Windows desktop release (v0.4.0+)

- **Windows builds run in GitHub Actions** (`.github/workflows/windows-build.yml`, `windows-latest`), triggered by pushing a `v*` tag. The build uses a *throwaway* signing key (discarded) only so Tauri produces the artifacts; `release.sh` re-signs locally with the real key. The real minisign key never goes to GitHub — same keep-it-local stance as the Apple credentials.
- **`release.sh` is the single multi-platform assembler.** It builds + notarizes macOS, then `gh run download`s the CI Windows installer, signs it locally, and writes ONE `latest.json` with both `darwin-aarch64` and `windows-x86_64` entries. `SKIP_WINDOWS=1` publishes macOS-only (emergencies).
- **Release rhythm:** bump version (with `bundle.android.versionCode`) → commit → push to main → push the `vX.Y.Z` tag (starts Windows CI and Android CI) → wait for both → run `./release.sh` → **sign the Android CI APK, get the user's device check of those exact bytes, and attach it** (see the Android section below) → **ship the iOS TestFlight build for the same version** (see the iOS section below) → **submit that same uploaded build for App Store review** (also below). The tag must be pushed *before* `release.sh` so the CI artifacts exist to fetch, and it is also the commit F-Droid builds from. **A release goes to ALL available platforms, every time (user direction, v0.5.78; the App Store became a standing leg at 1.0.0)** — `release.sh` covers macOS + Windows + `latest.json`, the Pages workflow covers the website, the Android APK attach and the iOS TestFlight upload are the manual legs, F-Droid builds and publishes its own APK from the tag, and the App Store submission rides the TestFlight build; a release is not done until it has shipped and been submitted.
- **`release.sh` PINS the Windows CI query to the tag's commit (`--commit <tag sha>`) whenever the tag exists locally (v1.0.40, `e99b3b8`).** At the 1.0.40 ship the unpinned `--status success --limit 1` returned month-old runs on some calls, and only the filename guard stopped a 0.5.91 installer after the macOS build had already been notarized. The pin closes that case and the re-pushed-tag case below. The paragraph below still describes the unpinned fallback, which runs only when the tag is not present locally. **Pin a lookup made BY HAND during the CI wait the same way (v1.0.42):** seconds after CI finished, an unpinned query returned an old run (`32255425533`) while the pinned one returned the tag's run (`36904871606`), so check CI with `gh run list --workflow windows-build.yml --commit <tag sha>`.
- **A re-pushed `vX.Y.Z` tag leaves a stale successful Windows CI run that `release.sh` can mis-select (0.5.34 post-mortem).** `release.sh` picks the Windows installer from the most-recently-*created* successful `windows-build.yml` run (`gh run list --workflow windows-build.yml --status success --limit 1`), and its only guard checks the installer *filename* contains the version — which CANNOT distinguish two runs of the same version. If the tag was moved (a false-start: tag pushed at commit A, then re-pointed to commit B), the first push's run for orphaned commit A stays a *successful* run; if A's run is newer-created than B's, or B's run hasn't finished yet, `release.sh` silently ships A's binary (the version-filename guard passes either way). **Standing check before running `release.sh` after any tag re-push:** verify the selected run's commit equals the tag commit — `gh run list --workflow windows-build.yml --status success --limit 1 --json databaseId,headSha` and confirm `headSha == git rev-parse vX.Y.Z^{commit}`. You can't cancel a run that already completed; rely on the create-order (the correct re-push is newer) and wait for *that* run to go green before releasing.
- **The Windows updater target is the NSIS installer itself (`*-setup.exe`), NOT a `.nsis.zip`.** Tauri v2 signs the installer (`.exe.sig`) for updates on Windows; there is no separate archive. The `latest.json` `windows-x86_64.url` points to the `-setup.exe`.
- **`tauri signer sign`: don't pass `--private-key-path` (`-f`) when `TAURI_SIGNING_PRIVATE_KEY` is already exported** — the env key and the path flag are mutually exclusive. `release.sh` exports the env key for the macOS build, so the Windows-install signing step relies on the env, no flags.
- **Building the iOS archive during the CI wait cancels the tag commit's `Pipeline` run, and that is expected (v1.0.29).** `pipeline.yml` runs under a `cancel-in-progress` concurrency group, so the iOS stamp push that follows the tag within minutes cancels the run on the tag commit (`34727465631` at 1.0.29, its Backend job already green, Frontend cut mid-run) and starts the successor on the stamp commit (`34727719196`), which is the run of record for the shipped tree. Verify THAT run, not the cancelled one, and say so in the deployment record; `windows-build.yml` and `pages.yml` are keyed to the tag and unaffected, and `release.sh`'s Windows selection guard still checks the tag commit.
- **Windows is distributed unsigned** (no Authenticode) for now — first launch shows a SmartScreen "unknown publisher" prompt. The in-app updater is unaffected (minisign verification, not Authenticode).

### iOS release (TestFlight + App Store)

- **After the TestFlight upload, the SAME uploaded build is submitted for App Store review (standing leg since 1.0.0; FR-22 of ios-app-store-release).** **PRECONDITION, STANDING SINCE v1.0.31: install that exact uploaded build on a real device and OPEN it before submitting anything.** 1.0.31.1 was submitted having never run on hardware and crashed on launch every time; the release-only tao use-after-free behind it was invisible to 6,269 frontend tests, 636 backend tests, both CI jobs, the iOS 27 simulator and `--validate-app`, which checks icons and entitlements rather than whether the app runs. The submission then had to be withdrawn to `DEVELOPER_REJECTED` before Apple could approve it, because the record's `releaseType` was AFTER_APPROVAL and an approval would have auto-released a crashing app to every user. A TestFlight install of the uploaded build takes minutes and is the only check that covers this. Then the submission itself, a manual App Store Connect action by the account holder: select the just-uploaded build for the version, confirm the metadata matches `appstore/LISTING.md` (the committed source of truth for every listing field, the privacy label, and the compliance answers), paste the review notes from `appstore/REVIEW_NOTES.md` verbatim (the review posture is key-free: no API key of any kind is supplied to Apple or committed to the repo; user decision 2026-08-25), and submit. Release **immediately on approval, no phased rollout** (phasing serves large installed bases; delaying a privacy-first app's fixes serves no one). **A rejection stalls ONLY the App Store leg**: it becomes a fix-forward item in the next release, and desktop, web, and TestFlight are never rolled back or delayed by Apple's review latency. Screenshots regenerate via `website/tools/capture-appstore.mjs` (synthetic demo data via `SR_DATA_DIR`, committed under `appstore/screenshots/`) whenever the photographed UI changes; unchanged screenshots do not need re-uploading per release.
- **CREATING a submission has MOVED (corrected v1.0.4).** `POST /v1/appStoreVersionSubmissions` now returns **403 FORBIDDEN_ERROR, "The resource 'appStoreVersionSubmissions' does not allow 'CREATE'. Allowed operation is: DELETE"**. The flow is now: `POST /v1/reviewSubmissions` (platform IOS + app relationship) -> `POST /v1/reviewSubmissionItems` (reviewSubmission + appStoreVersion) -> `PATCH /v1/reviewSubmissions/{id}` with `attributes.submitted = true`. **WITHDRAWING is unchanged** and still uses `DELETE /v1/appStoreVersionSubmissions/{versionId}`, which moves the version from `WAITING_FOR_REVIEW` to `DEVELOPER_REJECTED` (the editable state). To replace an in-review version: withdraw, PATCH the SAME version record's `versionString`, PATCH `relationships/build`, replace screenshots, then submit via the new flow -- the version record keeps every listing field.
- **Screenshot replacement is ORDER-SENSITIVE: replace a whole set, never a subset.** `DELETE /v1/appScreenshots/{id}` then re-uploading APPENDS to the end of the set, so swapping only the changed images scrambles the listing order. Per image: `POST /v1/appScreenshots` (fileName + fileSize + set relationship) -> PUT each returned `uploadOperations` part -> `PATCH` with `uploaded: true` and the file's **md5** as `sourceFileChecksum`. Poll `assetDeliveryState.state` until `COMPLETE` before submitting.
- **ASC metadata and submission can be driven via the App Store Connect REST API (how the 1.0.0 listing was entered and submitted), with three durable facts:** the metadata-capable API key is `QJA25M7XHM` — the env-default `BVVLBRRVL6` is upload-only and 403s on every metadata write; and the privacy nutrition label CANNOT be set via API (the appDataUsages endpoint family is retired, 404 PATH_ERROR), so a privacy-label change is an App Store Connect UI action by the account holder. And `GET /v1/apps/{id}/builds` REJECTS the `sort` parameter (`PARAMETER_ERROR.ILLEGAL`): list builds with `GET /v1/builds?filter[app]={id}&sort=-uploadedDate` instead. The 1.0.18 ship's version-listing helper had the relationship form and printed no build rows at all, with no error line, for exactly this reason (v1.0.18). **A NEW version record does not carry every listing field: read each one back before submitting (v1.0.35, again at v1.0.42).** The description, keywords and URLs carried over from the previous record, but the promotional text arrived EMPTY both times and was restored from `appstore/LISTING.md`. Compare every field against `LISTING.md` rather than assuming the new record inherited it.
- **Every desktop/web release is followed by an iOS TestFlight build of the SAME version, build 1 (standing rule since v0.5.78; user direction).** iOS is no longer a selective catch-up — run the recipe below after `release.sh` verifies, on every release, bundled Spool releases included. iOS-only follow-ups still increment the build number without a desktop release.
- **iOS app icons must be fully OPAQUE — NO alpha channel — or App Store Connect rejects the upload (altool error 90717).** The check is on the large 1024 app icon and it fires on *any* alpha channel, even a fully-opaque/redundant one (the SR icons carried an all-opaque alpha with anti-aliased edges and were still rejected on the first upload). Keep BOTH `src-tauri/icons/ios/` AND the committed `gen/apple` AppIcon.appiconset (`src-tauri/gen/apple/Assets.xcassets/AppIcon.appiconset/`) flattened to opaque RGB — composite onto white and save with NO alpha (all 18 PNGs). The desktop icons (`tauri.conf.json` `bundle.icon`, `src-tauri/icons/icon.png`) MAY keep their alpha — this rule is iOS-only. `gen/apple` is a committed generated artifact, so the flattened icons must be committed there (re-running `tauri ios init` would re-stamp Tauri's placeholders — don't rely on init). Precedent: the v0.5.68 iOS icon fix (`e070d73` icon swap + `21fd5b2` flatten).
- **iOS build + TestFlight upload is Claude's to run (same posture as `release.sh`), and is NOT `release.sh`** (that assembler is macOS + Windows desktop only). The recipe (full detail + fallback in `pipeline/mobile-app/how-to-see.md`): `tauri ios build` SCRUBS `DEVELOPER_DIR` from the `xcodebuild`/`xcrun` it spawns, so build through the `/tmp/xcshim` wrapper (`printf` the two shim scripts that re-export `DEVELOPER_DIR` and `exec` the real tool, `chmod +x`, then `PATH=/tmp/xcshim:$PATH`) AND `export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer` in the parent shell. Do NOT `sudo xcode-select` (it needs a password). Build the TestFlight archive with `--export-method app-store-connect --build-number N`, then upload with `xcrun altool --upload-app -f <ipa> -t ios --apiKey $APPLE_API_KEY_ID --apiIssuer $APPLE_API_ISSUER_ID` (the App Store Connect API key + issuer live in the login shell / `~/.appstoreconnect/private_keys/`). **The upload shell needs `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer` exported too, or bare `xcrun` cannot find `altool`** ("not a developer tool or in PATH", hit on the 0.5.93 ship) — the shim only covers the build; export it in the upload command's own shell as well. An iOS-asset-only change (like the icon fix) does NOT bump the desktop version — it ships as an iOS build-number increment against the current version (v0.5.68 build 2), no `release.sh`, no tag, no `latest.json`.
- **THERE IS NO TESTFLIGHT-ONLY PATH AGAINST A *RELEASED* VERSION STRING, and the bullet above is conditional on that (v1.0.30, apple-platform-readiness).** Once a version record reaches `READY_FOR_SALE`, Apple closes that version's train to **every** new build, TestFlight included -- `altool --validate-app` refuses with **90186** "train version 'X' is closed for new build submissions" plus **90062** "CFBundleShortVersionString must contain a higher version than the previously approved version". So the build-number increment above works only while the current version is UNRELEASED (still in review, or never submitted); against a released one the only routes are a version bump or letting the fix ride the next version that gets a record. **Check the version record's `appStoreState` BEFORE choosing the route, not after building the archive.** The 1.0.30.2 ship was authorized on the reasoning that a released version merely could not take a new *store* build and that TestFlight would still accept one; that reasoning is wrong, and the whole route was unexecutable. Note the narrow escape hatch is closed too: an iOS-only bump to the next patch fails the repo's own guard that the stamped iOS version never LEADS the app version. `--validate-app` is what made this a one-minute discovery instead of a consumed upload.
- **THE AGE-RATING DECLARATION CANNOT BE ANSWERED AHEAD OF A RELEASE -- it is gated behind an editable app-info record, so it is a step INSIDE preparing the next version, never a prerequisite you clear in advance (v1.0.30, measured).** The app has ONE `appInfos` record; while it is `READY_FOR_SALE` the whole App Information page is read-only in the UI **and** `PATCH /v1/ageRatingDeclarations/{id}` refuses with **409 `STATE_ERROR`, "This age rating declaration is not editable. Is the corresponding AppInfos editable?"** A new editable record appears only once a version is in preparation. So the 2026 social-media questions (`socialMediaAgeRestricted` was the unanswered field here, with `socialMedia` already `false`) are answered AFTER the version record exists and BEFORE submitting it -- do not schedule them as pre-release homework and do not read "nothing on this page is editable" as a permissions problem. `kidsAgeBand` and `developerAgeRatingInfoUrl` read null on a non-Kids app and are not blockers.
- **ALWAYS run `xcrun altool --validate-app` before `--upload-app` (standing step since the 1.0.14 ship).** Same file, same flags, same credentials as the upload itself (`-f <ipa> -t ios --apiKey $APPLE_API_KEY_ID --apiIssuer $APPLE_API_ISSUER_ID`, with `DEVELOPER_DIR` exported in that shell too, per the bullet above). It runs Apple's ingestion checks WITHOUT consuming the upload, takes about a minute, and fails loudly on precisely the two things that otherwise cost a whole cycle to discover after the fact: an icon carrying any alpha channel (altool error 90717) and a missing or unqualified entitlement. A clean run prints `VERIFY SUCCEEDED with no errors`, which is what 1.0.14 build 1 returned immediately before its successful upload. It is cheap enough that it is never worth reasoning about whether this particular ship needs it: run it every time. **What it does NOT check is whether the app launches** (v1.0.31) -- see the device-install precondition on the submission bullet above.

- **A THIRD SHIM, `/tmp/xcshim/swift`, IS REQUIRED SINCE SWIFT 6.4 (Xcode 27; first needed at the 1.0.38 ship).** Tauri and each iOS-capable plugin (clipboard-manager, dialog, geolocation, opener) compile a Swift package from a Cargo build script through swift-rs 1.0.7, which runs `swift build --sdk <iPhoneOS SDK> ... -Xswiftc -target -Xswiftc arm64-apple-ios16.0 -Xcc --target=arm64-apple-ios16.0`. Swift 6.4's `swift build` defaults to the new `swiftbuild` engine, which ignores those per-tool target flags and builds and links the package for macOS. The Rust compile then dies at `failed to run custom build command for tauri v2.11.2` with `ld: building for 'macOS'` and a cascade of macOS-SDK header errors (`CoreServices/CSIdentityBase.h`, `OpenGLES/EAGL.h`, `UIKit/NSAttributedString.h` not found).  
  ```sh
  printf '%s\n' '#!/bin/sh' 'export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer' 'if [ "$1" = "build" ]; then' '  shift' '  exec /usr/bin/swift build --build-system native "$@"' 'fi' 'exec /usr/bin/swift "$@"' > /tmp/xcshim/swift && chmod +x /tmp/xcshim/swift
  ```
  `/tmp/xcshim` must come FIRST on the build's `PATH`, since swift-rs runs a bare `swift`. After a failed cold attempt, delete `src-tauri/target/aarch64-apple-ios/release/build/tauri-*/out/swift-rs` before retrying. **Verify the output rather than trusting the shim:** every `out/swift-rs/**/lib*.a` under `src-tauri/target/aarch64-apple-ios/release/build/` must report `platform 2` (iOS) in `otool -l`'s `LC_BUILD_VERSION`, and `xcrun vtool -show-build` on the archived app's executable (`.../SnowRaven.app/SnowRaven`) must report `platform IOS`; both held at 1.0.38 build 1. SwiftPM marks `--build-system native` deprecated, so this is a bridge, not a fix. **Removal condition:** when swift-rs, or the Tauri release that pins it, builds a correct iOS package under Swift 6.4's default build system, drop the shim and confirm, from a cold `src-tauri/target`, that the same `platform 2` and `platform IOS` checks still hold.

### Android (F-Droid + GitHub APK)

The Android app (`com.dtgibson.snowraven`, Android 8.0 and later) ships two ways, and Google Play is not a channel (user direction, 2026-10-03): **F-Droid**, which builds the app from the tagged source on its own server and signs that APK with F-Droid's key, and a **universal APK signed with the user's key and attached to the GitHub release**. One build, three machines: CI builds the unsigned release universal APK from the tag, the release Mac signs that exact artifact and attaches it, and F-Droid's server builds its own from the same tag with the same script. The Mac never builds the shipped APK; its local builds are for emulator checks. The Android app has no updater and never contacts GitHub, so `release.sh` and `latest.json` carry nothing for it. The mechanics and their reasons are in `pipeline/android-release/schema.md` sections 3.3, 3.7, 3.8, 6 and 8; the release Mac's install log is `pipeline/android-release/toolchain.md`. Where that log and this section disagree, this section and `scripts/android/toolchain.env` win.

- **The toolchain pins live in ONE file, `scripts/android/toolchain.env`, and change together, deliberately.** Rust 1.96.1 with `aarch64-linux-android`, `armv7-linux-androideabi` and `x86_64-linux-android`; `tauri-cli` 2.11.2 (equal to `@tauri-apps/cli` in `package-lock.json`); Gradle 8.14.3; NDK 27.2.12479018 (r27c); JDK 17; Node 20; SDK platform 36; build-tools 36.0.0. CI reads the file, the release Mac reads it, and the F-Droid recipe repeats it as literals because a recipe cannot read the repository before its clone; `fdroidRecipe.test.ts` holds the recipe equal to the file. Rust is pinned here while Windows builds on `stable` because F-Droid may build a tag months later, when `stable` names a different compiler, and CI pins the same so a green CI run is evidence the recipe compiles. **A pin change also needs an fdroiddata recipe edit, by merge request, before the first tag that uses it:** F-Droid's bot makes each new `Builds` entry by copying the previous one, so the published recipe keeps the old `sudo:` literals until someone changes them there. The release Mac's build shell needs these exports (not yet in `~/.zprofile`):
  ```sh
  export JAVA_HOME=/opt/homebrew/opt/openjdk@17/libexec/openjdk.jdk/Contents/Home
  export ANDROID_HOME="$HOME/Library/Android/sdk"
  export NDK_HOME="$ANDROID_HOME/ndk/27.2.12479018"
  export PATH="/opt/homebrew/opt/openjdk@17/bin:$ANDROID_HOME/platform-tools:$ANDROID_HOME/emulator:$ANDROID_HOME/cmdline-tools/latest/bin:$PATH"
  ```
  plus Gradle 8.14.3 on `PATH` as `gradle` (Homebrew `gradle@8` or the official `gradle-8.14.3-bin.zip` under `~/.tauri/gradle-8.14.3`; `gradle --version` must report 8.14.3, since AGP 8.11.0 needs 8.13 or later and does not support Gradle 9), `cargo-tauri` from `cargo install tauri-cli --version 2.11.2 --locked`, and fdroidserver in a venv (`python3 -m venv ~/.fdroid-venv && ~/.fdroid-venv/bin/pip install fdroidserver`) for the local tooling run below. **Keep exactly ONE NDK under `$ANDROID_HOME/ndk`:** the Tauri CLI's `ensure_ndk` ignores `NDK_HOME` and takes the highest version it finds there, so a second, newer NDK silently replaces the pin. On F-Droid's image, which may carry several, the pin is therefore advisory; that is recorded, not worked around.
- **ONE build entry, run identically on CI, the release Mac and F-Droid's server: `npm --prefix frontend ci && npm --prefix frontend run build`, then `sh scripts/android/build-apk.sh`.** The frontend is its own step everywhere because F-Droid runs it in `prebuild`, before its source scan, and deletes `node_modules` afterward. The script writes the `gradlew` shim if it is missing, runs `cargo tauri android build --ci --apk --target aarch64 armv7 x86_64 --config '{"build":{"beforeBuildCommand":null}}'`, and stops unless exactly one APK sits in `src-tauri/gen/android/app/build/outputs/apk/universal/release/` (the Windows artifact-selection lesson). The output is one UNSIGNED release universal APK (arm64, 32-bit ARM, x86_64) and no AAB, since nothing consumes one. **Never build with bare Gradle:** Gradle's `rustBuild*` tasks call the Tauri CLI's `android-studio-script`, which reads its options from a WebSocket the parent `tauri android build` hosts and panics without it, so `gradle assembleUniversalRelease` (and F-Droid's `gradle:` build method) cannot build this app on any machine. **And never through the npm CLI:** the committed `BuildTask.kt` names `cargo tauri`, because on F-Droid's server the only Tauri CLI that may take part is one compiled from crates.io, so every machine runs the same `cargo install tauri-cli --version 2.11.2 --locked`; the npm CLI stays for desktop and iOS. **Gradle comes from `PATH`, never from a wrapper download:** no wrapper jar is committed (F-Droid's scanner deletes one by name with no checksum check), `gradlew` is a four-line shim that `exec`s `gradle`, and the version lives once, in `src-tauri/gen/android/gradle/wrapper/gradle-wrapper.properties`, which F-Droid's `gradlew-fdroid` reads.
- **The version code is `bundle.android.versionCode` in `src-tauri/tauri.conf.json`, moved with the version string at every bump: `major * 1000000 + minor * 1000 + patch` (1.0.49 is `1000049`).** F-Droid's update checker reads both values from that committed file at each tag through the recipe's `UpdateCheckData` regexes, and the CLI's own derivation would leave nothing committed to read. `androidVersionSource.test.ts` goes red on a code off the formula or a version that disagrees with `frontend/package.json`. The four-file version set stays four files, since `tauri.conf.json` is already one of them. **Android has no build number.** F-Droid keys a release on the version code and does not pick up a rebuild under a code it has already published, and Android will not install an APK over one with an equal code. So an Android-only rebuild of a shipped version has exactly the two routes a closed iOS train has: a full version bump, or letting the fix ride the next version.
- **The GitHub APK is signed on the release Mac with `apksigner`, from a keystore that lives outside the repository and never reaches GitHub (the Apple-key stance).** Paths and env names (schema 6.2): the keystore `~/.tauri/snowraven-android.p12` (PKCS12), named by `SNOWRAVEN_ANDROID_KEYSTORE`; its properties file `~/.tauri/snowraven-android-keystore.properties` (`storeFile`, `storePassword`, `keyAlias`, `keyPassword`; mode 0600), named by `SNOWRAVEN_ANDROID_KEYSTORE_PROPERTIES`. The committed signing block in `src-tauri/gen/android/app/build.gradle.kts` reads the properties file named by `SNOWRAVEN_ANDROID_KEYSTORE_PROPERTIES`, else the gitignored `src-tauri/gen/android/keystore.properties`, and creates a release signing config only when `storeFile` is set; with neither file the release build is UNSIGNED, which is what CI produces and what F-Droid signs itself. No password literal is ever written in that block (guarded). F-Droid signs its own build with its own key, so **the F-Droid APK and the GitHub APK do not update each other**: Android refuses an install over the other signer, and switching means uninstalling, which deletes the app's private storage (Help says so). Reproducible builds, which would let F-Droid publish the user-signed APK, are the recorded reversal and out of scope.

- **The release Mac's Android leg is three scripts, run in this order from the repository root in the build shell above, with each output kept for the ship record: `scripts/android/preflight.sh`, `sign.sh` and `attach.sh` (schema 6.2).** They share `scripts/android/release-lib.sh` (keystore resolution, the password handover, the `aapt2` and `apksigner` reads), and none of them changes `release.sh`'s preflight-build-notarize flow. Secrets come only from the two documented locations above: the properties file named by `SNOWRAVEN_ANDROID_KEYSTORE_PROPERTIES` (default `~/.tauri/snowraven-android-keystore.properties`) and the keystore named by `SNOWRAVEN_ANDROID_KEYSTORE` (default: the properties file's `storeFile`, else `~/.tauri/snowraven-android.p12`). A password goes only into a 0600 file in a private temp directory removed on exit and reaches `keytool` and `apksigner` by file, never as `--ks-pass pass:<password>`, which would write it into the session's command log. No script creates a keystore: a missing keystore or properties file prints the user step above and exits non-zero. `androidProjectPins.test.ts` holds the scripts to those rules (no keystore creation outside the printed step, passwords by file, no `gh release create` or `--clobber`, the device check before the upload).
  1. **Preflight:** `scripts/android/preflight.sh`. It lists every failure and exits non-zero before anything is signed, so nothing is attached. It checks JDK 17 on `PATH`; `apksigner`, `zipalign` and `aapt2` under `$ANDROID_HOME/build-tools/36.0.0`; `gradle --version` and `cargo tauri --version` equal to the `toolchain.env` pins (and the Gradle pin equal to `gradle-wrapper.properties`); the properties file at mode 0600, both files outside the repository, and the keystore opening with its password and alias (`keytool -list -storetype PKCS12 -storepass:file`); `tauri.conf.json`'s `version` equal to `frontend/package.json`'s and `bundle.android.versionCode` on the formula; the tag `vX.Y.Z` present locally, on `origin` at the same commit, and carrying the same version pair in its `tauri.conf.json` (a missing `changelogs/<versionCode>.txt` at the tag is a warning, since it costs only the F-Droid changelog); and the `android-build` artifact from the run PINNED to the tag's commit (`gh run list --workflow android-build.yml --status success --commit <tag sha>`, the Windows mis-selection lesson), which must hold exactly one APK, `SnowRaven_<version>_android_universal_unsigned.apk`, whose `aapt2 dump badging` reports `package: name='com.dtgibson.snowraven'`, the `versionName` and `versionCode` above, and no `application-debuggable`. The artifact lands in a fresh private directory (`mktemp -d` under the per-user `$TMPDIR`, mode 0700; there is no fixed `/tmp` work directory, because a shared path could have its file swapped between steps, security L2), and the last line printed is `UNSIGNED_APK=<path>`. Two toggles exist for dry runs and are never set on a ship: `ANDROID_APK=<path>` checks a local APK instead of downloading, and `SKIP_TAG_CHECK=1` skips the tag checks.
  2. **Sign:** `scripts/android/sign.sh <unsigned.apk> [<out.apk>]`, the output defaulting to `SnowRaven_<version>_android_universal.apk` inside another fresh private directory, printed as `SIGNED_APK=<path>`. It re-reads the input's package and version, then runs `zipalign -f -P 16 4` into a scratch file. **`-P 16`, not `-p`:** `-p` page-aligns the stored native libraries to 4 KB and would undo the 16 KB alignment AGP already gives them, which Android 15 and later need on 16 KB-page devices, and build-tools 36's `apksigner` page-aligns native libraries to 16 KB by default, so the two agree (measured: the CI-shaped APK passes `zipalign -c -P 16 4` before and after). Then `apksigner sign --ks-type PKCS12 --ks-key-alias <keyAlias> --ks-pass file:... --key-pass file:...` with apksigner's default schemes (v2 and v3 on a minSdk 26 APK; Android 8.0 verifies v2, and v1 is off). The signed file is moved into place only after `apksigner verify --print-certs`, `zipalign -c -P 16 4` and the version re-read pass, so a refused signature leaves no signed file. Before moving the file into place it reads the configured keystore's own certificate with `keytool -list -v` and refuses a signer that differs from it, so the first release is bound to the user's key exactly as every later one (security L2). It prints `Signer #1 certificate SHA-256 digest: ...`, `SIGNED_APK=` and `SIGNED_APK_SHA256=`; record the digest in the ship record. **Every release must print the same digest as the one before**, because a changed signer breaks the install-over path: from the second release on, set `SNOWRAVEN_ANDROID_SIGNER_SHA256` to the recorded digest and a different signer stops the script.
  3. **Attach**, only after the user's device check below: `ANDROID_DEVICE_CHECK=passed ANDROID_CHECKED_SHA256=<SHA-256 of the file the user checked> SNOWRAVEN_ANDROID_SIGNER_SHA256=<recorded digest> scripts/android/attach.sh <signed.apk>`, the input being the `SIGNED_APK=` path sign printed (no default); its file name is the asset name, `SnowRaven_<version>_android_universal.apk`. It refuses with no `ANDROID_DEVICE_CHECK` (`partial` is the no-device case, which is a written decision first), no `ANDROID_CHECKED_SHA256` (required on every run, not a warning), a file of any other name, a package or version mismatch, an APK that does not verify, one whose signer is not the configured keystore's own certificate (read with `keytool` on every run; the first release included), one signed by the Android debug key or by a certificate whose subject says `THROWAWAY` or `not for release`, a SHA-256 different from the checked file's, a missing `v<version>` GitHub release (`release.sh` creates it; this script never runs `gh release create`), and an existing asset of that name (no `--clobber`: replacing published bytes is a decision, not a re-run). Then `gh release upload v<version> <file>`, after which it downloads the asset back and compares SHA-256 with the local file. `DRY_RUN=1` runs every check and prints the upload instead.
