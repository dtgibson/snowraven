# SnowRaven release runbook

Moved verbatim from CLAUDE.md's release sections (2026-08-26, /doctor context cleanup) so the mechanics load at ship time instead of riding every session. The always-resident rules stay in CLAUDE.md's `## Versioning` section: bump BOTH version files, changelog on every bump, the dev-only exemption, run `release.sh` (never `gh release create`), the updater relaunch contract, the all-platforms rhythm, the cross-platform Rust deps rule, and the opaque iOS icon rule. Everything below is the how.

### macOS desktop (`release.sh`)

- **macOS ships a UNIVERSAL binary (v0.5.5+).** `release.sh` builds `--target universal-apple-darwin`, so one DMG (`SnowRaven_<ver>_universal.dmg`) and one updater bundle (`SnowRaven.app.tar.gz`) run on both Apple Silicon and Intel. With an explicit `--target`, Tauri nests the bundle under the target triple — `$CARGO_TARGET_DIR/universal-apple-darwin/release/bundle/...`, not `release/bundle/...`. The build needs BOTH Rust targets installed (`rustup target add aarch64-apple-darwin x86_64-apple-darwin`); `release.sh` preflights this and aborts with the install command if either is missing.
- **`release.sh` Intel arch:** `latest.json` maps BOTH `darwin-aarch64` and `darwin-x86_64` to the one universal updater bundle (same URL, same signature). The Intel key must be exactly `darwin-x86_64` — Tauri's `updater_arch()` returns `"x86_64"` on Intel, so mapping it to `"x64"` means Intel users never see any update as available.
- **`createUpdaterArtifacts: true` is required in `tauri.conf.json`** — `@tauri-apps/cli` v2.11.2+ defaults this to `false`. Without it, `tauri build` creates the `.app` and `.dmg` but skips the `.app.tar.gz` updater bundle entirely. The setting must be in `bundle.createUpdaterArtifacts`.
- **`release.sh` version guard:** After the build, `release.sh` reads `CFBundleShortVersionString` from the bundle's `Info.plist` and aborts if it doesn't match `tauri.conf.json`. This catches stale-artifact issues before anything is uploaded to GitHub.
- **The release machine MUST be on the pinned Node (`.nvmrc` = 24; `frontend/package.json` `engines.node >= 20.19`), and `release.sh` is self-healing (mac-release-build-blocked post-mortem).** A bleeding-edge/non-LTS Node (e.g. 25) crashes `npm ci` with npm's internal `Exit handler never called!` (npm/cli#8766) — this blocked the 0.5.45 release for days on a Mac that had drifted to Node 25, while the build VM (Node 24) and Windows CI (Node 20) installed the identical lockfile fine. `release.sh` now runs `npm ci` ITSELF at BOTH the repo root AND `frontend` (the **root** install provides the `tauri` CLI that `npm run desktop:build` resolves from root `node_modules/.bin` — a frontend-only install dies with `tauri: command not found`), and preflights — loudly, each naming its remedy — the required tools, the Node version against `.nvmrc`, `gh auth`, npm-registry + GitHub reachability, and a clean working tree, all BEFORE the slow build. Dev and releases now run on ONE machine — **Hephaestus**, the single dev+release Mac (the build VM and the old release Mac are retired); Node 24 is the nvm default wired into its `~/.zprofile`, which the `zsh -lc` login shell sources, so its whole release job is just `zsh -lc ./release.sh` — no manual `nvm use`, and no separate manual `npm ci` (release.sh runs the root + frontend installs itself). Homebrew's `node` on Hephaestus is 26 and is deliberately NOT used for this project. Dry-run the portable half (preflight + `npm ci`) with `CHECK_ONLY=1` (other knobs: `SKIP_NPM_INSTALL`, `ALLOW_DIRTY`, `ALLOW_NODE_MISMATCH`, `ALLOW_NPM_INSTALL_FALLBACK`). The signing/notarization/`latest.json` logic is unchanged. Bump `.nvmrc` deliberately (a logged decision) on any toolchain move.
- **Run `release.sh` from a non-GUI / automation context with `CI=true`** so Tauri passes `--skip-jenkins` and builds the DMG headless. Tauri's `bundle_dmg.sh` styles the disk-image window with Finder AppleScript (`osascript`), which needs a logged-in GUI session; without one the DMG step dies with `failed to run bundle_dmg.sh`. `CI=true` skips that GUI-only styling, so the raw DMG comes out unstyled — but `release.sh` then **re-applies the install-window layout headlessly**, injecting a committed `.DS_Store` (`src-tauri/dmg/dmg-DS_Store`, captured from a prior styled release, copied in with `hdiutil` right before notarization), so the shipped DMG is styled identically to an interactive build. Regenerate that template only if the DMG's volume name or item names change. **codesign/notarize/`latest.json` are unaffected** (they work cross-session). The seamless headless command is `CI=true SKIP_NPM_INSTALL=1 zsh -lc ./release.sh` (drop `SKIP_NPM_INSTALL=1` for a cold checkout). An interactive logged-in desktop run needs no flag (its Finder styling and the injected `.DS_Store` produce the same layout).
- **iCloud entitlements and embedded profile (v1.0.11, icloud-sync).** The Mac app ships with the restricted iCloud entitlements (`src-tauri/entitlements.icloud.plist`: the three `com.apple.developer.icloud-*` / `ubiquity-container-identifiers` keys for the container `iCloud.com.dtgibson.snowraven`, plus the `application-identifier` / `team-identifier` keys Tauri's codesign does not inject) AND a Developer ID provisioning profile embedded at `Contents/embedded.provisionprofile`, which is what authorizes those keys on a Developer ID build. The two are PAIRED by a release-time overlay, never by the committed config: `release.sh` copies the profile from `~/.tauri/snowraven-developerid.provisionprofile` (never in the repo) to the gitignored `src-tauri/embedded.provisionprofile`, builds with `--config tauri.icloud.conf.json` (which points `bundle.macOS.entitlements` at the iCloud plist and maps the copy through `bundle.macOS.files`), and removes the copy on every exit path. A plain `npm run desktop:build` or a `tauri dev` binary therefore has neither and lands in Settings' "This build cannot use iCloud" state by design (the app probes its own entitlement with `SecTaskCopyValueForEntitlement` and checks for the profile file). Two checks guard the ship: the PREFLIGHT dies if the profile is missing, does not decode (`security cms -D`), is for an App ID other than `<TEAMID>.com.snowraven`, lacks the container, or has expired; the POST-BUILD check (before DMG styling, so it covers the updater `.app.tar.gz` too) dies if `Contents/embedded.provisionprofile` is absent, if `codesign -d --entitlements` does not list all three iCloud keys and the container, or if `codesign --verify --deep --strict` fails. The preflight reads the two dotted entitlement keys with `/usr/libexec/PlistBuddy -c 'Print :Entitlements:...'`, never `plutil -extract`, which reads every dot in a key name as a path separator and returned nothing for `com.apple.application-identifier`, so the first preflight died on the correct profile (QA round 1); any change to that block is run verbatim against the real profile before it ships, because `CHECK_ONLY=1` skips it and the suite never sees it. **Renewal rule:** the profile expires with the Developer ID certificate; when the preflight reports expiry, regenerate the "Developer ID Application" profile for `com.snowraven` in the portal (Certificates, Identifiers & Profiles), download it to the path above, and re-run. **Portal prerequisites (one-time, human; done before the first iCloud release):** the explicit macOS App ID `com.snowraven` registered (if the portal rejects it as taken by another team, STOP: a macOS bundle-id change moves the app data directory and breaks the shipped updater, and needs a decision); the iCloud container `iCloud.com.dtgibson.snowraven` created (portal UI only; no public ASC API creates a container); iCloud enabled on BOTH App IDs (`com.snowraven` and `com.dtgibson.snowraven`) with the container assigned to each (assignment is portal UI); the Developer ID Application profile created and downloaded. **iOS half:** `src-tauri/gen/apple/snowraven_iOS/snowraven_iOS.entitlements` carries the same three iCloud keys (no application-identifier keys; Xcode injects them), so the App Store profile must carry the iCloud capability, and on this account Xcode CANNOT regenerate it: the Xcode-managed "iOS Team Store Provisioning Profile: com.dtgibson.snowraven" predates the capability, and its automatic repair tries to mint a cloud-managed Apple Distribution certificate, which BOTH API keys are refused (hit with `BVVLBRRVL6` and again with `QJA25M7XHM` on the 1.0.11 ship). **The wording of that refusal has CHANGED and grepping for the old string finds nothing.** Through 1.0.15 it read `FORBIDDEN_ERROR` resultCode 7495, "You haven't been given access to cloud-managed distribution certificates"; on the 1.0.16 ship the same refusal, from the same cause and with the same remedy, surfaced only as **`Cloud signing permission error`** with no `FORBIDDEN_ERROR` and no resultCode anywhere in the log. Expect either wording; neither is new, and neither is worth chasing. `-allowProvisioningUpdates` is therefore closed, not a convenience. The working path is a MANUAL App Store profile plus a manual-signing export, the "iCloud-era export" bullet in the iOS section below. `Info.plist` / `Info.ios.plist` deliberately carry NO `NSUbiquitousContainers` (the container is hidden from Finder and the Files app in v1). Windows CI (`windows-build.yml`) is untouched: `bundle.macOS.*` is ignored there and `src/icloud.rs` does not compile on Windows.
- **The shipped DMG *container* carries no code signature, BY DESIGN — a `codesign -dv` on the DMG reporting "not signed" is not a release regression (v0.5.74 ship).** The `.DS_Store` styling step above re-converts the disk image (`hdiutil convert` → UDRW, attach, inject the layout, detach, convert back to UDZO) *after* `tauri build` has signed it, which writes a NEW image file and drops the container signature. Everything that actually gates a user's download still holds: the converted DMG is what gets submitted to `notarytool` and `stapler staple`d (the styling deliberately runs BEFORE notarization so the ticket staples the final image), and the `.app` inside it is Developer-ID signed by the build. The signature the **updater** verifies is the minisign one on `SnowRaven.app.tar.gz`, never the DMG wrapper. Don't "fix" this by re-signing the DMG or by moving the styling after notarization — the latter would invalidate the staple.

- **After a Hephaestus reboot, the login keychain is LOCKED for remote (SSH/tailnet) sessions — every signing step fails until the USER unlocks it (v0.5.73 ship).** Symptoms: `codesign`/`xcodebuild -exportArchive` dies with `errSecInternalComponent`, `security show-keychain-info` says "User interaction is not allowed," and git's osxkeychain helper fails with `-25308`. The fix is once per reboot: the user runs `security unlock-keychain ~/Library/Keychains/login.keychain-db` in THEIR OWN terminal on the machine (a second ssh is fine). Claude cannot collect the password — the in-chat `!` command has no interactive TTY, so `security` reads EOF and fails without ever prompting; never ask for the password in chat. Check `security show-keychain-info` before a ship to catch this up front. (For git pushes, `git -c credential.helper='!gh auth git-credential' push …` sidesteps the keychain entirely.)
- **`release.sh` runs `touch src-tauri/src/main.rs` to force a Cargo relink, so a running `npm run desktop:dev` watcher will rebuild and RELAUNCH the dev app mid-release (v0.5.74 ship).** Harmless — the dev app and the release build use separate target dirs, and the release is unaffected — but it looks alarming if unexplained, and it matters when a live preview is being shown to the user during a ship: their app window will disappear and come back on its own. Either quit the dev watcher before releasing, or tell the user to expect the relaunch. Don't chase it as a crash.

### Windows desktop release (v0.4.0+)

- **Windows builds run in GitHub Actions** (`.github/workflows/windows-build.yml`, `windows-latest`), triggered by pushing a `v*` tag. The build uses a *throwaway* signing key (discarded) only so Tauri produces the artifacts; `release.sh` re-signs locally with the real key. The real minisign key never goes to GitHub — same keep-it-local stance as the Apple credentials.
- **`release.sh` is the single multi-platform assembler.** It builds + notarizes macOS, then `gh run download`s the CI Windows installer, signs it locally, and writes ONE `latest.json` with both `darwin-aarch64` and `windows-x86_64` entries. `SKIP_WINDOWS=1` publishes macOS-only (emergencies).
- **Release rhythm:** bump version → commit → push to main → push the `vX.Y.Z` tag (starts Windows CI) → wait for CI → run `./release.sh` → **ship the iOS TestFlight build for the same version** (see the iOS section below) → **submit that same uploaded build for App Store review** (also below). The tag must be pushed *before* `release.sh` so the CI artifacts exist to fetch. **A release goes to ALL available platforms, every time (user direction, v0.5.78; the App Store became a standing leg at 1.0.0)** — `release.sh` covers macOS + Windows + `latest.json`, the Pages workflow covers the website, the iOS TestFlight upload is the remaining manual leg, and the App Store submission rides the TestFlight build; a release is not done until it has shipped and been submitted.
- **A re-pushed `vX.Y.Z` tag leaves a stale successful Windows CI run that `release.sh` can mis-select (0.5.34 post-mortem).** `release.sh` picks the Windows installer from the most-recently-*created* successful `windows-build.yml` run (`gh run list --workflow windows-build.yml --status success --limit 1`), and its only guard checks the installer *filename* contains the version — which CANNOT distinguish two runs of the same version. If the tag was moved (a false-start: tag pushed at commit A, then re-pointed to commit B), the first push's run for orphaned commit A stays a *successful* run; if A's run is newer-created than B's, or B's run hasn't finished yet, `release.sh` silently ships A's binary (the version-filename guard passes either way). **Standing check before running `release.sh` after any tag re-push:** verify the selected run's commit equals the tag commit — `gh run list --workflow windows-build.yml --status success --limit 1 --json databaseId,headSha` and confirm `headSha == git rev-parse vX.Y.Z^{commit}`. You can't cancel a run that already completed; rely on the create-order (the correct re-push is newer) and wait for *that* run to go green before releasing.
- **The Windows updater target is the NSIS installer itself (`*-setup.exe`), NOT a `.nsis.zip`.** Tauri v2 signs the installer (`.exe.sig`) for updates on Windows; there is no separate archive. The `latest.json` `windows-x86_64.url` points to the `-setup.exe`.
- **`tauri signer sign`: don't pass `--private-key-path` (`-f`) when `TAURI_SIGNING_PRIVATE_KEY` is already exported** — the env key and the path flag are mutually exclusive. `release.sh` exports the env key for the macOS build, so the Windows-install signing step relies on the env, no flags.
- **Windows is distributed unsigned** (no Authenticode) for now — first launch shows a SmartScreen "unknown publisher" prompt. The in-app updater is unaffected (minisign verification, not Authenticode).

### iOS release (TestFlight + App Store)

- **After the TestFlight upload, the SAME uploaded build is submitted for App Store review (standing leg since 1.0.0; FR-22 of ios-app-store-release).** This is a manual App Store Connect action by the account holder: select the just-uploaded build for the version, confirm the metadata matches `appstore/LISTING.md` (the committed source of truth for every listing field, the privacy label, and the compliance answers), paste the review notes from `appstore/REVIEW_NOTES.md` verbatim (the review posture is key-free: no API key of any kind is supplied to Apple or committed to the repo; user decision 2026-08-25), and submit. Release **immediately on approval, no phased rollout** (phasing serves large installed bases; delaying a privacy-first app's fixes serves no one). **A rejection stalls ONLY the App Store leg**: it becomes a fix-forward item in the next release, and desktop, web, and TestFlight are never rolled back or delayed by Apple's review latency. Screenshots regenerate via `website/tools/capture-appstore.mjs` (synthetic demo data via `SR_DATA_DIR`, committed under `appstore/screenshots/`) whenever the photographed UI changes; unchanged screenshots do not need re-uploading per release.
- **CREATING a submission has MOVED (corrected v1.0.4).** `POST /v1/appStoreVersionSubmissions` now returns **403 FORBIDDEN_ERROR, "The resource 'appStoreVersionSubmissions' does not allow 'CREATE'. Allowed operation is: DELETE"**. The flow is now: `POST /v1/reviewSubmissions` (platform IOS + app relationship) -> `POST /v1/reviewSubmissionItems` (reviewSubmission + appStoreVersion) -> `PATCH /v1/reviewSubmissions/{id}` with `attributes.submitted = true`. **WITHDRAWING is unchanged** and still uses `DELETE /v1/appStoreVersionSubmissions/{versionId}`, which moves the version from `WAITING_FOR_REVIEW` to `DEVELOPER_REJECTED` (the editable state). To replace an in-review version: withdraw, PATCH the SAME version record's `versionString`, PATCH `relationships/build`, replace screenshots, then submit via the new flow -- the version record keeps every listing field.
- **Screenshot replacement is ORDER-SENSITIVE: replace a whole set, never a subset.** `DELETE /v1/appScreenshots/{id}` then re-uploading APPENDS to the end of the set, so swapping only the changed images scrambles the listing order. Per image: `POST /v1/appScreenshots` (fileName + fileSize + set relationship) -> PUT each returned `uploadOperations` part -> `PATCH` with `uploaded: true` and the file's **md5** as `sourceFileChecksum`. Poll `assetDeliveryState.state` until `COMPLETE` before submitting.
- **ASC metadata and submission can be driven via the App Store Connect REST API (how the 1.0.0 listing was entered and submitted), with two durable facts:** the metadata-capable API key is `QJA25M7XHM` — the env-default `BVVLBRRVL6` is upload-only and 403s on every metadata write; and the privacy nutrition label CANNOT be set via API (the appDataUsages endpoint family is retired, 404 PATH_ERROR), so a privacy-label change is an App Store Connect UI action by the account holder.
- **Every desktop/web release is followed by an iOS TestFlight build of the SAME version, build 1 (standing rule since v0.5.78; user direction).** iOS is no longer a selective catch-up — run the recipe below after `release.sh` verifies, on every release, bundled Spool releases included. iOS-only follow-ups still increment the build number without a desktop release.
- **iOS app icons must be fully OPAQUE — NO alpha channel — or App Store Connect rejects the upload (altool error 90717).** The check is on the large 1024 app icon and it fires on *any* alpha channel, even a fully-opaque/redundant one (the SR icons carried an all-opaque alpha with anti-aliased edges and were still rejected on the first upload). Keep BOTH `src-tauri/icons/ios/` AND the committed `gen/apple` AppIcon.appiconset (`src-tauri/gen/apple/Assets.xcassets/AppIcon.appiconset/`) flattened to opaque RGB — composite onto white and save with NO alpha (all 18 PNGs). The desktop icons (`tauri.conf.json` `bundle.icon`, `src-tauri/icons/icon.png`) MAY keep their alpha — this rule is iOS-only. `gen/apple` is a committed generated artifact, so the flattened icons must be committed there (re-running `tauri ios init` would re-stamp Tauri's placeholders — don't rely on init). Precedent: the v0.5.68 iOS icon fix (`e070d73` icon swap + `21fd5b2` flatten).
- **iOS build + TestFlight upload is Claude's to run (same posture as `release.sh`), and is NOT `release.sh`** (that assembler is macOS + Windows desktop only). The recipe (full detail + fallback in `pipeline/mobile-app/how-to-see.md`): `tauri ios build` SCRUBS `DEVELOPER_DIR` from the `xcodebuild`/`xcrun` it spawns, so build through the `/tmp/xcshim` wrapper (`printf` the two shim scripts that re-export `DEVELOPER_DIR` and `exec` the real tool, `chmod +x`, then `PATH=/tmp/xcshim:$PATH`) AND `export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer` in the parent shell. Do NOT `sudo xcode-select` (it needs a password). Build the TestFlight archive with `--export-method app-store-connect --build-number N`, then upload with `xcrun altool --upload-app -f <ipa> -t ios --apiKey $APPLE_API_KEY_ID --apiIssuer $APPLE_API_ISSUER_ID` (the App Store Connect API key + issuer live in the login shell / `~/.appstoreconnect/private_keys/`). **The upload shell needs `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer` exported too, or bare `xcrun` cannot find `altool`** ("not a developer tool or in PATH", hit on the 0.5.93 ship) — the shim only covers the build; export it in the upload command's own shell as well. An iOS-asset-only change (like the icon fix) does NOT bump the desktop version — it ships as an iOS build-number increment against the current version (v0.5.68 build 2), no `release.sh`, no tag, no `latest.json`.
- **ALWAYS run `xcrun altool --validate-app` before `--upload-app` (standing step since the 1.0.14 ship).** Same file, same flags, same credentials as the upload itself (`-f <ipa> -t ios --apiKey $APPLE_API_KEY_ID --apiIssuer $APPLE_API_ISSUER_ID`, with `DEVELOPER_DIR` exported in that shell too, per the bullet above). It runs Apple's ingestion checks WITHOUT consuming the upload, takes about a minute, and fails loudly on precisely the two things that otherwise cost a whole cycle to discover after the fact: an icon carrying any alpha channel (altool error 90717) and a missing or unqualified entitlement. A clean run prints `VERIFY SUCCEEDED with no errors`, which is what 1.0.14 build 1 returned immediately before its successful upload. It is cheap enough that it is never worth reasoning about whether this particular ship needs it: run it every time.
- **`tauri ios build` STAMPS the committed `gen/apple/snowraven_iOS/Info.plist`** (`CFBundleShortVersionString` + `CFBundleVersion` from the version and `--build-number`), so an iOS build leaves the working tree dirty. **Commit the stamp before `release.sh`** (its clean-tree preflight aborts otherwise) — a one-line `chore(ios): stamp iOS <ver> build <n>` commit, precedent `c505f2e` (v0.5.73) and the v0.5.71 closeout stamp.
- **`tauri ios build --export-method app-store-connect` ALSO needs the App Store Connect API key under TAURI's env names for its export/signing step — DISTINCT from the `altool` upload creds, and a real gap in the recipe above (hit + fixed on the 0.5.69 iOS build).** The upload step reads `APPLE_API_KEY_ID` / `APPLE_API_ISSUER_ID` from the login shell (passed to `altool --upload-app` as `--apiKey` / `--apiIssuer`); the *build/export* step reads three different names — `APPLE_API_KEY` (the key id), `APPLE_API_ISSUER` (the issuer id), and `APPLE_API_KEY_PATH` (path to the `.p8`). Map the login-shell ids across before building: `export APPLE_API_KEY="$APPLE_API_KEY_ID"; export APPLE_API_ISSUER="$APPLE_API_ISSUER_ID"; export APPLE_API_KEY_PATH="$HOME/.appstoreconnect/private_keys/AuthKey_$APPLE_API_KEY_ID.p8"`. Without all three the build dies at export with `APPLE_API_KEY, APPLE_API_ISSUER and APPLE_API_KEY_PATH must be provided for code signing`. Do this every iOS ship so the next one doesn't repeat it.
- **iCloud-era export (v1.0.11 onward): the archive comes from `tauri ios build`, the IPA from a manual-signing `xcodebuild -exportArchive`.** The App Store profile for `com.dtgibson.snowraven` is created (or renewed) through the ASC API with the metadata key `QJA25M7XHM`: `POST /v1/profiles` with `profileType` `IOS_APP_STORE`, the `com.dtgibson.snowraven` bundle-id relationship, and certificate `TLXMPPT4QY` ("Apple Distribution", SHA1 `1861F7A472C9D10C86D3BB55BC3A5B902AC7697B`); the profile expires WITH that certificate (2027-07-05), so renew both together. Decode `profileContent` (base64) to `~/.tauri/snowraven-ios-appstore.mobileprovision` and install a copy under `~/Library/Developer/Xcode/UserData/Provisioning Profiles/<UUID>.mobileprovision` (the UUID is the profile's `UUID` plist key, read with `security cms -D`) and `~/Library/MobileDevice/Provisioning Profiles/`. Then run `tauri ios build --export-method app-store-connect --build-number N` through the shim exactly as above: the archive succeeds (`** BUILD SUCCEEDED **`, `src-tauri/gen/apple/build/snowraven_iOS.xcarchive` with the stamped CFBundleVersion) and ITS OWN export fails at profile qualification with the cloud-signing refusal above (either wording) -- expected, not a failure to chase. **Move any existing `snowraven_iOS.xcarchive` aside BEFORE the build, and confirm the fresh one by its stamped `CFBundleVersion`, not by its presence.** `src-tauri/gen/apple/build/` is not cleaned between versions, so a previous version's archive sits there and an archive step that fails leaves it in place to be exported and uploaded as the new version -- the same stale-artifact hazard as the Windows CI run selection above, with no guard at all on this path (v1.0.16 found a 1.0.15 archive there from earlier the same day). Export the archive yourself: `xcodebuild -exportArchive -archivePath src-tauri/gen/apple/build/snowraven_iOS.xcarchive -exportPath <dir> -exportOptionsPlist <plist>` with a manual-signing options plist (`method` app-store-connect, `destination` export, `signingStyle` manual, `signingCertificate` "Apple Distribution", `teamID` 8QKC3L2FKP, `provisioningProfiles` mapping `com.dtgibson.snowraven` to the profile NAME, not its UUID, and `uploadSymbols` true), confirm the IPA's `DistributionSummary.plist` lists the icloud-container-identifiers, icloud-services (CloudDocuments) and ubiquity-container-identifiers entitlements, and upload with `xcrun altool --upload-app` as before (the stamp-commit rule is unchanged). First run: 1.0.11 build 1, profile `VBCQ5LZF6X` "SnowRaven iOS App Store iCloud 20260901", Delivery UUID `67270e05-c814-4c90-a823-a9886a87119d`, VALID in ASC within five minutes. Second run, 1.0.12 build 1, went through verbatim on the same profile (VALID within a minute of the upload), so this is the standing path, not a one-off; and `release.sh`'s preflight is fine with HEAD a commit or two past the tag (the iOS stamp, a test-only fix), as at 1.0.9, 1.0.11 and 1.0.12.
