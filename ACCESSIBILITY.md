# SnowRaven Accessibility

SnowRaven is built to be usable by everyone. It runs in the browser and as a desktop app, and it follows standard web accessibility practices so it works with keyboards and screen readers. This describes what is in place today. Accessibility is treated as ongoing work, not a finished checkbox, and the few known gaps are listed honestly at the end.

---

## Keyboard Navigation

Nearly all of SnowRaven is reachable and operable with the keyboard alone.

One thing colors everything below, so it comes first. The Mac, iPhone and iPad apps run inside Apple's WebKit engine, whose own default is narrower than the web's: a plain button and a plain link get no place in the tab order there, and a control is reached by Tab if it is a form field, or a disclosure triangle, or something the page has explicitly asked to have included. So SnowRaven asks, everywhere. No button and no link in the app's own screens is left to the browser's discretion: each one states its place in the tab order for itself, so the same controls are reached by Tab, in the same order, on the web, on Windows, and on the Mac, iPhone and iPad, without depending on a system setting. A few controls are deliberately kept out, and the next paragraph says which and why. The one thing this does not reach is the small number of controls the map library draws for itself rather than SnowRaven drawing them; those are set out under Known Exceptions below rather than glossed over here.

Every button, link, filter pill, toggle, sortable column header, and the species selector is a real control that activates from the keyboard (Enter, and Space as well on the ones that are buttons), and each is a tab stop on every platform. A "Skip to main content" link comes first, ahead of everything else, so keyboard users can jump straight past the header. A few controls are deliberately kept out of the tab order, always because another tab stop already reaches them, which is the standard behavior for what they are rather than an oversight. The main navigation is the clearest case, at the widths where it is a vertical list down the side of the window: it follows the standard pattern for tabbed interfaces, so the list holds a single tab stop rather than one per destination, the Up and Down arrow keys move between destinations, and Tab moves you past them into the page content. The species selector's list-toggle chevron is skipped for the same reason, the text box beside it being a tab stop that opens the same list. The species selector itself behaves like a proper combobox: type to filter, ArrowUp and ArrowDown move through the matches (the highlighted one scrolls into view), Enter selects it, and Escape closes the list. At phone widths the navigation is a bar across the bottom of the screen instead, and nothing there is kept out of the tab order: every button in the bar is its own tab stop, as is every row of the sheet the More button opens, which traps focus while it is open, closes on Escape, and returns focus to the button that opened it. That is the whole of the list: the main navigation's vertical list, the species selector's chevron, and the three Settings choice rows described in the next paragraph. Separately, a control that is genuinely unavailable rather than merely reached another way, such as a base map that needs a network connection, is switched off with the native disabled attribute and leaves the tab order the way any switched-off control does; that case is described under Offline States.

Settings groups that use a row of choices (color theme, text size, and date format) are arrow-key radio groups, so you Tab to the group and use the arrow keys to change the selection. The **Tab Layout** list, which lets you reorder your tabs, offers **Move up** and **Move down** buttons on every row as a full keyboard alternative to dragging. On the Mac, iPhone and iPad apps, the iCloud Sync section's **Sync API keys** switch stays in the tab order while it cannot be operated (it is marked `aria-disabled` rather than removed with the native `disabled` attribute), so the one-line reason associated with it is read in place, and each of its confirmations traps focus, closes on Escape, and returns focus to the control that opened it.

**The Calendar:** every day cell in the year grid is a real button in the tab order, not a coloured tile. Its accessible name gives the date, that day's figure for the metric you have selected, and what activating it does ("Mar 14, 2025: 3. Open day details"), so the shading is never the only way to read a day. A day you birded without recording anything for that metric names the metric outright, so it reads as a genuine zero rather than as an empty cell: "Jun 1, 2025: birded, 0 countable species. Open day details", or "0 checklists" or "0 individuals" as the Species / Checklists / Total count switch dictates. Activating a cell opens that day's details dialog, which carries all three of the day's figures regardless of the metric on the grid; focus moves into the dialog, stays there while it is open, and returns to the day you came from when it closes with Escape, the Close button, or the backdrop. Everything inside that dialog, the Close button and every checklist link in it, holds an explicit place in the tab order, which is what keeps focus in the dialog on the Mac, iPhone and iPad as well as on the web. The **Count all forms** switch below the grid stays in the tab order even when the metric you have chosen makes it inapplicable: it is marked `aria-disabled` rather than switched off, and the one-line note beside it is associated with the switch as its reason, so the explanation is met at the control rather than having to be gone looking for.

**Map markers (Map Explorer):** the markers drawn *on* the map are not a dependable keyboard route, for two different reasons. The sighting pins and the hotspot teardrops are painted on the GPU canvas, so they are not elements at all and can never be tab stops. The media-target and nearby-lifer chips are real buttons and are reached by Tab on every platform, but they ride on the map surface, so they move as you pan and zoom and a popup can cover them, which makes them an awkward thing to have to navigate by. Either way the same answer applies, and it does not depend on which kind a marker is. The Map Explorer sidebar provides a focusable, screen-reader-labelled list of the markers in the current map view: a "Sightings in view" list in My Sightings mode, a "Hotspots in view" list in Hotspots mode, a "Targets in view" list in Media Targets mode, and a "Nearby lifers in view" list in Nearby Lifers mode. Every item is a real button in the tab order; activating one with Enter or Space opens the same details popup a mouse click on the marker would open and pans the map to it, and activating it again closes the popup, so the marker's information is reachable, operable, and dismissable without a pointer. When the breeding-atlas overlay is on, an "Atlas blocks in view" panel on the map gives a keyboard path to each block: a focusable list whose rows open the block's breeding summary and eBird atlas link and pan the map to it. When the county overlay is on, a "Counties in view" panel gives a keyboard path to each county: a focusable list whose rows open the county's popup and pan the map to it, since the county fill is drawn on the GPU canvas and is pointer-only. Those two panels open a popup but do not close it again, unlike the in-view lists above; the popup itself carries the dismissal instead, so a keyboard user still opens and closes it without a pointer. The panel keeps parity with whichever shading metric is active: your species and checklist counts and the county's eBird link, or, under the Completeness metric, that county's "X/Y · Z%" progress. When a completeness figure cannot be produced, the row says plainly why (not yet looked up, no API key, offline, or an eBird error) rather than showing a blank, so the keyboard route never hides a state the map is showing. These lists are scoped to the current map view and update as you pan or zoom (very dense views are capped, with a "zoom in to narrow the list" hint), so the keyboard path tracks what's on screen rather than listing every marker at once. Where a popup on these maps has a close button, SnowRaven draws that button rather than the map library, so it holds a place in the tab order, Tab reaches it, and Enter or Space closes the popup however it was opened, including from a marker chip that no list row would close. The sighting and hotspot popups have no close button at all and do not need one, because the "Sightings in view" and "Hotspots in view" row that opens each of them closes it again, as described above. Either way, every popup these maps open can be dismissed from the keyboard. Every control SnowRaven itself draws on or around a map is keyboard-operable on every platform, the base-layer switcher, the filters, fullscreen, the location button, the share button, the marker chips and those popup close buttons among them: each holds a place in the tab order explicitly rather than relying on the browser to grant one. The map's own zoom answers the + and - keys while the map itself has focus. In the Map Explorer's bottom-right corner they are a single row in DOM order, so tab order and reading order are the same: the share button, then the location button, then fullscreen, then Filters where it applies. No two of them ever carry the same accessible name, in any state. The share slot's occupant depends on the view. On My Sightings it is the drop button, whose "Drop a pin at the map center" becomes "Move the pin to the map center" once a pin exists, and which reports `aria-pressed` because the map is holding something. On Hotspots, Nearby Lifers, and Media Targets it is a button that opens the existing search center pin's copy popup: "Copy the search center location", becoming "Close the location popup" while the popup is open, and it reports `aria-expanded` rather than `aria-pressed` because it discloses a popup rather than holding a pin. Closing the popup returns focus to whichever control opened it, and pressing that button to close never moves focus off the button just pressed. Before a search center has been set there is nothing to copy: the button stays in place and stays focusable, marked with `aria-disabled` and named "Set a search center to copy its location", and it carries a dashed border so the state does not rest on color alone. The location button tells you what it is doing through its accessible name, which is "Center the map on my location" at rest and "Finding your location" while a request is in flight; the glyph changes shape at the same time, so the state does not depend on the spinner's motion and survives a reduced-motion setting. While it works, the button marks itself unavailable with `aria-disabled` and ignores further presses, rather than being switched off with the native `disabled` attribute. That distinction is deliberate: a natively disabled control drops out of the tab order and loses focus, which would strand a keyboard user on the page body at the exact moment the result arrives, so the button stays focused and focusable across the whole press-to-result cycle. When a location request fails, the reason and the fix are announced from a live region on the map surface. That region is the only thing that announces the failure, and it is present in the accessibility tree from first render rather than appearing along with its first message, so the announcement is not missed. On the Hotspots, Nearby Lifers, and Media Targets views the same sentence is also shown, silently, in the filters sidebar beside the sidebar's own location button; it is not a second announcement, so the failure is read once rather than twice. The Hotspots view's "Color pins by" selector and its Week / 30 days window control are real buttons in the tab order that report their selection with `aria-pressed`, and the Recent activity mode's progress line is a polite live region that is present in the accessibility tree from first render rather than appearing along with its first message, with each new status a real node replacement so repeated updates are announced. The color ramp itself is luminance-graded so it stays ordered in grayscale, the non-value pin states differ in structure (a hollow center, a dashed ring, a pale fill) rather than hue alone, and the ramp tiers have an opt-in structural reading of their own: a "Use Tier Rings" switch (a real `role="switch"` control with a spoken name, revealed while a color mode is active) draws each tier as that many filled segments on a thin ring inside the pin, with the rest of the circle kept as a faint track, so a tier can be read by extent or by count with no color perception at all, and the legend's mini pins and the popup's tier badge draw the same segments from the same geometry so the surfaces cannot disagree. Because it is a vision-linked reading aid, that switch is remembered between sessions rather than resetting on relaunch. While a mode is active every pin's value or state is also stated in words in its popup and as a text column on its "Hotspots in view" row, so the coloring is never information a screen-reader or colorblind user is locked out of.

## Screen Reader Support

SnowRaven uses semantic structure and ARIA attributes so assistive technology can describe the interface accurately. Where the navigation is a vertical list, its destinations and their panels are linked with the correct tab/tabpanel roles and selected state; where it is the phone bottom bar, each button marks itself as the current destination instead, and every panel carries its own name either way. Filter pills announce whether they are pressed, toggles announce on/off as switches, and sortable table columns announce their sort direction. The species selector exposes its expanded state and current option. The in-view marker lists use real list semantics, and collapsed filter panels are made inert so their hidden controls never become stray tab stops. Information that is shown only with an icon or a color (breeding-code tiers, map recency dots) carries a hidden text label so it is never lost to a screen reader. Charts (life-list growth, checklists by month and weekday, temporal and media trends, sightings over time, and the like) expose a concise text summary via an image role, so their content isn't lost to a screen reader, and purely decorative chart flourishes are hidden from assistive tech. Regions that update on their own (the weather result, species and result counts, loading states, inline errors, and a keyboard tab move in the Tab Layout list) are announced as they change. When part of the app cannot load your saved eBird backup or Macaulay Library export, that failure is announced too: on all eight tabs that read your data (Statistics, the Calendar, Checklists, Breeding Codes, Named Birds, Species Detail, Multimedia and the Map Explorer) the message appears inside an alert region that is already present, and empty, from the moment the tab starts loading, rather than being created along with its text. A region that arrives with its first message is the standard way for an announcement to be missed, so the region is mounted first and filled afterwards, each message as a fresh child node. The region holds the sentence and nothing else: the alert icon beside it is hidden from assistive technology and the "Go to Settings" button sits outside it, so what is read out is the sentence itself. The Weather tab's checklist backlog reports a saved backup it cannot load in the same words and from the same kind of region. Because that one is a section you open and close rather than a tab, its region sits outside the part that collapses, so the region is in place before any message reaches it, rather than being created along with its text: opening the section fills a region that was already there, and closing the section empties that same region rather than removing it. The failure is announced when you open the section, and again each time you open it after that.

## A Visible Focus Indicator

Wherever keyboard focus lands, you can see it. Focused controls show a clear green outline (with a soft glow on buttons and tabs, and a border-hugging ring on inputs), so you always know where you are on the page. This includes bird-name links, and in-page "jump to" links move keyboard focus to the destination section rather than leaving it behind on the link.

## Color and Contrast

Color is never the only way information is conveyed. The current leader on a map, breeding-code evidence levels, and similar cues are always paired with text, a symbol, or a label in addition to color.

Every shaded surface also offers an explicit **Use Textures** switch, **off by default**, for reading a shade ramp without relying on hue at all: the map's breeding-atlas blocks, the Calendar's day grid, and county shading wherever it is drawn (the Map Explorer, the Species Detail sighting-locations map, and the Statistics geographic map). With it on, each tier is drawn as a hatch or crosshatch whose ink density rises with the tier (an open lattice at the low end through a tight crosshatch at the high end), so the levels stay distinguishable to a colorblind reader. The legend shows the same density steps as the surface itself, and the patterns follow the light and dark themes. The underlying figure is always available as text as well (in the popup on the map, and in the day popup on the Calendar), so the textures are an additional channel rather than the only alternative to color. The Map Explorer's hotspot color modes carry the pin-scale sibling of this convention: the opt-in "Use Tier Rings" switch described above, which encodes each ramp tier as filled ring segments rather than as a texture, since a crosshatch does not resolve at pin size. Body text and the primary interface colors (text, buttons, links, map popups, map pins, milestone and rank markers, and form controls) are chosen to meet the WCAG 2.1 AA contrast standard (4.5:1 for text, 3:1 for non-text UI) in both the light and dark themes; the breeding-tier badges and pills and the map target chips use dedicated text colors that pass on their own fills and tints. Chart figures are read from a label beside the bar rather than printed inside it; in the one place a percentage does sit inside a bar (the complete-checklists meter), its text color is chosen to meet AA against that fill in both themes. A full dark theme is included and can follow your operating system's light/dark preference.

## Text Size and Zoom

SnowRaven's text is sized in relative units, so it **honors your browser's or operating system's default text size** automatically. On top of that, a built-in **Text Size** control (Settings → Appearance) scales all text from 100% up to **200%**, meeting WCAG 2.1 SC 1.4.4 (Resize Text), and especially useful in the desktop app. Statistics chart labels, the help layout, and map popup text all grow with this control rather than clipping. Your choice is remembered across sessions.

Browser/page zoom (Ctrl/Cmd +/−) works too, and the desktop app enables the same zoom hotkeys. The layout reflows for narrow windows and at large sizes (including the navigation narrowing from a sidebar to a column of icons, becoming a bottom bar on a phone, and the help collapsing into a single column) without clipping content. At the largest sizes, wide data tables and the maps may scroll horizontally; this is expected and permitted by WCAG 2.1 SC 1.4.10 (Reflow), which exempts tables and maps.

**The Breeding Codes matrix on a phone.** This is the app's widest table, and on a narrow screen its code columns tighten to the width of their dots so far more of them fit at once, with thin vertical rules separating the columns and the species-name column held fixed on the left as you scroll the codes sideways, so a row stays identifiable no matter how far across you are. Long filter meanings wrap inside their pills, and a long bird name can wrap above its eBird and Birds of the World links. Every label remains complete, both links remain available with their full touch targets, and nothing escapes the name column. To read the matrix more closely you use your device's ordinary **pinch-to-zoom**. That is deliberate: the app sets no `maximum-scale` viewport clamp and applies no CSS scaling of its own, so the browser's native zoom is never disabled (WCAG 2.1 SC 1.4.4). Each column's terse code keeps a fuller spoken name on its sort control, and every count badge carries its breeding category as hidden text, so the tier colour is not the only carrier. The matrix scrolls with the page rather than inside a fixed-height box, so page zoom and the Text Size control both keep working on it. The tier legend beneath it spells every code out in full as visible text, and in the normal view a meaning too long for the line wraps onto a second line at phone widths instead of running past the edge of the card, so raising the Text Size never costs you the wording.

## Reduced Motion

If your operating system is set to reduce motion, SnowRaven honors it: loading spinners, transitions, and animated scrolling are reduced to near-instant so the interface does not move or animate unnecessarily.

## Turning Off Embedded Media

Species Detail and Named Birds can embed your Macaulay Library photos, recordings, and video inline. Those players are third-party content, so how they behave (autoplay, focusable controls inside the frame, motion in a video) is not something SnowRaven can style or restrain from the outside.

A **Disable embedded media** switch in Settings (**off by default**) turns them all off. With it on, no player is constructed at all: each one is replaced by a short neutral note, "Embedded media is disabled in Settings.", announced through a status role rather than as an error, since it is a preference you chose and not something that went wrong. Nothing else is lost. The item's own information (its capture date, its eBird checklist link, and a direct link to the asset on the Macaulay Library) is drawn from your own export, sits outside the player, and stays exactly where it was, so every piece of media is still identifiable and still reachable in one click. The choice is remembered across sessions.

## Focus Management

Where focus matters, SnowRaven manages it deliberately. Opening the Map Explorer's filter panel on a small screen moves focus into the panel and keeps it there while open; closing it (with Escape, the Close button, or by tapping the backdrop) returns focus to the button that opened it. Escape also exits map fullscreen and returns focus to the fullscreen toggle, so a keyboard user is never dropped to the page body. That holds on every map that has a fullscreen button: the Map Explorer, Species Detail's Sighting Locations map in both its Pins and Heatmap views, the Statistics Geographic Stats map, and the per-individual map on a Named Birds card. On those last three the expanded map also keeps the Tab key inside it, because unlike the Map Explorer the page it covers is still there behind it; the set of controls it can reach is re-read each time rather than remembered, so controls that appear and disappear while the map is open (a pin's popup, the share pin) are included as they come and go. Where switching the map's view replaces the fullscreen button itself, as Species Detail's Pins and Heatmap views do, Escape still lands on the button that is on screen rather than on the one that opened it.

## Offline States

The offline-support features added in v0.5.45 follow the same WCAG 2.1 AA bar as the rest of the app, in both the light and dark themes.

Offline and error states are conveyed by an icon paired with text, never by color alone. The three offline messages (you're offline, no API key, and server error) and the "last loaded result" staleness cue announce themselves through an appropriate live role: a status role for informational states and an alert role for genuine errors. When you are offline, the Satellite, Topo, and Trails base-map controls are disabled with a visible text reason that is also exposed to assistive technology: the disabled control is removed from the tab order, and its reason is referenced from the control, so the unavailable state is not signalled by color alone.

These offline surfaces are responsive from roughly 320-pixel phones up to large desktops and hold at 200% text scale without leaking horizontal page-scroll.

The Statistics tab's exotic-status check reports itself the same way. Its status line is a live region with `role="status"` and `aria-live="polite"`, rendered from first paint and never hidden while idle, so a message is announced rather than arriving with the region itself. Each message is placed in a child element keyed to its own sequence number, so pressing "Check again" twice announces twice even when the resulting sentence is identical. Every state's meaning is in its sentence: the muted Species figure while the check runs, and the tinted status icon, are supporting cues only and every icon in that region is hidden from assistive technology. While a check is running, its progress is a `progressbar` with real `aria-valuenow`, `aria-valuemin`, and `aria-valuemax` values, and the same figure is written out beside it as text.

The same tab's Projects check is built the same way, and adds two things worth stating. Every state it can be in carries its own sentence and only the controls that state can actually perform, so a state with nothing to offer (offline, or stored answers full) shows no button rather than one that would do nothing. And every figure it reports is written against the number of checklists it was drawn from, so a partial answer reads as a floor rather than as a finished total. Its progress bar and the text figure beside it quote the same pair of numbers as the sentence above them.

## Known Exceptions

The cross-cutting items previously tracked here are now addressed: the "open checklist on eBird" links are unified under one shared component with a single consistent accessible name (v0.5.31–v0.5.32), every external link announces that it opens in a new tab (v0.5.32), and the weather block names the correct moon phase for Southern-Hemisphere checklists (shipped v0.5.28). The Map Explorer's drop-a-pin gesture for setting the search center is pointer-only (right-click or long-press), but the search center is fully settable by keyboard through the place-name search, "Use my location", and the coordinate inputs, so it is an enhancement, not the only path. The placed pin is a presentational marker that visually echoes the search center, whose value is shown in the labeled coordinate inputs. The load-failure alert regions described above, on the eight tabs and on the weather backlog, have been verified against the rendered accessibility tree, which is not the same thing as hearing them: whether a given screen reader speaks them on macOS, Windows, iOS and the web has not been confirmed by a human listener, so that is recorded here rather than claimed. A tab that is not the one you are looking at is not announced either, because an inactive tab panel is hidden from assistive technology: a failure that happens while you are on another tab, including one that happens while you are in Settings replacing the file, is shown when you return to that tab rather than spoken. **The cross-cutting exception tracked here since v1.0.15, the tab order on the Mac, iPhone and iPad apps, is now closed.** Those apps run inside Apple's WebKit engine, whose default behavior is not to give a plain button or a plain link a place in the tab order at all; a control is reached by Tab there if it is a form field, or a disclosure triangle, or something the page has explicitly asked to have included. SnowRaven now asks, for everything it draws: **no button and no link in the app's own screens lacks an explicit place in the tab order,** apart from the few deliberate exceptions set out under Keyboard Navigation, each of which is already reached by a tab stop beside it. Two of those are the standard pattern for a group of choices, where the group holds one stop and the arrow keys move within it: the main navigation's vertical list, and the Settings choice rows. The third is the species selector's list-toggle chevron, which the arrow keys do not move to and do not need to, because the text box beside it is a tab stop that opens the same list. That is a property of the source rather than a survey of screens, which matters because a survey goes stale as screens are added: a test reads every shipped component file on every build and fails if a new button or link appears without one, so it cannot quietly lapse.

What remains is not SnowRaven's own markup. The map library draws a few controls for itself, and those carry no explicit place in the tab order, so on the Mac, iPhone and iPad they are reached only with the system's full keyboard access switched on. There is one kind left. The popup close buttons were the second, and they are no longer the library's to draw.

The **+ and - zoom buttons** in a map corner cost nothing, because the published keyboard route for zoom is the + and - keys with the map focused, and that does not go through the buttons.

The small **close button on a map popup** was the second kind, and it is no longer the library's to draw. **Every popup SnowRaven's maps open can be dismissed from the keyboard, on every platform.** Where a popup carries a close button, SnowRaven draws that button itself, in its own markup, with an explicit place in the tab order and a name that says which popup it closes, so Tab reaches it and Enter or Space closes it however the popup was opened, including from a marker on the map that no list row would close. That now covers the breeding-atlas block popup, the county popup, the Media Targets and Nearby Lifers popups and the sighting popup on the **Sighting Locations** map that Species Detail and a Named Birds card share, alongside the Statistics map's popup and the share popup, which already worked this way. The sighting and hotspot popups on the Map Explorer carry no close button at all and do not need one: they are opened from the "Sightings in view" and "Hotspots in view" lists, and activating the same row a second time closes them. Because these are the app's own controls rather than the library's, the same source test that checks every other button checks them too, so the claim above cannot quietly lapse as maps are added. Nothing about the mouse changes: the button looks the same, sits in the same corner, and keeps the larger touch target it already had.

Stamping the missing attribute onto the library's own elements from JavaScript would have closed this sooner, and it was deliberately not done: it would have put the claim above beyond the reach of the test that checks it, and a published promise nobody can verify from the source is worth less than one named control. Bringing the popups into SnowRaven's own markup was the real fix, and it is the one that was made, so every close button on a map popup is now a control the source test can see. The zoom buttons stay the library's, and stay named here rather than implied away.
