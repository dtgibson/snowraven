## Versioning

- Version is tracked in `frontend/package.json` (semver, patch increments for small features/fixes, minor for larger features)
- **Bump BOTH `frontend/package.json` AND `src-tauri/tauri.conf.json` to the same version.** `tauri.conf.json` is the source of the desktop *bundle* version (macOS `CFBundleShortVersionString`, Windows installer version, and the in-app updater's version check) and does NOT read from `package.json`. Forgetting it ships a mislabeled bundle and breaks the updater; `release.sh`'s version guard catches the macOS side, but the Windows installer is built by CI from `tauri.conf.json` at the tagged commit, so the tag must point at a commit where both are bumped. (Patch-only by default — never minor/major unless explicitly told.)
- `CHANGELOG.md` at the repo root must be updated with every version bump
- **A version bump is a FOUR-file set, and the fourth is the website: `frontend/package.json`, `src-tauri/tauri.conf.json`, `CHANGELOG.md`, and `website/index.html` (the `version-pill` visible text AND its `aria-label`, plus the `footer-version` line).** All four are asserted by one guard, `it('the website version pill and footer follow the app version')` in `frontend/src/lib/icloudKeysPublishedClaims.test.ts` -- a repo-wide release-parity check housed in a feature-named suite, which is why it is named here rather than left to be found. The website leg is stated in `.claude/rules/docs-and-website.md`, and that file is **path-gated** on `website/**` / `README.md` / `docs/**`, so a release-prep session touching only the two manifests and the changelog never loads it: that path-gating is the mechanism by which 1.0.14's prep (`e249051`) bumped three of the four, left the pill at `v1.0.13`, and shipped with the suite RED on `main` for five commits. Touching the file is not what repairs it -- `f02b063` edited `website/index.html` and still left the stale version; only the version-stamp step does. **Known weakness of the guard:** it is a `toContain` substring check over the whole file, so it goes green as soon as ONE correct version string exists anywhere -- a corrected pill with a stale footer still passes (ROADMAP).
- **Always bump the version and update the changelog when adding a feature or fix**, even if the user does not ask
- **A dev-only / toolchain change that does NOT affect the shipped bundle — a dev-dependency `npm audit fix`, a lockfile refresh, test-only tooling — does NOT require a version bump, changelog entry, tag, or release.** It produces a byte-identical app, so commit it straight to `main`; it reaches the release machine on the next `git pull`. The "always bump" rule above is about user-facing features and fixes. (Precedents in `DECISIONS.md`: the `dev-dependency-cleanup` `undici` patch, and the Node-25 release-tooling fix — both "no version bump.")
- **After pushing a version bump, run `./release.sh`** to build, notarize, and publish the macOS desktop app. This script creates the GitHub release (or uploads to an existing one), signs the updater bundle, and generates `latest.json` for in-app update detection. Credentials (Apple API key, notarization) stay local — never stored in GitHub.
- **Do not use `gh release create` directly** for desktop app releases — always use `release.sh` so the signed binary and `latest.json` are included. The in-app update check depends on `latest.json` being present in the release assets.
- **Tauri v2 macOS updater mechanism:** `downloadAndInstall` performs synchronous in-place bundle replacement — no shell script, no sleep, no `open -a`. The `.app` bundle is fully replaced on disk before the Promise resolves. After `downloadAndInstall` returns, call `relaunch()` (not `exit(0)`). `relaunch()` spawns `current_exe` (now the new binary) and exits cleanly. `exit(0)` just terminates the process with no relaunch, leaving the user with no running app.
- **Release rhythm (summary):** bump version → commit → push `main` → push the `vX.Y.Z` tag (starts Windows CI) → wait for CI green → run `./release.sh` → ship the iOS TestFlight build of the SAME version → submit that same build for App Store review. **A release goes to ALL available platforms, every time** (user direction, v0.5.78; the App Store became a standing leg at 1.0.0) — a release is not done until every leg has shipped and been submitted. **VERIFY the App Store leg against App Store Connect; never infer it from the repo (v1.0.17).** 1.0.15 and 1.0.16 each shipped a `VALID` TestFlight build and neither ever got an App Store *version record*, so the store sat on 1.0.14 for two releases — and nothing in this repo would have said so: a TestFlight build is not a submission, the changelog and tags look identical either way, and the miss was only found by querying ASC during the next ship. A ROADMAP item naming the debt was **not** enough; it was item 1 in Up Next while 1.0.16 shipped past it. So at every ship, list the version records for the last few releases (`GET /v1/apps/{id}/appStoreVersions`) and confirm each one either shipped or is deliberately deferred **in writing**; a deferral is a decision with a reason, never a silence. When releases have accumulated, the notes cover all of them. The full runbook lives in the `snowraven-release` skill (below).
- **Cross-platform Rust deps must live in `[dependencies]`, not `[target.'cfg(target_os = "macos")'.dependencies]`.** `tzf-rs` (used by the cross-platform `get_timezone` command) was mis-scoped there and broke the Windows build with "unresolved import." The macOS-only block is only for genuinely macOS-only crates (objc2*, the CoreLocation stack). A crate real on both Apple platforms goes in the `cfg(any(target_os = "macos", target_os = "ios"))` block, and an Apple-vendor crate needed only on iOS (`objc2-ui-kit`) in its own `cfg(target_os = "ios")` block, never the android|ios mobile block: the cfg says where a crate is real, not which build happens to pull it (v1.0.11).
- **iOS app icons must be fully OPAQUE — NO alpha channel — in BOTH `src-tauri/icons/ios/` AND the committed `src-tauri/gen/apple/Assets.xcassets/AppIcon.appiconset/`** (App Store Connect rejects the upload otherwise, altool error 90717; desktop icons MAY keep alpha). Flattening detail and precedent are in the release skill.
- **For ANY release, packaging, updater-artifact, TestFlight, or App Store work, invoke the `snowraven-release` skill** (`.claude/skills/snowraven-release/SKILL.md`). It holds the complete mechanics and post-mortem guards moved out of this file: `release.sh` preflights and the pinned-Node story, universal-binary and `latest.json` rules, headless DMG styling and notarization/keychain, the Windows CI artifact-selection guard, and the full iOS build + upload recipe with its env-name mappings. Do not ship from this file alone.

### Desktop app seams

Permanent architectural seams route all platform-sensitive operations. Use them in new code — do not bypass them.

- **Transport:** `transport.get()` / `transport.post()` from `frontend/src/lib/transport.ts` — for all outbound HTTP calls. In Tauri mode, `TauriTransport` routes each API path directly to a TypeScript service (weather, map, taxonomy, nominatim, stats, version). In web/Pi mode, `WebTransport` delegates to the Python backend.
- **Caching layers — pick by lifetime.** `CACHED_GET_PATHS` in `transport.ts` is the short-TTL (~90s) repeat-call cache; `replayStore` is the live-first offline replay of a last-loaded result. A **long-TTL persistent network cache** ("hold live data for days") follows `lib/countyCompletenessCache.ts` instead: a storage-seam document with an in-memory mirror, TTL-gated reads, per-entry shape validation on load (malformed entries dropped, never thrown on), a strict 250-entry cap plus a `JSON.stringify(data).length` payload-code-unit budget with `order[]` FIFO eviction, an in-flight dedupe Map, errors never cached, and offline stale-reads served for display. Keys, metadata, ordering and the document envelope are outside that budget, and one sole oversized newest payload is allowed; do not call it a byte cap. `replayStore` has the same semantics with a 300-entry cap, **with two stated exceptions worth knowing before copying it**: its `ensureLoaded` is the one durable store with no per-entry validation on load, and its adjacent `bytes` guard checks `Number.isFinite` only, so it admits negatives (both bounded by the 300-entry cap, both on the roadmap). Since v1.0.14 it also owns an ordered writer (below). `storage.ts` is the persistence seam, not a cache owner; `persistedStyle.ts` has a finite shipped caller graph but its string-accepting API is not structurally bounded. A path served by a durable cache stays OUT of `CACHED_GET_PATHS` — one caching layer per call. `lib/hotspotActivityCache.ts` (6h TTL, FIFO at 2,000) is the second instance of the `countyCompletenessCache` pattern and adds one rule worth copying (v0.5.92): a durable cache computes its DERIVED fields at ONE chokepoint — the cache module's own `dedupedFetch` — so every persisted entry is fixed-shape by a single write path rather than by every caller's discipline. **Sharpened at the third instance, `lib/checklistProjectsCache.ts` (v1.0.5): that chokepoint must also VALIDATE, not merely compute.** Run the candidate entry through the store's own per-entry validator — the same predicate the load path already uses — before merging, so "no out-of-bounds value can exist in this document" is a property of the cache MODULE rather than of whichever producer happens to sit upstream. It matters most where the decision to ship without a payload budget is justified by those very bounds: the projects store shipped with `isValidEntry` present in the module and called on load only, while its write path built entries from a defensive re-read whose contract was strictly weaker than the transport seam's normalizer (no pattern or length bound on the id string, no upper bound or length cap on the id array). Bounds enforced at the seam and again on load are two places the next store's author may simply not wire up; the validator at the write chokepoint is the one that travels with the pattern.
- **A BUNDLED BUILD-TIME ASSET AND A PERSISTED RUNTIME CACHE ARE DIFFERENT TRUST BOUNDARIES, and the per-entry validation rule above applies only to the second (v0.5.89).** The distinguishing question is whether an attacker can change the document without already being able to change the code that reads it. For a Vite-inlined JSON import the answer is no — malformed JSON fails the build, not the user's session — so the correct defenses are **build-time** (a generator that fails closed on implausible output) and **CI-time** (an equivalence test against an independent re-derivation, plus a size bound on the entry chunk), not runtime validation. `ebird-countability.json` is the reference: `build-countability.mjs` hard-fails on short lists, overlapping lists, and a name collision in the inversion; `countableForms.test.ts` asserts it member by member and pins its `version` to the taxonomy snapshot; `entryChunk.test.ts` bounds it. Worth stating because the cache rule is written forcefully enough to be applied where it costs bytes on first paint and buys nothing. **If such an asset ever becomes runtime-loaded, this note inverts and the cache rule applies in full.**
- **A durable cache may hold TWO stores with OPPOSITE retention policies, and the choice follows what an eviction COSTS (v0.5.87).** The escapee document is the reference: its checklist ledger is **FIFO**, because evicting an entry costs one redundant request and loses no answer; its species index uses **admission control** (fill to the limit, then stop admitting, never evict), because evicting there would destroy a paid-for network answer and, at capacity+1, would do so on every pass forever. This is the v0.5.86 rule applied rather than contradicted — capacity+1 is a measurement rule, not a universal policy. Gate admission on the CONTAINER's own size, never a separate counter, and prove it: a test re-merges one species fifty times to show admission capacity is not silently consumed, and both stores are measured at capacity+1 asserting **work done**, not elapsed time.
- **A denormalized, PUBLISHED classification field is a legitimate member of a persistent cache document when a passive reader structurally cannot re-derive it — provided the raw evidence stays the source of truth and the reader CONFIRMS rather than trusts it (v0.5.87).** `ProvenanceSnapshot.excludedNames` is the reference: the Calendar holds no name-to-code join and may not fetch one, so it cannot classify by code; Statistics publishes the escapee-only names, the raw tokens remain in the document, and Statistics always re-derives from them. The passive reader then **confirms** the published list against the persisted checklist ledger using its own observations, so a newly loaded export that adds a carrier re-opens that species offline exactly as it does on Statistics. **Without the confirmation step this is a stale-cache trap**; with it, the offline reader tracks a new export correctly. Stated limit: for a species the passive reader cannot re-open, a published name is only as current as the last Statistics visit.
- **A durable store keyed on USER-FILE CONTENT registers with the same teardown that deletes the file, and the rule that travels is the REGISTRY, not the discipline (v1.0.14).** Four stores each missed this because there were three clear paths, so wiring a new store meant remembering all three. One table and one entry point (`lib/clearDerived.ts` / `purgeDerivedOnClear`), called from `Settings.tsx handleDeleteFile` and both `icloudSync.ts` clear paths, with `cacheInventory.test.ts` pairing each store's exported purge to a row that calls it -- and `clearDerived.ts` carries no static imports at all, reaching every store through `import()`, because `Settings.tsx` is on App.tsx's static graph and `countyCompletenessCache.ts` must stay off the entry chunk. Five rules ride with it. **The purge is a PRODUCTION export, never the `_reset*ForTests` seam** -- those detach the in-memory mirror and leave the document on disk, so shipping one as the clear path looks correct in a test and clears nothing. **A store is registered on where its KEYS come from, not its VALUES**: `county-completeness-v1` holds only eBird's public payloads and still belongs, because a key exists only for a county the user has birded (accepted cost: those lookups re-fetch once after a clear and re-upload); by the same rule `hotspot-activity-v1` is deliberately OUT, and a future store's row is argued on its key set. **Purge on CLEAR only, never on REPLACE** -- the teardown is a dependency separate from the controller's `invalidate`, which the synced arrival also uses, so the pull path physically cannot reach it and `PRIVACY_POLICY.md`'s "asks only about checklists that have not been answered yet" stays true. **The purge must SUPERSEDE the store's in-flight work, not merely empty it**: cancel the debounced flush timer, stop a parked `ensureLoaded` from adopting the document it just read, and refuse a write from work that began before the purge -- a purge missing any one un-does itself a few hundred milliseconds later. **And that third guard's capture belongs at the FETCH CHOKEPOINT, before the request.** Identity (`store !== _store`) suffices only where the writer captured its store before the await; a PUBLIC entry point that calls `ensureLoaded()` for itself finds the fresh post-purge mirror perfectly valid and writes the deleted export's data into it, so it needs a monotone purge generation -- and a generation read inside the write path is entered only after the answer lands, by which time the counter has moved, so it is inert. Where the chokepoint is inside the store (`dedupedFetchChecklist`) the capture is internal; where it is outside (`transport.getReplayable`) the store exports `purgeGeneration()` and the chokepoint hands it back as a REQUIRED argument. **A best-effort teardown returns what it could not do** -- keep the `allSettled` loop so one store's failure does not abandon the rest, but resolve with the failures, and name what happened (not "delete failed" when the file is gone, not "try again" when the row is now empty); a background path with no user waiting may decline to surface it as a stated decision at the call site, never as a discarded value.
- **Nominatim has one bounded retention and provider-etiquette contract on both transports (v0.5.86).** Tauri and FastAPI each retain at most 4,096 rounded-coordinate county results with fill-and-stop admission: overflow calls still return their result but do not evict the admitted working set. On desktop, forward search and reverse county lookup share one request-start queue enforcing at least one second between starts, and concurrent reverse calls for the same rounded key share one in-flight Promise. Keep the JS/Python rounded-key semantics in parity, including negative half-step cases.
- **Outbound eBird fetching at volume follows ONE pacing contract on both transports (v0.5.92): spaced request starts + one key-global Retry-After-honoring cooldown + bounded per-item retries — the eBird analogue of the Nominatim queue, at eBird scale rather than Nominatim's mandated 1 s.** The mechanics are pure in `lib/rateLimit.ts`: 150 ms global start spacing (the concurrency pool stays a latency-absorbing ceiling; spacing is the governor); a 429 opens ONE shared cooldown gating every request start (the KEY is over the limit, not a slot), honoring a seconds-form `Retry-After` capped at 60 s, else bounded exponential 2 s → 30 s with jitter; a burst of simultaneous 429s counts as one wave, a post-cooldown success resets the ladder, and the cooldown deliberately survives a pass restart. Bounded retries per item (2), then the honest unanswered state with Retry; a 429 is NEVER cached. The upstream `Retry-After` is parsed, bounded, and re-serialized identically on both transports (`rateLimit.ts` ↔ `_parse_retry_after_seconds` in `backend/routers/map.py`) — never reflected raw — and both transports surface a 429 AS a 429 on EVERY eBird-backed `/map/*` route (one shared mapper per transport: `_raise_ebird_http_error` ↔ `throwEbirdHttpError`; single-sourcing prevents drift, so each route/function still keeps its own 429 test). Two test rules ride with it: anchor timing-policy measurements on CLIENT observation of request starts with a settled main thread, never network-side fulfill timestamps; and `rateLimit.ts` deliberately rides the entry chunk (dependency-free by extraction, policed by `entryChunk.test.ts`). **Scope since v0.5.93: every eBird-backed Map Explorer lookup is governed.** The cooldown/spacing STATE lives in the shared module-scoped gate `lib/ebirdGate.ts` (also entry-chunk-safe); the transport chokepoint routes `/map/hotspots`, `/map/recent-obs`, `/map/hotspot-region`, and `/map/county-species` through `gatedEbirdCall` (serialized spaced starts + cooldown wait-out + the same bounded retries), wired BELOW `CACHED_GET_PATHS` so a cache hit never waits. **One enforcement point per request:** `/map/hotspot-activity` is deliberately NOT transport-gated — the activity controller enforces the identical contract for it over the SAME shared state, so a 429 anywhere slows everywhere. A future eBird-backed lookup joins `EBIRD_GATED_PATHS` (transport.ts) or owns its enforcement over the shared state — never neither, never both. Accepted, stated cost: a transport-cache miss that an inner cache would serve (backend recent-obs single-flight; desktop raw-fetch dedupe) still waits for its start slot, bounded at the spacing floor. Still outside the gate by scope: the non-map eBird families (weather/tide checklist lookups, taxonomy, escapee provenance). **A pass-scale pacing layer rides ON TOP of the gate, in the pass's own controller — never inside gate policy (v1.0.8).** A sweep that must escalate across 429 waves owns that policy itself (the projects sweep: `sweepSpacingMs` in `rateLimit.ts` + the pause in `useChecklistProjects`); the gate contributes observation-only MONOTONIC fields (`waveCount` in `ebirdGate.ts` — never reset by a success, never consulted by gate policy) that a pass reads by DIFFERENCING over its own window, so single-shot lookups never inherit a sweep's escalation or pause. A layered schedule sleeps its FULL widened interval between items: the gate's floor elapses during the sleep, so the two never add, and "widened minus the floor" quietly under-delivers. Slower than the floor is always contract-compliant, so the layer needs no gate-policy change to exist.
- **Storage:** `storage.getApiKey()` / `storage.getSetting()` / etc. from `frontend/src/lib/storage.ts` — for all key, setting, and file access. Do not call `/settings/*` endpoints directly from new components.
- **Data-file change signal:** `lib/filesChanged.ts` + `useFilesEpoch()` (v1.0.11). **EVERY path that saves, replaces or removes a stored data file bumps the epoch through the seam, with no exception for the handler that did it** -- v1.0.14 dropped the earlier carve-out for the Settings tab's own handlers, whose reasoning ("the tab that did it already knows") is wrong in this app specifically: tabs are hidden with `display:none` rather than unmounted, so the other seven stay mounted with loaders keyed on the epoch, and that carve-out is exactly what left `Settings.tsx handleDeleteFile` as the one mutation path that never fired the signal while both synced paths did. A tab that loads a stored file puts the epoch in its load effect's deps rather than loading on mount only, so the new or removed file reaches it without a relaunch. A new tab that reads a stored file subscribes the same way. **Second instance, `lib/keysChanged.ts` + `useKeysEpoch()` for the api-keys document (v1.0.12):** the same shape is the house signal for any stored document another path can change under a mounted reader. App derives any prop-threaded version (`keysVersion`) from the epoch rather than counting saves itself, and a reader that checked the document on mount only (`BirdingStats`' `hasEbirdKey`) puts the epoch in its effect deps; a third stored document that gains an off-tab writer gets its own epoch module of this shape, entry-safe.
- **Promise boundaries: in an async function, `try { return v } catch` catches NEITHER a rejection of `v` NOR a throw from its `then` getter, so any "this never rejects" claim over a dependency that could return a promise needs `return await` (v1.0.16).** An async function's `return v` performs promise resolution of `v` **after** the try block has exited, so a thenable escapes through **two** doors on one enclosed-looking statement: the `then` call, and the `Get(v, "then")` getter lookup performed during resolution. Both were measured rejecting on the shipped shape of `lib/weatherBacklogLoad.ts` and fulfilling under `return await`; the cost on a synchronous array is one microtask tick. **A synchronous-today return type is not protection** -- the change that breaks the claim is a refactor nobody will connect to it, and this repo has form for exactly that move (the observations parse went off-thread for the same class of reason). On the day the dependency goes async, the `try` silently stops catching, a call site relying on the claim (here a `.then` with no `.catch`, with no global handler anywhere in `src`) becomes a live defect that parks the surface on its spinner for the session, and nothing goes red. **`return await` closes rejection; it does NOT close non-settlement** -- a thenable that never settles leaves the promise pending forever, no `try` closes that anywhere, and the answer is a timeout owned by whoever introduces a dependency that can hang. **Name that boundary at the definition site**: a totality claim with an unnamed exception is worse than an honest partial one, and "there are no stated exceptions" was wrong by two shapes before it was measured. `@typescript-eslint/return-await` cannot help -- `frontend/eslint.config.js` sets no `project` / `projectService`, so no type-aware rule runs at all.

- **A worker-backed promise owes a SETTLE CONTRACT, not two handlers (v1.0.14).** `parseOffThread` in `observationsCache.ts` is the reference: one idempotent `settle` covering all five exits -- a reply, `onerror`, `onmessageerror` for a reply that cannot be cloned back, a `postMessage` that throws on the way out, and silence past a budget -- clearing the watchdog, detaching the handlers, terminating the worker and settling exactly once, so a late event after the watchdog can neither re-settle nor double-terminate. **The silence budget scales with the input and its factor is MEASURED, never guessed:** parse throughput was 57.8 to 75.0 Mchar/s flat across a 20x size range (so linear in the input), and the shipped `30 s + 4 s/MB` is ~250x slower than measured, with the 30 s floor covering worker spawn, module evaluation and the request's structured clone. **A memoized promise inherits its producer's worst settle path** -- the pending promise sat in `inflight`, whose `.finally` therefore never ran, so every later caller for the whole session joined the dead promise. **And the failure signal must match the branch the consumers ALREADY take:** a failed parse resolves `null` rather than throwing, because all eight tab loaders map a *thrown* load to `setup-required` ("upload a backup" over a backup that is plainly loaded) while each already had an honest branch on a falsy result. A new load path picks its signal by reading its consumers, not by which is more idiomatic. The failure path also never re-runs the parse that just failed on the main thread; the one surviving synchronous parse is where `new Worker` throws because Workers do not exist.
- **A feature whose native half must stay off the entry chunk ships as an entry-safe store plus a dynamic-imported controller** (v1.0.11; `lib/icloud/icloudState.ts` / `icloudSync.ts` is the reference). Components read the store and call an `actions` slot the controller installs after boot, so the entry graph carries only the store, the platform gate and the copy; the controller, the native wrapper and its types emit as lazy chunks, and `entryChunk.test.ts` polices both halves.
- **Platform detection:** `isTauri()` from `frontend/src/lib/platform.ts` — single source of truth for branching on Tauri vs. web. Do not check `window.__TAURI_INTERNALS__` elsewhere.
- **Clipboard:** `copyText()` from `frontend/src/lib/clipboard.ts` — for all clipboard writes. In Tauri mode it uses the native `@tauri-apps/plugin-clipboard-manager` (no user-gesture requirement, so auto-copy after an `await` works); on web it uses `navigator.clipboard` with an `execCommand` fallback. **Do not call `navigator.clipboard` directly** — an async clipboard write that runs after an `await` (outside a click) throws `NotAllowedError` in WKWebView/WebView2 and is silently lost on desktop. The capability grants `clipboard-manager:allow-write-text` only (write, not read).
- **Opening an external URL from code:** `openExternalUrl(url)` from `frontend/src/lib/openExternal.ts` — **never `window.open()`**. `window.open()` is silently dropped in the Tauri desktop WebView (WKWebView never opens the system browser), so an external open works on web but does nothing on desktop with no error (the Weather Backlog's "Copy weather & go" hit exactly this, v0.5.67). The whole app opens external links only via `<a target="_blank">` anchors, which `tauri-plugin-opener` intercepts; `openExternalUrl` synthesizes exactly that — a transient, detached `<a target="_blank" rel="noopener noreferrer">` that is appended, `.click()`-ed, and removed — so it works in BOTH web and desktop. For a **user click**, prefer the shared link components (`OutboundLink` / `ChecklistLink` / `HotspotLink`); reach for `openExternalUrl` only when the open must happen from code (e.g. after an `await`). Keep the same id-shape guard + `encodeURIComponent` on any id in the URL as everywhere else.

### Desktop storage (Tauri)

`TauriStorage` in `storage.ts` uses **`tauri-plugin-fs` with `BaseDirectory.AppLocalData` for everything** — API keys, settings, file metadata, and CSV files. All data lives under `AppLocalData/data/`:

| File | Contents |
|---|---|
| `data/api-keys.json` | API keys (`ebird`, `openweather`) and, since v1.0.12, a per-key `meta` (change time and origin, or a cleared marker) validated on every read, so a pre-1.0.12 document reads as untimed and is never defaulted to now |
| `data/settings.json` | App settings (map center, zoom, etc.); the `icloud-sync` object is the one place sync state lives (preference, device id, the key-sync switch, a pending key removal, last-known shared state per file and per key slot), and anything new about sync joins that object as one link per save, never a new document |
| `data/metadata.json` | Uploaded file metadata |
| `data/ebird-backup.csv` | eBird data file |
| `data/ml-export.csv` | ML data file |

Every write calls `mkdir(DATA_DIR, { recursive: true })` before writing to ensure the directory exists.

**Shared-document writes serialize on a per-document promise chain (v1.0.9).** Every read-modify-write on a shared JSON document above (settings, api-keys, metadata) runs as a link on that document's chain in `TauriStorage` (`docChains`, keyed by the closed set of path constants) — a new writer joins the chain, never bypasses it; a link never awaits another chained op, and a failed link rejects only its own caller. Unserialized read-modify-write is the lost-update clobber that silently erased the projects ledger (post-mortem in DECISIONS.md v1.0.9); a future store that rewrites a whole shared document from a base read owes the same mechanism and an interleaving test shaped like `storageWriteSerialization.test.ts`.

**`data/replay.json` has an equivalent write chain of its own and deliberately does NOT join `docChains` (v1.0.14).** It is its own file with a single writing MODULE, so it has no read-modify-write to clobber -- but one module is not one write at a time: two concurrent `setReplayStore` calls completed in whatever order the filesystem returned, and a purge's smaller document was the likelier to land first and be overwritten by a pre-purge flush already inside the seam, which neither a cancelled timer nor an identity check reaches. `replayStore` therefore has its own ordered writer (`writeThrough`, the same shape and same two rules as `TauriStorage.chain`: the next write is not CALLED until the previous one settles). **The reason it needs no read-modify-write wrapping is structural and is recorded here because a future change would break it silently:** a write is reachable only from a flush that requires a completed `ensureLoaded`, or from the purge, which awaits it. **Add a re-load-after-purge and that reason is gone**, at which point this document owes the full `docChains` treatment.

**Do not use `localStorage`** — it is ephemeral in Tauri's WKWebView and cleared on every relaunch.  
**Do not use the system Keychain** (`keyring` crate / `invoke('get_api_key', ...)`) — it requires entitlements not configured in this app and fails silently.

**Persist all UI settings through the `storage` seam, never `localStorage` directly.** Anything that must survive a desktop relaunch (e.g. the tab layout) goes through `storage.getSetting`/`setSetting`. The web/Pi path may still read `localStorage` synchronously inside the seam for a flash-free first paint, but the seam — not `localStorage` — is the source of truth on desktop. (See the tab-layout post-mortem in DECISIONS.md.)

**A SHIPPED DEFAULT THAT USERS MAY HAVE A SAVED COPY OF MIGRATES AT READ TIME, AND ONLY FROM THE DEFAULT IT IMMEDIATELY REPLACED (v1.0.19).** When `DEFAULT_TAB_ORDER` changed, a saved order equal to the *previous* default was read as carrying no preference and returned as the new default; any order that differs in any way is a CUSTOM layout and is kept verbatim. Four parts make that safe and all four are load-bearing: keep the previous default as a NAMED CONSTANT so the check is one equality and not a heuristic; run the comparison AFTER the existing unknown-id drop and missing-tab append, so a stale saved copy is normalized before it is compared; preserve the hidden set through the swap; and write NOTHING back, so hydration stays a pure read and the user's document is untouched until they next reorder. **Exactly one generation migrates** -- an older default (here the pre-Calendar 0.5.42 order) is deliberately left alone, because chaining generations turns the one equality back into a heuristic. This narrows v0.5.41/v0.5.42's "saved layouts preserved" to **"saved CUSTOM layouts preserved"**, which is the formulation to use from now on. The migration is worth doing at all, rather than letting fresh installs have it, because these documents are device-local (iCloud syncs the two data files only, never settings), so a default that reaches only fresh installs never reaches the device the change was for.

**NATIVE-side state written by NATIVE code sits outside the `storage` seam, and that is not a violation of the rule above (v1.0.13).** The seam governs the *webview's* data under `AppLocalData/data/` and exists because WKWebView wipes `localStorage`. Window geometry is the standing example: `tauri-plugin-window-state` writes `.window-state.json` into `app_config_dir()` with `std::fs`, because geometry must be applied before the first frame and the seam is read after boot (a seam-based version would open at the configured default and visibly jump, and would need a new JS window-management grant to move the window at all). Such a file never passes through `TauriStorage`, never joins `docChains`, adds nothing to `settings.json`, and is never synced -- it is device-local by nature, so the iCloud scope statement and `PRIVACY_POLICY.md` are unaffected. Do not "fix" `src-tauri/src/window_geometry.rs` into the seam. Two things ride with it, both in `.claude/rules/security.md`: such a document stays out of the webview's granted `fs` scope only while its name begins with a DOT (on macOS `app_config_dir()` and `app_local_data_dir()` are the same directory), and every native read of a file outside the sealed bundle owes the `record_text_at` regular-file-plus-size-bound treatment.

**Two macOS facts for any native window work, both measured rather than inferred (v1.0.13).** `available_monitors()` returns an **EMPTY** list on macOS 26 -- tao 0.35 backs it with `CGGetActiveDisplayList`, which now reports a count of zero, reproduced standalone with no Tauri involved; `primary_monitor()` and `current_monitor()` still work, and `NSScreen` is the supported enumeration. Anything that walks that list on macOS silently does nothing, which is how the window-state plugin's position restore was dead on arrival (`window_geometry.rs` reapplies position itself for exactly this reason). And `set_size`/`set_position`/`maximize` are **asynchronous** on macOS, so at `setup()` the live window still reports the config defaults: decide from the SAVED record, never from `is_maximized()`. Separately, prefer a shared compile-time constant to a runtime lookup for a compile-time value -- `window_geometry::STATE_FILENAME` replaced an `AppHandleExt::filename` call, which is a `Manager::state` lookup that panics when unmanaged, and under this repo's `panic = "abort"` release profile that aborts during `setup()` with no window ever shown. `let _ = fallible()` swallows `Err`, not panics, so a "this cannot keep the app from starting" claim must account for panicking calls too.
