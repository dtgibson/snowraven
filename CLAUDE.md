# CLAUDE.md

This file is auto-loaded by Claude Code at the start of every session.
It holds pipeline conventions, tool rules, and project-specific
decisions that all builders must follow.

## Versioning

- Version is tracked in `frontend/package.json` (semver, patch increments for small features/fixes, minor for larger features)
- **Bump BOTH `frontend/package.json` AND `src-tauri/tauri.conf.json` to the same version.** `tauri.conf.json` is the source of the desktop *bundle* version (macOS `CFBundleShortVersionString`, Windows installer version, and the in-app updater's version check) and does NOT read from `package.json`. Forgetting it ships a mislabeled bundle and breaks the updater; `release.sh`'s version guard catches the macOS side, but the Windows installer is built by CI from `tauri.conf.json` at the tagged commit, so the tag must point at a commit where both are bumped. (Patch-only by default — never minor/major unless explicitly told.)
- `CHANGELOG.md` at the repo root must be updated with every version bump
- **Always bump the version and update the changelog when adding a feature or fix**, even if the user does not ask
- **A dev-only / toolchain change that does NOT affect the shipped bundle — a dev-dependency `npm audit fix`, a lockfile refresh, test-only tooling — does NOT require a version bump, changelog entry, tag, or release.** It produces a byte-identical app, so commit it straight to `main`; it reaches the release machine on the next `git pull`. The "always bump" rule above is about user-facing features and fixes. (Precedents in `DECISIONS.md`: the `dev-dependency-cleanup` `undici` patch, and the Node-25 release-tooling fix — both "no version bump.")
- **After pushing a version bump, run `./release.sh`** to build, notarize, and publish the macOS desktop app. This script creates the GitHub release (or uploads to an existing one), signs the updater bundle, and generates `latest.json` for in-app update detection. Credentials (Apple API key, notarization) stay local — never stored in GitHub.
- **Do not use `gh release create` directly** for desktop app releases — always use `release.sh` so the signed binary and `latest.json` are included. The in-app update check depends on `latest.json` being present in the release assets.
- **Tauri v2 macOS updater mechanism:** `downloadAndInstall` performs synchronous in-place bundle replacement — no shell script, no sleep, no `open -a`. The `.app` bundle is fully replaced on disk before the Promise resolves. After `downloadAndInstall` returns, call `relaunch()` (not `exit(0)`). `relaunch()` spawns `current_exe` (now the new binary) and exits cleanly. `exit(0)` just terminates the process with no relaunch, leaving the user with no running app.
- **macOS ships a UNIVERSAL binary (v0.5.5+).** `release.sh` builds `--target universal-apple-darwin`, so one DMG (`SnowRaven_<ver>_universal.dmg`) and one updater bundle (`SnowRaven.app.tar.gz`) run on both Apple Silicon and Intel. With an explicit `--target`, Tauri nests the bundle under the target triple — `$CARGO_TARGET_DIR/universal-apple-darwin/release/bundle/...`, not `release/bundle/...`. The build needs BOTH Rust targets installed (`rustup target add aarch64-apple-darwin x86_64-apple-darwin`); `release.sh` preflights this and aborts with the install command if either is missing.
- **`release.sh` Intel arch:** `latest.json` maps BOTH `darwin-aarch64` and `darwin-x86_64` to the one universal updater bundle (same URL, same signature). The Intel key must be exactly `darwin-x86_64` — Tauri's `updater_arch()` returns `"x86_64"` on Intel, so mapping it to `"x64"` means Intel users never see any update as available.
- **`createUpdaterArtifacts: true` is required in `tauri.conf.json`** — `@tauri-apps/cli` v2.11.2+ defaults this to `false`. Without it, `tauri build` creates the `.app` and `.dmg` but skips the `.app.tar.gz` updater bundle entirely. The setting must be in `bundle.createUpdaterArtifacts`.
- **`release.sh` version guard:** After the build, `release.sh` reads `CFBundleShortVersionString` from the bundle's `Info.plist` and aborts if it doesn't match `tauri.conf.json`. This catches stale-artifact issues before anything is uploaded to GitHub.
- **The release machine MUST be on the pinned Node (`.nvmrc` = 24; `frontend/package.json` `engines.node >= 20.19`), and `release.sh` is self-healing (mac-release-build-blocked post-mortem).** A bleeding-edge/non-LTS Node (e.g. 25) crashes `npm ci` with npm's internal `Exit handler never called!` (npm/cli#8766) — this blocked the 0.5.45 release for days on a Mac that had drifted to Node 25, while the build VM (Node 24) and Windows CI (Node 20) installed the identical lockfile fine. `release.sh` now runs `npm ci` ITSELF at BOTH the repo root AND `frontend` (the **root** install provides the `tauri` CLI that `npm run desktop:build` resolves from root `node_modules/.bin` — a frontend-only install dies with `tauri: command not found`), and preflights — loudly, each naming its remedy — the required tools, the Node version against `.nvmrc`, `gh auth`, npm-registry + GitHub reachability, and a clean working tree, all BEFORE the slow build. Dev and releases now run on ONE machine — **Hephaestus**, the single dev+release Mac (the build VM and the old release Mac are retired); Node 24 is the nvm default wired into its `~/.zprofile`, which the `zsh -lc` login shell sources, so its whole release job is just `zsh -lc ./release.sh` — no manual `nvm use`, and no separate manual `npm ci` (release.sh runs the root + frontend installs itself). Homebrew's `node` on Hephaestus is 26 and is deliberately NOT used for this project. Dry-run the portable half (preflight + `npm ci`) with `CHECK_ONLY=1` (other knobs: `SKIP_NPM_INSTALL`, `ALLOW_DIRTY`, `ALLOW_NODE_MISMATCH`, `ALLOW_NPM_INSTALL_FALLBACK`). The signing/notarization/`latest.json` logic is unchanged. Bump `.nvmrc` deliberately (a logged decision) on any toolchain move.
- **Run `release.sh` from a non-GUI / automation context with `CI=true`** so Tauri passes `--skip-jenkins` and builds the DMG headless. Tauri's `bundle_dmg.sh` styles the disk-image window with Finder AppleScript (`osascript`), which needs a logged-in GUI session; without one the DMG step dies with `failed to run bundle_dmg.sh`. `CI=true` skips that GUI-only styling, so the raw DMG comes out unstyled — but `release.sh` then **re-applies the install-window layout headlessly**, injecting a committed `.DS_Store` (`src-tauri/dmg/dmg-DS_Store`, captured from a prior styled release, copied in with `hdiutil` right before notarization), so the shipped DMG is styled identically to an interactive build. Regenerate that template only if the DMG's volume name or item names change. **codesign/notarize/`latest.json` are unaffected** (they work cross-session). The seamless headless command is `CI=true SKIP_NPM_INSTALL=1 zsh -lc ./release.sh` (drop `SKIP_NPM_INSTALL=1` for a cold checkout). An interactive logged-in desktop run needs no flag (its Finder styling and the injected `.DS_Store` produce the same layout).
- **The shipped DMG *container* carries no code signature, BY DESIGN — a `codesign -dv` on the DMG reporting "not signed" is not a release regression (v0.5.74 ship).** The `.DS_Store` styling step above re-converts the disk image (`hdiutil convert` → UDRW, attach, inject the layout, detach, convert back to UDZO) *after* `tauri build` has signed it, which writes a NEW image file and drops the container signature. Everything that actually gates a user's download still holds: the converted DMG is what gets submitted to `notarytool` and `stapler staple`d (the styling deliberately runs BEFORE notarization so the ticket staples the final image), and the `.app` inside it is Developer-ID signed by the build. The signature the **updater** verifies is the minisign one on `SnowRaven.app.tar.gz`, never the DMG wrapper. Don't "fix" this by re-signing the DMG or by moving the styling after notarization — the latter would invalidate the staple.

- **After a Hephaestus reboot, the login keychain is LOCKED for remote (SSH/tailnet) sessions — every signing step fails until the USER unlocks it (v0.5.73 ship).** Symptoms: `codesign`/`xcodebuild -exportArchive` dies with `errSecInternalComponent`, `security show-keychain-info` says "User interaction is not allowed," and git's osxkeychain helper fails with `-25308`. The fix is once per reboot: the user runs `security unlock-keychain ~/Library/Keychains/login.keychain-db` in THEIR OWN terminal on the machine (a second ssh is fine). Claude cannot collect the password — the in-chat `!` command has no interactive TTY, so `security` reads EOF and fails without ever prompting; never ask for the password in chat. Check `security show-keychain-info` before a ship to catch this up front. (For git pushes, `git -c credential.helper='!gh auth git-credential' push …` sidesteps the keychain entirely.)
- **`release.sh` runs `touch src-tauri/src/main.rs` to force a Cargo relink, so a running `npm run desktop:dev` watcher will rebuild and RELAUNCH the dev app mid-release (v0.5.74 ship).** Harmless — the dev app and the release build use separate target dirs, and the release is unaffected — but it looks alarming if unexplained, and it matters when a live preview is being shown to the user during a ship: their app window will disappear and come back on its own. Either quit the dev watcher before releasing, or tell the user to expect the relaunch. Don't chase it as a crash.

### Windows desktop release (v0.4.0+)

- **Windows builds run in GitHub Actions** (`.github/workflows/windows-build.yml`, `windows-latest`), triggered by pushing a `v*` tag. The build uses a *throwaway* signing key (discarded) only so Tauri produces the artifacts; `release.sh` re-signs locally with the real key. The real minisign key never goes to GitHub — same keep-it-local stance as the Apple credentials.
- **`release.sh` is the single multi-platform assembler.** It builds + notarizes macOS, then `gh run download`s the CI Windows installer, signs it locally, and writes ONE `latest.json` with both `darwin-aarch64` and `windows-x86_64` entries. `SKIP_WINDOWS=1` publishes macOS-only (emergencies).
- **Release rhythm:** bump version → commit → push to main → push the `vX.Y.Z` tag (starts Windows CI) → wait for CI → run `./release.sh` → **ship the iOS TestFlight build for the same version** (see the iOS section below). The tag must be pushed *before* `release.sh` so the CI artifacts exist to fetch. **A release goes to ALL available platforms, every time (user direction, v0.5.78)** — `release.sh` covers macOS + Windows + `latest.json`, the Pages workflow covers the website, and the iOS TestFlight upload is the remaining manual leg; a release is not done until it has shipped.
- **A re-pushed `vX.Y.Z` tag leaves a stale successful Windows CI run that `release.sh` can mis-select (0.5.34 post-mortem).** `release.sh` picks the Windows installer from the most-recently-*created* successful `windows-build.yml` run (`gh run list --workflow windows-build.yml --status success --limit 1`), and its only guard checks the installer *filename* contains the version — which CANNOT distinguish two runs of the same version. If the tag was moved (a false-start: tag pushed at commit A, then re-pointed to commit B), the first push's run for orphaned commit A stays a *successful* run; if A's run is newer-created than B's, or B's run hasn't finished yet, `release.sh` silently ships A's binary (the version-filename guard passes either way). **Standing check before running `release.sh` after any tag re-push:** verify the selected run's commit equals the tag commit — `gh run list --workflow windows-build.yml --status success --limit 1 --json databaseId,headSha` and confirm `headSha == git rev-parse vX.Y.Z^{commit}`. You can't cancel a run that already completed; rely on the create-order (the correct re-push is newer) and wait for *that* run to go green before releasing.
- **The Windows updater target is the NSIS installer itself (`*-setup.exe`), NOT a `.nsis.zip`.** Tauri v2 signs the installer (`.exe.sig`) for updates on Windows; there is no separate archive. The `latest.json` `windows-x86_64.url` points to the `-setup.exe`.
- **Cross-platform Rust deps must live in `[dependencies]`, not `[target.'cfg(target_os = "macos")'.dependencies]`.** `tzf-rs` (used by the cross-platform `get_timezone` command) was mis-scoped there and broke the Windows build with "unresolved import." The macOS-only block is only for genuinely macOS-only crates (objc2*, the CoreLocation stack).
- **`tauri signer sign`: don't pass `--private-key-path` (`-f`) when `TAURI_SIGNING_PRIVATE_KEY` is already exported** — the env key and the path flag are mutually exclusive. `release.sh` exports the env key for the macOS build, so the Windows-install signing step relies on the env, no flags.
- **Windows is distributed unsigned** (no Authenticode) for now — first launch shows a SmartScreen "unknown publisher" prompt. The in-app updater is unaffected (minisign verification, not Authenticode).

### iOS release (TestFlight)

- **Every desktop/web release is followed by an iOS TestFlight build of the SAME version, build 1 (standing rule since v0.5.78; user direction).** iOS is no longer a selective catch-up — run the recipe below after `release.sh` verifies, on every release, bundled Spool releases included. iOS-only follow-ups still increment the build number without a desktop release.
- **iOS app icons must be fully OPAQUE — NO alpha channel — or App Store Connect rejects the upload (altool error 90717).** The check is on the large 1024 app icon and it fires on *any* alpha channel, even a fully-opaque/redundant one (the SR icons carried an all-opaque alpha with anti-aliased edges and were still rejected on the first upload). Keep BOTH `src-tauri/icons/ios/` AND the committed `gen/apple` AppIcon.appiconset (`src-tauri/gen/apple/Assets.xcassets/AppIcon.appiconset/`) flattened to opaque RGB — composite onto white and save with NO alpha (all 18 PNGs). The desktop icons (`tauri.conf.json` `bundle.icon`, `src-tauri/icons/icon.png`) MAY keep their alpha — this rule is iOS-only. `gen/apple` is a committed generated artifact, so the flattened icons must be committed there (re-running `tauri ios init` would re-stamp Tauri's placeholders — don't rely on init). Precedent: the v0.5.68 iOS icon fix (`e070d73` icon swap + `21fd5b2` flatten).
- **iOS build + TestFlight upload is Claude's to run (same posture as `release.sh`), and is NOT `release.sh`** (that assembler is macOS + Windows desktop only). The recipe (full detail + fallback in `pipeline/mobile-app/how-to-see.md`): `tauri ios build` SCRUBS `DEVELOPER_DIR` from the `xcodebuild`/`xcrun` it spawns, so build through the `/tmp/xcshim` wrapper (`printf` the two shim scripts that re-export `DEVELOPER_DIR` and `exec` the real tool, `chmod +x`, then `PATH=/tmp/xcshim:$PATH`) AND `export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer` in the parent shell. Do NOT `sudo xcode-select` (it needs a password). Build the TestFlight archive with `--export-method app-store-connect --build-number N`, then upload with `xcrun altool --upload-app -f <ipa> -t ios --apiKey $APPLE_API_KEY_ID --apiIssuer $APPLE_API_ISSUER_ID` (the App Store Connect API key + issuer live in the login shell / `~/.appstoreconnect/private_keys/`). An iOS-asset-only change (like the icon fix) does NOT bump the desktop version — it ships as an iOS build-number increment against the current version (v0.5.68 build 2), no `release.sh`, no tag, no `latest.json`.
- **`tauri ios build` STAMPS the committed `gen/apple/snowraven_iOS/Info.plist`** (`CFBundleShortVersionString` + `CFBundleVersion` from the version and `--build-number`), so an iOS build leaves the working tree dirty. **Commit the stamp before `release.sh`** (its clean-tree preflight aborts otherwise) — a one-line `chore(ios): stamp iOS <ver> build <n>` commit, precedent `c505f2e` (v0.5.73) and the v0.5.71 closeout stamp.
- **`tauri ios build --export-method app-store-connect` ALSO needs the App Store Connect API key under TAURI's env names for its export/signing step — DISTINCT from the `altool` upload creds, and a real gap in the recipe above (hit + fixed on the 0.5.69 iOS build).** The upload step reads `APPLE_API_KEY_ID` / `APPLE_API_ISSUER_ID` from the login shell (passed to `altool --upload-app` as `--apiKey` / `--apiIssuer`); the *build/export* step reads three different names — `APPLE_API_KEY` (the key id), `APPLE_API_ISSUER` (the issuer id), and `APPLE_API_KEY_PATH` (path to the `.p8`). Map the login-shell ids across before building: `export APPLE_API_KEY="$APPLE_API_KEY_ID"; export APPLE_API_ISSUER="$APPLE_API_ISSUER_ID"; export APPLE_API_KEY_PATH="$HOME/.appstoreconnect/private_keys/AuthKey_$APPLE_API_KEY_ID.p8"`. Without all three the build dies at export with `APPLE_API_KEY, APPLE_API_ISSUER and APPLE_API_KEY_PATH must be provided for code signing`. Do this every iOS ship so the next one doesn't repeat it.

## Conventions

### Ports
- Backend runs on port **1620** (not 8000)
- Frontend dev server runs on port **5173** (Vite default)
- Vite proxies `/weather`, `/tide`, `/nominatim`, and the other backend route prefixes to `http://localhost:1620` (see `frontend/vite.config.ts`). **When you add a backend route, add its path prefix to that proxy.** Otherwise the web-dev path hits Vite's SPA fallback (HTML) instead of the backend and the call silently fails under `npm run dev` — this bit the new `/tide/at` route in 0.5.34 (and, latently, the existing checklist tide, which is normally exercised only via the desktop app or the FastAPI-served build).

### Environment
- API keys live in `backend/.env` — never commit this file
- Required keys: `EBIRD_API_KEY`, `OPENWEATHER_API_KEY`
- OpenWeather key must be subscribed to "One Call by Call" at openweathermap.org
- **The on-disk data directory is single-sourced in `backend/datadir.py` (`DATA_DIR`, overridable with `SR_DATA_DIR`) — a backend module that reads `data/` MUST import it, never re-derive `Path(__file__).parent…/"data"` (v0.5.77).** Four routers (`settings`, `settingskv`, `mapdefaults`, `taxonomy`) each derived it independently until the override was added; a **partial** override is worse than none — the app would read demo data on one route and real data on the next, which is precisely the privacy failure the override exists to prevent (it lets the website screenshot capture drive a throwaway synthetic dataset instead of `mv`-ing the user's real eBird export aside). `backend/tests/test_datadir.py` asserts every consumer resolves through the one module, so a new router that re-derives its own path fails the suite — extend that test rather than adding a parallel one.
- **An env var read at MODULE IMPORT time cannot be set in `backend/.env`, and fails SILENTLY when you try (v0.5.77).** Routers import while `main` is still importing, which is before `load_dotenv()` runs, so an import-time `os.environ` read never sees a `.env` value — the code just uses its default with no error. `SR_DATA_DIR` is the live example and must be set in the process environment before the backend starts. The API keys above are unaffected (they are read per-request, after `load_dotenv()`). The same import order is why a file write can never redirect the data root — the security-positive half of the same fact, so don't "fix" it by moving the read later. State both halves at the definition site (`backend/datadir.py`'s docstring is the reference).

### Stack
- Backend: Python 3.10+, FastAPI, Starlette, uvicorn, httpx, timezonefinder
- Frontend: React, Vite, TypeScript, Tailwind CSS v4, shadcn/ui
- Tests: pytest (backend), vitest (frontend)
- CI: GitHub Actions (`.github/workflows/pipeline.yml`)

- **Backend runtime and CI verification versions are exact security/reproducibility pins (v0.5.72).** Keep `backend/requirements.txt` at the audited compatible runtime set (`fastapi==0.141.1`, `starlette==1.3.1`, `python-multipart==0.0.32`, `python-dotenv==1.2.2`) until a deliberate, tested upgrade. Keep backend CI's development tools explicit too: `ruff==0.15.20` and `pytest==9.1.1`; never restore unconstrained `pip install ruff pytest`, which made a tagged release depend on whatever PyPI served that day.

- **No impure calls during render — `react-hooks/purity` is enforced by eslint (build-blocking).** Never call `Date.now()` / `new Date()` (or other impure functions) inside a component render body or a `useMemo`/`useCallback`. For a "now" reference in recency / time-window filters, use a module-level session constant (`const SESSION_NOW_MS = Date.now()` at module top) and read it in the memo, or thread a `nowMs` arg into a pure helper — the pattern in `MapExplorer.tsx` (the Time Range window) and `BirdingStats.tsx`. Event handlers may call `Date.now()` directly (they don't run during render).

- **A histogram whose bin count derives arithmetically from a data VALUE (not from row count or distinct values) must bound its ladder structurally in the compute layer (v0.5.78).** The CSV parser admits any `parseInt`-able integer, so one corrupt cell can otherwise mint millions of bins (~3 GB heap and a render-time `RangeError` from a `Math.max(...spread)` — the checklist-duration Medium, empirically confirmed). `computeDurationBins` (`lib/birdingStats.ts`) is the reference: a plausible-range input guard (`[0, 1440]`, eBird's 24 h checklist cap — out-of-range rows fall into the honest "N of M have a usable duration" coverage note) PLUS a structural `DURATION_MAX_BIN_INDEX` clamp so the ladder is bounded even if the guard is bypassed. Pair it with reduce-not-spread for any `Math.max`/`Math.min` over a data-length array (bounded spreads over fixed-size arrays are fine). A histogram bounded by distinct values (the observer-count chart) is a different, inherently bounded shape — do not generalize from it.

- **When a preference's copy multiplies combinatorially (N independent toggles means 2^N labels), GENERATE it from one ordered manifest plus pure functions — never a hand-written lookup table (v0.5.81).** `SHARE_PARTS` in `lib/shareLocation.ts` is the reference: one ordered table drives the payload lines, the switch labels, their accessible names, the popup button label, and the mode sentence, so adding a fourth destination is one row and zero new copy. Three properties are load-bearing:
  - **Keep the manifest noun its OWN column, never the visible label lowercased.** The one-column-plus-`.toLowerCase()` shortcut reads correctly on today's rows and silently produces "Bing maps link" on the next one. Same class of trap: a `countWord` ladder that stops at the shipped count and starts mixing a digit into a sentence of word forms.
  - **The generic functions take the driving table as a DEFAULTED parameter, and the suite proves the claim by actually adding a hypothetical extra row** and asserting every derived output from it. Extensibility asserted only against the shipped table is untested by construction; this is the mechanism that surfaced the noun trap before it shipped.
  - **Where a copy decision rests on a rendered measurement (a character ceiling, a wrap count, a fixed-width container), state the number AND keep a test that fails if the generated string exceeds it.** The prose figure alone drifted by one character here with nothing failing.
  A structural state (all toggles off) is a structural answer, not an extra string: **no control that looks pressable may put an empty string on the clipboard** — replace the control with a sentence rather than disabling it.
- **A displayed whole-percent share for a NONZERO count must never render a bare rounded "0%" (v0.5.79).** Route share display through `fmtSharePct(count, total)` (`lib/statsFormat.ts`) — "<1%" for a nonzero share that rounds to zero, honest "0%" only for a truly zero count — never raw `Math.round(count/total*100)`.

### Running tests
```
cd backend && python -m pytest tests/ -v
```

- **`frontend/src/test-setup.ts` installs baseline `requestAnimationFrame`/`cancelAnimationFrame` shims for every test file** (wired via vitest `test.setupFiles` in `vite.config.ts`). Reason: recharts bundles `@reduxjs/toolkit`, whose autoBatch fallback timer (100 ms, calls bare `cancelAnimationFrame`) can outlive a jsdom test file and fire in a later DOM-less node-env file in the same worker — the source of the old ~11% full-suite flake. Never remove the shims or convert them to per-test `vi.stubGlobal` stubs (per-test stubs can't cover timers that fire after their file's environment is torn down). The shims are `typeof === 'undefined'`-guarded, so jsdom files keep their natives and a file's own stubs still win.
- **Component tests that stub a scheduling queue must wait on an observable stub-queue precondition before flushing.** A `waitFor` on rendered DOM resolves on the React commit, which under suite load can land BEFORE a passive effect queues into the stubbed queue — flushing then drains an empty queue and the test asserts against a frozen shell (the BirdingStats frozen-shell flake). After the DOM wait, add `await waitFor(() => expect(rafQueue.length).toBeGreaterThan(0))` (or the equivalent for the stubbed queue), then flush. Never assume effect timing relative to `waitFor`, and never substitute a wall-clock sleep. Reference: `renderAndLoad()` in `BirdingStats.test.tsx`.
- **A strict performance contract may sample complete executions to resist shared-runner scheduling noise, but may not weaken its threshold (v0.5.72).** Calendar QA-41 still requires one complete `buildDayCells` execution below 50 ms; it measures seven full executions and asserts their minimum. Do not time partial work, raise the limit, or discard the contract. Use this bounded repeated-measurement pattern only for deterministic work whose isolated baseline is comfortably below the threshold and whose one-off wall time is vulnerable to unrelated parallel test load. **A performance assertion needs margin AND repetition, and 2x is not margin (v0.5.84).** Where an isolated baseline sits within ~2x of the ceiling, a single measurement will breach under ordinary CI contention; measure the baseline against the ceiling explicitly before choosing the fixture size, and where a fix opens an enormous gap (bounded vs unbounded regex, scan vs backtracker) buy the margin from that gap rather than from a quiet machine. The two v0.5.84 guards sit ~30x and ~15,000x under their ceilings and 6x and 12-46x over the defect, a gap no shared runner closes in either direction. Each timed run must also defeat any memo on the path (a distinct input per run), or the guard measures a cache hit.

- **A FIXED-SIZE CACHE'S PERFORMANCE CLAIM MUST BE MEASURED AT CAPACITY PLUS ONE (v0.5.85).** At capacity it never evicts and every measurement after the first is a hit, so it reports its best case as if it were its typical case — and a hostile input set is chosen by whoever supplies the data, for whom one key more than the cache holds is the cheapest possible attack. This produced **both** High findings on `normalizeSpeciesName`'s memo bound, and then invalidated the remediation proposed to fix the first. Measured through the real module, min of interleaved rounds with rotating start order: the over-length **single slot** cost 3,493.7 ms on two alternating 40,000-character names against 2.4 ms uncapped (a one-entry cache is defeated by two keys, and it had been benchmarked on one repeated name); the short cache evicting **FIFO** cost 2,544.9 ms at capacity+1 on ordinary 24-character names, **167x worse than having no cache at all**, on 32,769 distinct names, which is 0.75 MB of name data in a CSV well under 5 MB. **Admission control — fill to the limit, then stop admitting, never evict — is identical below capacity and 34x, 11x and 85x better at capacity+1**, which is why the reviewer's recommended character-budgeted FIFO was not adopted unmodified: it had been measured at 8 rotating names against a capacity of 26, the same below-capacity class of measurement that let the slot through. Four rules follow, each of which was a live wrong turn:
  - **State the guarantee STRUCTURALLY (entry count, key length, slot occupancy, character budget), never as a byte product.** Three measurements of the same design gave 172, 208 and 173 B/entry; the first assertion built on one of them (`32,768 x 172 B < 6 MiB`) stated a ceiling the true worst case exceeds **and passed anyway**. ### Responsive layout — standing conventions

The app is responsive from ~320px phones to large desktops (the 0.5.37 sweep, extended by the 0.5.55 mobile-prep pass with touch-target sizing and iOS input-zoom lenses). The rules:

- **Make layout responsive by LIFTING it to a class, never with an inline style.** React inline styles are specificity 1,0,0 and BEAT class rules, and an inline `display:grid`/`flex` can't be reached by a media query — that is exactly why `.sr-two-col`/`.sr-compare-panels` and the sweep's hooks exist. To make a container respond, REMOVE its inline `display`/`gridTemplateColumns`/`flex-direction`/`flex-wrap`/`gap` and add the class; keep colors/padding/borders inline (tokens only). The sanctioned inline exceptions are responsive-by-construction (no breakpoint math): px→rem width conversions and `minmax(min(<px>, 100%), 1fr)` self-collapse tracks so a fixed track shrinks below a phone width instead of overflowing.
  - **An inline `alignItems` on a flex container is a latent CROSS-AXIS WIDTH constraint on every child, which activates the moment a tier flips that container to `flex-direction: column` (v0.5.83).** The child then shrink-to-fits to its widest descendant's min-content, and the child's own `minWidth: 0` is powerless because it relaxes the MAIN axis. That is the Help overlay defect: `.sr-help-row`'s inline `alignItems: 'flex-start'` is load-bearing above 640 (the sticky TOC) and became a width rule below it, sizing the prose column to a `white-space: pre` coordinates block's longest line (494px at 1x, 955px at 200%). **Before adding a `flex-direction: column` override to a tier, check what the parent's `align-items` will start governing — and fix it at the CHILD** (`align-self: stretch` + `width: 100%`, `!important` to out-rank the child's own inline block), never by weakening the parent. Constraining the column is necessary but not sufficient: an unbreakable URL-shaped string or a long single word still leaks, so pair it with a wrap allowance (`overflow-wrap: anywhere; word-break: break-word`) written INTO the tier rule rather than by attaching the unconditional `.sr-wrap-anywhere` class, whose reach would extend past the tier the evidence covers.
- **The shared layout vocabulary (all in `globals.css`):** `.sr-action-row` (a label + trailing action(s) row that wraps instead of overflowing; give the growable child `.sr-min0`; add `.sr-action-row-stack` to stack ≤480), `.sr-grid-2/-3/-4` (fixed N-up that collapses 3/4→2 at ≤1024 and all→1 at ≤640), `.sr-grid-auto` (self-collapsing `auto-fill minmax(--sr-grid-min,1fr)` — no breakpoint math; best default for tile grids), `.sr-grid-chart-aside` (content + a pie/donut aside that stacks ≤640), `.sr-field-row` (inline form controls that stack ≤480 where native date inputs can't shrink), `.sr-scroll-x` (contained horizontal scroll for wide tables), leaf helpers `.sr-min0`/`.sr-truncate`/`.sr-wrap-anywhere`, `.sr-pad-x-trim` (trim component-local side padding on phones), and `.sr-map-explorer-panel`.
- **The 0.5.55 mobile-prep additions (also `globals.css`) — use these, don't re-inline:** `.sr-touch-target` (raises a dense fixed-height button/pill toward ~44px min-height, in the ≤640 tier ONLY — desktop density is untouched; it does not change the visible glyph/label size, and a control that must be 44px on desktop too needs its own rule), `.sr-map-popup-body` (wrap the inner content div of any map popup that can grow tall — `max-height: min(60dvh, 26rem)` + internal scroll + `overscroll-behavior: contain`, so it never runs off a short phone viewport), `.sr-input-16` (add to any `<input>`/`<select>`/date-time control carrying a sub-16px inline font-size — sizes it in the ≤640 tier to suppress iOS focus-zoom; **the one place a px font-size is correct**, since the iOS zoom threshold is an absolute px value, and it avoids a `maximum-scale` viewport clamp that would kill pinch-zoom. **The class must sit on the `<input>`/`<select>` element ITSELF and out-rank its inline font-size** — the rule carries `!important` precisely because the thing it must beat is an inline style (specificity 1,0,0); put it on a wrapper, or leave the rule non-`!important` against an inline sub-16px font, and the guard is silently inert. This was inert on ~25 inputs app-wide until fixed in v0.5.61), `.sr-ctl-row` (v0.5.81 — put it on a **filter block**, and every interactive descendant inside it gets one phone-tier text size; it sizes descendants, never the container), and `.sr-wrap-flex` (wrapping inline flex control groups / header rows — lift the inline `display`/`flex-wrap` here, keep gap/colors inline or via `--sr-wrap-gap`). The `index.html` viewport carries `viewport-fit=cover`.
- **A phone-tier size that must clear an absolute px floor AND stay consistent with a scale-tracking neighbour is written `max(<px floor>, <rem>)`, ONCE, as a single declaration covering both sides (v0.5.81).** The old flat `.sr-input-16` value satisfied the 16px iOS floor and nothing else: at 1x it left pills at 12px beside 16px selects in the same wrapping filter row, and at 200% in-app text scale it INVERTED (pills 24px, controls still pinned at 16px), so the controls became the small ones for exactly the user who enlarged their text. `font-size: max(16px, 0.75rem) !important` in the ≤640 tier is shared verbatim by `.sr-input-16` and `.sr-ctl-row :is(button, select, input)`; the two sides can never differ at any scale, which two rules holding two literals that agree today cannot promise. State the guarantee as a property of the FORMULA across the whole input domain (`max(16px, rem)` is ≥16px for every value of `rem`, including a browser/OS default font size the user has lowered), not as "it computes 16px at 1x and 24px at 200%" — sampling the four in-app text scales would have missed that `rem` also tracks the browser default. The two selectors deliberately differ in specificity ((0,1,0) vs (0,1,1), both `!important`), which is exactly why they must share one declaration and a test must lock the values identical: then which one governs a guarded control is moot rather than reasoned about. Guard: `frontend/src/lib/filterControlSizeCss.test.ts` (parses the real `globals.css`, same posture as `milestoneContrast` / `countyContrast` / `calendarContrast`). **Corollary for VERTICAL fit, which the formula answers structurally so it needs no measuring (v0.5.82):** `max(16px, <rem>)` never TIGHTENS a box whose inline size is already that rem. It raises only while the rem is below 16px (below ~133% text scale, where it pins to exactly 16px); above that it returns the rem, i.e. the inline value the box was already built for. So a fixed-height control guarded this way cannot start clipping vertically at any scale — which is why adding the guard to nine controls sitting in fixed 34px boxes needed no accommodation.
- **A phone-tier size guard that makes a row stop FITTING inside a fixed-width container needs a companion layout rule, and the companion belongs beside it in the same tier, scoped to the feature's own subtree (v0.5.82).** Raising a control to 16px can push a side-by-side pair past its container: the Map Explorer's Date Range pair renders `08/09/2026` at 12px and `08/09/202` at 16px in the 120.5px each gets from a 282px sidebar. The repair is a `.sr-field-row` stacking rule scoped to the map sidebar through the whole ≤640 tier — NOT widening `.sr-field-row`'s own 480 breakpoint, which has six consumers and would restack five surfaces that sit in the full-width main panel with 220px+ per field and have no problem. Never weaken the `.sr-input-16` guard to resolve a clip; the guard is the requirement and the layout is what yields. Same "prefer the rule that lives inside the feature's own subtree" principle as the scroll-margin case above.
- **Put a control's font size on the control ELEMENT, not on a label span nested inside it (v0.5.81).** A size on a descendant beats any class on an ancestor, so a container rule like `.sr-ctl-row` cannot reach it — and the two forms are visually indistinguishable until the container rule exists, so this is invisible in review. Calendar's local `Switch` declared its size on the label `<span>` and would have stayed small beside everything else in its strip; the declaration moved up to the `<button>` (the span inherits, so desktop is byte-identical) and a test pins it. Corollary when measuring: a font size read off a control's box is not the size the user reads — measure the text-owning element.
- **A `rem` cap inside a fixed-`px` container measures the wrong thing — measure the container (v0.5.80).** `--sr-text-scale` multiplies the root font size, but a `height: 220px` card (the Named Birds card map) does not follow, so a `rem` max-height GROWS on a container that did not, and at 200% text scale it can double. When a popup or panel must fit a px-measured box, compute the cap from container geometry and write it as a **px custom property from a ref side effect** (no `setState`, no render-time measurement), with a floor at the ~44px touch-target size so the cap can never shrink a control out of reach. `SharePopup.tsx`'s `COMPACT_BODY_MAX_PX` / `COMPACT_BODY_MIN_PX` / `COMPACT_CHROME_PX` / `COMPACT_EDGE_MARGIN_PX` are the reference. This does NOT replace `.sr-map-popup-body` (`min(60dvh, 26rem)`) — that one is correct because its constraint is the *viewport*, not a container. Known modelling limit: `COMPACT_CHROME_PX` is a fixed px estimate of partly rem-sized chrome, so it under-estimates at large text scales; the cap itself is sound. **The CONVERSE is the same rule and shipped as a defect for fourteen versions (v0.5.91): a fixed px constant standing in for TEXT-SIZED chrome cannot be right at any scale.** `.sr-map-explorer-panel` was `calc(100dvh - 178px)` (132px in the phone tier) where the real header + tab nav + footer measures **223px to 484px** across five widths and four text scales, so the map's corner FABs sat below the bottom of the window until the user scrolled. `lib/mapPanelChrome.ts` is the repair and follows this bullet exactly — measure, publish a px custom property from a ref side effect, keep the old constants only as the pre-measurement fallback so first paint is unchanged. Two properties make the measurement safe rather than circular, and both are worth copying: measure the elements AROUND the sized box (here `<main>`'s two offsets, never the panel's own height), so nothing observed can change when the published value does; and REJECT an unusable reading (non-finite, negative, or a zero-height footer) rather than clamping it to 0, since publishing 0 would size the panel to a full `100dvh` and be the same defect but worse. Round with `ceil`, never `round`, so a fractional chrome cannot leave a half-pixel page scroll behind. The floor that can act on the outcome belongs in the stylesheet with the outcome (`min-height: 340px`, 300px on iOS), which is why 320px at 200% text scale still overflows by 24px by design.
- **Two standing mobile checks for new UI (the 0.5.55 lenses beyond the 0.5.37 sweep):** (1) touch targets on fixed, dense controls must meet the ~44px posture in the ≤640 tier (reach for `.sr-touch-target`); (2) no form control may ship a sub-16px font-size on phone (reach for `.sr-input-16`) or iOS auto-zooms on focus. Both hold at 320px and 200% in-app text scale.
- **Any `position: fixed` OR `position: sticky` element escapes `.sr-ios-app body`'s safe-area padding and needs its OWN `.sr-ios-app`-gated inset — and therefore cannot keep its positioning in an inline style (v0.5.81, proven three times).** `.sr-ios-app body { padding-top: env(safe-area-inset-top) }` protects every in-flow surface; a fixed element is viewport-relative and a sticky one resolves `top` against its scrollport, so both sit ABOVE that padding and render under the status bar / Dynamic Island (and, in landscape, the sensor housing). An inline `inset: 0` / `top: 0` is specificity (1,0,0) and unreachable from a stylesheet, so the positioning must be **lifted into a `globals.css` class first** (values byte-identical), which is the only thing that gives the inset somewhere to hang. Shipped instances: `.sr-map-fullscreen-panel` (map fullscreen), `.sr-help-panel` + `.sr-help-toc` (the Help overlay), `.sr-bc-matrix--pinned thead th` (the pinned Breeding Codes band), and `.sr-skip-link:focus` (the "Skip to main content" link). Rules that hold:
  - **Gate on `.sr-ios-app`, NEVER a bare `env()`.** `index.html` ships `viewport-fit=cover` to browsers too, so `env(safe-area-inset-*)` is non-zero in iOS Safari on the **web** build; an ungated rule fixes the app and silently changes shipped web rendering on every notched phone. `.sr-ios-app` is set on `<html>` by `main.tsx` only when `isIOS()`, so desktop and web stay byte-identical. Assert in the test that the ungated base rule contains no `env(`.
  - **Pad, don't shrink; top/left/right only.** Tailwind preflight's global `box-sizing: border-box` keeps a `100dvh` panel exactly `100dvh` with only its content box moving inward. Mirror `.sr-ios-app body` and add no `padding-bottom` (the FAB cluster and each overlay's own bottom padding already clear the home indicator; adding one shrinks a `flex: 1` scrollport into a dead band).
  - **A viewport-height calc INSIDE such an overlay must subtract the top inset too**, or a child capped that way over-extends by exactly the inset — invisible on a phone, live on iPad. The Help TOC's `calc(100vh - 52px)` stranded its last entries there until the gated variant subtracted it. Same family as the v0.5.80 "measure what actually bounds it" rule.
  - **Each overlay gets its OWN sibling rule; do not generalize.** The two full-screen overlays share only the three-line inset block (the map panel additionally needs `height: 100dvh` and carries a landscape coupling where the sidebar overlay reaches the padded edge through `.sr-map-content`'s `position: relative`; Help has neither), so a shared utility would still need a per-overlay positioning class and buys one declaration block at the cost of a second class name on the element. **Revisit a shared utility at a third overlay, not at two.**
  - **Watch the containing block when an inset is expected to reach a descendant.** An absolutely positioned child resolves against its nearest *positioned* ancestor's **padding box** — so a fixed panel's own padding does NOT inset an `absolute; left: 0` child unless that panel is the containing block. Name the actual positioned ancestor and assert its `position`, since removing it fails nothing today.
  - **Pad only a full-viewport box; a POINT-ANCHORED element is RE-POINTED, and only in the state that is on screen (`skip-link-safe-area`, the last of the family).** The "pad, don't shrink" rule above is the two panels' shape *because* they are `inset: 0` boxes; padding a `width: auto` pill instead grows it by the inset and paints its own background across the Island. The precedent that fits a point-anchored element is `.sr-ios-app .sr-bc-matrix--pinned thead th`, which moves an offset. Three sub-rules, each of which was a live wrong turn:
    - **Gate on the on-screen state, not the element.** `.sr-skip-link`'s base `top: -100px` is an off-screen *park* and is load-bearing: the pill is 41px tall at 1x and 62px at 200% text scale (measured, not estimated), so adding a 59px inset to the parked state — by `calc()` or by `padding-top`, both fail identically — puts its bottom edge at +21px and the HIDDEN link becomes permanently visible in the Island band. The inset belongs on `:focus` alone. Generally: before insetting a fixed element, ask which of its states the offset is describing.
    - **Only the edges the element actually declares.** `left` yes (at risk in landscape, and self-correcting — in the rotation where the housing is on the far side `inset-left` is 0 and the `calc` collapses to the shipped 16px); `right` never, because the element declares none and adding one to a `width: auto` fixed box stretches it across the viewport. This is the deliberate deviation from the two panel rules, which need both edges only because `inset: 0` pins both. Say so in a comment beside the rule, or it reads as an omission.
    - **Anchor the `calc` to the shipped literal** (`calc(16px + env(…, 0px))`), so the rule degrades to today's exact geometry wherever the inset is 0, and keep the `0px` fallback or the whole declaration is invalid where the variable is unsupported.
  - **This does NOT make it three overlays.** The skip link shares the escape and the gate, not the pad block, so the "revisit a shared utility at a third overlay" count above still stands at two.
- **Breakpoint tiers:** ~480 (small phone), **640 (the established phone boundary — don't move it; lots hangs off it)**, ~1024 (tablet), and a `.sr-panel` max-width cap (1280px, centered) for large desktops. Prefer self-collapsing `.sr-grid-auto` so most grids need no breakpoint; reserve explicit collapses for column control. Do NOT add JS `window`/`resize`/`innerWidth` checks — TabNav's ResizeObserver and the CSS tiers cover it. **When a render BRANCH (which DOM mounts, not just styling) must change by breakpoint and pure CSS can't express it**, use a render-safe `useSyncExternalStore` over `matchMedia` (`lib/useIsPhone.ts`: subscribe to the `MediaQueryList` `change` event, `getSnapshot = () => mql.matches`, `getServerSnapshot = () => false`, old-Safari `addListener` fallback), NEVER a `window.innerWidth`/`resize` listener. This is the React-sanctioned external-store media pattern (no innerWidth arithmetic, no per-pixel handler, no impure render read), so it honors the spirit of the no-resize rule while doing what CSS cannot. (NOTE: the Calendar tab NO LONGER uses `useIsPhone` to force a view — as of v0.5.68 its Compact/Large toggle governs at ALL widths, so the two views are distinct on a phone too. Earlier docs describing a phone-forced Compact calendar view are obsolete; the hook remains blessed and is still used where a genuine render-branch must flip by breakpoint.)
- **A user-relabelable / swappable toggle stores label-AGNOSTIC internal state values — what the option renders semantically (e.g. `'months'` / `'overview'`), NOT value names that encode the visible label (`'large'` / `'compact'`).** The Calendar view toggle churned labels twice: v0.5.60 coupled the enum values to the labels for "code and UI agreement," so v0.5.62's label swap would otherwise have forced a lockstep value rename. Semantic, label-agnostic values let the labels and the code drift independently — a future relabel/swap touches only the option copy, never the state values or their consumers. (The values are session-only `useState` here, so there is no persisted string to migrate either way.)
- **When a child's legibility depends on its OWN cell size — not the viewport — gate it with a CSS container query, not a viewport breakpoint.** The same viewport width yields very different cell sizes (a desktop 3-up narrow panel and a phone single column are both "narrow" to a media query but sized oppositely), so a viewport tier can't decide whether an in-cell number fits. Give the sized element `container-type: inline-size` and reveal the number span under a `@container (min-width: …)` floor; below it, hide only the number span so the cell/grid never distorts and the shading still carries magnitude. The `.sr-cal-minimonth` (152px floor) day-number reference from v0.5.60 was RETIRED in v0.5.62 (the year-overview mini-cells reverted to shading-only, so both the numbers and the container-query CSS are gone) — the pattern remains the sanctioned approach when a cell-sized number genuinely earns its place. If you re-introduce it, the px floor is the same sanctioned legibility exception as `.sr-input-16`, and size everything else in rem so it holds at 200% text scale.
- **A `position:absolute` element wider than the viewport leaks PAGE horizontal scroll on a phone even when invisible.** Two such bugs were fixed in 0.5.37 (TabNav's `visibility:hidden` overflow probe; absolutely-positioned `.sr-only` spans inside a horizontally-scrolled table). **Standing check:** any wide / `max-content` element or off-screen measurement node must sit under an `overflow:hidden` / `position:relative` ancestor so it can't extend `document.scrollWidth` on a phone. Wrap any new wide table in `.sr-scroll-x` (which carries `min-width:0` + `position:relative`); don't add a blanket `body{overflow-x:hidden}` (it would break the tables' `wideMode` page-scroll). Fixes must hold at 200% in-app text scale — size in rem, never convert rem→px to "fix" overflow. Relatedly (v0.5.91): an absolutely positioned box with only `left` set **shrink-to-fits against the space from that edge**, so the shipped loading chip's `left: 50%; transform: translateX(-50%)` gives any WRAPPING occupant of that anchor half the container's width (measured as 8 lines where 4 were expected). The chip gets away with it because it is effectively single-line; anchor a wrapping one `left` AND `right` and centre its child.
- **`.sr-wrap-flex` is INERT on a cluster that also carries an inline `flexShrink: 0` — the class needs a width cap to bind (v0.5.82).** A pinned flex container is never narrowed, and a container that is never narrowed has no reason to break a line, so `flex-wrap: wrap` computes correctly and changes nothing: the Breeding Codes count-and-view cluster measured 475px inside a 296px box with the class applied and wrapping enabled the whole time, the single largest unclipped overflower on any tab at 320px/200%. Pair the class with `maxWidth: '100%'` (responsive by construction, no breakpoint math, the same pairing `.sr-scroll-x` already uses) — measured identical in effect to dropping `flexShrink: 0`, and preferred because it keeps the do-not-get-squeezed intent rather than discarding it. Write the TEST as the invariant (given an inline `flexShrink: 0`, a width cap must be present) so either measured-equivalent form stays green and neither-of-them does not. General shape: **adding a responsive class is not evidence the layout responds** — a stylesheet test passes on an inert class, which is exactly how this one shipped inert.
- **A wrapping flex row is not contained until EVERY nested automatic minimum on the overflow path is released (v0.5.86).** At 320px/200%, the Breeding Codes filter row wrapped yet measured 327.11px inside a 272px parent because both its pill and the pill's label retained `min-width: auto`. The repair uses feature-specific hooks — `.sr-bc-filter-row`, `.sr-bc-filter-pill`, `.sr-bc-filter-pill-label` — with `min-width: 0` on both nested flex items, phone-only `height: auto !important` plus the existing 30px minimum, and `overflow-wrap: break-word` for the emergency slash-run. Do not put these layout declarations on shared `.sr-ctl-row`; other filter surfaces and wider layouts are outside the measured repair.
- **A container that sizes itself INTRINSICALLY (`width: max-content` / `min-content`) takes the maximum over ALL its children's contributions, not just the one it was built around — so a wrapping sibling silently becomes the ruler (v0.5.84).** This is the Breeding Codes Unbounded card: it was built around the table and was in fact being sized by the tier legend beside it, a wrapping row of nowrap chips whose max-content is every chip on one unwrapped line (1749px against the table's 792px). Any wrapping sibling qualifies — a legend, a chip row, a footer strip, a filter cluster — and the symptom appears somewhere else entirely, on the child that was supposed to be doing the sizing. **Constrain the SIBLING with `width: min-content; min-width: 100%`**, which lets it floor the container but never dictate it: `min-content` makes it contribute only its widest single item to both intrinsic sizes, and the percentage stretches it back across the resolved container in layout without feeding back, because a percentage is indefinite while the container is being sized intrinsically. Two forms to reject: sizing the container from a different keyword (it is still the maximum over both children, so the defect shrinks rather than goes away and returns silently the first time the content shifts), and **zeroing the sibling's contribution (`width: 0`, `contain: inline-size`) — never do this where the sibling holds unbreakable `white-space: nowrap` content**, since the container can then fall below that content's own minimum and the content hangs outside its border, which is reachable on a phone at 200% text scale.
- **The Breeding Codes matrix is BY DEFAULT a NATURAL full-height, page-scrolling table at ALL widths — NOT a capped-height frozen-header data-grid (v0.5.69, amended v0.5.81).** A frozen title row + capped-height data-grid was built and live-tested during the mobile pass, then REVERTED at the user's request for the natural table (the reason is in DECISIONS: pure CSS cannot combine a page-frozen header + an unbounded-height table + contained horizontal scroll — `overflow-x:auto` forces the vertical axis to `auto`/`hidden`, binding a sticky header to the wrapper instead of the page). The tier legend sits in normal flow after the last row. **v0.5.81 adds an opt-in "Pin code labels" toggle (default off, session-only) that pins the header — offered ONLY in the "↔ Unbounded" view**, where neither the card nor the wrapper sets `overflow`, so a `position: sticky; top: 0` `<th>` anchors to the page for free and the table keeps its full natural height. Normal view is deliberately NOT given the capped box: at 200% text scale a row is ~68px, so `60dvh` leaves ~5 rows with the legend stranded (worse than what v0.5.69 reverted) and `26rem` (832px) exceeds the viewport, which puts the scrollport's top — and the pinned header with it — off-screen. That arithmetic, not preference, is why the v0.5.69 shape stays reverted. Invariant: **pinned implies Unbounded** (pinning from Normal switches and pins in one press; unpinning restores the view you came from; pressing `↔ Normal` clears the pin). `position: sticky` sits on each `<th>` individually, NEVER on `<thead>`/`<tr>` (WKWebView honors sticky on cells only), and `border-collapse: separate` is required. **Phone narrowing is single-sourced in `.sr-bc-code-col`** (`frontend/src/globals.css`): base ~44px on desktop, `@media (max-width:640px)` → ~30px dot-width columns + 0.625rem headers. Change the phone width THROUGH that class, never an inline width. Thin vertical column rules come from `--sr-border-subtle` right-borders on `.sr-bc-code-col` / `.sr-bc-name-col` (all widths). The species-name column is horizontally sticky ONLY (`left:0`, no `top`). Magnify is native viewport pinch — NO CSS `zoom` / `transform:scale` (unreliable in WKWebView, same reason the v0.5.64 ZoomableWideSurface was reverted). **The ≤640 dot-width narrowing holds in BOTH the Normal and the "↔ Unbounded" (wideMode) views (v0.5.70):** `.sr-bc-matrix` on the `<table>` (base `width:100%; min-width:max-content`; `@≤640` `table-layout:fixed; width:max-content; min-width:0`) makes the declared `.sr-bc-code-col` widths *authoritative* — under `table-layout:auto` a cell width is only a floor a wide/uncapped table never reaches — and `.sr-bc-card` on the wideMode card (base `max-content`; `@≤640` `min-content`) hugs the fixed-width table so there's no trailing whitespace. **CORRECTED at v0.5.84 — that "hugs the table" claim was TRUE on the phone tier and FALSE on desktop from v0.5.70 until this bundle, and the same false sentence sat in `globals.css`.** `max-content` on a column flex container is the maximum over ALL its children, and the card's other child is the tier legend, a wrapping row of "CODE Full Label" chips whose max-content is every chip on one unwrapped line: it measured 1749px against the table's 792px and won, the table's `width: 100%` then resolved against that inflated card, and `table-layout: auto` stretched every column to fill it (code columns 97px instead of their declared 44px, the card 519px past the panel). What makes the claim true now is one added top-level rule, `.sr-bc-card > .sr-bc-legend { width: min-content; min-width: 100%; }`, which lets the legend FLOOR the card but never dictate it. Keep it top-level (it must hold in the ≤640 tier too) and scoped under `.sr-bc-card` (Normal view never carries that class, which is what makes "Normal is untouched" a property of the stylesheet rather than of a measurement). **AMENDED at v0.5.85 — "Normal is untouched" is no longer the whole story: Normal view's legend now has its OWN phone-tier constraint, and the two rules are converses that must not be merged.** v0.5.84 stopped the legend *dictating* an intrinsic card width, which can only happen in Unbounded. In Normal the card is a stretched flex item at the panel's width, so an unbreakable `white-space: nowrap` chip is simply wider than it: at 320px/200% with all 23 codes the widest label ran **81.08px** past the legend's content box, out through the card's rounded border and off screen (the band reaches 390px and 1.5x). The Normal-view fix is three declarations in the ≤640 tier, each load-bearing and two of them invisible to a box measurement — `min-width: 0` on **both** `.sr-bc-legend--normal .sr-bc-legend-tier` and `.sr-bc-legend--normal .sr-bc-legend-chip` (both are flex items, whose `min-width: auto` floors them at their min-content width regardless of available space), plus `white-space: normal` and `overflow-wrap: break-word` on the chip, with the base `.sr-bc-legend-chip { white-space: nowrap }` lifted top-level byte-identical to the inline value it replaces. Three things must not be flattened: the **`.sr-bc-legend--normal` scope** (the component adds it exactly when it omits `.sr-bc-card`, so the two can never co-occur — unscoped, `min-width: 0` on the tier group would lower the legend's min-content, which is precisely the value v0.5.84's rule reads, and every CSS guard would stay green through it); **`break-word` into `anywhere`** (renders identically and would let both `min-width: 0` go, but collapses min-content to a single character, the zero-contribution shape v0.5.84 named and rejected — `break-word` never affects intrinsic sizing); and **`overflow-wrap` itself**, which a box-based test reports as unnecessary. No hanging indent is needed: flex collects items onto a line only while they fit, so a chip wide enough to wrap is always alone on its flex line, and every line opens with a bold code or continues the one above. **CSS caution:** `table-layout:fixed` needs a *definite* width (`max-content; min-width:0`), NEVER `width:100%` inside a `max-content`/shrink-to-fit container (a circular constraint that runs the table to the browser's ~500,000px element-width cap); and a `max-content` card over a fixed table sizes to the columns' *intrinsic* width (huge whitespace) — use `min-content` to hug it (both layout-only, caught only in live phone preview). Files: `frontend/src/components/BreedingCodeTable.tsx` (+ its test), `frontend/src/globals.css`.
- **PINNED LABEL ROWS ARE ONE PATTERN ACROSS TWO TABLES (Breeding Codes and Multimedia), and the pattern is a CONTROL, not just a mechanism (`freezable-label-rows`).** Both offer an opt-in pill (default OFF, session-only `useState`, no storage seam) that pins the header row, offered in the "↔ Unbounded" view, under one invariant: **pinned implies Unbounded**. Four things are deliberately shared, and a third pinnable table should reuse all four rather than re-inventing them:
  - **The state machine is `frontend/src/lib/pinnedLabels.ts` (`nextPinnedState` / `nextViewState`), used by BOTH tabs.** Same posture as `nextShadingState`: pure transitions wired into both toggles, never a `useEffect` mirroring one piece of state onto another. It also carries the `announce` flag (true only on the press that PINS) so the two surfaces cannot drift on when they speak. The invariant is proved once there, including over random walks; what each component test still owes is the WIRING.
  - **The sticky sits on each `<th>` individually, never on `<thead>`/`<tr>`** (WKWebView honors sticky on cells only), with `border-collapse: separate`. Multimedia's shipped on the `<tr>` from v0.0.29 and was therefore very likely dead in the macOS app and on iOS while alive in Chromium.
  - **Everything the band needs lives in the stylesheet, never inline** (`.sr-bc-matrix--pinned` / `.sr-ll-table--pinned`): an inline style is specificity (1,0,0), so the `.sr-ios-app` safe-area gate could never re-point `top` and the band would pin into the Dynamic Island. That gate is a gate, never a bare `env()`. The band's fill moves onto the `<th>` because a sticky CELL travels while its `<tr>` stays in flow, so a fill left on the row scrolls out from under the band.
  - **The focus guard is `scroll-margin-top` on the pinned body cells AND their descendants** (four selectors), because the focusables are not the cells: `BirdName` renders a `<button>` inside each row header. Read the computed value off the element that RECEIVES FOCUS before claiming WCAG 2.2 SC 2.4.11; a rule on the cells alone computes `0px` on everything that can actually take focus. Never `scroll-padding-top` on the root, which would outlive the tab (hidden tabs stay mounted).
  - The pinned-state note's classes are surface-neutral (`.sr-pinstatus` / `.sr-pinnote`) precisely because both tabs render them; a `.sr-bc-*` name on the Multimedia tab would be a name that lies.
- **Two reversals are recorded here because both were built, previewed on device, and reversed by the user (`freezable-label-rows`); do not re-derive either.** (1) **Pinning freezes the CODE HEADER ROW ONLY.** A two-axis reshape (`leftFreeze = !wideMode || pinnedNow`, plus an inline `z-index: 4` corner) also kept the species-name column frozen in Unbounded; it measured well and was still not what was wanted. The shipped predicate is `!wideMode`: the name column's freeze is a property of **Normal view**, and the pill is named "Pin code labels" because naming the axis is what makes the label accurate. (2) **Multimedia gets the same opt-in control, not an always-on band.** Repairing the mechanism and leaving it always-on in Unbounded was the design's verdict and was reversed: the user asked for parity of the CONTROL. Named cost, carried in the PR rather than hidden: Chromium users (web, Windows) had an always-on header pin in Unbounded and now press a button for it. Published prose must scope both correctly: "the name column stays fixed in either view" is FALSE (it was caught in review on three surfaces at once, and it predates this work).

### Accessibility — standing conventions

The app targets WCAG 2.1 AA (the 0.5.31 pass). These are the durable, enforceable contracts; the published statement is `ACCESSIBILITY.md` and must stay true to the shipped code (a wrong accessibility statement is a liability, same posture as the privacy policy).

- **Contrast is fixed at the token, in BOTH themes — with a typed naming system.** Three text-on-X cases have distinct token families in `globals.css`: `--sr-tier-N-fg` (tier-colored text ON an 8–15% tier tint), `--sr-tier-N-text` (text ON the solid tier fill), and the on-fill tokens for specific surfaces (`--sr-map-target-*-text`, `--sr-milestone-*`, `--sr-rank-pin-*`, `--sr-on-chart-blue-dark`, `--sr-border-input` for form-control boundaries at ≥3:1 non-text). Pick the family by what the text sits on; never reuse a fill token (`--sr-tier-N` / `-rgb`) as a text color (the fill palette is left untouched for atlas/hatch parity). Verify with the same WCAG luminance math, both themes, before shipping a new pair.
- **`--sr-text-disabled` is for genuinely disabled CONTROLS only** (WCAG-exempt). Informative text, empty states, and captions use `--sr-text-muted`. Do not use `text-disabled` for content.
- **A token whose underlying fill differs by theme may need OPPOSITE text colors per theme** — `--sr-on-chart-blue-dark` is `#FFFFFF` light / `#0A0A0A` dark for exactly this reason. A single value can't always pass on a light-in-one-theme, dark-in-the-other fill.
- **Filter controls follow the Checklists.tsx pattern: an explicit `aria-label` on every `<select>` / date input / search box** that would otherwise rely on a placeholder or a nearby caption. `Checklists.tsx` is the reference; the pattern is now applied app-wide.
- **`SegControl` and segmented/pill toggles carry `aria-pressed`** reflecting the selected state.
- **Overlays route EVERY close affordance (Escape, Close button, backdrop) through one close function that restores focus to the opener.** If the opener unmounts while the overlay is open (e.g. a FAB that only mounts when the panel is closed), run the restore in an effect AFTER the close render commits via a flag ref — not at close() time, when the ref is still null (the `closeSidebar` / `restoreFiltersFocusRef` pattern in `MapExplorer.tsx`). A focus trap must **re-query its focusables per Tab keydown**, not cache them once (collapsed/`inert` content changes the set); `HelpDocs.tsx` and `MapExplorer.tsx` are the references.
- **Wrap a decorative recharts chart in `inert` — recharts ignores `accessibilityLayer={false}` on `PieChart`** (its root `<svg>` stays focusable and leaves an axe aria-hidden-focus ghost). The same `inert` clamps collapsed filter panels so hidden controls aren't stray tab stops.
- **A CSS-COLLAPSED disclosure panel is not hidden — it needs `inert` while closed, plus a test asserting the LITERAL attribute in BOTH states (v0.5.87).** A panel collapsed with `grid-template-rows: 0fr`, `max-height: 0`, or `opacity: 0` is clipped, not unmounted, so its focusable descendants stay in the tab order and the accessibility tree while `aria-expanded="false"` says otherwise (WCAG 2.4.3, 4.1.2). The escapee account panel measured exactly 9 such focusables. The fix is `inert` on the clipped inner div — the same fix on the same grid-rows shape as the Map Explorer's collapsed filter panel. Assert the literal attribute in both states, because **React 19 emits `inert={false}` correctly as absent while pre-19 rendered the truthy string `inert="false"`**, which would pin the panel permanently inert. This is NOT the "Show all N counties" idiom, which conditionally renders and is only the source of the expander BUTTON's styling; say so in the component and the CSS so the two are not confused. **Corollary (v0.5.92): a live region consumed by a collapsing subtree renders OUTSIDE the `inert` boundary.** `inert` removes its subtree from the accessibility tree entirely, so a `role="status"` region inside the clipped panel re-enters the tree along with its first message — the insert-with-first-message trap by another route. Put the region outside the inert-able element; `HotspotModeControl` is the reference (its test asserts the literal `inert` attribute in both states).
- **`scroll-padding` goes on the SCROLLPORT, `scroll-margin` on the FOCUS TARGET — and in this app the focus target is almost never the cell (v0.5.81).** When a sticky band can obscure keyboard focus (WCAG 2.2 SC 2.4.11 Focus Not Obscured), the vertical guard is `scroll-margin-top` on the elements that actually receive focus. Table cells, rows, and list items are not focusable; the real target is the `<button>`/`<a>` inside them (`BirdName` nests one three levels deep in every species row), and `scroll-margin` neither inherits nor applies to an ancestor — so a rule on the cell computes `0px` on every focusable and is completely inert. Use the descendant combinator (`… tbody th *`), not a child combinator, and verify by reading the computed `scroll-margin-top` **off the element that receives focus** before claiming the SC. The `scroll-padding-top`-on-the-scrollport half is geometrically correct and is nonetheless the WRONG reach here: the scrollport is the page, and `mountedTabs` only grows with hidden panels at `display: none`, so a root-scoped rule (or a `:root:has(…)` variant — selectors match the DOM tree irrespective of computed `display`, verified in Chromium) stays in force on every other tab after the user pins and navigates away. **Prefer the rule that lives inside the feature's own subtree.** The same component's horizontal axis IS the genuine `scroll-padding` case (`BreedingCodeTable.tsx`'s `scrollPaddingLeft`), because there the wrapper really is a scrollport; the two axes are not symmetric. Scope any regression tripwire to the leak (a `:root`/`html`-scoped declaration), not to the property or selector vocabulary — a stylesheet-wide ban on `scroll-padding-top` or `:has(` fails unrelated future work under a test name that points at the wrong thing.
- **An overlay hosted INSIDE a map binds its Escape handler in the CAPTURE phase at `document`, with `stopPropagation` (v0.5.80).** `MapExplorer`'s shipped fullscreen-exit and sidebar-close Escape handlers are bubble-phase on `document`, so a bubble-phase handler on a new in-map overlay cannot beat them — one Escape would dismiss the overlay AND exit fullscreen. Capturing at `document` and calling `stopPropagation` makes the overlay the innermost dismiss layer and prevents the outer handlers firing at all. `SharePopup.tsx` is the reference; it stays one close path (the close control, Escape, and any maplibre dismissal all route through the same function, per the bullet above).
- **A live region whose text is set to the SAME string does not announce — put the message in a sequence-keyed child node (v0.5.80).** `aria-live` fires on DOM *mutation*, and React bails out when reconciling a text node to an identical string, so pressing the same control twice announces once while the visible confirmation re-renders both times and every `textContent` assertion stays green. The repo rule "render the region from the start, only change its text" is necessary but NOT sufficient. The fix is `{msg ? <span key={seq}>{msg}</span> : null}` inside the `role="status"` region, with `seq` advancing per announcement — each one is a real node replacement while the region's `textContent` stays exactly the message. Do NOT append an invisible character to force a diff: it makes every `textContent` assertion quietly false. Any such region needs a test that presses the same control twice and counts DOM mutations (`SharePopup.tsx` + `SharePopup.test.tsx` are the reference). **One nuance on that test, verified empirically in v0.5.81:** mutation-counting only discriminates against the wrong implementation when the message node stays **permanently mounted** and its text is toggled. Where the node unmounts while the region remains (the Breeding Codes pin note), the remount is already a real DOM addition, so an unkeyed child passes the same test. Still write the keyed child — but describe the guard by what it actually rejects, rather than banking a false confidence. **A guard whose discrimination has been shown to be absent should say so in its own comment and name the test that DOES reject the defect** (the Breeding Codes pin note is the reference: its mutation-counting test cannot reject an unkeyed child, the file says exactly that, and an adjacent test carries the real `aria-live` guarantee).
- **A live region driven by a PER-ITEM progress callback needs its announcement rate stated, bounded, and measured against a REAL-DURATION pass — never a fast mock (v0.5.87).** The escapee progress region announced 75 times over a 9.7 s pass, about 7.7 per second, because the sequence-keyed child fired per request; a fast mock would have let any throttle suppress everything and reported a rate the user will never see. **Throttle the EMISSION, not the announcement**, so the sentence, the progress bar and the `N / M` readout keep one source of truth and cannot disagree on screen. Never throttle a terminal status or the first definite figure, keep the region always rendered (never `display: none` while idle, per the rule below), keep the sequence-keyed child, and mutation-check in BOTH directions — removing the throttle must go red, and throttling the opening figure must go red. **v0.5.92 sharpening: the throttled emission must be a FROZEN SNAPSHOT of the progress accumulator, never the shared accumulator object itself — and the throttle is verified at the RENDER, by a timestamped text-change measurement over a real-duration pass.** Emitting the live accumulator lets every per-arrival re-render observe its in-place mutations, so the rendered text updates at arrival rate while the emission rate is nominally throttled; the defect shipped with the unit suite green because the suite asserted the emitted objects, not the rendered timeline. `useHotspotActivity`'s `flushEmit` is the reference (its regression test was proven red against the shipped defect on the mutation and frozen-snapshot assertions independently).
- **A CSS rule whose subject is an ARIA element must be checked against the ACCESSIBILITY TREE, not only against layout — and `display: none` on a live region is the specific trap (v0.5.83, caught in security review as a Medium).** `display: none` removes an element from the tree entirely, so a `role="status"` region hidden while idle is *inserted along with its first message*, which is the documented way to make a live region fail to announce. `.sr-map-geo-error:empty { display: none }` did exactly that to the map's location-failure region, and it broke **every** announcement rather than only the first, because the handler clears the message before each press (so each one was a `none` → `flex` transition) — and it defeated the sequence-keyed child from the bullet above, whose entire premise is a STABLE region whose child is replaced. It is invisible to every layout measurement, to a `textContent` assertion, and to jsdom (which loads no stylesheet), so the component test passes on the broken build and is necessary but not sufficient; pair it with a stylesheet scan over every rule whose subject is the region, asserting nothing sets `display`/`visibility`/`content-visibility` to a hiding value plus a positive `display: flex` so the scan cannot pass vacuously by the rule being deleted. Verify with Playwright's `ariaSnapshot` against a real render while the region is IDLE. **The same "use a real accessibility tree" instruction covers accessible NAMES, and the jsdom proxy has a specific known deviation (v0.5.84, and it cost a QA cycle).** `computeAccessibleName` from `dom-accessibility-api` — what testing-library uses — omits the inter-node space real engines insert per the accname algorithm, so it reports a spurious one-space delta between an `.sr-only` cue node and an `aria-label`; a build measured that, called it "measured, not reasoned about", and published a bold claim that the name had changed when Chromium and WebKit both render it byte-identical. jsdom has no accessibility tree, so there was never anything there to measure. Assert a name in a component test with `getByRole(..., { name })` (which pins the guarantee rather than the mechanism that carries it), and settle any claim that a name CHANGED against `ariaSnapshot` plus CDP `Accessibility.getFullAXTree` in Chromium **and** WebKit, the engine the macOS and iOS apps actually ship on. House posture, unchanged since `SharePopup.tsx`: the region is always rendered and only its child changes. A `.sr-only` duplicate announcer is the wrong repair where the announced text IS the visible card (it would put the same sentence in the reading order twice).
- **To portal a control into an EXISTING flex row, use `display: contents` on the slot — never `order` (v0.5.80).** `order` moves the box visually while leaving DOM order unchanged, which desynchronizes tab order from reading order (WCAG 2.4.3 Focus Order). `display: contents` makes the wrapper transparent to layout so DOM order IS visual order, and the new control simply takes its place in the sequence. `.sr-map-fab-slot` (the share pin's slot as the first item of `.sr-map-fab-cluster`) is the reference; it also means no shipped control in the cluster moves. **Its counterpart cost, found in v0.5.91: such a wrapper has NO BOX, so a `ResizeObserver` on it reports 0x0 and never fires.** Any layout observer walking the app shell's children must descend one level through a `display: contents` child or it silently misses exactly the case it exists for — `App` wraps the tab nav in one, so a tab strip collapsing into its dropdown (which an in-app text-scale change alone can trigger at an unchanged viewport width) would go unobserved. `chromeBoxes` in `lib/mapPanelChrome.ts` is the reference.
- **DOM map markers are real `<button>`s** via `neutralizeMarkerWrapper` (`lib/mapPins.ts`) on the `<Marker>` ref — never a clickable `<div>`.
- **The "open this checklist on eBird" affordance is the shared `components/ChecklistLink.tsx`, used for EVERY checklist link app-wide.** One visual signature (the lucide external-link icon) and one accessible-name formula, which is **label-aware**: with a visible date/count the name leads `{label} — open checklist on eBird (opens in a new tab)` (WCAG 2.5.3 Label in Name, so Voice Control can activate it by what's on screen); with no label it names the id directly; the functional suffix is identical everywhere (WCAG 3.2.4). A `compact` prop renders icon-only for dense spots (species pills, fixed-width cells, map popups) while keeping that same name; an optional `title` adds a hover tooltip without changing the accessible name. It keeps the `SUBMISSION_ID_RE` guard (junk id → plain text, never a styled 404 link).
- **Every NON-checklist external link goes through the shared `components/OutboundLink.tsx`** — it guarantees `target="_blank"` + `rel="noreferrer"` and an "(opens in a new tab)" cue (a clean spaced `aria-label` from string children / an explicit label, else an `.sr-only` cue node for JSX children). Canonical new-tab wording is "(opens in a new tab)". It is named `OutboundLink`, **not** `ExternalLink`, to avoid colliding with lucide-react's `ExternalLink` ICON; decorative ↗/→ glyphs beside a link are `aria-hidden`. Don't hand-roll an external `<a target="_blank">` — use `OutboundLink` (or `ChecklistLink` for checklists).
- **A location NAME that is a PUBLIC eBird hotspot renders through the shared `components/HotspotLink.tsx` (v0.5.40).** It turns the name into a link to `ebird.org/hotspot/{locId}` ONLY when the caller passes `isHotspot` true AND the id passes `LOCATION_ID_RE` (`/^L\d+$/`); a personal location, a junk/absent id, or a not-yet-resolved Set all render as plain text — never a styled 404 link (the pre-existing inline links gated on id-format ALONE, which wrongly linked personal locations; this is the fix). It wraps `OutboundLink` and reuses the `Open {name} on eBird (opens in a new tab)` name formula (`hotspotLinkAriaLabel`); `compact` = icon-only (map popups), `truncate` = ellipsis a long name while keeping the trailing icon (the link color is forced `var(--sr-accent)` so a caller's plain-text color can't bleed onto it). **Public-vs-personal is decided by `isPublicHotspot` against a region-scoped Set** (`lib/hotspotSet.ts`): one cached fetch per distinct `stateProvince` region in the backup via `GET /map/hotspot-region` (eBird `ref/hotspot/{regionCode}`) → union of locIds → O(1) membership, NOT one call per location. Tabs get it via the parameterless `useHotspotSet()` hook (loads the backup itself through `observationsCache`; the `getHotspotSet` module cache keys on the region list so all tabs share one build). No key / a failed fetch degrades to an empty Set (everything plain). When a list renders many rows, call `useHotspotSet()` ONCE in the parent and pass `isHotspot` down — don't call the hook per-row. The backend route and `lib/tauri/mapService.ts` `getHotspotRegion` are dual-transport parity — keep them in lockstep, and `/map/hotspot-region` is in `CACHED_GET_PATHS`.
- **The Calendar tab is deliberately OFFLINE / zero-network — render location names there as PLAIN TEXT, NOT through `HotspotLink` (v0.5.63).** The app-wide "a public-hotspot location name links to eBird via `HotspotLink`" convention above is **explicitly waived on the Calendar tab**: `HotspotLink` needs `useHotspotSet()`, whose region-scoped `GET /map/hotspot-region` fetch would add a live network dependency to a tab whose entire promise is that it computes purely from the already-loaded backup and works with no connection. The day-popup checklist rows show the checklist's location as escaped plain-text JSX (no anchor, no `OutboundLink`, no fetch); a code comment in `Calendar.tsx` marks this, and this note makes it a durable convention so a future dev doesn't "upgrade" those names into linked hotspots and silently break the tab's offline guarantee. Any new Calendar-tab surface follows the same rule.

### Overlays and stacking

- **Sighting-point sizing is single-sourced in `lib/mapPins.ts` — `POINT_SIZE_RADIUS_FACTOR` (normal:1, small:0.5) + a `factor` arg on `pinRadiusExpr`/`pinFillRadiusExpr` (factor-1 short-circuits so Normal is byte-identical), parity-locked by `mapPins.test.ts` (v0.5.53).** The Map Explorer "Point Size" control (Normal / Small / Off, `PointSize` in `lib/mapExplorerTypes.ts`; Pins-mode-only, under the Pins/Heatmap toggle; session-only `useState`, no `storage` seam) drives it via `SightingMarkers`' `pointSize` prop — **Off** returns null (removes the `sr-sight-circle` layer AND gates its click/hover handlers so a shaded breeding-block / county choropleth reads through), **Small** applies the 0.5 radius factor, **Normal** is unchanged. It **COMPOSES with the v0.5.47 shade auto-dim** (radius factor and opacity dim are independent axes — Small + an active shade multiplies opacity by the dim factor); the heatmap is untouched. Don't hardcode a second radius scale — thread the `factor` through `mapPins.ts`.
- **Sighting-pin maps use the shared `SightingsMap` (`components/SightingsMap.tsx`) — don't re-inline the Species Detail pins map (v0.5.26).** It owns the DOM `<Marker>` pins, the single state-driven `<Popup>` (its own `selectedCoord`), `MapBoundsFitter`, and the static `SP_PIN_HTML` sprite; Species Detail and the Named Birds card both consume it. Build its `markers` with the pure `lib/sightingMarkers.ts` `buildSightingMarkers` (skip null coords, group by `lat,lng`, dates newest-first) so skip-null / empty→no-map / same-coord aggregation stays one tested function. The heatmap/intensity/map-mode toggle stay LOCAL to Species Detail — the extraction is the pins path only. Callers must gate on `markers.length > 0` (the empty guard is the caller's, so no WebGL context mounts for a no-coordinate entity). **Where a list can mount per-row maps, bound concurrent WebGL contexts structurally with a single-open accordion (one live map = one context), not an instance counter/queue** — the Named Birds tab does this via a `singleOpen` prop on `NamedBirdsTable` (Species Detail's map-less list stays multi-open).
- **Keep maplibre OFF the entry chunk — the per-row map and the map tabs stay lazy (v0.5.42).** Even though the map *tabs* are `React.lazy`, a single statically-imported component can silently drag the ~1 MB / 273 KB-gz maplibre vendor bundle onto first paint — `NamedBirdRow`'s static `import { SightingsMap }` did exactly this (latent regression, fixed in 0.5.42). Rule: NO component reachable from `App.tsx`'s STATIC import graph may statically import `SightingsMap` / `SnowMap` / `react-map-gl/maplibre`. The per-row `SightingsMap` and the map tabs (Map Explorer, Species Detail) stay `lazy()` + `<Suspense>`, warmed at idle via App's `requestIdleCallback` warmer — define the importer locally in App (`() => import('./components/SightingsMap')`) and keep the map component file component-only so `react-refresh/only-export-components` passes. Standing check after any map-touching change: a fresh `npm run build` must show `vendor-maplibre` ABSENT from `dist/index.html`'s modulepreload and no bare `import "./vendor-maplibre"` in the entry chunk. `chunkSizeWarningLimit` is 1100 because the isolated maplibre vendor chunk (~1 MB, off first paint) is legitimately over 500 KB. **This rule now has an automated guard — `frontend/src/lib/entryChunk.test.ts` walks `App.tsx`'s static import graph (asserting `SightingsMap`/`SnowMap`/maplibre and the on-demand `CountyLayer`/`us-counties.json` are not statically reachable) AND checks the built `dist/index.html` modulepreload for any county/maplibre entry. Extend `entryChunk.test.ts` when you add a new off-entry-chunk asset or component rather than relying on the manual build inspection alone.**

Three rules came out of placing it: **(a) no INTERACTIVE control may take the map's top-centre anchor** — at 320px it measures 206x31px at 1x and 294x148px at 200%, where it buries the layers switcher completely, so that anchor holds only `pointer-events: none` statements (the loading chip, the search-outcome region) and a tap-through claim about one is asserted with `document.elementFromPoint` naming what the tap actually reached, never merely that the overlay declares `pointer-events: none`; **(b)** the switcher grows downward from the top while the cluster grows upward from the bottom, so their collision is **scale-dependent rather than width-dependent** and must be measured at all four shipped text scales, not at three widths; **(c)** where a new row genuinely has nowhere to fit, the answer is to WITHHOLD it and leave its function reachable where it already was, measured (`lib/useSearchControlFit.ts`, against the shipped disc line's top, which is bottom-anchored and therefore invariant to whether the row is rendered) rather than gated at a fixed breakpoint — the same answer TabNav already gives.

### Security — standing checks

- **The atlas block popup is built as escaped JSX (`AtlasLayer.tsx`), not an HTML string.** Block name/code render as React children (auto-escaped) and the eBird atlas URL is `encodeURIComponent`-wrapped, so it's injection-safe even though the data is bundled/trusted (`ca-atlas-blocks.json`). **Standing check:** keep this popup — and the other map popups — as JSX; do NOT switch atlas/marker popups to `dangerouslySetInnerHTML`. The few `dangerouslySetInnerHTML` uses on the maps are static SVG constants or run user/external text through `escHtml` first (e.g. the target-chip label in `MapExplorer.tsx`); preserve that.
- **An eBird id from CSV data is shape-validated before it becomes a link.** Gate a checklist `href` on `SUBMISSION_ID_RE` (`/^S[0-9]{1,15}$/`, from `components/speciesDetail/ui`) — and a location id on `/^L\d+$/`, a catalog id on `/^\d+$/` — before interpolating it into an anchor; render the id as plain text when it doesn't match (don't ship a styled 404 link from a junk column value). For checklist links this guard now lives inside the shared `ChecklistLink` (so every checklist site inherits it); apply it directly for location/catalog ids and anywhere else a raw id becomes an href. Pair it with `encodeURIComponent` where the id rides in a query string.
- **A parsed link target becomes an `href` only through a scheme gate, and the house formulation is `/^https?:\/\//i` — never the looser `/^https?:/i`, which admits `https:evil` (v0.5.84).** The in-app Help renderer interpolated a markdown link target straight into `href`, so it would have emitted a live styled `javascript:` or `data:` anchor if ever pointed at content other than the compile-time `docs/HELP.md`. The gate is `isSafeHelpLinkTarget` in `frontend/src/lib/helpLinks.ts` (a `lib/` home because `renderInline` is module-private and a non-component export from a `.tsx` trips `react-refresh/only-export-components`, the same constraint that put MediaEmbed's constants in `lib/mediaEmbed.ts`); the anchor is `OutboundLink`, per the v0.5.32 decision. On a miss the link TEXT renders as escaped plain text and the anchor is dropped — the established answer everywhere in this app (`ChecklistLink`, `HotspotLink`, `CommentText`): never ship a styled link you cannot vouch for. Note that an `![alt](src)` image reaches `href` by this same path (the scanner's link alternative starts at the `[`, so the `!` falls through into the preceding text slice), which is why one gate closes every door in that renderer. Three durable points: **(1) a scheme gate is not complete until the tokenizer FEEDING it is bounded** — the scanner runs first, so a quadratic tokenizer hangs the main thread before any target reaches the gate, and the gate alone does not make a "safe against untrusted content" claim good; **(2) verify a security predicate against the PARSER that will consume its output, not against your test list** — a predicate over URLs is a claim about what the WHATWG URL parser does, and it strips leading control characters and all ASCII tab/newline before reading a scheme, so a few dozen lines of Node `URL` (the same specification browsers implement) settle in seconds what reasoning about regexes cannot, and fuzzing the byte range into each injection position turns "no test found a leak" into "no input in this space can leak"; **(3) the gate authorizes the SCHEME, not the host** — userinfo, backslash authority and punycode confusion are out of its scope, which is correct and consistent with `CommentText`, and is stated at the definition site so the next reader inherits the boundary rather than the headline. The two copies of the predicate (here and `CommentText.tsx:23`) are separate on purpose; consolidating them is a deliberate step, not an accident.
- **User/API comment text renders only through the shared `components/CommentText.tsx`** — escaped JSX segments, anchors emitted only for validated `http(s)` URLs. Its input contract matters: pass entity-ENCODED text (eBird API data, e.g. the comparer) as `raw`; pass ALREADY-DECODED text (anything from `lib/checklistsTab.ts` / `stripWeatherTideBlocks`, which operate on decoded text) with the `decoded` prop. Never decode twice — a double decode renders text differently than written and breaks the Checklists tab's display==search invariant.
- **Module-level `/g` regex hygiene (0.5.27 post-mortem):** a global regex carries shared mutable `lastIndex`, and `String.prototype.matchAll` CLONES the regex *including* its current `lastIndex` — a stale offset silently skipped matches and made the weather/tide strip fail order-dependently. Reset `lastIndex` (or scan once up front) before any reuse. Regexes that scan untrusted comment text must also be linear by construction: precompute match positions in single passes and length-bound lazy quantifiers (`commentBlocks.ts`, same posture as `namedBirds`' `NAME_TAG_RE`) — the unbounded version was quadratic (4.1s on a 400KB hostile comment, on the main thread). **v0.5.84 closed two more instances (`speciesUtils.ts`'s `normalizeSpeciesName`, rewritten to a linear scan; `helpLinks.ts`'s inline scanner, length-bounded) and added six rules for the next one; v0.5.85 then closed six further sites and added two rules of its own (the third and fourth bullets, each marked v0.5.85) — eight in all. When you append a rule here, correct this count in the same edit:**
  - **Sweep through the real exported ENTRY POINT, not the regex literal.** A literal-level sweep over-reports and under-reports in both directions: two candidates changed verdict entirely once the real call path was exercised — one read 0.0 ms until the `hasWeatherBlock` marker gate was satisfied (then 2,243 ms), another was saved by a `trim()` until a shape that defeats it. A row is only real if it is a shape that actually arrives.
  - **State the sweep's SCOPE honestly, and re-derive the claim at the moment it is written.** "This was the last instance" is a claim about the whole codebase, it decays between brief and ship, and it is the exact sentence that stops the next person looking. A v0.5.84 build shipped it and was wrong about the very file it cited as precedent. **v0.5.85 then proved the rule twice over: re-deriving the sweep instead of working from the recorded list of five turned up a SIXTH site the review had missed** (`countyBoundaries.ts:129`, `normalizeCountyName`, which runs once per observation over the CSV `County` column). All six are now linear scans with the guards below. As of v0.5.85 the sweep was re-run across `frontend/src` and every remaining regex literal carrying an unbounded quantifier with something that can fail after it measured linear (~2x per doubling at 10k/20k/40k) through its real path -- a measurement with a date on it, not a guarantee. Either re-run the sweep and list what remains, or scope the claim to the file; never write that it is finished. This is the published-prose "grep the predicate" rule applied to a claim in source.
  - **A rewrite that replaces a quantified pattern with a SCAN has no constant, so a bound guard's headroom test is vacuous there -- put NON-VACUITY in that slot instead (v0.5.85).** The other three of the four tests carry over unchanged (structural, timing, parity); the fourth becomes proof that the probe set REJECTS a named, plausible, wrong implementation of the same scan, because a parity sweep that is merely too weak passes against anything. Do not invent a headroom assertion that cannot fail in order to keep the count at four. That substitution is empirical rather than stylistic: across the six v0.5.85 sites the real-data corpora were largely unable to discriminate at all -- the demo export holds no URLs for the `commentText` site and no weather blocks for either `commentBlocks` site, and TIGER's county NAME field carries no administrative suffix, so a 7,869-value sweep of a real `County` column exercised the changed branch **exactly zero times**. Reconstruct the corpus that reaches the branch (here, TIGER names with each suffix appended, which is what eBird actually writes into the CSV), and assert BOTH numbers: that real data diverges zero times AND that the probes do discriminate.
  - **A timing fixture only guards linearity if the old pattern actually FAILED on it -- a fixture where the match SUCCEEDS at the first start position was never quadratic and will certify a broken build (v0.5.85).** Four of the six sites' second fixtures passed on the reverted pattern at 0.0 ms, because a greedy quantifier that swallows the hostile run and then matches never backtracks: `' '.repeat(40000) + 'borough'` is linear under the very regex that takes 2,501 ms on `' '.repeat(40000) + 'boroughx'`. Build the hostile input so the pattern **fails after consuming the run** (a near-miss suffix, a dash with no digits after it, a punctuation run stopping one character short of the end), and prove it by reverting locally and watching the test go red. Where a success-path fixture is worth keeping as coverage, say in its own comment that it cannot reject a revert and name the test that can -- the same posture as the Breeding Codes pin-note guard.
  - **Bound the whole path, not just the regex the audit named** — a sibling literal reachable from an exported function leaves the same defect one call away from a future caller.
  - **Measure the bound against the strings the scanner actually RECEIVES, not the raw file.** The raw `HELP.md` reports a 22,179-char "code span" from backticks pairing across two fences, ~44x the true maximum, which would have justified a uselessly large bound; strip the blocks that never reach the scanner (fenced code) first, then measure. Justify the constant against that maximum (500 is 5.4x the longest token of any kind and 11.9x the longest link target), and verify bounded and unbounded tokenize the real content identically.
  - **A bound guard needs FOUR tests, because none covers the space alone:** structural (a quantifier was dropped — and a syntactically-bounded-but-infinite quantifier passes this one by construction), timing (the bound is present but meaningless), parity against the unbounded form (the bound changed real output, and content growing past it surfaces as a failure rather than a link silently degrading to literal text), and headroom. Only the parity test should stay GREEN under a revert; the others must go red.
  - **Pin the constant's VALUE structurally, not via the timing ceiling.** A structural assertion that a quantifier "contains `String(THE_CONSTANT)`" is true for every possible value of that constant, and a `longest * 2 <= BOUND` headroom check gets *easier* as the bound grows — which leaves a wall-clock ceiling sized for the linear-vs-quadratic question as the only value-sensitive guard, and it tolerates roughly an order of magnitude of drift. Assert the safe range directly; it is one line and it cannot flake.
- **A backend pydantic pattern that twins a JS shape guard must use `[0-9]`, never `\d` (0.5.54 security review).** pydantic v2's rust-regex engine treats `\d` as Unicode decimal digits — `US-CA-٠١٢` passed `^US-[A-Z]{2}-\d{3}$` — while the JS twin's `\d` is ASCII-only, so the "same" pattern validates differently on the two transports. Write explicit ASCII classes on the Python side of any twinned guard, and include a non-ASCII-digit case in the malformed-input test (`/map/county-species` in `backend/routers/map.py` is the reference).
  - **Matching character classes are only HALF of parity — compare the ANCHORS too, and give every twinned pattern a trailing-newline row in its shared fixture (v0.5.87).** Python's `$` matches before a trailing newline and JavaScript's does not, so `re.match(r"^[A-Z]{1,4}$", "X\n")` accepts a value its `.test()` twin rejects. The escapee provenance twins asserted identical explicit ASCII classes, cited the v0.5.54 finding by name, and were **still divergent for two review rounds**, because no fixture row could tell them apart: the harm was `"X\n"` counting on both sides but then failing the store's own token guard on reload, silently discarding the whole species record and re-fetching it every session on web/Pi. **`re.fullmatch` (or `\Z`) is the house form for the Python half of any twinned guard**, and the fixture needs trailing-, leading- AND embedded-newline rows; assert the anchors directly in both parity tests, and mutation-check by reverting to `.match()`.
  - **Pydantic `pattern=` constraints are the deliberate CARVE-OUT and must NOT be "fixed" toward `fullmatch`.** They run on the Rust regex engine, which rejects the trailing newline; `backend/routers/map.py` and `backend/routers/media.py` are correct as they stand. Say so wherever the anchor rule is restated, or the next reader will change them.
  - **Both pre-existing counter-examples are CLOSED (v0.5.88), by two different fixes.** `backend/routers/settingskv.py`'s `_KEY_RE.match(key)` was the anchor half (its class was already explicit ASCII) and is now `fullmatch`, so a trailing-newline key can no longer become a second file beside a real one. `weather.py` / `tide.py` were the character-class half (their anchor was already `fullmatch`) and now share one `CHECKLIST_ID_RE` on `backend/services/ebird.py`, the module both already imported from — `re.compile(r"^S[0-9]{1,15}$")` since v0.5.90, which length-bounded it (ceiling 15, aligned with `SUBMISSION_KEY_RE` in `exoticProvenanceCache.ts` so a 16-20-digit id can no longer pass every guard and then fail the store's own key guard) and gated `/checklists/{checklist_id}` on it as that handler's first act. Neither fix would have closed the other, which is why the two rules are stated separately above. **Single-sourcing a guard prevents the copies DRIFTING; it does nothing to prevent a copy being DROPPED — so each consumer keeps its own route-level test**, and mutating one call site must turn only that consumer's test red. Same rule as the v0.5.87 copy-constant one recorded under Documentation, in a different domain. Note also that the JS side is NOT one-to-one: the same bounded literal (`/^S[0-9]{1,15}$/`, lockstep since v0.5.90) appears in six places, and the guard that gates the outbound *request* is `isValidChecklistId` (`lib/checklistId.ts`), while `SUBMISSION_ID_RE` gates only whether an id becomes a link — the parity test drives both and asserts they agree, so neither can drift away from the backend with the file still green.
- **A route that interpolates a user-supplied value into an OUTBOUND URL must constrain that value to a character class which cannot express a scheme, host, credential, or path separator — and must say in its docstring why the destination cannot be steered (v0.5.76 security review).** This is the SSRF check, and it is the one that matters whenever the backend fetches on the user's behalf. `/media/embed-status` is the reference: the host and path are a module constant and only `^[0-9]+$` (bounded length) can reach the single interpolated segment, so no `://`, `@`, `?`, or `../` is representable. Also confirm redirects are not followed (`httpx.AsyncClient()` defaults to `follow_redirects=False`) so a third party cannot bounce the request elsewhere, and never reflect the upstream body, headers, or cookies back to the client — reduce the response to the minimum the app needs. **A route that makes an outbound call also constrains its NUMERIC parameters with explicit `Query(..., ge=, le=)` bounds (v0.5.91).** `/map/recent-obs` is the reference (`lat` ±90, `lng` ±180, `dist` 1-200); `/map/hotspots`, its sibling in the same file, declares bare `lat, lng, dist` and forwards out-of-range numerics to eBird unchecked. It is not SSRF — the values ride `params=`, so no separator, scheme, credential or host is expressible, and the realistic impact is a wasted upstream call — but two sibling handlers disagreeing inside one file reads as intentional and is not. Pre-existing, on ROADMAP, deliberately not fixed inside the v0.5.91 feature.
  - **Measure what a route can REACH end to end on a live server over raw sockets — an isolated URL builder over-states it and a convenience client under-states it, and both directions were live in one v0.5.88 review.** `httpx.URL(base + "../../etc/passwd")` really does collapse to `/etc/passwd`, and a write-up called traversal reachable on that basis; it is not, because **Starlette's default `str` path converter matches `[^/]+`**, so a captured path value is always exactly one segment and no traversal form reaches the handler (`%252F`, backslash, overlong-UTF-8 `%C0%AF` and fullwidth-solidus U+FF0F all fail to smuggle a separator). The inverse trap is equally real: a `TestClient` probe normalizes `%2F` before the request leaves, so it would have confirmed the same false claim for the wrong reason. Over-claiming risk is the safer direction and is still false — it sizes deferred work a grade too high. Same lesson this repo already states for CSS and geometry, applied to a route. **Where the protection comes from ROUTING rather than from a guard, say so at the call site**, since switching that route to `{checklist_id:path}` (regex `.*`) removes exactly it.
- **When a refactor RELOCATES security-relevant code, prove it byte-identical against the pre-change revision — don't reason about it (v0.5.77).** Consolidating four routers onto the shared `datadir.py` moved the base path every settings-store traversal guard resolves against, and "I didn't touch the guard" is not evidence. Diff the guard-bearing code against HEAD, and diff the whole surface the refactor could have moved (the OpenAPI schema was diffed in an isolated worktree: identical, 31 endpoints, same order, catch-all still registered last). This repo consolidates constantly, so treat it as the standing check for any such move. **Sharpened in v0.5.81: identical declaration values are necessary but NOT sufficient when the refactor also LOWERS specificity.** Lifting an inline style (1,0,0) into a class (0,1,0) hands every other rule in the stylesheet a chance to win that it did not previously have, so the proof needs a **cascade-competitor scan** alongside the value diff. Two things that scan must get right: (1) it covers **every stylesheet the bundle emits**, not just `globals.css` — SnowRaven also ships `maplibre-gl.css` (imported by `SnowMap.tsx`, emitted as a lazy `vendor-maplibre-*.css` chunk that stays in the document once any map tab has mounted, and the larger of the two); and (2) it tests the **rightmost compound** of each selector, since an ancestor part of a descendant combinator can always be satisfied. Where the lifted rule's correctness depends on beating Tailwind preflight (its `* { padding: 0 }` competes directly with any `padding` a lifted class adds), record the **layer**, not only the specificity: user CSS in `globals.css` is unlayered and preflight sits in `@layer base`, and unlayered beats layered regardless of specificity. Specificity is the second, independent ground; recording only it means a future move of these rules into an `@layer` would silently forfeit the stronger one. Verify the layer mechanically (brace depth at the rule in the built CSS), not by eye. **Two v0.5.84 extensions.** (1) **Adding a FIRST class to a previously unclassed element is the same cascade event and earns the same scan** — the rule above is framed around a refactor that *lowers* specificity, but an element carrying no class was unreachable by every class selector in the bundle, and giving it one makes it newly reachable; run the same scan with the same two requirements. (2) **For a stylesheet edit, a comment-stripped declaration-block multiset diff against `HEAD` is the cheap mechanical proof that no existing control was weakened** — normalize whitespace, strip comments, split on rule boundaries, diff the multisets. "Zero blocks removed" settles in one command what reading a diff can only suggest, and it is immune to a large prose-only hunk hiding a one-line deletion. Reach for it whenever a CSS change lands in a file that also carries safe-area gates, contrast tokens, or accessibility guards.
- **A lookup table keyed by an UNVALIDATED string must be read through `Object.hasOwn`, so the lookup is allowlist driven (v0.5.81).** A bare `TABLE[raw]` on an ordinary object literal returns a *truthy inherited member* for at least twelve strings — `'constructor'`, `'__proto__'`, `'toString'`, `'valueOf'`, `'hasOwnProperty'`, `'isPrototypeOf'`, `'toLocaleString'`, `'propertyIsEnumerable'`, and the four `__defineGetter__` / `__defineSetter__` / `__lookupGetter__` / `__lookupSetter__` accessors — so a `TABLE[raw] ? mapped : fallback` guard silently takes the wrong branch for every one. A null-prototype table also works; prefer the guard, because its safety is visible **at the point of use**, where a null-prototype construction expression is invisible at the lookup and is exactly what a later reader "simplifies" away with no test failing. `normalizeShareCopySelection` (`lib/shareCopyPreference.ts`) is the reference. **The WRITE side pairs with it (v0.5.90): an accumulator map that will hold external-string keys is built as `Object.create(null)`** — on a plain `{}` a `__proto__` key hits the inherited setter, silently dropping a primitive entry and silently swapping the returned map's prototype when the value is an object; the four returned maps in `lib/tauri/taxonomyService.ts` (`codes`/`orders`/`formCodes`/`out`) are the reference. **A normalizer's malformed-input test list must include prototype-chain member names**, not just nonsense strings: `''` / `'nonsense'` / `0` / `[]` / `NaN` all exercise the same path, while `'constructor'` and `'__proto__'` exercise a different one. Add a pollution probe too, and **write it with `JSON.parse`, not an object literal** — `{ __proto__: … }` in source is special-cased by the language to set the prototype and creates NO own property, so it tests a shape that cannot arrive from storage; `JSON.parse` produces the real own `__proto__` key that can. (`Object.hasOwn` is the first ES2022-era runtime API in the app's shipped source — Safari 15.4 / Chrome 93 — and was cleared against both native targets: `minimumSystemVersion: "16.0"` on macOS and `IPHONEOS_DEPLOYMENT_TARGET = 16.0`, with Windows on evergreen WebView2. The `es2023` tsconfig target governs syntax downleveling and type-checking, not runtime API availability, and Vite polyfills no runtime methods, so the next such crossing needs the same explicit check.)
- **A "no outbound request" claim is verified by tracing every consumer of the URL-shaped strings, not by grepping for `fetch` (v0.5.81).** The absence of a network primitive is necessary but not sufficient — a URL string can leave the page through an `href`, an `img.src`, a `new URL()` handed onward, a `preconnect` hint, or a navigation. Confirm where each built URL actually goes.
- **A change that alters WHICH COMPONENT makes a third-party request is a `PRIVACY_POLICY.md` change, even when the destination host is unchanged (v0.5.76).** The policy describes who talks to whom, so moving a request from the browser to the self-hosted backend (or the reverse), or adding a request the user did not initiate, needs the policy updated in the same change — the same standing rule as adding a new provider. It is easy to conclude no update is needed because the host was already disclosed; that reasoning is wrong.

### Weather/tide blocks in comments

- **`stripWeatherTideBlocks()` (`lib/commentBlocks.ts`) is the single source of truth for hiding pasted weather/tide blocks** (the Checklists tab's toggle). A block is a SPAN — emoji header → end of attribution link — never whole lines: eBird's CSV export collapses pasted newlines into spaces, so user prose shares the block's line and can continue after the attribution. While blocks are hidden, display AND search both use the stripped text ("search matches what you see"), and an empty-after-strip comment counts as having no comment; the has-weather/has-tide FILTER flags read the raw comment regardless. The marker vocabulary must stay synced with `weatherFormatter.ts`/`tideFormatter.ts` — the tests build fixtures by calling the real formatters so a format drift breaks them. When changing any of this, re-verify against a real export: the three shipped strip bugs (same-line prose, moon-emoji night blocks, attribution-less blocks) were all invisible to formatter-fixture tests and only surfaced on real data.
- **Generated night-block headers are condition emoji + moon-phase emoji, UNSPACED (`☁️🌗`, v0.5.28).** The stripper anchors a block on its LAST emoji run before the first labeled line, so any future header change that splits the emoji into separate runs (e.g. adding a space) will leak the leading emoji on strip — keep the header emoji one contiguous run. The moon emoji needs NO strip-marker vocabulary entry (`EMOJI_RUN_RE`'s `\p{Extended_Pictographic}` already covers it); don't add one.
- **The moon-phase algorithm is a hand-ported `lunarphase-js@2.0.3`** — pure-UTC Julian Day, a deliberate deviation from the library's runtime-tz-dependent form so both runtimes are deterministic and identical — **duplicated byte-for-byte in `frontend/src/lib/weatherFormatter.ts` and `backend/formatters/weather.py`.** Change it in BOTH ports plus the golden oracle (`frontend/src/lib/weatherFormatter.golden.py`) in the same change; the byte-golden tests lock the parity. It is NOT an npm/pip dependency — do not add the library.

### Desktop app seams

Permanent architectural seams route all platform-sensitive operations. Use them in new code — do not bypass them.

- **Transport:** `transport.get()` / `transport.post()` from `frontend/src/lib/transport.ts` — for all outbound HTTP calls. In Tauri mode, `TauriTransport` routes each API path directly to a TypeScript service (weather, map, taxonomy, nominatim, stats, version). In web/Pi mode, `WebTransport` delegates to the Python backend.
- **Caching layers — pick by lifetime.** `CACHED_GET_PATHS` in `transport.ts` is the short-TTL (~90s) repeat-call cache; `replayStore` is the live-first offline replay of a last-loaded result. A **long-TTL persistent network cache** ("hold live data for days") follows `lib/countyCompletenessCache.ts` instead: a storage-seam document with an in-memory mirror, TTL-gated reads, per-entry shape validation on load (malformed entries dropped, never thrown on), a strict 250-entry cap plus a `JSON.stringify(data).length` payload-code-unit budget with `order[]` FIFO eviction, an in-flight dedupe Map, errors never cached, and offline stale-reads served for display. Keys, metadata, ordering and the document envelope are outside that budget, and one sole oversized newest payload is allowed; do not call it a byte cap. `replayStore` has the same semantics with a 300-entry cap. `storage.ts` is the persistence seam, not a cache owner; `persistedStyle.ts` has a finite shipped caller graph but its string-accepting API is not structurally bounded. A path served by a durable cache stays OUT of `CACHED_GET_PATHS` — one caching layer per call. `lib/hotspotActivityCache.ts` (6h TTL, FIFO at 2,000) is the second instance of the `countyCompletenessCache` pattern and adds one rule worth copying (v0.5.92): a durable cache computes its DERIVED fields at ONE chokepoint — the cache module's own `dedupedFetch` — so every persisted entry is fixed-shape by a single write path rather than by every caller's discipline.
- **A BUNDLED BUILD-TIME ASSET AND A PERSISTED RUNTIME CACHE ARE DIFFERENT TRUST BOUNDARIES, and the per-entry validation rule above applies only to the second (v0.5.89).** The distinguishing question is whether an attacker can change the document without already being able to change the code that reads it. For a Vite-inlined JSON import the answer is no — malformed JSON fails the build, not the user's session — so the correct defenses are **build-time** (a generator that fails closed on implausible output) and **CI-time** (an equivalence test against an independent re-derivation, plus a size bound on the entry chunk), not runtime validation. `ebird-countability.json` is the reference: `build-countability.mjs` hard-fails on short lists, overlapping lists, and a name collision in the inversion; `countableForms.test.ts` asserts it member by member and pins its `version` to the taxonomy snapshot; `entryChunk.test.ts` bounds it. Worth stating because the cache rule is written forcefully enough to be applied where it costs bytes on first paint and buys nothing. **If such an asset ever becomes runtime-loaded, this note inverts and the cache rule applies in full.**
- **A durable cache may hold TWO stores with OPPOSITE retention policies, and the choice follows what an eviction COSTS (v0.5.87).** The escapee document is the reference: its checklist ledger is **FIFO**, because evicting an entry costs one redundant request and loses no answer; its species index uses **admission control** (fill to the limit, then stop admitting, never evict), because evicting there would destroy a paid-for network answer and, at capacity+1, would do so on every pass forever. This is the v0.5.86 rule applied rather than contradicted — capacity+1 is a measurement rule, not a universal policy. Gate admission on the CONTAINER's own size, never a separate counter, and prove it: a test re-merges one species fifty times to show admission capacity is not silently consumed, and both stores are measured at capacity+1 asserting **work done**, not elapsed time.
- **A denormalized, PUBLISHED classification field is a legitimate member of a persistent cache document when a passive reader structurally cannot re-derive it — provided the raw evidence stays the source of truth and the reader CONFIRMS rather than trusts it (v0.5.87).** `ProvenanceSnapshot.excludedNames` is the reference: the Calendar holds no name-to-code join and may not fetch one, so it cannot classify by code; Statistics publishes the escapee-only names, the raw tokens remain in the document, and Statistics always re-derives from them. The passive reader then **confirms** the published list against the persisted checklist ledger using its own observations, so a newly loaded export that adds a carrier re-opens that species offline exactly as it does on Statistics. **Without the confirmation step this is a stale-cache trap**; with it, the offline reader tracks a new export correctly. Stated limit: for a species the passive reader cannot re-open, a published name is only as current as the last Statistics visit.
- **Nominatim has one bounded retention and provider-etiquette contract on both transports (v0.5.86).** Tauri and FastAPI each retain at most 4,096 rounded-coordinate county results with fill-and-stop admission: overflow calls still return their result but do not evict the admitted working set. On desktop, forward search and reverse county lookup share one request-start queue enforcing at least one second between starts, and concurrent reverse calls for the same rounded key share one in-flight Promise. Keep the JS/Python rounded-key semantics in parity, including negative half-step cases.
- **Outbound eBird fetching at volume follows ONE pacing contract on both transports (v0.5.92): spaced request starts + one key-global Retry-After-honoring cooldown + bounded per-item retries — the eBird analogue of the Nominatim queue, at eBird scale rather than Nominatim's mandated 1 s.** The mechanics are pure in `lib/rateLimit.ts`: 150 ms global start spacing (the concurrency pool stays a latency-absorbing ceiling; spacing is the governor); a 429 opens ONE shared cooldown gating every request start (the KEY is over the limit, not a slot), honoring a seconds-form `Retry-After` capped at 60 s, else bounded exponential 2 s → 30 s with jitter; a burst of simultaneous 429s counts as one wave, a post-cooldown success resets the ladder, and the cooldown deliberately survives a pass restart. Bounded retries per item (2), then the honest unanswered state with Retry; a 429 is NEVER cached. The upstream `Retry-After` is parsed, bounded, and re-serialized identically on both transports (`rateLimit.ts` ↔ `_parse_retry_after_seconds` in `backend/routers/map.py`) — never reflected raw — and both transports surface a 429 AS a 429, fixture-locked. Two test rules ride with it: anchor timing-policy measurements on CLIENT observation of request starts with a settled main thread, never network-side fulfill timestamps; and `rateLimit.ts` deliberately rides the entry chunk (dependency-free by extraction, policed by `entryChunk.test.ts`). Scope today: only the hotspot-activity pass is governed — the other eBird surfaces share the key but not the cooldown (extension is on ROADMAP; reuse `rateLimit.ts`, don't re-derive).
- **Storage:** `storage.getApiKey()` / `storage.getSetting()` / etc. from `frontend/src/lib/storage.ts` — for all key, setting, and file access. Do not call `/settings/*` endpoints directly from new components.
- **Platform detection:** `isTauri()` from `frontend/src/lib/platform.ts` — single source of truth for branching on Tauri vs. web. Do not check `window.__TAURI_INTERNALS__` elsewhere.
- **Clipboard:** `copyText()` from `frontend/src/lib/clipboard.ts` — for all clipboard writes. In Tauri mode it uses the native `@tauri-apps/plugin-clipboard-manager` (no user-gesture requirement, so auto-copy after an `await` works); on web it uses `navigator.clipboard` with an `execCommand` fallback. **Do not call `navigator.clipboard` directly** — an async clipboard write that runs after an `await` (outside a click) throws `NotAllowedError` in WKWebView/WebView2 and is silently lost on desktop. The capability grants `clipboard-manager:allow-write-text` only (write, not read).
- **Opening an external URL from code:** `openExternalUrl(url)` from `frontend/src/lib/openExternal.ts` — **never `window.open()`**. `window.open()` is silently dropped in the Tauri desktop WebView (WKWebView never opens the system browser), so an external open works on web but does nothing on desktop with no error (the Weather Backlog's "Copy weather & go" hit exactly this, v0.5.67). The whole app opens external links only via `<a target="_blank">` anchors, which `tauri-plugin-opener` intercepts; `openExternalUrl` synthesizes exactly that — a transient, detached `<a target="_blank" rel="noopener noreferrer">` that is appended, `.click()`-ed, and removed — so it works in BOTH web and desktop. For a **user click**, prefer the shared link components (`OutboundLink` / `ChecklistLink` / `HotspotLink`); reach for `openExternalUrl` only when the open must happen from code (e.g. after an `await`). Keep the same id-shape guard + `encodeURIComponent` on any id in the URL as everywhere else.

### Desktop storage (Tauri)

`TauriStorage` in `storage.ts` uses **`tauri-plugin-fs` with `BaseDirectory.AppLocalData` for everything** — API keys, settings, file metadata, and CSV files. All data lives under `AppLocalData/data/`:

| File | Contents |
|---|---|
| `data/api-keys.json` | API keys (`ebird`, `openweather`) |
| `data/settings.json` | App settings (map center, zoom, etc.) |
| `data/metadata.json` | Uploaded file metadata |
| `data/ebird-backup.csv` | eBird data file |
| `data/ml-export.csv` | ML data file |

Every write calls `mkdir(DATA_DIR, { recursive: true })` before writing to ensure the directory exists.

**Do not use `localStorage`** — it is ephemeral in Tauri's WKWebView and cleared on every relaunch.  
**Do not use the system Keychain** (`keyring` crate / `invoke('get_api_key', ...)`) — it requires entitlements not configured in this app and fails silently.

**Persist all UI settings through the `storage` seam, never `localStorage` directly.** Anything that must survive a desktop relaunch (e.g. the tab layout) goes through `storage.getSetting`/`setSetting`. The web/Pi path may still read `localStorage` synchronously inside the seam for a flash-free first paint, but the seam — not `localStorage` — is the source of truth on desktop.
