# Release ledger

Per-version App Store and Android records, one entry per ship, moved out of `CLAUDE.md` on 2026-10-21 so the always-loaded file holds the rule and this file holds the record. The rule that governs this file is in `CLAUDE.md`, Versioning: at every ship, query App Store Connect for the version records and TestFlight trains and account for every version in writing here, because a rollup, a deferral, a TestFlight-only release and a silent skip leave the same evidence in App Store Connect, and only the sentence written here separates them. The Android leg gets the same per-version sentence: the F-Droid state in one of seven words (not yet submitted; merge request open; included and this tag not yet built; included and built, not yet published; included and this tag picked up; superseded on F-Droid, naming the version that carries it; deferred, with the reason) and the GitHub APK with its signer SHA-256. **A version with no sentence here is a skip.** Mechanics are in the `snowraven-release` skill.

The entries below are the text as it stood in `CLAUDE.md`, split per ship and otherwise unchanged. New entries are added at the END of each section in the same ship, in the same shape.

## App Store (iOS)

### Rhythm, rollups and the three genuine skips

**Release rhythm (summary):** bump version → commit → push `main` → push the `vX.Y.Z` tag (starts Windows and Android CI; F-Droid builds its own APK from it) → wait for CI green → run `./release.sh` → sign the Android APK, get the user's device check, attach it → ship the iOS TestFlight build of the SAME version → submit that same build for App Store review. **A release goes to ALL available platforms, every time** (user direction, v0.5.78; the App Store became a standing leg at 1.0.0) — a release is not done until every leg has shipped and been submitted. **VERIFY the App Store leg against App Store Connect; never infer it from the repo (v1.0.17).** 1.0.15 and 1.0.16 each shipped a `VALID` TestFlight build and neither ever got an App Store *version record*, so the store sat on 1.0.14 for two releases — and nothing in this repo would have said so: a TestFlight build is not a submission, the changelog and tags look identical either way, and the miss was only found by querying ASC during the next ship. A ROADMAP item naming the debt was **not** enough; it was item 1 in Up Next while 1.0.16 shipped past it. **AND WRITING THIS RULE HERE WAS NOT ENOUGH EITHER: IT HAPPENED A THIRD TIME, AT 1.0.18 (v1.0.20).** Queried at the 1.0.20 ship, version records exist for 1.0.19, 1.0.17, 1.0.14, 1.0.13 and 1.0.4, while TestFlight holds VALID builds for 1.0.15.1, 1.0.16.1, 1.0.17.1, **1.0.18.1** and 1.0.19.1 -- so 1.0.18 is the third release to ship a VALID build and never receive a store version record. Nothing was lost to users (1.0.17 carried 1.0.15 and 1.0.16 to the store, 1.0.19 carried 1.0.18), and each skip was found the same way and only that way: **by querying ASC at the next ship.** Record the pattern rather than the intention -- a roadmap item and a rule in this file have each now failed to stop it, so do not add a third reminder; do the query. So at every ship, list the version records for the last few releases (`GET /v1/apps/{id}/appStoreVersions`) and confirm each one either shipped or is deliberately deferred **in writing**; a deferral is a decision with a reason, never a silence. **THE QUERY CANNOT DISTINGUISH A DELIBERATE ROLLUP FROM A SILENT SKIP, WHICH IS WHY THE WRITTEN RECORD IS LOAD-BEARING RATHER THAN CEREMONIAL.** When a release is folded into the next one -- the in-review record withdrawn, retargeted at the newer version, repointed at the newer build and resubmitted -- the older version ends with a `VALID` TestFlight build and no version record of its own, which is the same evidence signature a skip leaves.
