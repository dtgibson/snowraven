## Shipped

121 versions shipped. Last shipped: **what counts as a species now follows eBird's own rule (v0.5.89)** -- SnowRaven used to work out whether a bird counted toward your list by looking at the shape of its name, guessing from a "sp.", a slash, or an "x". eBird already answers that question in the taxonomy SnowRaven ships with it, so it now just reads the answer. The rule in one sentence: a form that leaves the species in doubt does not count (a spuh, a slash, a hybrid, an undescribed form), and a form that only leaves the subspecies in doubt counts as its parent species. **Most totals go up.** 88 names eBird counts were being left out, folding into 59 species, and they are everyday birds: `Canada Goose (moffitti/maxima)`, `Redpoll (Common/Hoary)`, `Dark-eyed Junco (Slate-colored/cismontanus)`, `Iceland Gull (thayeri/kumlieni)`, `Red-tailed Hawk (calurus/abieticola)`. **A few go down**, because 81 names were counting that eBird does not count: three named hybrids whose names give no hint they are hybrids (`Brewster's Warbler (hybrid)`, `Lawrence's Warbler (hybrid)`, `Bogota Sunangel (hybrid)`), 25 spuhs, and 53 undescribed or unrecognized forms. Those birds stay on your Life List; only the count changes. The same number now appears everywhere, where Statistics, the Calendar, county Completeness and the Multimedia count had been applying three slightly different rules and could disagree about the same bird. The switches are renamed to match what they now do: **Count spuh, slash & hybrids** becomes **Count all forms** (Statistics and Calendar) and **Show sp./slash** becomes **Show all forms** (Multimedia and Species Detail), and the two Show switches now cover the whole set, so the rows on screen and that tab's own "X of N species" agree instead of leaving hybrids visible that the count had excluded. It all still works with no connection, and nothing new is fetched.

Previously: **two corrected backend input checks, with nothing to see (v0.5.88)** -- this release changes nothing you can see or do, and saying so plainly is more useful than dressing it up. SnowRaven's self-hosted backend checks the shape of a value before it trusts it: the name of a settings entry, one step before that name becomes a file on disk, and a checklist id before it goes out to eBird. Each check was letting through a narrow class of value it was written to refuse. A settings name ending in a stray line break slipped past and quietly created a second settings file beside the real one, and it skipped a second safety check meant to keep certain names reserved. A checklist id written with digits from a non-Western numbering system slipped past too, which meant the backend disagreed with the equivalent check the app itself makes before sending the request. They look like one problem and are two, and fixing either would not have fixed the other. Both now refuse exactly what they always said they refused, and every settings entry and checklist id that worked before works identically.

Earlier: **an escapee-aware species count on Statistics (v0.5.87)** -- the headline species total can now match the life-list number eBird itself shows you. A new **Count escapees** checkbox, off by default, follows eBird's own rule: birds recorded as Provisional or Naturalized count toward your list, birds recorded as escapees do not. Turn it on and you get exactly the number the tab showed before, so nothing is taken away. On the reference export the default figure reads 264 rather than 267, dropping Graylag Goose, Swan Goose and Muscovy Duck, and a panel beneath the figure names them, since a total quietly falling by three with no account of itself is the failure this repo keeps rejecting. Working out which birds those are is a bounded, cached lookup rather than a sweep of your whole history: whether a bird is an escapee is recorded per sighting, but the question is per species and one checklist answers it for every bird on that checklist at once, so the app works out offline which handful of checklists it needs and asks for only those. On the reference export that is 73 lookups in about ten seconds, cached for 30 days, and a later export re-checks only what it has not already resolved. A species it could not resolve still counts, so the number only ever converges downward and never wrongly erases a bird you have seen. With no eBird key, no connection, or a failed lookup, the tab says which and shows the uncorrected number. The Calendar still opens, counts and shades with no connection at all.

Two hardening changes have nothing to see: Tauri and FastAPI now retain at most 4,096 rounded-coordinate Nominatim results without churning the admitted set, with one shared desktop request-start queue; and seven safe-area stylesheet guards inspect nested rules through a fail-closed AST rather than silently skipping an at-rule tier.

## On the Horizon

Ideas worth tracking, not yet scheduled:

- **The two pre-existing regex anchor divergences the v0.5.87 sweep surfaced are DONE (v0.5.88).** They were one class of defect but two independent bugs, and neither fix would have closed the other. `backend/routers/settingskv.py`'s `_KEY_RE.match(key)` was the anchor half and is now `fullmatch`, closing a trailing-newline key that returned 200 and wrote a second file beside the real one while walking past the reserved-key check. `weather.py` and `tide.py` were the v0.5.54 character-class half and now share one `CHECKLIST_ID_RE = re.compile(r"^S[0-9]+$")` on `services/ebird.py`; `fullmatch` stays at each call site, so each router keeps its own route-level test. No traversal was ever reachable through the settings store, verified over raw sockets. Pydantic `pattern=` constraints stayed exempt and were not swept in.
- **Gate `/checklists/{checklist_id}` on `CHECKLIST_ID_RE`** -- surfaced by the v0.5.88 security review (Low, pre-existing, outside that change's approved scope). `services/ebird.py` exports a second public function taking a checklist id, `fetch_checklist_species`, and its only caller (`routers/checklists.py`) applies no shape guard, so an unvalidated id reaches the same outbound eBird URL construction. **The reachable injection is the QUERY STRING ONLY** -- `/checklists/S1%3Ffoo=bar` arrives as `S1?foo=bar` and builds `.../checklist/view/S1?foo=bar`. Do not widen this wording when scheduling it: within-host path traversal, host steering and request splitting were each measured end to end on a live uvicorn over raw sockets and are all unreachable, because Starlette's default `str` path converter matches `[^/]+`, so the value is always exactly one segment and `%2F` is never decoded into it (the `%252F`, backslash, overlong-UTF-8 `%C0%AF` and fullwidth-solidus attempts all fail to smuggle a separator). An earlier, wider wording claiming traversal was measured and withdrawn. The fix is one import and one `if` plus a route-level test; the fragility worth noting is that the protection comes from routing rather than from a guard, so switching this route to `{checklist_id:path}` would remove exactly that protection.
- **Length-bound `CHECKLIST_ID_RE`** -- also from the v0.5.88 security review (Low, pre-existing; `HEAD`'s `S\d+` was equally unbounded, so that change neither introduced nor worsened it). `^S[0-9]+$` refuses every dangerous character and still admits any length: measured through the real route, a 65,001-character id passes the guard and reaches an outbound request, with no practical server-side ceiling found in this configuration. That deviates from the house SSRF rule, whose reference guard (`/media/embed-status`) is explicitly bounded, and the neighbouring `_KEY_RE` in the same change is `{1,128}`. `^S[0-9]{1,20}$` would do it; the shared fixture's `S999999999999` row (12 digits, currently asserted valid with the note that the guard bounds shape rather than length) needs its expected verdict re-confirmed against whatever ceiling is chosen. Worth pairing with the `/checklists` gate above, since both concern the same constant's fitness as an SSRF guard.
- **Route `taxonomyService.ts`'s object-literal lookups through `Object.hasOwn`** -- surfaced by the v0.5.89 audit (Informational, pre-existing, in a file that build does not touch). `cache.byCom[comLower]` and its siblings (`:246, 253, 288, 308-309`) index bare object literals with a lowercased species name taken from the user's CSV, which is exactly the class the v0.5.81 rule exists to prevent: a name of `constructor`, `toString` or `valueOf` returns a truthy inherited member and takes the wrong branch. Impact is low and bounded -- the resulting value is `encodeURIComponent`-wrapped before it reaches a URL, so the outcome is a malformed favicon request rather than injection, and it needs the user to load a hostile CSV into their own local app. Flagged mainly because v0.5.89's new code follows the rule correctly, so a reader could reasonably assume the module already did. `shareCopyPreference.ts:84` is the reference.
- **Clear the `nanoid` npm audit advisory** -- found during the v0.5.89 release preflight. It arrives through vite to postcss, appears in no `dist` asset, and was already in v0.5.88's lockfile, so it is build-time only and pre-existing. Per the repo's own rule a dev-dependency fix is a separate change with **no version bump, tag or release**; it reaches the release machine on the next `git pull`.
