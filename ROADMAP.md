(2) **All eight tab loaders' OUTER `catch` still maps any post-status throw to `setup-required`, so the guarantee holds for the throws that have been enumerated and NOT structurally -- and v1.0.16 turned that from a general worry into a named, reachable case with a divergence attached.** A `storage.getFilesStatus()` that REJECTS is not "no file stored", but every one of the eight lands it in the same outer catch and shows the setup panel, which is this family's own lie at the one layer nobody swept. The desktop is unaffected by the divergence, for a reason worth keeping in view when this is picked up: `TauriStorage.readMeta`'s blanket catch swallows its own failures into `{ebird: null, ml: null}`, so the rejection never reaches a loader there. That is the `readMeta` twin of item (1)'s `readFile` problem, and the two want doing together. **`WebStorage.getFilesStatus` is the third of that shape and the one nobody has named:** it returns `{ebird: null, ml: null}` for any non-ok response, so a backend answering 500 reads as "no file stored" on web and Pi and lands every surface, the backlog included, on the setup guidance rather than on a load failure. - **A device whose clock is LIVE more than a day ahead still ping-pongs with its peers** -- the v1.0.12 security review's one open Low (Finding 1, narrowed), availability only, no key lost or exposed.
