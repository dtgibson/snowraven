A. Launch

Green from the tap to the first frame

Android has no launch backdrop, so three resources do the job the iOS storyboard does: the system splash, the window background, and the HTML launch frame the app already ships. All three are the brand green with the raven, in both themes, so nothing white can appear between them.

What each frame is

System splash (API 31 and later). windowSplashScreenBackground is the brand green and windowSplashScreenAnimatedIcon is the adaptive icon's foreground, so the splash is the mark on the green. No core-splashscreen library, no fixed wait: it yields on the Activity's first draw.
API 24 to 30. No system splash exists, so the window background itself is a layer-list: the green with the same mark centered. It reads as the same frame.
Window background, both themes. android:windowBackground is @color/ic_launcher_background in values/ and values-night/ alike. The green is the launch color on every platform and is not a light color, so dark mode cannot flash; the first thing the app's own theme paints is its first frame.
Status bar during launch. Light glyphs over the green (windowLightStatusBar=false in the splash theme). Once the app paints, enableEdgeToEdge() picks the glyph color from the system theme.

Handoff

Splash to window to launch frame to first frame is four paints of the same green with the mark in the same place. The frame-to-frame change the user can see is the splash's circular icon plate giving way to the bare 88px mark; nothing animates between them, and the launch frame removes itself the instant React has painted, as it does today.

Old WebView

Below the Chromium 111 floor the launch frame stays and says one thing: SnowRaven needs a newer Android System WebView: update it through your phone’s app store or system update, then open SnowRaven again. It names no store, because an F-Droid or sideloaded install may be on a phone with none of Google’s; the System WebView updates through whatever store the device has, or through the ROM’s own update. No Reload button, because reloading cannot change the WebView.

B. Edge to edge

The app draws under the bars and its own rows stay clear

Android paints the webview under the status bar and the navigation bar, and the WebView reports env(safe-area-inset-*) as zero. The native Activity reports the real insets into four CSS variables, an sr-android-app root marker gates rules that read them, and the compact header and the phone bar pad themselves exactly as the iOS rules pad with env(). Toggle the keyboard to see what moves.

Mechanism

Injected insets, the Architect's option (b). MainActivity installs one window-insets listener on the webview and sets --sr-inset-top/right/bottom/left on documentElement in CSS px (inset over density). The app keeps drawing under the bars in its own theme, so the strip under the status bar is --sr-bg in light and in dark, and the in-app theme toggle is honored there as it is on iOS.
Root marker sr-android-app. Added by main.tsx when isAndroid(). Every Android inset rule reads only the four variables and never env(), so a future WebView that starts reporting env() cannot double-pad. sr-ios-app is never applied on Android.
Which surfaces, exactly. One Android twin for each iOS rule, same selector list: body top/left/right; the phone bar and the More sheet bottom; the nav column top and height; the map fullscreen panel top/left/right; the FAB cluster bottom; the Help panel and TOC; the dialog root; the palette and inbox roots; the pinned table bands; the skip link. The two pinned-band rules and the skip link re-point an offset; everything else pads.

Status bar glyphs

Dark glyphs over the light in-app theme, light glyphs over the dark one, following the theme the app has painted, not the system setting. The page reports light or dark to native through a web message listener registered in the same MainActivity hook as the insets, and native sets the status and navigation bar icon appearance to match: on first paint, on every Appearance change, and when the system theme flips while the app is open in the System setting. Status-bar glyphs follow on every supported Android; navigation-bar glyphs follow on API 26 and later, and on 24 and 25 stay light over the platform's dark scrim.

Keyboard

The keyboard is an occluder, not decoration. The ime() inset is applied natively as bottom padding on the webview, so the viewport shrinks exactly as it does under adjustResize and Chromium scrolls the focused input into view on its own. The system bars stay injected variables; the keyboard is the one inset the app must never paint under.

While the keyboard is up, the phone bar slides out (160ms ease-out, instant under reduced motion) instead of riding on top of the keyboard where it would spend a quarter of the remaining height. 100dvh surfaces shrink with the viewport, so a sheet or the fullscreen map never hides a field under the keys.

Landscape and cutouts

A punch-hole or a landscape sensor housing arrives as a larger top or side inset in the same variables; the fullscreen map's pills, its Filters sidebar and its corner buttons clear it the way they clear the Dynamic Island, because the padding is on the panel and the FAB cluster reads the bottom and side variables.

C. Settings

Only the settings that apply to this phone

No iCloud Sync, no Alerts, no widgets, no updater footer. Each is a whole section that is absent, so no heading is left over an empty card. Everything else keeps its order: API Keys, Default Files, Help, Appearance, Sharing, Default Location, Tab Layout, eBird bar-chart files, Troubleshooting, Acknowledgments.

Troubleshooting

If the map or species lookups stop working, rebuilding the app's local caches usually fixes it. Afterwards, close and reopen the app.

Acknowledgments
No update footer: Android updates come through F-Droid or a newer APK

Scroll inside the frame. The dashed notes mark where an Apple section would sit; they are not rendered in the app.

Decisions

Import wording. The two Default Files rows read Import file…, Import new… and Importing…, the approved iOS strings; Upload appears nowhere on the tab.
Troubleshooting stays. Rebuild caches clears, skips the relaunch, and says Caches cleared. Close and reopen SnowRaven to finish. in the iOS words.
No placeholders. Nothing says "not available on Android". Help is where the platform split is stated, in one sentence.

Help sentence (written without a stop)

On Android there is no iCloud Sync, no home-screen widget and no Alerts; those are Mac, iPhone and iPad features. Everything else on this page works the same way.

Help also gains the two install sentences: Installs from F-Droid and from the GitHub APK are signed by different keys and do not update each other; switching between them means uninstalling one and installing the other, and your files and keys do not carry over unless you import them again. And: On Android, updates arrive through the F-Droid client or by installing a newer APK from the GitHub release over the old one, never from inside the app.

Largest system font

Android's font scale reaches the WebView as text zoom on top of the in-app Text Size. Rows wrap rather than clip: the description column takes overflow-wrap: anywhere already, the quiet buttons keep their 30px minimum, and the row grid lets the action drop under the text at the phone tier exactly as it does at 200% today.

D. Location

Two branches, decided by a measurement

Location on Android is the Android System WebView’s own geolocation with nothing of Google’s, and whether that works is measured on an emulator before the location path is built. Branch A: the surface stands, the system dialog on first press, the approved denied sentence. Branch B, the default until a passing measurement lifts it: every location control is absent, with no placeholder and nothing else moved. The three buttons switch between them.

Branch A, the dialog is Android’s. Its words, its Precise and Approximate choice and its three buttons are the OS’s; SnowRaven cannot change them and does not try.

The denied sentence

Allow location for SnowRaven in Settings → Apps → SnowRaven → Permissions → Location, and make sure Location is turned on, then try again.

Same register and the same arrow path as the iOS and Windows sentences. It names the app's own permission and the phone's master switch in one line, because the plugin reports both refusals on the same path. It is the only platform sentence shown on Android.

Branch A, what the user sees, by state

  • First press: the system dialog. Allow returns the position; the map centers on it.
  • Refused, or "don't ask again": the red note, no second dialog.
  • Location off at the phone level: the same note, because the plugin reports the switch as a refusal.
  • No fix in ten seconds: the timeout sentence the app already has, not the denied one.
  • A phone without a network location service (a de-Googled ROM): a position may take longer or need GPS; that is the phone’s provider set, not the app, and one Help sentence says so only if the emulator reading shows it.

Approximate location

With both permissions declared the dialog offers Approximate. The app asks for high accuracy and the WebView downgrades it itself when only Approximate is granted; the measurement’s step 4 records whether that yields a position a few kilometers off or the generic unavailable sentence, and that decides one Help sentence. The surface is the same either way.

Branch B, surface by surface

  • Map Explorer: the FAB row is share, Filters, fullscreen; the locate disc is simply not in the row and flex closes the gap, so nothing is reserved. The map still opens on the Default Location and moves to a searched place.
  • Filters sidebar: no Use my location row; the place search takes the full row.
  • Settings, Default Location: description, the three fields, Save. No button, no error line, no blank band where the button was, no sentence about location.
  • Targets: the Measure distances from chooser opens on Default Location and the place search; no My location item.
  • Weather: no Current weather and tide control; the checklist lookup and the Planner stay, and Plan with no place takes its existing no-place state.

E. Tablet

A 10-inch tablet gets the wide layout, as iPad does

At 1280 CSS px the nav picks the sidebar density from measured width, and <main> starts at the top of the window under the status-bar inset. In portrait (800 wide) the same rule picks the icon rail. No tablet-specific reading: the Android tablet is the desktop layout with the insets injected, exactly as iPad is the desktop layout with env().
