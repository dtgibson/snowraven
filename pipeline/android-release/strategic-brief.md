# Strategic Brief: Android Release

Revised 2026-10-03 on a Stage 1 re-entry: the store leg is F-Droid, not Google Play. The parity cut, the version floor, the application id, the launch and inset design, the verification posture and the GitHub-release APK stand as first written.

## What We're Building
SnowRaven on Android phones and tablets: the same Tauri app that ships to macOS, Windows, iPhone, iPad and the self-hosted web/Pi install, built as an Android app, distributed through F-Droid with a universal APK on every GitHub release, and joining the release rhythm as a standing leg so every version from here on ships to Android too. The Android build carries no Google code of any kind.

## Why Now
The shipped mobile-app roadmap item said iOS first, Android to follow, and the iOS half has been live on the App Store since 1.0.0 with widgets, Alerts and iCloud Sync layered on since. The mobile foundation is already paid for: the Cargo cfg blocks, the mobile capability file, the dialog plugin and the dormant Android icon set all exist, so what is missing is the Android project, a build and signing recipe, the F-Droid metadata and the published claims. Android is the last platform a birder might carry into the field that SnowRaven cannot reach, and the "to follow" line has sat on the Horizon since the mobile item shipped. The user will not pay Google to distribute a free public good, which is what makes F-Droid the store and not a fallback: it costs nothing, it builds from the AGPL source the repo already publishes, and its users are exactly the birders most likely to be carrying a phone without Google services.

## The User Problem
A birder with an Android phone has their eBird backup and Macaulay export and no way to open SnowRaven in the field: the desktop app needs a laptop and the web/Pi install needs a server at home. The product's promise is your own data on your own device, and today that promise stops at the Apple phones. This release gives an Android birder the same local-first dashboard, the same weather and tide block, the same maps and targets, with their files and keys staying on their phone, from a store that asks for no account and a build that contains nothing of Google's.

## Success Criteria
- A release-signed build (not a debug build) installs and opens to the first usable screen on an Android emulator at the chosen version floor and on an emulator at a current Android version, verified by a screenshot of the running app, never by a process check.
- The user installs the same build on their own Android device, opens it, loads their eBird backup and Macaulay export through the file picker, and reports that the Weather lookup, Species Detail, Statistics, Map Explorer and Targets all work with their keys. Agents never touch that device; they give exact steps and record the reported result.
- Every Apple-only section is absent on Android rather than present and broken: no updater footer, no iCloud Sync section, no widgets or Alerts settings, and no control that invokes a plugin the Android binary does not carry. Location controls follow the location decision below: present only if the measured Google-free route serves them, otherwise absent, and never present and failing.
- The Android app makes the same device-to-provider requests as the iOS app and no others: no GitHub update check, no new host, no new endpoint, and no request to any Google service.
- The Android build's merged release dependency tree contains no `com.google.android.gms`, no `com.google.firebase` and no other Google library, and the source tree passes F-Droid's scanner with no prebuilt binary and no non-free dependency, verified by running `fdroid scanner` and `fdroid lint` locally against the prepared fdroiddata entry, and by `fdroid build` on the Mac if the host toolchain allows; where a step cannot run locally, a written checklist against the inclusion policy stands in and says so.
- The version string is shared with every other platform, the Android version code is written at the bump from the same formula Tauri uses and asserted by a guard, F-Droid's update checker can read both from the tagged commit, and the release runbook names the Android leg beside the Windows and iOS legs.
- The repo carries everything F-Droid needs to build and list the app: the aligned license fields, the in-repo Fastlane metadata (title, short and full descriptions, a changelog per version code, screenshots), and the fdroiddata build recipe. The fdroiddata merge request is prepared from them and either submitted or deliberately deferred in writing, in the same style CLAUDE.md keeps for the App Store version records.
- The first release's Android availability on the day of the ship is the GitHub-release APK; the F-Droid listing arrives when F-Droid's review and build cycle lets it, and that gap is recorded, not implied away.
- The website, README and privacy policy mention Android only after the user has read and approved the exact sentences.

## Scope
- An Android project under `src-tauri/gen/android`, generated once by `tauri android init` and committed, with a documented regeneration procedure that mirrors the iOS keep-aside-and-restore rule. The gradle wrapper jar the generator commits is the one prebuilt binary in that tree: it is removed from the commit (CI, the release machine and F-Droid each supply their own gradle) unless the Architect confirms F-Droid's scanner accepts an official wrapper jar by checksum.
- One build for phones and tablets: the existing responsive frontend, the phone tiers, 200% text scale and the WCAG 2.1 AA posture carry over unchanged.
- The TypeScript service path (`lib/tauri`) for every outbound call, exactly as on iOS; no Python backend on Android.
- The plugins the Android binary needs: fs, os, opener, clipboard-manager and dialog, with Android grants in `capabilities/mobile.json`. The geolocation plugin is NOT among them (see the location decision); its Cargo line and its capability grants become iOS-only.
- Location on Android per the decision below: the plugin-free route is measured, and the controls are shown or absent on the result.
- File import through the native document picker, with the Android reading of the iOS Mechanism A/B switch measured on an emulator rather than assumed.
- The committed Android icon set brought into the project as an adaptive icon, and a 512px store icon for the metadata folder.
- A launch state owned by The Designer: Android has no `launch_backdrop`, so the window background and the system splash are what a user sees first.
- A re-keying of the capability gates: every `isIOS()` branch that really means "mobile" or "no updater" gets an Android reading on purpose, with `showUpdaterFooter`, `supportsAppRelaunch`, `compactChrome`, the import mechanism, the map fullscreen rule and the location path each argued one at a time.
- The license made machine-readable: `src-tauri/Cargo.toml`'s empty `license` and `frontend/package.json`'s missing `license` field both carry the SPDX id that matches the LICENSE file and any "or later" statement the repo makes, and a guard keeps them equal.
- The store listing as in-repo Fastlane metadata, which F-Droid reads from the tagged commit: `fastlane/metadata/android/en-US/` (F-Droid's documented layout; `metadata/en-US/` at the repo root is also read, and the Architect picks one and names it) with `title.txt`, `short_description.txt` (80 characters), `full_description.txt`, `changelogs/<versionCode>.txt` (500 characters, one per release from this one on), `images/icon.png` and phone and tablet screenshots. This is published copy: prepared as a held proposal in the pipeline folder, shown rendered, written only on the user's express yes.
- The F-Droid build recipe: the fdroiddata metadata YAML for `com.dtgibson.snowraven`, with the SPDX license, source and issue URLs, `UpdateCheckMode: Tags` against `^v[0-9.]+$`, `UpdateCheckData` reading the version name and version code from `src-tauri/tauri.conf.json`, `AutoUpdateMode: Version`, and a first `Builds` entry whose steps install the pinned Rust toolchain and Android targets, the pinned Node, the NDK F-Droid provides, run the frontend build and the Tauri Android build, and name the output APK. Prepared in the pipeline folder; the one-time merge request to `fdroiddata` is a user step with exact instructions, or prepared by the build for the user to submit under their own GitLab account.
- The release leg: a CI job that builds the release universal APK on the version tag, the way `windows-build.yml` builds the installer; signing with the user's own keystore on the release machine; the APK attached to the GitHub release beside the macOS and Windows assets; a device check before the GitHub asset is published; the per-release metadata changelog file; the runbook entry in the `snowraven-release` skill; and the version-record list in CLAUDE.md gaining an Android line that records, per release, whether F-Droid has picked the tag up or the listing is still pending.
- Held proposals, never writes, for the remaining published surfaces: one Android sentence each for the website and README, and the privacy policy edits (the Overview's platform list; an Android App paragraph beside the iOS App section saying the build contains no Google services, no Play, no Firebase and no analytics, and where its data lives and whether Android's device backup includes it, as the manifest decides; the Software Updates section saying Android updates arrive through the F-Droid client, or by downloading a newer APK from the GitHub release and installing it over the old one, and that the Android app makes no update check of its own; and the Your Location paragraph per the location decision).
- `docs/HELP.md` updated where it names platforms, written without a stop as the standing rule allows, and carrying the two facts an Android birder needs that no store tells them: an APK from GitHub and a build from F-Droid are signed by different keys, so switching from one to the other means uninstalling first, which deletes the files and keys stored on the phone (keep the export files and re-import); and installing the GitHub APK requires allowing installs from the browser or file manager, once, in Android's settings.

## Out of Scope
- Google Play in every form: no Play Console, no Play App Signing, no Data safety form, no content rating questionnaire, no Play upload, no internal testing track. Nothing in this run creates a Google account or pays Google.
- iCloud Sync on Android, in any form, and any Android cross-device sync in its place. The section stays hidden because `showICloudSync` is already false off Apple platforms; no "not on Android yet" placeholder, since iCloud can never come to Android and Help already names it as a Mac, iPhone and iPad feature.
- Home-screen widgets and the Alerts background check. Both are Swift and WidgetKit today; an Android equivalent is a feature of its own, not a port. Hidden on Android, not stubbed.
- The window-geometry plugin and the in-app updater, which the desktop cfg already excludes from mobile binaries. No Android self-update path of any kind, including an in-app "newer version on GitHub" notice.
- Reproducible builds. F-Droid signs with its own key unless a build is proven byte-reproducible, and proving that for a Rust, Node and gradle chain is a project of its own; v1 accepts F-Droid's signature and says so in Help and the privacy policy.
- Android Auto, Wear OS, Chromebook-specific work, foldable-specific layouts and any Android-only feature beyond parity.
- Native Android code beyond what Tauri and its plugins generate and the plumbing this run already owns in `MainActivity.kt` (insets, the theme listener, and the location permission callback if the measurement admits it); no Kotlin feature work, no new screen, flow or capability, and no vendored or forked geolocation plugin in v1.
- A Tauri or tao upgrade. The locked 2.11.2 and the vendored tao stay; if the vendored crate will not build for the Android target, that is a flag for the user, not a license to upgrade.
- Any other store or repository: no Accrescent, no IzzyOnDroid, no self-hosted F-Droid repo. The GitHub-release APK is the only non-F-Droid path.
- Changing the product's privacy posture: no analytics, no crash reporting SDK, no Firebase, no Google library of any kind, in any build.

## Key Decisions
- **Alignment: inside the founding strategy.** The product brief's distribution decision already names a mobile store, the shipped mobile item said Android would follow, and nothing in Out of Scope touches it. Android serves the same birder with the same local-first promise and widens where the product can be used, not what it is. F-Droid fits the brief better than Play did: a free app, built from published AGPL source, with nothing of a platform vendor's inside it.
- **F-Droid is the store leg; the GitHub-release universal APK stays and is the first-day path.** The APK is how an Android birder gets the app before F-Droid inclusion lands and how a phone without the F-Droid client gets it at all; it carries no updater and no update check, which Help and the privacy policy say. It is not a self-hosted store and gains no repository index.
- **No Google services in the Android build, as a product decision and not only a store requirement.** F-Droid's inclusion policy refuses non-free dependencies, and `com.google.android.gms:play-services-location` is what `tauri-plugin-geolocation` 2.3.2 pulls into its Android build. The posture is stated once, here, so it holds even if the store changes again: nothing from Google compiles into, links into or is requested by the Android app. This closes the Architect's earlier flag that a de-Googled phone would get no location: there is no Google-dependent route left for such a phone to lack. The facts relied on about F-Droid: it builds every app from source on its own servers, requires an FSF or OSI approved license (AGPL-3.0 qualifies), refuses prebuilt binaries in the tree and non-free libraries, and tags anti-features rather than blocking for a non-free network service. SnowRaven talks to eBird, OpenWeather, NOAA and tile servers, so a `NonFreeNet` tag on the listing is possible and is accepted; the conservative reading is to expect it and not argue it.
- **Location on Android: the geolocation plugin is out; the WebView's own geolocation is measured; the controls default to absent.** The plugin's Cargo dependency and capability grants move from the `any(android, ios)` block to iOS-only, so the Android binary never links Play Services. The Architect measures, on a release-signed emulator build, whether `navigator.geolocation` in the Android System WebView serves `getCurrentLocation` without Google code: that needs the WebView's geolocation permission callback (`onGeolocationPermissionsShowPrompt`) to be granted by wry's chrome client or by an override in the `MainActivity.kt` this run already edits, plus the runtime location permission requested there, and the WebView's own position fix, which is the platform's code on the device rather than anything compiled into the app. If that route works within that plumbing, "Use my location" and the "Current" lookup ship on Android with the Android system permission prompt, and the Designer's location surface stands. If it does not, every location control is absent on Android in v1, the honest state being typed coordinates and place search, with `getCurrentLocation` throwing the existing `unavailable` code rather than a new one, and no "not available on Android" placeholder. The default is absent; only the measurement lifts it. Reversal: a Google-free location plugin backed by `android.location.LocationManager`, either accepted upstream in `tauri-plugin-geolocation` as a Play-Services-free flavor or vendored beside tao with a stated removal condition, is the v2 route; and the no-Google posture itself is not reversed by any store.
- **Version floor: minSdk 24 (Android 7.0), Tauri v2's documented minimum; targetSdk at the current stable API.** F-Droid imposes no target level, so the current level is chosen for the permission and storage behavior it brings, not for a store rule. Nothing native in this app needs a newer floor, and the frontend's real constraint is the Android System WebView, which updates independently of the OS on every API 24 device, so a higher OS floor would buy little. The Architect states the WebView version the shipped frontend needs (container queries at minimum) and decides whether an older WebView gets a plain in-app message or is left to fail; the Planner carries that as a requirement, not a hope.
- **Parity cut: every tab ships; every Apple-only seam is absent.** The honest in-app state for each is hidden, decided per section above. The one place a plain sentence is right is Help, which already names the Apple features by platform.
- **Capability gates are re-keyed per branch, never by renaming `isIOS` to "mobile".** Today `showUpdaterFooter` is `!isIOS()`, so on Android it would show a footer that calls a plugin the binary does not carry. Each `isIOS()` call site is classified as Apple-specific, mobile, or no-updater, and gets `isAndroid()` or a mobile predicate only where the argument holds; `isWindows()`'s user-agent sniff is not the pattern to copy, since `platform()` from the os plugin is the synchronous truth on Android as it is on iOS.
- **The Android application id is permanent and must match the iOS bundle id: `com.dtgibson.snowraven`.** `tauri.conf.json`'s identifier is `com.snowraven`, while the iOS project ships as `com.dtgibson.snowraven`. F-Droid keys its listing, its update checker and its signing on the application id and never lets it change, exactly as Play would not have, so the Architect sets it deliberately in the generated project rather than taking the derived default, and the user confirms the choice (flagged).
- **Version string shared, version code written at the bump from Tauri's own formula, both readable from the tagged commit.** `tauri.conf.json`'s version is the Android `versionName`. F-Droid's update checker reads the version code from a committed file at each tag, and Tauri's build-time derivation leaves nothing committed to read, so the bump step writes `bundle.android.versionCode` in `tauri.conf.json` as `major * 1000000 + minor * 1000 + patch` (1.0.48 is 1000048) and a guard asserts it equals that formula from the version string, failing the suite on a bump that forgot it. The four-file version bump stays four files, since `tauri.conf.json` is already one of them. The code is monotonic for as long as versions increase, which the release rhythm already guarantees. The iOS "stamped version never leads the app version" guard gets an Android twin.
- **Signing: the GitHub APK is signed by the user's own key; the F-Droid build is signed by F-Droid.** The tag-triggered CI job produces the unsigned release APK the way the Windows job produces the installer; the signing keystore lives only on the release machine, like the Apple keys, never in GitHub, and signs the GitHub asset there. Whether a keystore exists today is unknown (flagged); generating one is a user-performed step with exact instructions, and its backup is the user's, since losing it means a future GitHub APK cannot install over an earlier one. F-Droid's build server signs its own build with F-Droid's key, which makes the two APKs non-interchangeable on one phone (Help says so); reproducible builds, which would let F-Droid publish the user-signed APK instead, are out of scope for v1 and recorded as the reversal.
- **The F-Droid leg joins the rhythm once, then rides the tags.** Inclusion is a one-time merge request to fdroiddata carrying the metadata YAML; review takes weeks and is outside this run's control, and F-Droid's own build and publish cycle adds days after each tag. After inclusion, every `vX.Y.Z` tag is picked up by F-Droid's update checker, which adds a build entry automatically under `AutoUpdateMode: Version`, builds it and publishes it with no per-release upload from this repo. The per-release work for Android is therefore the metadata changelog file, the signed GitHub APK, and the CLAUDE.md version-record line. The F-Droid listing's state at each ship (not yet submitted, in review, included, picked up this tag or not yet) is written down in that line, because a listing that has not appeared and a release F-Droid has not yet built leave the same evidence from the outside, which is the exact discipline CLAUDE.md keeps for App Store version records. If the merge request is not submitted at the first ship, that is a deferral written in the same place with its reason.
- **Verification follows the device boundary and the 1.0.31 lesson.** Agents verify on emulators only, with the release-signed build, by screenshot. A green suite and an emulator screenshot do not prove a release build launches on hardware, so the user's own install and open of the exact signed APK precedes its publication on the GitHub release. The F-Droid-built APK is not device-checked by this run before F-Droid publishes it, because F-Droid builds and publishes on its own cycle; the local `fdroid build` run, where feasible, is the check that the recipe produces a launching app, and a failure found only after F-Droid's build is a fix that rides the next tag. Automated tests remain the usual gate; no broad manual sweeps are added.
- **Published surfaces are held proposals.** The Fastlane metadata (the F-Droid listing), the website and README sentences and the privacy policy edits are prepared in the pipeline folder, shown rendered, and written only on the user's express yes. The listing's full description is derived from the fixed website register and the privacy policy's words, and makes no claim the policy does not; the no-Google sentence is a fact about the build, verified by the dependency-tree criterion above before it is written.
- **Store copy uses American spelling, no em dashes, and the fixed website register** (one or two sentences per surface, no operating detail, no reassurance). The per-release changelog file is held to F-Droid's 500-character limit and carries the same approved sentences the App Store What's New does, with Apple-only lines dropped.
- **Rust cfg discipline holds.** Android-real crates go in the `any(android, ios)` block; nothing Apple-vendor moves out of its block to make the Android target compile. `lib.rs`'s `cfg(mobile)` plugin registration already covers Android; the iOS-only block stays iOS-only, and the geolocation plugin's registration joins it.
- **The first Android ship is a full-rhythm release**, not an Android-only drop: it bumps the version with every other platform, and from then on a release is not done until the Android leg has shipped (the GitHub APK published after the device check, the changelog file committed, the F-Droid state recorded) or been deferred in writing.
