## Breeding-code lookup hasOwn

### What this does
The List Comparer's Checklists mode turns each eBird API breeding code into its display code through `apiBreedingToDisplay` (`frontend/src/lib/breedingCodes.ts`). That function read its translation table with a bare index. The table is an ordinary object literal, so twelve inherited names came back as JavaScript members instead of strings. A code of `__proto__` made React throw and the whole app fell to "Something went wrong". The other eleven drew an empty pill whose accessible name and tooltip were JavaScript source text. The read now goes through `Object.hasOwn`, so any code that is not an own key of the table passes through unchanged and takes the existing unknown-code fallback (tier 1, label equal to the raw code), exactly as `ZZ` always has.

### How to test
1. `cd frontend && npx vitest run src/lib/breedingCodes.test.ts src/components/ChecklistComparer.test.tsx`: 66 passed (38 of them new).
2. `npm run typecheck` and `npm run lint`: both clean.
3. To see the defect the rows guard, change line 63 of `breedingCodes.ts` back to `return API_BREEDING_TO_DISPLAY[apiCode] ?? apiCode` and run step 1 again: 37 rows go red, plus one unhandled "Objects are not valid as a React child" error from the `__proto__` render row. Restore the line afterwards.
4. Manual, optional: there is no way to make real eBird data carry one of these codes, so nothing visible changes. Comparing two real checklists with breeding codes still shows the same pills (for example API `FY` reads `CF`, Carrying Food).

### Notes for reviewer
- **One read, one table.** `API_BREEDING_TO_DISPLAY` is read only in `apiBreedingToDisplay`. `resolveApiBreedingCode` and `strongerBreeding` inherit the fix, and the comparer's `BreedingBadge` is the only shipped consumer. The table, the fallback value and every other function are unchanged. The guard is at the point of use, with a comment naming the rule in `.claude/rules/security.md`, rather than a null-prototype table (the house preference, so a later reader cannot "simplify" it away with no test failing). `normalizeShareCopySelection` in `lib/shareCopyPreference.ts` is the same shape.
- **Tests, extended in the two existing files.**
  - `breedingCodes.test.ts`: an `it.each` over the twelve names through `apiBreedingToDisplay` (asserting the result's type is `string` and equals the code), another through `resolveApiBreedingCode` (type checks on `code` and `label`, then the exact tier-1 fallback def), and a `JSON.parse` pollution probe. The probe parses a payload carrying both an own `__proto__` key and a `breedingCode` of `"__proto__"`, asserts the own key really exists and `Object.prototype` gained nothing, then runs the parsed code and the smuggled `XX` key through the lookup, with the brief's three measured controls (`S1` to `S`, `FY` to `CF` tier 4, `S7` to `S7` tier 2).
  - `ChecklistComparer.test.tsx`: an `it.each` over the twelve names, each served on side A as a `JSON.parse`d `ChecklistData` through the real comparer under jsdom, asserting the badge found by role `img` and name `<code>: <code>`, its text equal to the code, its title, and the tier-1 text token. A known-code control row (`FY`) goes through the same parsed-payload helper, so the helper is shown to reach the badge.
  - Checks read the accessible name and text, never console error counts.
- **Mutation check (red count).** With the bare read restored on a scratch copy: **37 of the 38 new rows went red** (12 `apiBreedingToDisplay`, 12 `resolveApiBreedingCode`, the `JSON.parse` probe, 12 renders) plus 1 unhandled render error. The one that stayed green is the `FY` control, as intended (known codes never depended on the guard). All 28 existing rows stayed green. `__proto__`'s render row failed because the tree unmounted (the "Objects are not valid as a React child" throw, the brief's crash); the other eleven failed on the accessible name. Restored from a snapshot taken at the intended state and verified by sha256; the re-run was 66/66 green.
- **Bundle.** The guard ships in the entry chunk (+19 bytes, `entryChunk.test.ts` 100/100 green). Built CSS is byte-identical to a baseline build (same `index-kngkoBkd.css` hash, 166,881 bytes; baseline built twice for determinism), so the new test comments added no Tailwind rules.
- **Out of scope, as the brief measured.** `computeBreedingBreakdown`'s plain `{}` accumulator in `lib/speciesStats.ts` takes CSV codes but drops all twelve names, so it has no observable defect. The backend twin is a Python dict with no prototype hazard. Comparer results are never persisted.
