Pin code labels

An opt-in control on the Breeding Codes tab that keeps the code header row visible while the species matrix scrolls, so a circle partway down a long list still has an identifiable column. Default off, session only, and byte-identical for anyone who never turns it on.

The open call

Decided · pinning is offered where it is free

The two views differ structurally. In Unbounded nothing between the <th> and the document sets overflow, so position: sticky; top: 0 anchors to the page and the table keeps its full natural height. Pinning there costs a fixed header band and nothing else. In Normal the overflow-x: auto wrapper is the scrollport, so a pinned header requires a capped-height inner box, which is the shape live-tested and reverted in v0.5.69.

The brief left it open whether to offer pinning in Normal anyway, since an opt-in a user chooses is a different thing from a default imposed on them. That argument is real, and it is not what settles this. What settles it is a hard requirement: the surface must hold at 320px and at 200% in-app text scale, and a capped-height box cannot.

The capped box has no viable height at 200% text scale. Size the cap in viewport units and it stays put while every row doubles, leaving about five rows in a box you scroll separately from the page. Size it in rem and at 200% it grows taller than the phone viewport, which puts the top of the scrollport, and therefore the pinned header, off-screen. The feature would silently stop working in the exact configuration it was measured against. min(rem, dvh) collapses back to the first case.

So Normal view is not offered a mechanism that cannot survive its own acceptance criteria. Pinning is offered in Unbounded, where it costs a fixed band, and the control reaches that view for the user in one press rather than sitting inert.

How the control behaves

One pill, Pin code labels, sits immediately left of the shipped ↔ Unbounded button inside a role="group" named Table view, so the two read as related presentation controls rather than a filter. The invariant is simple and it is what makes the control honest:

Pinned implies Unbounded. Pressing Pin from Normal moves the table to Unbounded and pins it, in one press. Pressing Pin again returns the view the user came from and unpins, so the round trip leaves no residue. Pressing ↔ Normal while pinned clears the pin, because Normal cannot pin, and the pill visibly un-presses in the same row.

That is the answer to "no dead control, no wall." Nothing is removed from Normal view, it renders exactly as it ships today. The pin control is enabled there and does the whole job. Because the change is instantly reversible and non-destructive, the cost is made legible at commit rather than guarded behind a warning: the view toggle beside it flips in place, a status note names what happened, and one more press undoes it. A permanent line of explanatory text in an already dense row would tax the large majority who never pin.

The pinned header

Boundary

Unpinned, the header keeps its shipped hairline, inset 0 -1px 0 var(--sr-border). Pinned, two things change together: the hairline steps up to var(--sr-border-medium), and a soft haze is added beneath it so rows read as passing under the band rather than smearing into it.

The haze is the one new token, --sr-sticky-shadow, declared in both themes and tinted with the app's own ink rather than pure black: 0 3px 6px -2px rgba(15,17,23,0.12) in light and 0 3px 8px -2px rgba(2,2,4,0.60) in dark, where a light haze would be invisible against --sr-bg. It is a full-value shadow token, the same convention as --sr-card-shadow and --sr-switch-thumb-shadow.

The header band stays --sr-bg, which is already the shipped value and already opaque, so rows cannot show through. It also means the floating band matches the page behind it laterally while contrasting against the --sr-surface rows sliding beneath, which is where the boundary needs to read.

On contrast, stated plainly. --sr-border-medium is about 1.65:1 against --sr-bg in light. It is not claimed as a WCAG 1.4.11 pass and does not need to be: the header is identified by its text, and the pinned state is carried by the pill's aria-pressed and its visible pressed styling. The line and haze are visual reinforcement, not the sole means of identifying a component or its state. Pushing the line to a 3:1 value would read as a rule rather than a hairline and would break the tab's quiet-utility register.

Sticky mechanics

  • position: sticky goes on each <th> individually, never on <thead> or <tr>. WKWebView and older Safari honor sticky on cells only, and this ships in WKWebView on both macOS and iOS.
  • border-collapse: separate is already set inline on the table and is required for sticky table headers. Nothing to change.
  • The pinned rules live in globals.css under .sr-bc-matrix--pinned, not inline, because the iOS variant must override top under the .sr-ios-app gate and a React inline style at specificity 1,0,0 is unreachable from a stylesheet. The shipped thBase.boxShadow moves out of the inline object into .sr-bc-matrix thead th for the same reason.
  • top: 0 is correct on desktop and web. Under .sr-ios-app it becomes env(safe-area-inset-top, 0px), mirroring .sr-ios-app body's padding-top. Without it the band would pin into the notch on a notched iPhone.
  • scroll-margin-top: 3rem on the pinned table's body cells keeps keyboard focus from landing under the band (WCAG 2.4.11), the vertical twin of the shipped scrollPaddingLeft. It sits on the target, so no class on <html> and no scroll listener is needed. 3rem clears the band at both 100% and 200% text scale.
  • z-index: 3 on every pinned header cell. In Unbounded the body name cells carry no z-index, so there is no intersection to arbitrate and all header cells can share one layer.

The top-left corner, both axes, both views

Because pinning is offered only in Unbounded, and Unbounded is exactly the view that drops the horizontal name-column freeze, the corner cell is never sticky on both axes at once. That is not a happy accident, it is a second argument for the call.

Stated the other way: with pinning on, the corner cell is an ordinary member of the pinned header row. It holds vertically and travels horizontally with everything else. Scrolling right in Unbounded carries the species names off screen, which is the shipped Unbounded behavior and is deliberately left alone here. Adding a left freeze to Unbounded is a plausible follow-on and is out of this brief's scope.

320px phone, Unbounded and pinned

Both frames are 320px wide with the shipped @media (max-width: 640px) contracts applied: 30px dot-width code columns, 0.625rem headers, table-layout: fixed; width: max-content on the table inside a width: min-content card, and min-height: 2.75rem on both view-group buttons. Scroll either frame down to watch the band hold, and sideways to confirm the columns stay aligned under it.

Control states

The pill uses the shipped ghostBtn() styling, accent-tinted when pressed, with a 12px Lucide Pin glyph marked aria-hidden. The glyph earns its place: it is the one non-text marker in a right-hand cluster whose other member is ↔, and it makes the control findable in a row that already holds twenty text pills.

Accessible name: Pin code labels, and nothing else. It is the button's own text content, with no aria-label anywhere, so the visible label and the accessible name cannot drift apart. aria-pressed carries the state, per the repo's segmented and pill convention. The consequence a sighted user learns from the flipping view toggle is carried for screen readers by aria-describedby pointing at a persistent .sr-only span reading Pinning uses the Unbounded view. A description, not a name, so WCAG 2.5.3 stays trivially satisfied.

Status note

While pinned, one muted line sits directly above the card, in the same geometry as the shipped filter strip but on the neutral --sr-surface-faint rather than the accent tint, since the accent is already spent on the pressed pill and pinning is not a filter:

Code labels stay at the top while you scroll. Pinning uses the Unbounded view, so the matrix scrolls with the page.

The element is a role="status" region that is rendered from the start and carries its message in a key={seq} child, so pressing Pin repeatedly announces every time rather than only the first. Unpinning needs no announcement of its own, the button's aria-pressed transition is the announcement, and the note simply leaves.

Motion

Almost none, deliberately. A sticky header is continuous positioning, not a transition, and the honest answer is that there is nothing to animate. Fading the boundary in only once the band is actually overlapping content would need a scroll observer, which this repo avoids as a pattern and which would buy a detail nobody is looking for.

One standing caution for the build: do not pair the pinned header with scroll-behavior: smooth anywhere on the page. A smoothed scroll under a fixed band reads as the band drifting, which is the one way this can be made to look broken.
