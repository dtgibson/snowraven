# Bug Brief — Duo Welcome and Audit Fixes

Three confirmed defects, one release: **1.0.60** (from 1.0.59), all platforms. Saved ideas: A `d4286595`; B `48e7cd14`; C `35194446`, `859ea759`, `06ff8df8` (three captures of one advisory). Confirmed in code at `236576c4`; nothing fixed here.

## What is broken
- **A. Welcome screen ignores the side safe areas.** `components/WelcomeScreen.tsx:55-61` sets the first-run overlay's position and padding inline (`position: fixed; inset: 0; padding: '32px 24px'`). An inline style beats every class rule, so no `.sr-ios-app` or `.sr-android-app` inset can reach it. On the Duo's outer screen (466 pt wide, in-app insets 0 / 84 / 34 / 0 pt, DECISIONS.md 1.0.59) the card spans x = 24 to 442, while the safe edge is at 382: it runs 60 pt into the camera column.
- **B. iOS can call the four monitor commands.** `src-tauri/capabilities/default.json` names no `platforms`, so it applies on iOS, and its `core:default` pulls in `core:window:default`, which grants `allow-current-monitor`, `allow-primary-monitor`, `allow-monitor-from-point` and `allow-available-monitors` (tauri 2.11.2, `gen/schemas/acl-manifests.json`). `ios.json` and `mobile.json` deny nothing. Two of these abort on the Duo's inner screen (tao #1373). No app code calls them (`iosMonitorLookups.test.ts`), so this is defense in depth (security L1, Low).
- **C. `npm audit` in `frontend/` reports 4 advisories (2 high), all in dev and build tools.** `source-map-js` 1.2.1 (high, GHSA-68fv-2mgg-jv7q, pulled in by postcss, css-tree and @tailwindcss/node); `vite` 8.0.16 (high: three launch-editor advisories, GHSA-9jrq-w75r-8gcw and GHSA-rq7h-c2jc-7f22); `vitest` and `@vitest/mocker` 4.1.11 (moderate, GHSA-qxg6-89mg-rqv8 and GHSA-xp26-3454-mjgp). The Pi's `start.sh` runs `npm ci`, which prints them. `npm audit --omit=dev` reads 0. Both were re-run with network on 2026-10-22.

## Steps to reproduce
- **A.** (1) Erase and boot the iPhone Duo simulator (iOS 27.1, `D0CBEB76-7F70-4CDC-AB71-2A1F989317B7`). It boots folded, on its outer screen. (2) Install a build and launch it with no keys and no files, so the Welcome screen shows. (3) From inside the app, read `env(safe-area-inset-right)` (84) and the card's `getBoundingClientRect().right` (about 442, against 382). The same shape should appear on Android turned sideways with a side cutout; that case is not measured.
- **B.** Read `default.json` (no `platforms` key) and the generated ACL manifest's `core:window` default set; `ios.json` has no deny entry. The abort itself only happens on the inner screen, which this Mac cannot draw (Xcode 27.1 has no Simulator app), so the grant is confirmed from the ACL, not from a crash.
- **C.** `cd frontend && npm audit` with network gives the 4 advisories, and `npm audit --omit=dev` gives 0. Never use `--offline`, which reports a false 0.

## Expected behavior
- **A.** The Welcome content starts and ends inside the safe area on both sides, keeping its 24px breathing room (`calc(24px + inset)`, as the Alerts inbox root does at 641px and up), on iOS and on Android. With every inset at 0 (iPhones held upright, iPad, desktop, web, Pi) nothing moves.
- **B.** On iOS the four commands are refused. In Tauri a deny beats an allow (`ipc/authority.rs` checks `denied_commands` first). Desktop and Android are unchanged, and the iOS app still launches and draws.
- **C.** `npm audit` reads 0 on the full tree and on `--omit=dev`, and each package stays inside its declared range: `vite ^8.0.10` and `vitest ^4.1.11` in `package.json`, plus `^1.2.1` for source-map-js in each of its dependents.

## Blast radius
- **A.** The Welcome root only. The pattern to follow is `.sr-help-panel`: positioning lifted from inline into a class, a `.sr-ios-app` rule that pads, and a `.sr-android-app` twin reading `var(--sr-inset-X, 0px)` (`globals.css` lines 2343-2374, rows in `iosChrome.test.ts`). The stylesheet-wide guards pick up the new rule by themselves: `androidInsetsCss.test.ts` (needs the twin), `safeAreaPerSide.test.ts` (each side reads its own inset) and `findUngatedSafeAreaRules` (no `env()` on the ungated base rule). It is not a bottom surface, so `bottomSurfaceSideInsets.test.ts` does not take it. **The top inset is a decision:** the family pads the top too, but on every notched iPhone held upright that shifts the vertically centred card down by half the top inset. The Engineer either includes it (the family's shape) or writes down why not (CLAUDE.md, a decision not to act). Out of scope, though they have the same inline-fixed shape: `Calendar.tsx:923` (the day dialog) and `RootErrorBoundary.tsx:26`.
- **B.** iOS only (`ios.json` is `platforms: ["iOS"]`). `androidProjectPins.test.ts:370` pins `ios.json`'s permissions to exactly the three geolocation grants, so that row changes in the same commit. The `description` strings in `ios.json` and `default.json` say what `ios.json` holds. A bad identifier fails `tauri-build` at compile time, so the launch screenshot is the runtime check.
- **C.** `npm audit fix` takes the newest release in each range: vite **8.3.5** (published 2026-10-21; it moves rolldown from 1.0.3 to about 1.2 and lightningcss from 1.32 to 1.33), vitest 4.1.12 and source-map-js 1.2.2. A smaller fixed vite exists (8.1.6 or 8.2.4, both 2026-10-06); the Engineer picks one and records why. The built frontend on every platform can change (CSS minify, chunking), and the website verify in CI reads `frontend/dist`. Today the lockfile carries 38 native binding entries for rolldown, lightningcss and tailwind oxide, covering macOS, Windows, Linux CI, F-Droid and the Pi's linux-arm64 and arm-gnueabihf, and it must keep every platform. The `server.cors: false` row pins the setting, but the dev-proxy preflight behaviour behind it was measured on Vite 8.0.
- **Release.** The six-file bump to 1.0.60: `frontend/package.json`; `tauri.conf.json` (version, and `versionCode` 1000060); `CHANGELOG.md`; `website/index.html` (pill text, its `aria-label`, footer); Fastlane `changelogs/10000601.txt`, `10000602.txt` and `10000604.txt`; and the F-Droid recipe (three `Builds` entries, `CurrentVersionCode` 10000604). The Fastlane changelog text and the App Store What's New are published copy: prepare them as a held patch and wait for the user's explicit yes. `CHANGELOG.md` and in-app text need no stop. 1.0.59 was in App Store review as of 2026-10-21, so the Deployer checks App Store Connect before creating the 1.0.60 record and writes the outcome in `RELEASE_LEDGER.md`.

## What done looks like
- **A.** On the Duo simulator's outer screen (or whichever iOS simulator boots), a screenshot plus an in-app reading show the content between x = 24 and 358. Guard rows on the Help-panel model check four things: no inline positioning or padding left in `WelcomeScreen.tsx`, no `env()` on the base rule, a gated rule that pads, and the Android twin. With every inset at 0 the render matches 1.0.59. The inner screen and the real Duo stay Partial (standing decision).
- **B.** `ios.json` carries `core:window:deny-current-monitor`, `deny-available-monitors`, `deny-primary-monitor` and `deny-monitor-from-point`, and a row in `iosMonitorLookups.test.ts` pins all four. The `androidProjectPins.test.ts` row is updated. A launch screenshot on an iOS simulator shows the app drawn. The inner screen stays Partial.
- **C.** `npm audit` with network reads 0 on the full tree and on `--omit=dev`. As a control, the pre-change lockfile, audited in a scratch copy, still shows the 4. `npm run build`, `eslint` and the full vitest suite are green after the toolchain move, and the set of native bindings per platform matches the set before.
