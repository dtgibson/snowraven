# Decisions: ebird-store-hygiene (Improve lane, Stage 2, the Engineer)

The implementation record for the approved `change-brief.md`. Nothing was sent to eBird: every figure is a test, a build, a read of the code, or a local probe of both shipped checklist paths with the outbound client faked. Probe scripts and outputs are in the session scratchpad, not the repo.

## D-01 Malformed replies: what was measured, and what was brought in

The brief asked for the further shapes to be measured before any row was written (`.claude/rules/security.md`, v1.0.29). A 243-shape corpus was driven through both shipped paths: the desktop `getChecklist` under vitest with a real `Response` over the row's bytes, and the web/Pi route through `TestClient` with real `httpx.Response` objects. Shapes: non-object and non-JSON bodies in all three modes, `obs` items of every JSON type, `speciesCode` of every type, `obsAux` and `mediaCounts` of every container and value type, header fields, NaN and Infinity, UTF-16, invalid UTF-8 inside and outside a string, one and two byte-order marks, and the count bounds.

| desktop status-less errors (read as offline by `isOfflineError`) | 38 | 0 |

**Brought in (one rule set, twinned, type tests only):**
1. A 200 that is not JSON fails in every mode. The Python decode mirrors the Fetch spec (D-03).
2. A body that is not a JSON object fails in every mode. This is new for `fields=projects`: the desktop service threw a status-less TypeError for `null` (the Projects sweep reads that as offline and stops) and answered a list or scalar body as "no projects", which the store keeps for a year; web/Pi already failed them, with Python's text.
3. In the species-reading modes, an `obs` item that is not an object fails the answer (the brief's rule), and so does an item whose `speciesCode` is present and not a string (D-04).
4. `obsAux` and `mediaCounts` are normalized the same way on both and never fail the answer (D-05).

**Recorded, not brought in** (the 14 remaining; none changes a verdict except the last):
- `howManyStr: null`: desktop `"X"`, web/Pi `null` (2 shapes). Display only, read by neither the escapee check nor Projects.
- `comments: 0` or `false`: desktop passes the value, web/Pi `""` (`??` against `or`; 4 shapes). Display only.
- A header `locName` that is an EMPTY object: desktop passes it, web/Pi falls back to the id, because Python reads `{}` as false (2 shapes). A non-empty object is passed through on BOTH transports, and as a React child on the List Comparer it would throw into `RootErrorBoundary`, so on a hostile reply it is an availability edge rather than a display difference; `howManyStr` and `comments` are the same family, not type-normalized either (security report I2). Pre-existing, outside this build's diff, and in the idea inbox, not this run.
- `projectIds: [1050.0]`: desktop keeps 1050, web/Pi drops it (`isinstance(v, int)` refuses a float; 3 shapes). This is the Projects normalizer pair with its own fixture (`checklistProjects.fixture.json`), outside piece 3's scope; the fix is to accept a whole-valued float in `_norm_project_fields`, as `_media_count` now does. eBird has not been seen to send one.
- Two leading byte-order marks: desktop answers, web/Pi fails (3 shapes, the only status difference). This is the test runner, not the app: Node's undici `Response.json()` strips a second BOM, where the Fetch spec (and so WKWebView, WebView2 and Android's WebView) strips one and then `JSON.parse` refuses the second, which is what Python now does. Measured: `new TextDecoder().decode()` plus `JSON.parse` refuses it under the same Node. No fixture row depends on it.
- Found by the Auditor, outside the 243-shape corpus: a JSON integer literal longer than 4,300 digits anywhere in the body. Web/Pi refuses it with the fixed 502, because CPython's integer-conversion limit (`sys.int_max_str_digits`, 4,300 on Python 3.15) makes `json.loads` raise and `_decode_answer` catches that; desktop's `JSON.parse` accepts it (as `Infinity`). The refusal is the safe direction (a failed answer stamps nothing and is asked again), eBird does not send such numbers, and no fixture row is added (security report I1). An overflowing float such as `1e400` agrees on both.
- Seen on the way past, agreeing on both and pre-existing: the body's `locId` is interpolated unvalidated into the follow-up `ref/region/info/{locId}` URL on both transports (same host, key in a header). For the Auditor; not touched.

**Linearity of the new scans** (security.md, a scan over untrusted text): each check reads every `obs` item once with constant work (type tests and at most a few own-property reads), and the `obsAux` search reads each entry of one observation once, so the pass is linear in the body's size and dominated by the platform decode that precedes it (`res.json()` on desktop, `json.loads` on web/Pi), which is pre-existing and already linear. No regex runs over the body. Nothing caps the body's size or read time, on either transport, and that is pre-existing: the desktop `tauriFetch` clears its 10 s timer when the headers arrive, before the body is read, and httpx's `timeout=10.0` limits each connect and each socket read, not the whole body. So the bound is the decode's own, not the 10 s budget an earlier draft of this paragraph named (security report L1). Capping the size of eBird's responses is a separate decision, not owed by this build.

## D-02 One wording for every refused body

D-10 (1.0.66) gave web/Pi "Could not fetch checklist: eBird's answer had no observation list". That is false for a body that is not JSON or holds an unreadable item. Rather than one message per shape, every refused body now carries one fixed detail, `CHECKLIST_UNREADABLE` = "eBird's answer could not be read", true for each shape, through the route's unchanged generic clause ("Could not fetch checklist: ..."). The desktop wording stays "Could not fetch checklist (HTTP 502)." (D-10's choice). Neither carries a URL, the key, or anything from the body. The brief's "fails with one verdict and fixed wording" is read as one wording per transport. In-app text, so no review stop; the List Comparer shows it.

## D-03 The Python decode mirrors the WebView's

httpx's `resp.json()` is `json.loads(resp.content)`, which differs from the WebView's `Response.json()` three ways, each measured: it decodes UTF-16 and UTF-32 bodies, it fails outright on an invalid UTF-8 byte the WebView reads as U+FFFD, and it accepts `NaN`, `Infinity` and `-Infinity`. `_decode_answer` decodes `content.decode("utf-8-sig", errors="replace")` and refuses the three constants through `parse_constant`. Measured: Python's replacement decoder matched the WHATWG `TextDecoder` on all 7,695 probed byte sequences, and with the constants refused `json.loads` accepted exactly what `JSON.parse` accepted on 48 grammar cases (not universally: an integer literal over 4,300 digits separates them, recorded in D-01). `RecursionError` is caught as well, although 100,000 nested levels decoded on Python 3.15 without one (V8 decoded 1,000,000). Consequence: the three router suites' fakes now carry real JSON bytes (`resp.content`), since the service no longer calls `resp.json()` on the checklist body.

## D-04 A species code that is not text makes the observation unreadable

Both transports passed a numeric code through as a "species", web/Pi answered 500 for a list code (unhashable in the route's taxonomy join, outside its `try`), and the two disagreed on an object code. Options were to skip such an item (as an absent or empty code is skipped) or to fail the answer. Chosen: fail, because a skipped carried species is exactly what the escapee check stamps as "not in eBird's answer" for 30 days (the D-02 harm), while a failed answer stamps nothing and is asked again. An absent, `null` or empty code is still skipped on both, as before (a presence test spelled `is None` / `=== null` on both sides, per security.md).

## D-05 Display fields normalize; they never fail the answer

The species and its provenance are readable whatever shape `obsAux` or `mediaCounts` has, so those two fields follow the house posture for sub-fields (exoticCategory, projectIds): a value of the wrong shape reads as absent. Breeding code: the first object entry of `obsAux` whose `fieldName` is `breeding_code`, its `value` when non-empty text, else its `auxCode` when non-empty text, else "" (Python's shipped `or` semantics for strings; desktop's `??` returned "" or a non-string). A media count: a non-negative whole number up to `MEDIA_COUNT_MAX` (999,999,999, declared on each side and compared by the fixture's boundary pair), else 0; a whole-valued float is accepted because `JSON.parse` cannot tell 3.0 from 3, and `bool` is excluded explicitly. Behavior change on web/Pi for malformed values only: `"3"` was 3 and is now 0, `1.5` was 1 and is now 0, `True` was 1 and is now 0, and a list or string `mediaCounts` was a 502 and now reads as no media.

## D-10 How the two escapee-pass findings are tested

- **I1** (purge counter read after the first await): the row detaches the store's mirror with the test seam, the state I1 names and no shipped path reaches, parks the store's next disk read (reading the document first and parking after, testing.md v1.0.62), starts a pass with Check again, purges while it is parked, and asserts no request, a `cancelled` partial, nothing failed and an empty ledger. Each half alone is red: the read moved back after the await (re-check kept), and the read kept before with no re-check.
- **I3** (finished pass keeps its token): the token is private and what it holds is memory, which no hook output shows (a Stop after the pass was already a no-op, so no behavior differs). So it is a SOURCE row: comments stripped (the strip itself asserted), and `runPass`'s last `finally` must call `pass.stop()`. Red for the call deleted and for it commented out. The Stop callback's comment ("A finished pass's token is already spent") was false until this change; it is now true.

## D-11 The TTL rows, and why the stores' readers call the shared predicate

Each of the four readers has rows at exactly 24 hours ahead (honoured) and 24 hours plus 1 ms (due), and each mutation reverting one reader to its old test turns only that reader's rows red, measured across all four readers' suites. The Recent activity controller's row reads the controller's own split, through a pass with no eBird key: the pass computes fresh against remainder, reports it (`cacheServed` is its fresh count, and the no-key error appears only because something was left to fetch) and launches nothing, so the store's chokepoint is never consulted. A first version asserted the network was reached, and the Tester found the chokepoint's reversion reddened it too, because the refetch runs through the real chokepoint; the controller adds a cache-served answer to `cacheServed`, so no status field after a launch isolates its split. `buildTargetIds` and the Recent activity controller call `isWithinTtl` with the store's own constant (1.0.66 D-12's shape), so a suite that fakes the store keeps its TTL seam meaningful while the real window runs. The activity store's offline row asserts the loader WAS asked (due) and the stored answer still served, so it is red without the window, where the completeness store's equivalent row passes either way. Display and the offline stale-serve are unchanged (1.0.66 D-11, D-12).
