## Exotic provenance reuse: the escapee check settles instead of re-asking eBird on every load

### What this does
The Statistics tab's escapee check already kept eBird's answers for 30 days, but it never settled when a species in the export is missing from every answer (a name a 2026 split moved to a nominate daughter while eBird answers under the slash code, such as Willet and Marsh Wren, or an answer that simply lacks the species). The v1.0.1 heal then reopened the same checklists on every load: 29 requests per load on the user's export, forever. The store now records, in the same `exotic-provenance-v1` document, that eBird answered a checklist the export says carries a species and had no row for it; the heal skips such a species for the existing 30-day TTL, unasked carriers stay askable, and the status line no longer says "checked" while species are still open.

### How to test
1. `cd frontend && npx vitest run src/lib/exoticProvenanceConvergence.test.tsx` runs the measured shape through the real `storage.ts` under the Tauri and the web/Pi seams: consecutive loads send 29, 8, 0, 0 checklist requests, a settled load sends none, and after Clear the pass asks again.
2. `npx vitest run src/lib/exoticProvenance.test.ts src/lib/exoticProvenanceCache.test.ts src/lib/useExoticProvenance.test.tsx src/components/ExoticProvenanceAccount.test.tsx src/lib/settingsRouteBudget.test.ts` covers the predicate's symmetric difference, the store's write, load, cap and purge rows, the controller's TTL, Check again and failure rows, the new sentence, and the route budget.
3. In the web dev app (`pipeline/exotic-provenance-reuse/how-to-see.md`): open Statistics with the browser's Network panel filtered to `checklists`, reload twice, and see no request on the third visit, with the line "eBird's answers did not include 3 of your species, so they still count." Check again re-asks them.

### Notes for reviewer
- **Measured before and after** (the fixture of the measured shape, both seams, real storage): before `[29, 29, 29, 29]`, after `[29, 8, 0, 0]`. Load 1 stays 29 because the saved ledger is past the TTL, as on the real store; load 2 asks only the 8 Willet checklists never asked before (what Help already promises); every later load is 0.
- **Mechanism** (`lib/exoticProvenanceCache.ts`): one optional field, `unmatched` (code to fetch time) plus `unmatchedOrder`, same key and version (absent means no stamps). Written only in `mergeChecklist`, below the purge-generation guard, from a successful answer, for a code the controller says the checklist carries (`index.byChecklist`), that is in the cover, that the answer has no row for, and that has no record. A row refused by a full species index is still a row. A code outside the cover the checklist was asked under is never stamped, which keeps the v1.0.1 domestic-form heal intact (its rows are unchanged and green).
- **Bounds**: cap 16,384 (equal to the species cap, above the world list, and the largest power of two that fits): the worst-case document measured 16,494,726 B with the stamps against the route's 16,777,216 B (15,446,152 B before). FIFO by first stamp, refreshed in place, so stamping is O(1) per carried code with no order search. The load path clamps to the newest stamps, reads own keys only, validates with the same predicate as the write, drops a stamp beside a record, and records each key at first sight (a 20,000-fold repeated key costs one validation, asserted as work done).
- **Predicate** (`lib/exoticProvenance.ts`): `carriersNeedingRefetch` takes the stamp set as a required fourth argument; the stamps stay out of `ProvenanceSnapshot`, so classification and the passive readers cannot see them. A generated-corpus row shows the stamp only removes carriers, exactly as taking the stamped codes out of `remaining` would, and that the empty set is the v1.0.1 predicate.
- **Status** (`lib/useExoticProvenance.ts`, `lib/exoticCopy.ts`): new partial reason `unmatched`, reported by the auto-start skip and by a pass that ends with species open for no other reason. Never `complete` while `remainingSpecies` is non-empty, agreeing with Life Lists' `checkCompleteFor`. Check again ignores the stamps for its run only from that state; Try again and the other partial states keep their meaning (D-13). No component change: every partial reason already gets the warning icon and Check again.
- **Mutation table**: thirteen mutations of the new guards (heal ignoring stamps, no carried codes, `complete` from either path, the retry bypass in both directions, the row check, first-sight dedupe, write-side validator, drop on admission, load clamp, write snapshot, record beside stamp on load) each turn a test red. The row check survived until the refused-admission row was added.
- **Unchanged**: the backend, `lib/tauri/checklistService.ts`, `transport.ts`, `clearDerived.ts` (the store is already registered and the purge deletes the whole document), the passive readers, classification, `PRIVACY_POLICY.md`, `website/`, `README.md`, `docs/HELP.md`. No new endpoint, host or request; only repeat requests to eBird's checklist view are removed.
- **Not in this change**: the version bump and changelog (the Deployer's six-file set), and the held release copy.
- **Known limitations**: `/checklists/` still sits outside the eBird pacing gate (D-06 item 1, its own change). Within one pass, Willet still spends 26 requests that all come back without it (D-06 item 3). A future-dated stamp (clock skew, a hand-edited file) is honoured until the clock passes it plus the TTL, the same as the ledger's entries, which is the safe direction: the species keeps counting and Check again re-asks. A species whose row is refused by a full species index is not stamped and keeps re-asking, as before; that index cannot fill on real data.
