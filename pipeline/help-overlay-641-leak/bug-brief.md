# Bug Brief — help-overlay-641-leak

## What is broken
At **200% text scale only**, in a bounded band of viewport widths **just above the 640 tier**, the Help overlay's content column is narrower than the unbreakable link text `github.com/dtgibson/snowraven-mini` (399.77px rendered), and above 640 that column carries no wrap allowance. The `<a>` overflows its column and drags the whole help body sideways — 23px at 641px. Pre-existing: v0.5.83's `help-docs-phone-width` wrote its wrap allowance inside `@media (max-width: 640px)`, so 641px and up never received it.

## Steps to reproduce
1. `cd frontend && npm run dev`; open the app, dismiss the Welcome dialog (Escape), click **Help** in the footer.
2. Set `--sr-text-scale: 2` on `<html>` (the real mechanism, `textScale.ts:31`; in-app: Settings → Text Size → 200%).
3. Viewport 641x900 → the help body scrollport drags **23px** horizontally; the sole leaking element is the `snowraven-mini` `<a>`, 399.77px wide, 46.77px past a 353px column content box.
4. **Do not assert on page `scrollWidth`** — it read exactly the viewport width in all 40 configurations measured, every broken one included, because `.sr-help-panel` is `overflow: hidden`. Measure the element's client rects against `.sr-help-content`'s content box, plus the row's parent scrollport for drag.
5. Measured with Playwright (`website/tools/node_modules`) against the running app on the current tree, all four supported scales (1 / 1.25 / 1.5 / 2) x 14 widths (320–1440).

## Expected behavior
No horizontal drag and no column overflow at any supported width or text scale, with the two-column layout intact: `.sr-help-row`'s inline `alignItems: 'flex-start'` and the sticky 200px TOC must be untouched, and every configuration that measures clean today must stay byte-identical.

## Blast radius
- **Two nested bands, both narrower than "above the tier"**: element overflow spans **641–687px** (0.77px at 687, gone at 688 = 288 + 399.77); user-visible drag spans **641–663px** (23px → 1px, gone at 664). Between 664 and 687 the row's 24px right padding absorbs the leak, so drag under-reports the defect by 24px of width. Clean at every width at 1x / 1.25x / 1.5x, and clean at 200% from 688px up (content `maxWidth: 680` keeps it clean at all large widths). The prompt's "sidebar `clamp`" hypothesis is wrong — the TOC is a fixed `width: 200, flexShrink: 0`, so the column is exactly `viewport − 288` and the band is pure arithmetic.
- **Only the wrap allowance is missing above 640 — not the constraint.** v0.5.83 needed two halves because the tier flips the row to `flex-direction: column` and hands `alignItems: 'flex-start'` control of width. Above 640 the row is a real row, `flex-start` governs the vertical axis, and the column's `flex: 1; minWidth: 0` already fills correctly (measured `viewport − 288` at every width). `align-self: stretch` / `width: 100%` must **stay ≤640-only** — above 640 they would fight `flex: 1`.
- **Verdict: a media rule scoped to the Help subtree, not the unconditional `.sr-wrap-anywhere` class.** The helper cannot be scoped to a tier, and attaching it in markup would change wrapping at every width and scale, whereas the evidence covers 641–687px at 200% alone; the repo prefers the rule inside the feature's own subtree, and the adjacent v0.5.83 rule set exactly this precedent by inlining the same two declarations rather than adding the class. Recommend a `min-width: 641px` rule on `.sr-help-content` over pinning the upper bound to 687 — that edge is a function of the longest link's rendered width and would silently stop covering a longer future URL.
- **The existing guard will fail and must be amended, not bypassed**: `frontend/src/lib/helpContentWidthCss.test.ts` test 3, "lives ONLY inside the ≤640 tier, leaving 641px and up byte-identical", asserts every `.sr-help-content` rule sits inside the phone tier. Split it — constraint declarations stay ≤640-only, the wrap allowance may appear above. Its comment ("641/768/1024/1440 measured clean before the fix") and the matching `globals.css` sentence ("641px through 1440px measured clean and stay untouched") are true at 100% only and must be corrected; ROADMAP.md:164 already records the 23px remainder honestly.
- **Files**: `frontend/src/globals.css` (the `.sr-help-content` rules) and `helpContentWidthCss.test.ts`. `HelpDocs.tsx` needs no change — the `.sr-help-content` class already exists. No interaction with the three bundle commits: `help-link-scheme-gate` (cb15fdd) re-owns this very anchor (hand-rolled `<a>` → `OutboundLink`) but is geometrically inert — measured on the current tree, the link is 399.77px / 46.77px over / 23px drag, byte-identical to v0.5.83's pre-scheme-gate QA figures. `uniform-map-fabs` and `pin-labels-column-width` edited `globals.css` (206 and 47 lines) without touching the help block.

## What done looks like
Drag is 0 at 641px/200% and no element overflows `.sr-help-content`'s content box anywhere in 641–687px at 200%; 1x / 1.25x / 1.5x at all widths and 200% from 688px up are byte-identical; the ≤640 tier is unchanged and still measures 0 drag at 320/390/430/640; `.sr-help-row` keeps `align-items: flex-start` and the TOC still sticks (pinned through scrollTop 100, releasing after, at 641/768/1024/1440). Verified by real render, measuring the element against its container — never page `scrollWidth`.
