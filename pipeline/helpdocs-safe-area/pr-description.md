## Dynamic Island covers the Help overlay header

### What this does
On the iOS app, opening the in-app Help overlay pinned it to the physical top of the screen, so its 52px header row rendered underneath the status bar and Dynamic Island. The book icon and the "SnowRaven Documentation" title sat squarely inside the Island band. The overlay's `position: fixed; inset: 0` was an inline style in `HelpDocs.tsx`, which is viewport-relative and therefore escapes the `.sr-ios-app body` safe-area padding that protects every in-flow surface in the app.

The positioning is now a class, `.sr-help-panel` in `globals.css` (values byte-identical to the old inline ones), which gives the safe-area inset somewhere to hang. An `.sr-ios-app`-gated companion rule pads the panel clear of the status bar, the Dynamic Island, and the landscape sensor housing. This is the same mechanism, and the same fix shape, as the map fullscreen panel in build 1 of this bundle.

A second defect from the same root cause is fixed alongside it: the table-of-contents nav capped itself at `calc(100vh - 52px)` and never subtracted the top inset, so above 640px (iPad, where the inset is typically 24px) it over-extended past the scrollport and its last entries became unreachable. That cap is lifted to `.sr-help-toc` at the same value, with an `.sr-ios-app` variant that subtracts the inset.

### How to test
1. Build and run the iOS app on a Dynamic Island device (iPhone 14 Pro class or newer), TestFlight or the simulator.
2. Tap **Help** in the app footer. The header row now starts below the status bar: the book icon and the "SnowRaven Documentation" title are fully readable, and nothing sits under the clock, bell, or battery.
3. The Close button is still at the right end of that row and still has its ~44px touch target.
4. Rotate to landscape in both directions. The icon and title clear the sensor housing in either rotation, and the documentation body is inset on both sides.
5. Press Escape (hardware keyboard) or tap Close. The overlay dismisses and focus returns to the Help button that opened it.
6. On an iPad, open Help and scroll the sidebar table of contents to its end. The last entry, "Updating SnowRaven", is reachable and fully visible.
7. Raise the in-app Text Size to 200% and repeat step 2. Nothing clips at the top.
8. Narrow to a 320px-wide phone viewport. The TOC still stacks above the content and scrolls with it.
9. On desktop or web, open and close Help. Rendering is unchanged.

### Notes for reviewer
- **The inset is `.sr-ios-app`-gated, not a bare `env()`.** `index.html` ships `viewport-fit=cover` to browsers too, so `env(safe-area-inset-*)` is non-zero in iOS Safari on the **web** build. An ungated rule would have fixed the app and silently changed shipped web rendering on every notched phone. This repeats the QA round-1 finding documented at `globals.css:655-664`. `.sr-ios-app` is set on `<html>` by `main.tsx` only when `isIOS()`, so desktop and web never carry the class. Both new gated rules have a test asserting their ungated base rule contains no `env(`.
- **Its own sibling rule, deliberately not a shared inset utility.** The two overlays have only the three-line inset block in common: the map panel additionally needs `height: 100dvh` (its inner column resolves `height: 100%` against it) and carries the landscape coupling where the sidebar overlay reaches the padded edge through `.sr-map-content`. Help has neither, so a shared utility would still need a per-overlay positioning class and would buy one shared declaration block at the cost of a second class name on the element. Worth revisiting at a third overlay, not at two. `.sr-help-panel` deliberately has no `height`, and a test asserts that so a copy-paste from the map rule cannot quietly add one.
- **Padding, not a smaller box.** Tailwind preflight sets `box-sizing: border-box` globally, so the panel still fills the viewport and only its content box moves inward. The surface color still paints edge to edge, including behind the status bar. Nothing in the overlay is absolutely positioned, so there is no descendant resolving against the panel's padding box (the coupling that made build 1's sidebar removal load-bearing has no analogue here).
- **The TOC cap had to be lifted too, for the same specificity reason one level down.** An inline `maxHeight` is 1,0,0 and would have beaten both the base cap and the `.sr-ios-app` one, so the iPad over-extension would have survived the fix silently. The base value is unchanged, so desktop and web are byte-identical; the `≤640` tier's `max-height: none !important` still wins over both new rules, so the phone still stacks the nav static and scrolls it with the content.
- **The bottom edge was checked against this overlay's own chrome, not assumed, and deliberately left alone.** There is no footer or bottom-pinned control. The content column carries 80px of bottom padding and the sticky TOC nav 32px, both clearing the ~34px portrait home indicator (and the ~21px landscape one), so nothing renders under it today. Adding a `padding-bottom` would shrink the panel's content box, and since the body is the `flex: 1` scrollport that means a dead band below it. This mirrors `.sr-ios-app body` and the map panel, which are also top/left/right only.
- **`position: sticky` was checked and is clear.** The TOC nav sticks to its scrolling ancestor (`bodyRef`), not the viewport, so it never escapes the inset, and `globals.css:2053` forces it static at ≤640 anyway.
- **Tests are mutation-verified, not just written.** Each new assertion was confirmed to fail against the wrong implementation it exists to reject: (A) a bare ungated `env()` on the base panel rule, (B) the positioning left inline, (C) the gated TOC cap without the inset subtraction, (D) the TOC cap left inline, (E) the rules DRY-consolidated into the `≤640` media block, which would strand the iPad. All five fail their named test, and the baseline restores green. Mutation E is caught because the new `parseTopLevelRules` helper skips at-rule blocks whole, the same any-width guarantee `mapIosFullscreen.test.ts` gets from its media-stripping walk.
- **Test home:** `iosChrome.test.ts`, the non-surface-specific iOS chrome guard that already parses the real `globals.css`. Not `mapIosFullscreen.test.ts` or `breedingCodePinnedCss.test.ts`, which are both surface-specific, and no parallel file. One DOM-side assertion was added to the existing `HelpDocs.test.tsx` so the class is proven to reach the rendered element, not just to exist in the stylesheet.
- **Preserved and re-verified:** the focus trap still re-queries its focusables per Tab keydown, Escape still closes, focus still restores to the opener (covered by `HelpDocs.test.tsx`), and the TOC/`HELP.md` parity guard (`helpToc.test.ts`) still passes.
- **No documentation update needed.** No user-facing copy, described behavior, privacy surface, or accessibility contract changes; this is an iOS-only layout inset.
- No version bump or changelog entry: this is one build of a bundled Spool release, and the single bump plus combined entry happen once at the end of the bundle.
