# Decisions: hotspot-reports

- **D-01 (2026-11-10, The Designer). First design direction, drawn inside `pipeline/design-system.md`.** No token is minted and no new pattern is introduced; the page is built from registers the app already has. The mockup is `pipeline/hotspot-reports/design.html` and the spec is `design-spec.md`. This is a first direction for the user's review, not an approved design. The choices worth recording, each with what would reverse it:
  - **The picker is the Life Lists Region picker's anatomy at the 40px hero register.** The Region picker is 30px because it sits in a filter strip; here the control chooses the whole page, which is what the species picker's `md` register (40px, the Species Detail hero scale) is for. Rows are two lines (name, then a meta line), flat, in name order. Reversal: the 30px strip register if the user wants the control quieter.
  - **A kind is a glyph AND its word, or nothing.** lucide `MapPin` plus "Hotspot", lucide `Star` plus "Personal location" (the Map Explorer already draws a star on a personal location's pin), both in `--sr-text-muted`, never a hue. A location whose kind is not yet known gets no tag at all, so no "unknown" word exists on the page. The tag sits on the meta line, so a name never moves when the classification arrives. Reversal: a glyph alone in a fixed leading slot, which is more compact and asks the user to learn two glyphs.
  - **The count block reuses Statistics' hotspot partition (`.sr-hs-*`) with counts where Statistics prints percentages**, plus a third, dashed segment for locations not yet known (the app's "dashed means not checked" mark). **When nothing at all is classified the split is not drawn**: the total stands with one status row giving the reason. This is narrower than QA-27's "three figures in every state" and is flagged for the Planner (see D-02).
  - **The location's totals (FR-50) are the header's headline pair**, with the rule sentence of FR-39 directly under them, so the figure and its counting rule are read together. The other statistics stay in their own card.
  - **The life list is the Life Lists ledger row with one deliberate deviation from that pattern: a column header row at wide widths.** The ledger pattern says "no column header" because its count sentence names the one date; this list carries two figures per row (first date here, and how many of the location's checklists include the species), and NFR-07 asks for headers. The header row is visual and `aria-hidden`; every cell carries its own words for assistive technology, and the stacked form spells the words out on screen. Reversal: drop the header row and rely on the count sentence alone.
  - **Weather, protocols, months and years all use the shipped distribution row (`.sr-wx-row`)**, so this tab is a third surface of that primitive and its phone tier. Two additions scoped under this tab's own classes: the most common band is named in a sentence above its group and its row label is set at weight 700 (two cues, neither a color), and a protocol label wraps instead of taking the row's desktop ellipsis, because a protocol name is user-file text bounded at 64 characters. No shared declaration changes.
  - **The per-row share bar in the life list is `--sr-chart-slate`, not the accent**, and does not animate: up to 100 are on screen at once and they are reinforcement beside a printed figure.
  - **One column or two is decided by the report's own width (a container query), not the viewport**, so a wide window at 200% text stacks as a phone does. The thresholds in the spec (55em for the report, 30em for the list rows) were measured in the mockup and are re-measured against the real containers in the built app, under a classic scrollbar (ui.md, v1.0.50 and v1.0.56).
  - **The jump row is the Statistics jump-nav's chip, shown only while the report is one column**, where the long list sits above the other sections. It is navigation, not a filter or a switch.
  - **Focus after a ranked-row press lands on the report's name heading** (`tabIndex={-1}`, no ring, the house programmatic-focus form), not on the picker, because focus on the picker opens its list.
  - **The map sits in a headed card with no corner controls** (Open Question 4's default); its height is one class, `.sr-hsr-map`, shared with the loading fallback.
  - **Tab glyph: lucide `MapPinned`**, used nowhere else in the app. **Tab position: directly after Life Lists** (the default). *Superseded by D-03: the user placed the tab between Breeding Codes and Checklists.*
  - **More sheet: the default is drawn, `min(73dvh, 616px)`.** In the mockup the sheet's own styles, copied from `globals.css`, measure 616px in Chromium and in WebKit at 393 by 852 with a 34px inset, which is the Architect's arithmetic. That is a mockup measurement, not the built app's; the Engineer's WebKit measurement of the built app governs the number.

  - **FR-26.** The no-key reason carries the house "Add a key in Settings" link (the Statistics hotspot block's own control). It is inside the count block; the Planner may strike it.
  - **FR-31 and QA-31.** The jump row is a sixth element of the report while it is one column. QA-31 forbids controls that filter, switch or export, which this is not; a line in FR-31 would make it explicit.
  - **FR-37 and NFR-07.** "A real table or list with headers" is met as a list whose header row is visual; if QA reads it as requiring `th` cells, the list becomes a table at wide widths and the stacked form needs its own answer.

- **D-04 (2026-11-10, The Engineer). `kindOf` follows the shipped share's ORDER: a location with no askable region code is not yet known even when its id is in the Set.** Schema 5 describes `kindOf` as "in the Set is hotspot; otherwise an askable answered region is personal", but `computeHotspotShare` (the oracle QA-15 sums against) tests the region code FIRST and counts a code-less row as unclassified whatever the Set holds. Summing `kindOf` must equal the shipped function, so `kindOf` takes its order. The case cannot arise from a real export (the Set holds only ids some askable region answered with, and a hotspot's own rows carry its state), so nothing a user sees changes; it is recorded so nobody "fixes" the order to match the schema prose. Reversal: if `computeHotspotShare` ever reorders, `kindOf` follows it and `hotspotReportsKind.test.ts`'s sum row says so.

- **D-05 (2026-11-10, The Engineer). QA-33's example form `Red-tailed Hawk (calurus/alascensis)` is not listed, because the shipped countability predicate reads it as non-countable.** It is not a name eBird publishes, so `isNonCountableForm` judges it by the naming convention, where a slash on the raw name is a non-countable shape. The tab follows the shipped predicate (bird-names.md: where a convention and an artifact disagree on which predicate a call site takes, the convention wins and the deviation is stated in code). Reversal: none; the predicate is the app's one countability rule.
