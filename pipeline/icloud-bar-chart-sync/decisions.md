## Security review fixes, The Engineer (2026-09-28, after The Auditor)

11. **M1 and L1 are fixed in code; schema §8.3 and §10.2 are corrected to match.** M1: the merge's dedupe (and the load path's, same shape) now records a key at first sight, before its verdict, so a key repeated in `order` is validated once. At the Auditor's shapes the merge went from 2.8 to 3.4 s (552 KB) and 11 s (1.1 MB) to 2.5 ms and 4.8 ms. L1: the day-obs pass reads the purge generation at its start, before the listing and every download, and hands it to `mergeSharedSnapshot(text, gen)` as a required argument. When the generation has moved by the push half, the pass also skips the push: the Clear owns the iCloud half (it removes every device's snapshot and resets the preference the pass captured). A snapshot the Clear could not remove goes at the next check, which finds no local document. The Auditor recommended the push skip as well, and it was taken.

12. **Held privacy text, item 38, corrected (L2). Needs the user's express approval with the rest of the held patch.** Only this one sentence changed, identically in `PRIVACY_POLICY.md` and `website/privacy.html`, inside `held-published-copy.patch`. The earlier text claimed the day copies held "only" a list of fields, and the list left out what else the snapshot stores. Each entry stores `fetchedAt` (when that device asked eBird), `complete` (whether the day was over when it asked) and `bytes` (the list's size). Each copy also has the same small record a file has: its name, upload time, size, checksum and the device it came from.
    - **Before:** "Your app settings, map preferences and cached lookups stay on each device and are never synced, with one exception: the day-by-day lists of species that eBird reported in a county, which the Targets tab fetches with your key, are written into the same container as one copy per device, each holding only what that device fetched from eBird (the county, the day, and each species eBird listed with the time and place of that report as eBird gives them), so your other devices do not repeat those requests."
    - **After:** "Your app settings, map preferences and cached lookups stay on each device and are never synced, with one exception: the day-by-day lists of species that eBird reported in a county, which the Targets tab fetches with your key, are written into the same container as one copy per device, each holding only what that device fetched from eBird (the county, the day, when that device asked and whether the day was over by then, the list's size, and each species eBird listed with the time and place of that report as eBird gives them), along with the same small record each file has, so your other devices do not repeat those requests."
    - The next sentence ("They hold none of your own sightings.") is unchanged. The patch's guard row for item 38 asserts the new text, and its fields row now also checks the entry's own fields (`fetchedAt`, `complete`, `bytes`, `species`) against the sentence. With the patch applied, the 17 test files that read the published files passed (377 tests). The patch was then reversed and all seven touched files were confirmed byte-identical by hash.
    - **Item 44 (App Store review notes) is deliberately unchanged.** Its sentence ("The one cache that is: the Targets tab's per-day lists of species eBird reported in a county, one copy per device, so the user's other devices do not repeat those eBird requests; they hold no user sightings.") makes no "only" or completeness claim, so it is not false. Reverse this if Apple review asks what the day copies contain. The fix would then mirror item 38's parenthesis in that bullet.

13. **The merge stays on the main thread in this build. The worker is the named follow-on (schema V4, security I1).** Measured by the Auditor: a realistic 9.47 MB snapshot (300 entries, 57,000 records) merged into an empty store in **49 to 55 ms** (Node/V8 on this Mac, 3 runs). That is the ~50 ms threshold the schema set for escalation. It was not moved off-thread here for four reasons. (1) The merge runs at most once per CHANGED peer snapshot, because an unchanged digest is never downloaded again (`state.peers`). (2) It runs inside a background iCloud check, not on a user action. (3) 10 MB is the day store's own payload budget, so this is the worst case for a legitimate peer. (4) After M1, a hostile snapshot costs time linear in its size too.
    - **Reverse when** any of these holds. The same merge measures over ~50 ms under JavaScriptCore (the Mac, iPhone and iPad runtime) on a measurement the user performs or a simulator provides. `DAY_OBS_MAX_BYTES` is raised. Or the merge moves onto an interactive path, such as a tab visit.
    - **The fix and its location:** move `JSON.parse` and the per-entry validation in `mergeSharedSnapshot` (`frontend/src/lib/countyDayObsCache.ts`) into a worker shaped like `parseOffThread`, with the settle contract of CLAUDE.md v1.0.14, returning validated entries to the main thread, which keeps only the union and the one eviction pass. The caller, `runDayObsPass` in `frontend/src/lib/icloud/dayObsSync.ts`, is unchanged apart from awaiting it.

## Security confirmation fixes, The Engineer (2026-09-28, after the Auditor's L3 and I6)

14. **Held privacy text, item 38, corrected again (L3). PENDING THE USER'S EXPRESS APPROVAL, with the rest of the held copy; nothing is written to the published files.** Each device's copy is its whole local day store, and the merge puts the entries it takes from other devices into that same store, with no mark of where they came from and each keeping the `fetchedAt` of the device that fetched it. The push half then uploads the store. So after the first merge, a device's copy holds day lists its other devices fetched, and "only what that device fetched" was false. For the same reason, "when that device asked" becomes "when the list was asked for", the Auditor's wording. The second sentence changes because a county-day list is eBird's public data and can include a report the user submitted to eBird: what is true is that nothing comes from the user's own files. Both sentences change identically in `PRIVACY_POLICY.md` and `website/privacy.html`, inside `held-published-copy.patch`.
    - **Sentence 1, before:** "Your app settings, map preferences and cached lookups stay on each device and are never synced, with one exception: the day-by-day lists of species that eBird reported in a county, which the Targets tab fetches with your key, are written into the same container as one copy per device, each holding only what that device fetched from eBird (the county, the day, when that device asked and whether the day was over by then, the list's size, and each species eBird listed with the time and place of that report as eBird gives them), along with the same small record each file has, so your other devices do not repeat those requests."
    - **Sentence 1, after:** "Your app settings, map preferences and cached lookups stay on each device and are never synced, with one exception: the day-by-day lists of species that eBird reported in a county, which the Targets tab fetches with your key, are written into the same container as one copy per device, each holding the day lists that device has, whether it fetched them from eBird or took them from your other devices' copies (the county, the day, when the list was asked for and whether the day was over by then, the list's size, and each species eBird listed with the time and place of that report as eBird gives them), along with the same small record each file has, so your other devices do not repeat those requests."
    - **Sentence 2, before:** "They hold none of your own sightings."
    - **Sentence 2, after:** "They hold nothing from your own files."
    - **Guard.** In the patch's `icloudBarChartPublishedClaims.test.ts`, the row titled after the old phrase no longer checks the native device-id refusal. It now asserts the merge-then-push property: the merge inserts a taken peer entry into the live store (`insertEntry(store, key, peer)`) and schedules its flush; the flush writes the whole mirror to the one local document; the pass merges, then drains the writer, then pushes this device's own copy under its own id, in that order; and the native push reads that same `county-day-obs.json`. The row goes red on each of three mutations, checked on copies: the push moved before the pull, the merge writing elsewhere, and the merge not scheduling a flush. The text rows, the fields row's title and the item 44 agreement row assert the new wording.
    - **Verification.** `git apply --check` passes. With the patch applied, all 25 test files that read the published files pass (671 tests, `privacyPageParity` included), and typecheck is clean. The reverse left the six unmodified files identical to HEAD and `targetsPublishedClaims.test.ts` identical to its pre-apply bytes, confirmed by a forward re-apply with a hash match.
    - **Left as it is, by direction.** Item 44's review-notes clause "they hold no user sightings" is unchanged. It makes no provenance claim, but the same point about a submitted report applies to it. It is named here so the user can decide at the approval.

## Follow-up fix landed in build 5 (steady-speed-check-tests, The Engineer, 2026-09-29)

15. **Targets Remove: focus after a confirmed remove now reliably lands on Add file.** This closes build 1 QA's Known Limitation 1. `ModalDialog` chooses where focus returns when its close transition ends. When that happened after `removeBarChartFile` resolved but before the parent's manifest re-read switched the card to absent, it focused Remove, which was still mounted and enabled. When the card then went absent, Remove unmounted and focus fell to `<body>`, against design-spec section 1 ("focus returns to the Add file button").
    - **The fix,** in `frontend/src/components/targets/TargetsBarChartFile.tsx`: a confirmed remove records its county. An effect then moves focus to Add file once the card's absent state has committed and the card is no longer busy. It moves focus only when focus was lost (`<body>`) or is still inside the section, so it never takes focus from somewhere the user went. A failed removal, a switch to another county, or an unreadable manifest (`unknown`) drops the pending move. `ModalDialog` is unchanged, as is its choice of target in the usual order.
    - **Tests,** in `TargetsBarChartFile.test.tsx`. One three-row roster covers the orders the removal, the absent render and the dialog's close can land in, and a fourth row checks the no-steal guard.
      - Without the fix, the "dialog closes, then absent" row fails 3 of 3 (focus on `<body>`).
      - With the guard mutated out, the guard row fails.
      - The mid-removal row cannot fail in jsdom without the fix, because jsdom leaves focus on the disabled Replace button (a browser drops it) and React reuses that element as Add file. It is kept so the fix is held to that order too.
    - **Not changed here:** the same close-time choice is shared by Settings' Remove all bar-chart files dialog. Its fallback is the button itself, which stays mounted, so the defect cannot occur there.
