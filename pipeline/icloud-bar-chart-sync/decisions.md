## Security review fixes, The Engineer (2026-09-28, after The Auditor)

11. **M1 and L1 are fixed in code; schema §8.3 and §10.2 are corrected to match.** M1: the merge's dedupe (and the load path's, same shape) now records a key at first sight, before its verdict, so a key repeated in `order` is validated once. At the Auditor's shapes the merge went from 2.8 to 3.4 s (552 KB) and 11 s (1.1 MB) to 2.5 ms and 4.8 ms. L1: the day-obs pass reads the purge generation at its start, before the listing and every download, and hands it to `mergeSharedSnapshot(text, gen)` as a required argument. When the generation has moved by the push half, the pass also skips the push: the Clear owns the iCloud half (it removes every device's snapshot and resets the preference the pass captured). 13. **The merge stays on the main thread in this build. The worker is the named follow-on (schema V4, security I1).** Measured by the Auditor: a realistic 9.47 MB snapshot (300 entries, 57,000 records) merged into an empty store in **49 to 55 ms** (Node/V8 on this Mac, 3 runs). That is the ~50 ms threshold the schema set for escalation. It was not moved off-thread here for four reasons. (1) The merge runs at most once per CHANGED peer snapshot, because an unchanged digest is never downloaded again (`state.peers`). (2) It runs inside a background iCloud check, not on a user action. (3) 10 MB is the day store's own payload budget, so this is the worst case for a legitimate peer. (4) After M1, a hostile snapshot costs time linear in its size too.
    - **Reverse when** any of these holds. The same merge measures over ~50 ms under JavaScriptCore (the Mac, iPhone and iPad runtime) on a measurement the user performs or a simulator provides. `DAY_OBS_MAX_BYTES` is raised. Or the merge moves onto an interactive path, such as a tab visit.
    - **The fix and its location:** move `JSON.parse` and the per-entry validation in `mergeSharedSnapshot` (`frontend/src/lib/countyDayObsCache.ts`) into a worker shaped like `parseOffThread`, with the settle contract of CLAUDE.md v1.0.14, returning validated entries to the main thread, which keeps only the union and the one eviction pass. The caller, `runDayObsPass` in `frontend/src/lib/icloud/dayObsSync.ts`, is unchanged apart from awaiting it.

## Device pass on 1.0.40.1, The Engineer (2026-09-29, fix errand, hands-off)

17. **User report on TestFlight 1.0.40.1: "The first bar chart sync and delete worked fine. However, when I attempt to upload a bar chart from another device, it appears to be stuck on the 'waiting to upload' step."** Diagnosed from the code and the faked-native harness only (this Mac is not signed into iCloud; no device was touched). Still unknown at the time of writing: which device was which, whether it was the county just deleted, and whether Check now or a relaunch clears it.
    - **What puts a county in "Waiting to upload", and what moves it on.** Four paths in `countySync.ts`: (a) the push returned `uploaded: false` (the daemon has not sent it yet, normal straight after any push); (b) a later check's `none` decision read the listing's `file.uploaded === false`, which native computes as the county file AND its record both reporting `NSURLUbiquitousItemIsUploadedKey` (`item_file_status`); (c) the push rejected with `unavailable` or `timeout`; (d) the listing rejected and the county was an unpushed local change. Only a LATER CHECK moves (a) or (b) on.
    - **Hypotheses ruled out.** (1) A tombstone does not block: a file added after the removal is newer than the cleared marker, so the table says push; a remembered clear yields to it and is dropped. (3) No record time the second device cannot produce (every Tauri manifest time is `toISOString()` output) and no view that only the first device holds (the pass sets a view for every county in the union each check). (5) The county pass has no eviction or admission. A scratch two-device run of the real controller (peer upload, pulled here, peer removal or our own, then our add of the same county) pushed once and read "Up to date" at the next check, so with a native layer that behaves, the county logic settles.
    - **Root cause 1, confirmed in code: nothing reliably runs that later check.** The native watch (`start_watch_on_main` in `icloud.rs`) observes `*.record.json` only, never `barcharts/<code>.txt`, whose upload flag also gates the row, so when the file finishes uploading after its record no event fires. The check that this device's own record write triggers is queued behind the push check and runs before the daemon has sent anything. What remains is the five-minute visible poll, returning to the app, and Check now, which is in Settings and not on the Targets tab. A user watching the Targets card after an add therefore sees "Waiting to upload" for up to five minutes. This is hypothesis (2) in a sharper form: it is not a connectivity retry that is missing but any re-read after the upload completes. It is not specific to the device that did not make the first upload: any device's add is exposed, and whether a record event rescues it depends on which of the two items finishes uploading last. The first device's row very likely did the same and was either not watched or was refreshed by leaving the app. This variant clears on Check now, on relaunch and on returning to the app.
    - **Root cause 2, confirmed in code: a refused write was shown as "Waiting to upload", forever.** `pushCounty` mapped a native `unavailable` or `timeout` to "Waiting to upload". The push writes only into the local container, so offline it SUCCEEDS with `uploaded: false`; `unavailable` is a filesystem or coordinator failure and `timeout` a write that did not land within the 8 s command budget. Each check retried the push, failed again and showed "Waiting to upload" again, and the check itself reported success. This variant survives Check now and relaunch. Hypothesis (4): no deterministic write failure specific to a second device was found in `push_item_at` (the subdirectory is created on first write whoever made it, and a cleared marker is replaced by rename like any record), so only a device can say whether one occurred; if it did, it now shows. Also found: a listing refused with anything other than `timeout` / `unavailable` put an unpushed county on "Waiting to upload" without failing the check, against schema section 5 step 2, which names only those two.
    - **The fix.** (1) `icloudSync.ts`: after every check that reached iCloud and left a county reading "Waiting to upload", one follow-up check re-reads the flag after `UPLOAD_RECHECK_MS` (15 s), at most `UPLOAD_RECHECK_MAX` (8) in a row, two minutes, after which the five-minute poll governs as before. Nothing is armed after a failed check (offline keeps the FR-05 behavior), while a check is already queued, or while the window is hidden (the foreground trigger re-reads). The count resets only when a check leaves no county waiting, or when the user adds a file, so a file iCloud never takes cannot keep it running. Any check that starts drops a pending re-read and re-arms from its own outcome, and `stopWatching` clears the timer (disable and dispose). The re-read never re-uploads: an identical record decides `none`. (2) `countySync.ts`: every push refusal reads "Could not sync" with its mapped reason ("iCloud could not be read." or "iCloud did not respond in time.") and Retry, and the next check pushes again. The listing answered in that check, so a push timeout is the NFR-04 "answered once, then out of budget" case, not FR-05's offline one. (3) The listing maps only `timeout` / `unavailable` to "Waiting to upload" for an unpushed county, every other refusal to "Could not sync", per schema section 5 step 2. No new strings: every label and reason is an approved existing one, and `docs/HELP.md` already describes both states as they now behave.
    - **Which devices.** Every Apple build with sync on, the shipped Mac desktop 1.0.40 included: the controller is the same TypeScript in every bundle, and neither defect is iOS-specific. The fix reaches each platform only with a new build. No Rust changed.
    - **Tests, in `countySync.test.ts`.** The fake's listing now reports the upload flag per county (set from `knobs.pushUploaded` on a push, true for a seeded record), and the harness takes `uploadRecheckMs` (60,000,000 by default, so no existing test arms it). Against the unfixed source, 5 of the 7 fail, each at its own assertion. Mutating the cap out of `armUploadRecheck` fails the bound row (dozens of checks against 8). 18. **User report on TestFlight 1.0.40.2, after entry 17: "When I add a bar chart to the phone, it appears on the iPad. When I delete from the phone, it is deleted from the iPad. But if I delete a file on the iPad, it does not get deleted from my phone. Diagnosed from the code, Apple's documentation and forum record, and the faked-native harnesses; this Mac is not signed into iCloud and no device was touched.
    - **Ruled out from the code.** (1) *The iPad not writing the marker.* `barChartsCleared` writes it unconditionally through `pushItemsCleared`, and the native write is the same `atomic_container_write` the eBird backup's record goes through, which the user confirms reaches the phone. A refused write puts "Could not sync" with Retry on the iPad's Targets card (the sync line renders in the absent state too), which the user did not see. (2) *Time comparisons.* The marker carries the delete's own time, newer than the phone's add, so the table says delete-local; the D4 fallback does not apply to a clear; origins and device ids decide only an exact-millisecond tie, and the validator accepts `ipad`. (3) *Placeholders and listing scope* (the brief's a, b and c). The listing reads `Documents/barcharts/` with `read_dir`, maps `.US-XX-000.record.json.icloud` back to its county through the region-code predicate, finds a county file's placeholder, and requests the download of every record it cannot read; the county pass requests each file download it decides on. (4) *The watch.* The NSMetadataQuery is a documents SCOPE, so `barcharts/*.record.json` is inside it.
