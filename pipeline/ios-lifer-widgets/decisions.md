# Decisions log - iOS Lifer Widgets

## Stage 1 (The Strategist, hands-off)

- **Minimum iOS: app stays at 16.0, widget extension targets 17.0.** The Strategist's draft raised the whole app to iOS 17.0 on the premise that an embedded extension cannot target a newer OS than its containing app. That premise is wrong on iOS: an app extension may declare a newer deployment target, the system does not load it below that version, and the app itself is unaffected (the pattern every iOS 13 app used to ship iOS 14 WidgetKit widgets). Corrected in `strategic-brief.md` Key Decision 5 as a factual fix that lowers impact: no App Store minimum change, iPhone 8 / 8 Plus / X users keep getting updates and simply do not see widgets. Caveat carried to the Architect: widgets disappearing silently below iOS 17 must be stated in help, and a debug install to a device below the extension's target fails with "Failed to get descriptors for extensionBundleID". Sources: Apple Developer Forums thread 650651; scastiel/kado issue #97.

## Stage 4 (The Designer, user feedback on the first direction)

- **Media Targets gains a media setting: Photo / Audio / Both (default Both).** User direction, 2026-09-24: "allow the user to select between photo, audio, or both. If both is selected, show a glyph next to the bird's name indicating whether a photo or audio or both is needed." This reverses the brief's Out of Scope bullet ("a media-type sub-filter ... the widget shows any missing type"). Semantics: Photo = recorded species with no Photo in the Macaulay export; Audio = no Audio; Both = no Photo OR no Audio (union). Video is not considered by the widget in any setting, so a species missing only Video is not listed (the user named photo and audio only; stated to the user as a redirectable assumption). Glyphs appear only under Both, per row: photo, audio, or both glyphs, with VoiceOver reading "needs photo", "needs audio", "needs photo and audio". Nearby Lifers is unchanged.
- **Tap-through under Both lands on the in-app All type filter.** The in-app type chips combine with AND (`targetTypeFilter` in `MapExplorer.tsx`: Photo+Audio means missing BOTH) and have no "photo or audio" setting, so Photo and Audio map to the matching single chip and Both maps to All, a superset that may also show video-only targets. The "matches Map Explorer" criterion is equality for Photo and Audio, and for Both "Map Explorer All minus species missing only Video". No in-app filter change in this build.
- Routed as scoped errands to The Planner (PRD), The Architect (hand-over shape, deep-link grammar, fixture) and The Designer (mockup), since the change reaches the requirements and the data design, not only the look.
- **Revised the same day: Video is back in, and Both becomes All.** User direction, 2026-09-24: "I forgot about video, please include that as an option for sorting and show a glyph as well." The Media setting is now Photo / Audio / Video / All (single choice, default All). Photo, Audio and Video each list recorded species missing that type in the Macaulay export; All lists species missing any of the three, which is exactly the in-app Media Targets definition. Glyphs appear only under All, per row, one for each missing type (photo, audio, video), with VoiceOver reading "needs photo", "needs audio", "needs video" or the combination ("needs photo, audio and video"). This supersedes the two entries above where they differ: Video is no longer excluded, and the tap-through is now an exact match in every setting (Photo, Audio, Video map to the matching single in-app chip, All maps to the in-app All chips), so the "All minus video-only" superset caveat is gone.
- **The fourth Media value is named "Any", not "All".** User direction, 2026-09-24, approving the design otherwise ("everything else looks great"). The widget's value and its deep-link token become **Any** / `media=any`. Only the widget's word changes: the in-app Media Targets chip it maps to on tap-through is still labeled **All**, and the Time range value **30 days** keeps its internal `'all'` window token. Meaning, default and behavior are unchanged (missing any of photo, audio or video; default for a new widget).

## Stage 8 device pass: re-entry at The Designer (Case 3)

- **A bird tap shows only that bird, centered.** User device pass, 2026-09-24, on TestFlight 1.0.36 (1): tapping a bird in the widget opened the right Map Explorer view with pins for many nearby birds, but did not single out the tapped bird. User direction: "Ideally tapping a bird would only show that bird centered." The approved design carried only the view in the link (fifteen exact allowlisted URLs), so a row tap and a whole-widget tap were the same link; this is a design change, not a defect. New behavior: tapping a bird (a row on medium/large, the one-bird card on small) opens the matching view with the map showing only that species, centered on the sighting the widget listed, with a visible way back to all nearby birds; tapping the widget outside a bird row (the header) keeps today's view-only behavior. The deep-link grammar grows beyond fifteen exact strings, so The Architect and The Auditor re-review it. Re-entered at Stage 4 per the 1.0.29 precedent (approved parts not re-litigated); Engineer, Tester and Auditor run again over the delta, and the iOS build ships as 1.0.36 build 2 (the 1.0.36 train is still open: no store record yet). Desktop 1.0.36 is unaffected (links exist only on iOS).
- **Approved 2026-09-24 ("yes, build it and send me build 2"):** the bird-tap landing (only that species, centered on the listed sighting with its popup open, a "Only {name} · Show all" pill in the FAB cluster; header tap unchanged; species-absent fallback shows all with a statement line). Orchestrator correction for the Engineer: the link's species-code pattern must match the app's existing `SPECIES_CODE_RE` in `frontend/src/components/SpeciesLinks.tsx` (`/^[a-z0-9-]{2,16}$/`), not the schema's stricter `^[a-z0-9]{3,16}$`, so a valid eBird code the app already accepts never degrades to the view link; share one definition where the entry-chunk rules allow, and keep the Swift builder's class identical.
- **Records reconciled after the bird-link security re-review (I10, I11):** `schema.md` now states the shared species pattern `^[a-z0-9-]{2,16}$` everywhere, and `design-spec.md` states that a small widget has one tap target, so a tap anywhere on a listing card (header included) opens the bird, while a small widget showing a state sentence opens the view.
