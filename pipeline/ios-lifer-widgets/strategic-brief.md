# Strategic Brief - iOS Lifer Widgets

## What We're Building

Home-screen widgets for the iPhone and iPad app that show the nearest recent reports of the birds you still need, measured from where you are right now: one widget for **Nearby Lifers** (species not on your life list) and one for **Media Targets** (species you have recorded but are missing a photo, audio or video for). Each widget is a distance-sorted list, configurable to the last day, last week or last 30 days, and tapping it opens the matching section of the Map Explorer tab with the same window and your current location already applied.

## Why Now

Nearby Lifers and Media Targets already exist in Map Explorer and already answer exactly this question, but only after the user opens the app, opens the tab, picks the view, and presses Use my location. The question they answer ("is there a bird I need within reach today?") is a glance question, and a glance surface is the one thing the app has no answer for. The iOS app has been on the App Store since 1.0.0 with iCloud Sync, native location and a settled release recipe, so the platform work this needs (a second target, an App Group, a second profile) lands on a mature base rather than a moving one.

## The User Problem

The birder in `product-brief.md` keeps their own eBird backup and Macaulay export in SnowRaven precisely so the app can tell them what they are missing. On a phone, the moment that matters is not a planned session at the desk; it is a free hour, an unfamiliar town on a work trip, or a morning deciding where to walk. Today the app cannot meet that moment without four taps and a fetch, so the nearest lifer reported an hour ago goes unnoticed. A widget puts "nearest bird you need, and how far" on the home screen with no taps at all, and one tap takes them into the map view that already knows how to show it.

## Success Criteria

- A user who has loaded their eBird backup (and, for Media Targets, their Macaulay export) and entered their eBird key can add either widget and, within its first refresh, see real species with real distances from their current position, sorted nearest first, without opening the app.
- Changing the widget's time range (Day / Week / 30 days) changes what it lists, and it matches what the corresponding Map Explorer view shows for the same window, location and radius.
- Tapping the widget opens SnowRaven directly on Map Explorer, on the matching view (Nearby Lifers or Media Targets), with the widget's time range selected and a search already run from the user's current location, so the tapped bird is on the map.
- With location denied or unavailable, the widget still shows something honest: results from the saved Default Location with a caption saying so, or a plain instruction to open SnowRaven and allow location, never a blank tile and never a stale list presented as current.
- With no eBird key, no backup, or no network, the widget says which one is missing in a sentence, the same honest register the Map Explorer overlays already use.
- The widget's own outbound requests go only to eBird with the user's own key, and nothing about the user reaches the developer; `PRIVACY_POLICY.md` describes what the widget does in the same plain terms as the rest of the policy, and nothing in it or in `ACCESSIBILITY.md` is left untrue by the build.
- The uploaded build is installed on a real iPhone, the widget is added, refreshes, and tap-through is exercised before the App Store submission, per the standing v1.0.31 rule.

## Scope

- **Two widget kinds**, named as the app names the views: **Nearby Lifers** and **Media Targets**. Two kinds rather than one kind with a "which list" parameter, so both are discoverable by name in the widget gallery and a user can place either or both.
- **Widget families**: `systemSmall` (the single nearest bird, its distance and how recently it was reported), `systemMedium` (the nearest three), `systemLarge` (the nearest eight or so). iPhone and iPad, the same extension.
- **One configuration parameter per widget**: Time range, with the same three values the in-app Time Range filter offers (Day / Week / 30 days, i.e. `TimeWindow` 'day' | 'week' | 'all' with 1 / 7 / 30 days). Default: last week.
- **Distance** in miles from the device's current location at refresh time, using the same great-circle rule as `lib/mapExplorerFormat.ts` `distanceMiles`, and the same nearest-first ordering `lib/nearbyLifers.ts` already applies.
- **Search radius**: fixed at 25 miles for v1 (the ceiling Search this area already uses; sent to eBird as 40 km). Not configurable in v1.
- **Data hand-over from the main app** into a shared App Group container: the recorded-species set (for lifers), the media-target species codes (for media targets), the eBird API key, and the saved Default Location. Written on every data-file change (the existing `filesChanged` / `keysChanged` epochs are the trigger), removed on the Settings clear paths.
- **A live fetch in the widget**: one eBird `data/obs/geo/recent` request per refresh per location and window, the subtraction and sort done in the extension, both widget kinds served from one shared on-device result so two placed widgets do not double the requests.
- **Location in the widget** via WidgetKit's `NSWidgetUsesLocation`, riding the app's existing When In Use grant. Fallback to the saved Default Location when location is denied or unavailable, with a caption.
- **Tap-through deep link**: a custom URL scheme (`snowraven://map/lifers` and `snowraven://map/targets`, carrying the window) declared in `src-tauri/Info.ios.plist` and the two generated plists, delivered to the webview, and a small in-app navigation seam that selects the Map Explorer tab, sets `viewMode` to `'lifers'` or `'targets'`, sets the Time Range and runs Use my location. This is the first addressable navigation in the app; today the launch tab comes from the saved tab layout and Map Explorer's view is component state only.
- **Honest empty and error states** in the widget for: no key, no backup (or no Macaulay export for Media Targets), location denied with no Default Location, offline, and an eBird 429 or error (keep the last good list, mark it with its fetch time).
- **Published statements and help**: the Your Location and iOS App sections of `PRIVACY_POLICY.md`, a Widgets subsection under Map Explorer in `docs/HELP.md`, one sentence in `ACCESSIBILITY.md` about the widget's VoiceOver labels, the App Store review notes, and at most one proposed sentence each for `README.md` and `website/` (approval gate; see Key Decisions).
- **Release plumbing**: the widget extension target in `src-tauri/gen/apple/project.yml`, App Group entitlement on both the app and the extension, the extension's bundle id and its own App Store provisioning profile, the export step updated to sign both, and the release skill updated with the recipe.

## Out of Scope

- Any map inside the widget. WidgetKit cannot host an interactive map, and a static snapshot per refresh would cost a tile request plus rendering on every timeline entry for little glance value. The map is what the tap-through is for.
- Lock-screen and StandBy accessory families, Apple Watch complications, Live Activities, and interactive widget buttons.
- Hotspots and My Sightings widgets ("etc." in the idea resolves to nothing more: those two views have no nearest-thing-you-need question). A nearest-unvisited-hotspot widget is a plausible follow-up, not v1.
- A configurable radius, a per-widget custom center, or a media-type sub-filter (Media Targets in the app can narrow to photo / audio / video; the widget shows any missing type).
- macOS desktop widgets, Windows, and the web/Pi build. The Mac app is the Tauri desktop bundle and this feature adds no desktop surface; the design should not preclude a macOS WidgetKit extension later, but nothing is built for it.
- Background location, Always authorization, geofencing, or notifications. The widget reads location only when WidgetKit refreshes it.
- Any change to what iCloud Sync carries. The App Group hand-over is device-local and never synced.
- Any new outbound service. The widget talks to eBird only, with the user's own key, exactly the endpoint Nearby Lifers and Media Targets use today.

## Key Decisions

1. **Feasibility shape: the app hands over the static inputs, the widget does the live part.** A WidgetKit extension is a separate Swift process; it cannot run the webview, the TypeScript, or read the app's sandbox (`AppLocalData/data/`). Two directions were weighed. (a) The app precomputes the whole answer and the widget only renders it: rejected, because the app is not running when the user glances, so the list would be anchored to wherever the app was last opened and would go stale within hours. (b) The app hands over what only it knows (recorded-species set, media-target codes, key, Default Location) and the widget gets location, fetches eBird, subtracts, sorts and renders: chosen. The hand-over is small (hundreds to a few thousand names), the fetch is one request, and the logic is the same rule `lib/nearbyLifers.ts` applies. Refresh reality: WidgetKit grants a budget of roughly 40 to 70 refreshes a day per widget at the system's discretion, so the timeline is planned at about a 30 to 60 minute cadence with `WidgetCenter.reloadAllTimelines()` called from the app on hand-over changes. The widget shows its data's fetch time so "how fresh is this" is never a guess. Risks for the Architect: extension memory and runtime limits against a 40 km / 30 day recent-obs payload (mitigate by requesting `maxResults`, decoding once, filtering to the two lists from one result, and never holding two payloads); eBird etiquette under periodic refresh (one fetch per rounded location and window, a 15 minute on-disk cache in the App Group shared by both widget kinds, 429 honored by keeping the last list and backing off, mirroring `lib/rateLimit.ts` in spirit); and the first Swift in the repo (see 8).
2. **Location.** The extension declares `NSWidgetUsesLocation` and uses `CLLocationManager` at refresh time; it inherits the app's When In Use grant, so the app's existing prompt ("SnowRaven uses your location to center the map on your current position") is where permission is granted, and its string is widened to mention the widget. Denied or unavailable: fall back to the saved Default Location with a "from your default location" caption; no Default Location either: a one-line instruction to open SnowRaven and allow location. The widget never asks for Always and never runs in the background beyond WidgetKit's own refresh.
3. **Scope of v1** is the two lists above, three home-screen families, list presentation only, one Time range parameter matching the app's three values, a fixed 25 mile radius, and tap-through to the matching Map Explorer view. "Media lifer" in the idea is read as the app's existing **Media Targets** concept (recorded species missing at least one media type, from the Macaulay export, or the manual target list when no export is loaded); the widget does not invent a third list.
4. **Platforms**: iPhone and iPad only. macOS widgets, Windows and web/Pi are out of scope (stated above); the release still ships every platform per the rhythm, with unchanged desktop binaries carrying the version bump.
5. **The app's minimum iOS stays at 16.0; only the widget extension targets iOS 17.0.** Widget configuration on iOS 17 uses App Intents (`AppIntentConfiguration`), one Swift file; on iOS 16 it would need the legacy SiriKit intent-definition path, a second mechanism for an audience that by now is negligible. An iOS app extension may declare a newer deployment target than its containing app: the system does not load it below that version and the rest of the app is unaffected (the long-standing WidgetKit pattern since iOS 14 widgets shipped inside iOS 13 apps). So the App Store minimum does not change, iPhone 8 / 8 Plus / X owners (capped at iOS 16) keep receiving updates, and they simply get no widgets. That limit is stated in `docs/HELP.md` ("widgets need iOS 17 or later") so an empty widget gallery on an old device is never a mystery. The Architect confirms App Store validation accepts the split target and that the debug-install error Apple reports for a device below the extension's target is handled in the release recipe. (Orchestrator correction, see `decisions.md`: an earlier draft raised the app to 17.0 on the mistaken premise that an extension cannot target a newer OS than its app.)
6. **Deep link mechanism.** A custom URL scheme rather than Universal Links: there is no developer-operated domain to host an apple-app-site-association file, and the product brief rules one out. The scheme is registered in `src-tauri/Info.ios.plist` (the one plist that survives `tauri ios init`) and the two generated copies, pinned identical by extending `iosSceneManifest.test.ts` or a sibling guard. The runtime delivery to the webview is the Architect's call (`tauri-plugin-deep-link` is the obvious candidate); whichever it is, the URL is parsed by an allowlist (two paths, three window values) and anything else is ignored, per `.claude/rules/security.md`. The in-app seam is entry-chunk safe and does not import Map Explorer statically.
7. **Privacy and published statements change, and this is the drift to be conscious of.** Two founding sentences are no longer strictly true once a widget exists: `product-brief.md` says network calls happen "on demand", and `PRIVACY_POLICY.md` says the app "requests location only while you're using the app, never in the background". A widget refresh happens on the system's schedule, reads location, and sends it to eBird with the user's key without a tap. That is the same request Nearby Lifers makes today, to the same provider, with the same key, and nothing reaches the developer, so the founding posture (no server, no collection, device-to-provider only) holds; but the two sentences must be rewritten to say what the widget does, when, and how to stop it (remove the widget, or deny location). `ACCESSIBILITY.md` gains a sentence about the widget's VoiceOver labels. The App Store privacy answers are expected to stay "Data Not Collected" (the developer still collects nothing) but must be re-confirmed by the account holder in the App Store Connect UI, since the label cannot be set by API; the review notes describe the widget and its location use. `README.md` and `website/` get at most one proposed sentence each, shown before/after and approved by the user before anything is written (CLAUDE.md standing rule).
8. **Release implications.** A second target (`snowraven_widgets`, type app-extension, WidgetKit) in the committed XcodeGen `project.yml`; a second bundle id (`com.dtgibson.snowraven.widgets`) registered in App Store Connect; the App Group `group.com.dtgibson.snowraven` capability on both App IDs; App Group entitlement in both entitlement files (the app's alongside its three iCloud keys); a second `IOS_APP_STORE` profile created through the ASC API exactly as the existing one is, expiring with the same distribution certificate; the manual-signing `xcodebuild -exportArchive` export options mapping both bundle ids to their profiles; and `--validate-app` before upload, which is what catches a missing entitlement. `tauri ios build` must keep working with an extra target; `project.yml` is already hand-maintained (the scene manifest), so the precedent exists, and a guard should pin the target and the App Group id across the files that name them. This is the first Swift in the repo: the widget's subtraction, window and distance rules become a third runtime of the same rule (Python, TypeScript, now Swift), so the Architect owes a parity fixture the Swift tests and vitest both consume, and the honest statement that CI on `ubuntu-latest` cannot compile Swift, so those tests run on the release machine. The device-install-before-submission rule applies with the widget added and tapped.
9. **Alignment**: serves the same birder and the same purpose (richer use of their own data, alongside eBird); no accounts, no server, no new provider; the two data files and the key stay on the device, with a device-local hand-over that never joins iCloud Sync. The extension is a separate process that only reads the App Group snapshot and never touches the app's `storage.ts` documents, so the single-webview invariant in CLAUDE.md is unaffected and stays true. The feature drifts only on the two published sentences in decision 7, which the build rewrites rather than leaves stale.
