Nothing under the camera, on either screen.

Three surfaces in the app are pinned to the bottom edge and escape the page's safe-area padding: the phone bar, the More sheet and the Alerts inbox. Each pads the bottom inset today and neither side. This refinement gives them left and right padding that reads the OS inset for its own side, and nothing else changes anywhere.

Today

The end cell, the sheet's rows and the inbox's rows sit under the inset. The page above them is already clear, because .sr-ios-app body pads that edge; the three fixed surfaces are viewport-relative and never saw the padding.

Proposed

Each surface pads, it does not move. Its fill, hairline and rounded corners still run edge to edge under the camera; the five cells divide what is left, and the sheets' rows, search field and scrollbar start inside the inset. With the inset at 0 the two frames are byte-identical.

Tap More or the bell in either frame to see the sheets rise with the shipped 220 ms ease-out. The frame is the Duo's outer display at 1x, 466 by 678 points. The hatched strip is a simulated OS inset with the camera in it; the simulator's screen masks do not place the inner camera, so the real values come from the Engineer's measurement, and the rules read whatever the OS reports.

The rules, exactly

Three iOS rules gain two declarations each, and the two Android twins gain the same pair reading the injected variable. Each edge reads its own side's inset only; safeAreaPerSide.test.ts pairs them and androidInsetsCss.test.ts derives the twins.

.sr-ios-app .sr-navbar {
  padding-bottom: calc(6px + env(safe-area-inset-bottom, 0px));
  padding-left: env(safe-area-inset-left, 0px);
  padding-right: env(safe-area-inset-right, 0px);
}
.sr-ios-app .sr-nav-sheet {
  padding-bottom: calc(14px + env(safe-area-inset-bottom, 0px));
  padding-left: env(safe-area-inset-left, 0px);
  padding-right: env(safe-area-inset-right, 0px);
}
.sr-ios-app .sr-inbox-sheet {
  padding-left: env(safe-area-inset-left, 0px);
  padding-right: env(safe-area-inset-right, 0px);
}
/* 641px and up the inbox is a centred panel, so the ROOT pads and the sheet resets */
@media (min-width: 641px) {
  .sr-ios-app .sr-inbox-root {
    padding-top: calc(24px + env(safe-area-inset-top, 0px));
    padding-left: calc(24px + env(safe-area-inset-left, 0px));
    padding-right: calc(24px + env(safe-area-inset-right, 0px));
  }
  .sr-ios-app .sr-inbox-sheet { padding-left: 0; padding-right: 0; }
}

Where the four Duo sizes land

The density is chosen from measured width (lib/navDensity.ts), not from a device check, so every Duo size lands in a tier the app already ships. Nothing here is new; it is the arithmetic made visible.

Outer, portrait

466 x 678 pt · phone tier

Phone bar. The only Duo size that shows the bar. Five cells of 93 pt, so labels stay (the container query drops them under 17 rem). The More sheet's 70dvh binds first at 678 pt, so it scrolls with Settings pinned, as expected.

Outer, landscape

678 x 466 pt · rail

Icon rail, 618 pt of content. 678 minus the 216 pt sidebar is under 640, so the derivation refuses the sidebar. Every iPhone in landscape gets this today; the rail column scrolls on a short screen.

Inner, portrait

669 x 951 pt · rail

Icon rail, 609 pt of content. Above the phone tier by 29 pt, so the bar never shows here and the focus-zoom guard does not apply. This is the open call below.

Inner, landscape

951 x 669 pt · sidebar

Sidebar, 735 pt of content. The first iPhone screen wide enough for it. The Map Explorer reserves its own 266 pt sidebar and drops to the rail, exactly as a landscape iPad does.

The open call: focus zoom above 640 px

WebKit zooms the page when a field under 16 px takes focus, and it does so for the phone idiom at any width. The app floors its controls at 16 px only inside the 640 px phone tier, so an iPhone in landscape, and the Duo's inner screen in both orientations, tap a 13 px filter and watch the page jump. iPads do not zoom, which is why extending the floor to every iOS width would be pure cost there.

Today, inner screen: the page zooms to 1.23x

Filters
visualViewport.scale 1.231

Controls at 13 px. The tap brings the keyboard and a zoom the user has to pinch back out of.

Proposed, inner screen: floored, no zoom

Filters
visualViewport.scale 1.000

The same max(16px, rem) floor the phone tier uses, gated so it reaches iPhones only.

Recommended gate

Gate on the screen's shortest side rather than on isIOS(), which cannot tell the two families apart. Every iPhone's shortest side is at most 669 pt (the Duo's inner screen); every iPad's is at least 744 pt (iPad mini). Both device dimensions are tested so the gate holds whichever one WebKit reports in landscape.

@media (min-width: 641px) and (max-device-width: 700px),
       (min-width: 641px) and (max-device-height: 700px) {
  .sr-ios-app .sr-input-16,
  .sr-ios-app .sr-ctl-row :is(button, select, input) {
    font-size: max(var(--sr-ctl-floor), var(--sr-ctl-rem, 0.75rem)) !important;
  }
  .sr-ios-app .sr-ctl-label {
    font-size: max(calc(var(--sr-ctl-floor) * var(--sr-label-ratio, 1)),
                   calc(var(--sr-ctl-rem, 0.75rem) * var(--sr-label-ratio, 1))) !important;
  }
}

Measured on the Duo simulator's outer screen (iOS 27.1, Safari): screen 466 x 678, navigator.platform iPhone, (max-device-width: 700px) matches. The inner screen's reading, and the tap that settles whether it zooms, need the Simulator app, which this Xcode 27.1 install does not include; that is the Engineer's first step. If the tap reads scale 1.000, this block is not added and the null result is recorded.

What feels better, and what does not change

  • Nothing sits under the camera or the Dynamic Island on either display: the three bottom surfaces now pad every edge the OS reports, the page already did.
  • Tapping a filter on the inner screen does not zoom the page, if the measurement says it does today.
  • Every shipped iPhone in portrait is byte-identical: both side insets are 0 there, and 0 px of padding is no padding.
  • iPad, Mac, Windows, web and Pi are untouched: every rule is gated on .sr-ios-app or .sr-android-app, and the focus-zoom gate excludes every iPad by its shortest side.
  • Could shift, on purpose: an Android phone narrow enough to show the bar in landscape moves its end cells clear of a display cutout, which is the same fix on the other platform.
