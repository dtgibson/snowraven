# Change Brief — Map Explorer Before Calendar

## What is changing
`DEFAULT_TAB_ORDER` in `frontend/src/lib/tabLayout.ts` swaps two existing entries so Map Explorer takes Calendar's slot and Calendar takes Map Explorer's. Today the default is `weather, birding-stats, calendar, species-detail, map-explorer, life-list, breeding-codes, checklists, comparer, named-birds` (Weather, Statistics, Calendar, Species Detail, Map Explorer, Multimedia, Breeding Codes, Checklists, List Comparer, Named Birds). The phone bar (`TabNav.tsx`, `PHONE_FAVOURITES = 4`, `items.filter(id !== 'settings').slice(0, 4)`) therefore shows Weather, Statistics, Calendar, Species Detail plus More, and Map Explorer sits first in the More sheet. After the swap the default is `weather, birding-stats, map-explorer, species-detail, calendar, life-list, breeding-codes, checklists, comparer, named-birds`; the bar shows Weather, Statistics, Map Explorer, Species Detail plus More, and the More sheet opens with Calendar, then Multimedia, Breeding Codes, Checklists, List Comparer, Named Birds, Settings.
One normalizer step rides with it so the new default reaches existing devices (see "What done looks like"): `parseLayout` treats a saved order that equals the 1.0.18 default element-for-element as carrying no order preference and returns the new default in its place, hidden set untouched, nothing written back. Any saved order that differs from the old default is kept verbatim, as today. No new write path: hydration still never persists (App.tsx `persistLayout` is called only from reorder, hide/show and Restore defaults).

## Why now
The user's saved idea: "Swap the position of calendar and map explorer, so map explorer shows above the fold for iphone navigation." Since 1.0.17 a phone gets a bottom bar of the first four visible destinations in the saved order; the Map Explorer is the destination the user reaches for on the phone, and by default it is one tap deeper than it needs to be, behind More. The tab layout is device-local (iCloud syncs the two data files only, not settings), so a default that only fresh installs receive would not reach the phone this idea is about; that is why the normalizer step is in scope rather than a follow-on.

## User-facing impact
Fresh installs and any device whose Tab Layout was never touched see the new order everywhere the nav renders (sidebar, rail, bar). A device whose saved order still equals the old default (Restore defaults was pressed, or a tab was hidden or shown without reordering) picks up the new order on next launch, keeping its hidden set. A device with any other saved order is unchanged. The first visible tab is still Weather, so the launch tab does not move. Nothing else changes: same icons, labels, anatomy, keyboard behavior, focus trap and More sheet; the Tab Layout section's Restore defaults button compares against the new default, so a migrated layout reads as default there too.

## Design pass
Not needed. No surface changes how it looks or feels: the bar keeps its five-cell anatomy with a different existing glyph in cell three, and the More sheet loses one row and gains another. Both compositions already exist for any user who reorders today, and `lib/tabIcons.tsx` already renders every glyph at bar scale. The normalizer step is logic only.

## Decisions touched
- **v0.5.41 "Default tab order ... updated" and v0.5.42 (Checklists tab-order tweak):** "defaults and normalization only; a user's already-saved custom layout is preserved." This run keeps custom layouts preserved and narrows the letter of "saved layouts preserved": a saved order identical to the previous default is not a custom layout and now follows the new default. `parseLayout` already normalizes a stale saved layout (appending tabs added later), so this is the same class, a refinement not a reversal. Older defaults (the 0.5.41 order) stay out of scope; those layouts already sat still through 0.5.42's move under the precedent recorded then.
- **v1.0.17 nav rework:** "the two tab-layout persistence decisions are reused as-is, same document, key, seam and normalizer." Same document, key and seam; the normalizer gains one step. "The phone bar's four favourites are the first four visible tabs in the saved order, nothing new is stored" stays true.
- **2026-05-28 desktop tab-layout post-mortem** (persist through the `storage` seam), **2026-05-24 localStorage decision** and **lazy `useState` initializer**: untouched, no new write path, no new read.
- **2026-05-27 responsive navigation:** already partly reversed by 1.0.17; untouched here.
