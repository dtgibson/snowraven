01 · The control

One button, borrowed whole from the Map Explorer

There is no new button language here. The Map Explorer has shipped a circular fullscreen FAB for sixty-odd versions, and this is that control, in that vocabulary, joined to the share-pin drop button in a single bottom-right row. A user who has expanded the Map Explorer already knows how to expand a Named Birds card.

Where the exit lives

In exactly the place the enter lived. The button does not move to a corner of the window, does not become an X, and does not gain a label. It is one control in its other state, which is what aria-pressed is for, and leaving it under the finger that just pressed it is the whole reason a toggle beats a pair of buttons. Escape is the second route, and it already appears in ACCESSIBILITY.md for the Map Explorer, so this makes that sentence true of every map rather than adding a claim to it.

The row

Share button first, fullscreen second, left to right, matching the Map Explorer cluster. The order is DOM order: the share button portals into a display: contents slot that is physically first, so reading order, tab order and visual order are the same thing and no order property exists anywhere.

The row is a transparent flex wrapper. It paints nothing, so the only colour this feature introduces on any surface is background: var(--sr-bg) on the expanded panel. Two declarations are carried over from the Map Explorer cluster on purpose: pointer-events: none on the row with auto on its buttons, because the 10px gap between two discs would otherwise be a dead strip that swallows a map drag, and the flex-wrap quartet, which changes no rendered position at any supported width but bounds the failure if a third control is ever proposed for this row.

03 · The expanded state

One rule, four mounts, no chrome of its own

The expanded geometry is a single shared class, .sr-map-fs-panel, added alongside whichever base class the container already has. One rule means the three surfaces are identical when expanded as a property of the stylesheet rather than of anyone's discipline, and it means the iOS inset, the background and the entrance are each written once.

DeclarationValueWhy
position, inset, height, z-indexfixed, 0, 100dvh, 1200Byte-identical to the shipped Map Explorer panel. One fullscreen geometry in the app, not two.
backgroundvar(--sr-bg)Opaque from the first frame. The surface behind is a live page, not a dimmed one, so a gutter or a slow style load must never show it.
border, border-radiusnone, 0A full window map with rounded corners and a hairline shows the page ground in four corners and reads as a rendering fault. Restored exactly on collapse.
overflowhidden (kept)The clip is what keeps the canvas and its controls inside the box. It has no bearing on the corners.
iOS paddingtop, left, right onlyMirrors the shipped panel rule, gated on .sr-ios-app, never a bare env(). The canvas is meant to bleed to the home indicator.

A specificity trap worth naming now

The phone tier sets .sr-map-container { height: 300px } inside the @media (max-width: 640px) block at the very end of globals.css. Both that and the panel rule are one class deep, and the media block always comes last, so at phone width the expanded map would be 300px tall. The fix is to scope that one declaration .sr-map-container:not(.sr-map-fs-panel), and to leave a note on the other two container rules that any future phone-tier height override owes the same guard. Raising the panel rule's specificity artificially would work and would be the wrong shape.

The corner row needs its own iOS bottom inset

The panel pads top, left and right, deliberately. That inset reaches the base switcher and the top-left zoom stack for free, because the map fills the panel's content box, but it leaves the corner row sitting over the home indicator. So the row insets its own bottom, and only while expanded: the collapsed in-flow map already sits inside the body's own safe-area padding, and a bottom inset there would push two discs up into a 220px card map for no reason. Right is not re-inset, because the panel's own padding already moved that edge.

Where the toggle is not

The button exists only where a map exists. Two boxes in this feature's territory hold no map, and neither grows a control: they would offer to expand nothing.

Statistics, before the map mounts

Loading map…

The placeholder is deferred to idle and must keep the exact box, so it takes the same new .sr-geo-map class and causes zero layout shift when the real map replaces it. No toggle, because there is nothing yet to expand.

A named bird with no coordinates

No sighting of this bird carries a location.

The card draws no map at all rather than an empty one, and the same is true of a species with no usable coordinates on Species Detail. The absent map is the reason the toggle is absent, not a separate rule to remember.

What does not change

Nothing appears, nothing disappears, nothing resizes. Not the base switcher, not the drop button, not the toggle's own size modifier. The map keeps its centre, its zoom, its open popup, its dropped share pin, its base layer and its county shading, because it is the same map instance the whole time. A control that only existed at full window would be a second feature with its own layout budget, and the map at full window is not short of room, it is short of nothing.

04 · Motion

The panel does not fly. The controls settle.

The instinct is to scale the map up from the button that opened it. That instinct is wrong here for three separate reasons, and naming them is more useful than the animation would have been.

A scaling live canvas tears. MapLibre renders at the final size while CSS scales the element, so the tiles stretch and snap at the end of the transition, and it fights the explicit resize the feature has to perform on every mode change anyway.

A transform is the one property this feature is forbidden. The whole overlay depends on position: fixed resolving against the viewport, which any ancestor transform destroys. QA checks that specifically while an entrance animation is running. A transform on the panel itself is defensible on paper and costs a measurement round to prove; it is not worth it for a flourish.

A fade would show the page through. The panel must be opaque from frame one. Fading it in from zero opacity means the Named Birds table is visible behind a half-transparent map for eighty milliseconds, which is the exact thing the opaque-background requirement exists to prevent.

So the geometry change is instant, and what animates is the one thing that genuinely travelled: the corner row, arriving in its new corner. A 150ms rise and fade, the app's own ease-out, entrance only.

Why entrance only

Collapsing puts an in-flow box back where it was. Animating that would mean fading the page itself in, which reads as a flicker. The app already made this call once: SpeciesCombobox's listbox opens on a 140ms ease-out and closes instantly. This is that rule, not a shortcut. Every animation's end state is its resting state, so the app's global reduced-motion block collapses all of it and nothing is lost. No per-component media query is added, and the design system says not to add one.

05 · Open questions

The two that were mine

OQ-08 · No

The Named Birds card map does not gain a base switcher when expanded

The strongest argument is not the one about write paths. It is that the card map does not participate in the base-map preference at all: with the switcher off, the map never reads the stored setting either, so it is always Positron regardless of what the user picked on Species Detail or the Map Explorer. Adding the control while expanded would not be revealing a setting that was already in effect. It would be introducing a second, divergent base-map state on a card, and a new write into settings.json from a surface that has never written one.

And it fails the plainer test too: a control that does not exist collapsed and appears expanded is fullscreen-specific chrome, which is out of scope by name. The card answers one question, where this individual has been seen, and the basemap is not part of that question.

OQ-09 · Stays compact

The Named Birds toggle keeps --compact at full window

There is a real argument the other way, so it is worth stating: at full window on a desktop the expanded card map would carry 30px discs where the other three carry 36px, and that is an inconsistency at exactly the moment the surfaces look most alike.

It loses on three counts. A control that grows under the finger that just pressed it is a second state change the user did not ask for, on the one map where the button sits closest to the edge. The touch and target floors are already met without it: at the phone tier compact is 2.5rem, which is 40px at normal text and 80px at 200%, comfortably past the 24px minimum and at the app's own touch posture. And the difference is six pixels on desktop, where nothing is being tapped.

06 · Measurements

The row at 320px and 200% text

The tightest case this feature has. These are the row's own widths, which are exact because every value is in rem: at 200% in-app text scale the root is 32px. The container widths they sit inside are per surface and must be measured in a browser against the built stylesheet, not calculated here.

The glyph ratio is constant across the two scales within a tier, which is the point of sizing the glyph in rem through --sr-fab-glyph rather than leaving it on lucide's pixel size attribute. It changes between the desktop and phone tiers because the phone tier grows the disc and not the glyph, which is the shipped family's own posture and not this feature's to alter. Every disc in every row clears the 24 by 24 target minimum, the smallest being the desktop compact disc at 30px, and reaches the app's roughly 44px touch posture at the phone tier.

The row wraps rather than overflowing. It carries the Map Explorer cluster's flex-wrap and max-width pair, so if it ever cannot fit, the second disc drops to a line below, still right-aligned, still reachable. Without that pair it would overflow to the left, off the edge of the map, where page scrollWidth would still read a clean 320 and certify a broken build. The arithmetic: it wraps only if the container's content width falls below 218px in the standard register or 194px in compact. Measured here it does not wrap at any theme, tier or scale, but the container widths belong to three different hosts, so whether that holds is the Tester's measurement, not this page's claim.

Both themes

The map canvas is the always-light basemap whatever the app theme is, so in dark mode the expanded panel is a light map inside a dark app. That is the shipped Map Explorer appearance, and the controls carry it: a --sr-surface disc reads as near black on the light canvas in dark theme and as white with a hairline and the family's shadow in light theme. Neither is new, and the panel's --sr-bg ground is only ever visible for the moment before a style resolves. Flip the theme control above with a map expanded to see it.

The feature adds no token, no shadow, no new colour value and no new font size. Every declaration it introduces is either a token reference or a geometry value copied from a shipped rule.

Provenance of the numbers above

Measured against this file in Chromium and WebKit through Playwright, at 1280px and 320px, at 100% and 200% in-app text scale, in both themes: twelve runs, identical in both engines. Also confirmed on every run, with a map expanded: the panel's rect equals the viewport rect exactly, no ancestor of the panel carries a transform, filter, backdrop-filter, perspective, contain or will-change, page scrollWidth never exceeds innerWidth, no control's box leaves its map, and no interactive target falls under 24 by 24. Escape collapses, focus returns to the toggle, the collapsed box measures identical to its pre-expand box, and document.body's captured overflow is restored rather than assumed.

Design system: extended, not evolved. No deviation to log.

One reproduction detail: the shipped .sr-map-fab base shadow is a legacy pure black rgba(0,0,0,0.18), predating the house rule that every shadow is tinted with the app's own ink. This mockup draws it with the ink value. The feature changes neither, since that rule is shared with the Map Explorer cluster and touching it would move shipped pixels there.
