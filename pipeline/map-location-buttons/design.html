Map Location Buttons

Two round buttons in the corner of the map, one of which does not exist yet and the other of which is wearing its face. This is the decision record for the glyph pair, the button states, the failure message, and how four controls fit a 320 pixel phone.

SnowRaven v0.5.82· Stage 4 — The Designer· 10 Aug 2026· Measured in Chromium against the synthetic demo dataset
01

The glyph pair

The share button plants a flag and draws a teardrop. Whatever sits beside it has to be unmistakably not-that.

The pin that gets planted is a staff with a right-pointing pennant and a foot circle — chosen in v0.5.80 precisely because shape, not hue, had to carry the distinction on a map where every colour was already spoken for. The button never followed. So the control announces itself with the universal “a place / find me” teardrop and produces a flag.

SharePinSprite — the artifact the button produces

The reference silhouette. Anything the button draws has to be recognisably this.

Candidates for the share button

MapPin shipped · rejected

A teardrop with a hole in it: the single most overloaded “you are here” mark in consumer mapping. It shares nothing with the sprite and actively claims the job of the button next to it.

Flag rejected

A wavy banner on a short pole. The sprite’s pennant is a hard triangle; at 17 px this one collapses into a filled rectangle and loses the very feature that identifies it.

FlagTriangleRight chosen

Vertical staff at x=6, right-pointing triangular pennant from the top — the same construction, on the same axis, pointing the same way as the sprite. FlagTriangleLeft mirrors it and would point the pennant away from the coordinate.

Candidates for the location button

Navigation the default · rejected

Two independent problems. Its dominant mass is a triangle, and so is the flag’s — the only thing separating them is a hairline staff (see the pair test below). And in every mapping app it means turn-by-turn: go there, not centre on me.

Crosshair rejected

Its ring is r=10, so it runs to the edge of the box and reads as a heavy second circle inside a circular button. It also means aim at a point on the map, which is what the share pin does.

Locate rejected

Right family, missing the point. Without the centre dot it is an empty reticle — a target, not a position. The dot is the part that says me.

LocateFixed chosen

Radial, symmetric, centred on a dot — the shape a birder has already learned from every phone map they own, and the one MapLibre’s own geolocate control uses. Against a tall, asymmetric, top-heavy flag it is the maximum available contrast.

The pair test — 36 px buttons, 17 px glyphs, as shipped

The question is not whether each glyph is good on its own. It is whether a birder glancing at the corner of the map can tell the two apart without reading anything. Second row is the same pair in grayscale, which is the colour-blind and low-light case.

Pair

Share → FlagTriangleRight. Location → LocateFixed. Linear-and-asymmetric against radial-and-symmetric: the distinction survives grayscale, a 17 px render and a glance.

Carry

Moving off Navigation means the sidebar’s “Use my location” button changes glyph in the same edit (FR‑18 is a two-site invariant). Glyph only — label, size, colour and behaviour untouched.

Four controls, 320 pixels

Measured in the running app, not calculated. The arithmetic was right; the reason it fails was not.

At 200% in-app text scale 1rem is 32 px, so the phone-tier 2.75rem FAB computes to 88 px. Adding a fourth control takes the cluster from 268.9 px to 366.9 px against 288 px of usable width. Because the cluster is anchored right: 16px and grows leftward, it overflows to the left:

Why each declaration is there

The Architect prescribed flex-wrap plus a max-width cap, on the standing rule that a container which is never narrowed never breaks a line. Measuring it showed the rule does not bite here — the cluster is absolutely positioned, so its shrink-to-fit width is already bounded by the map area — and that the two declarations earn their place for different reasons than expected:

DeclarationWhat it actually does
flex-wrap: wrapDoes the load-bearing work. Alone it stops the clipping — but it leaves the cluster flush against the left edge with the Filters pill orphaned in the bottom-left corner, which reads as a bug (try the flex-wrap only toggle above).
justify-content: flex-endDoes the visible work. Right-aligns both rows so the wrap reads as a deliberate two-row cluster hugging the corner rather than a collapse.
max-width: calc(100% − 32px)Guarantees the 16 px left gutter. At today’s content widths it changes no rendered position; it bounds the failure for a longer Filters label, another locale, or a fifth control.
row-gap: 10pxMatches the existing column gap so the two rows sit on the same rhythm.
pointer-events: none
(+ auto on buttons)		New here. The cluster box grows from 134 px to 371 px tall once a message is in it, and an absolutely positioned div swallows every gesture inside its box. Verified: a pointer at the message’s centre now reaches CANVAS.maplibregl-canvas, and so do the gaps between the FABs — which they did not before.

Two things the render showed that are out of scope but will now be more visible. The fullscreen toggle stays 36 px while its neighbours grow to 88 px at 200%, so it reads as the odd one out (the PRD defers this deliberately). And the glyphs stay a fixed 17 px inside boxes that grow to 88 px, so at 200% they float in a lot of white. Both are pre-existing properties of .sr-share-drop-btn, which FR‑04 forbids altering; the new button inherits them rather than introducing them. The Filters pill also already overlaps the attribution at 200% today, and the wrap does not worsen it — the cluster grows upward, away from it.

03

The failure message

A hundred characters of remediation text, on a map area 363 pixels tall.

The obvious home was the shipped loading chip’s band at top: 12px. Measuring killed it: the layer switcher runs the full width of a phone (105 px tall at 200%), a message there sits on top of it at every phone size, and elementFromPoint confirms the two occupy the same space. Pushing it below the switcher does not help either — at 320 px and 200% the free band between the switcher and the cluster is 96 px and the longest message renders 227 px tall. Nothing fits at the top.

Placement

The message is a full-width row inside the bottom-anchored cluster, first in DOM order, above the buttons.

This is not a compromise, it is the better design, and it removes every magic number:

proximity
It appears directly above the button that produced it, where the eye and thumb already are — instead of 300 px away at the top of the map.
the buttons never move
The cluster is bottom-anchored, so a new row extends it upward. Measured across empty / short / longest message at three viewports: every button’s top and left is byte-identical. The control the user needs to press again does not shift under their finger.
no offset arithmetic
flex: 0 0 100% claims its own row; the cluster’s row-gap is the gap; its justify-content: flex-end is the alignment; its max-width is the width cap. One set of declarations, two jobs.
safe area for free
.sr-ios-app .sr-map-fab-cluster already insets the cluster, so the message inherits iOS safe-area handling with no new rule.
the live-region contract holds structurally
The region is a sibling of the button that feeds it, so it is mounted whenever a message can be produced. It is present from first render (QA‑20), and the one state where it is absent — the mobile Filters overlay, which unmounts the cluster — is a state in which the button cannot be pressed.

.sr-map-geo-error:empty { display: none } is load-bearing, not cosmetic. A flex: 0 0 100% row with no content still claims a full row and a row-gap, which would push every button down by ~10 px permanently. Verified: with the rule, the empty cluster measures byte-identically to no region at all. It also means no stray text node may be rendered inside the container — {geoError ? <span/> : null} and nothing else.

Every string is describeLocationError() verbatim. Pressing the same reason twice replays the entrance, exactly as the sequence-keyed child replays the announcement.

Appearance

tokens
--sr-error-bg fill, --sr-error-border, --sr-error text. An already-audited pair: 4.82:1 light, 7.07:1 dark. No new token, no new contrast test.
opaque, not translucent
It sits over live map canvas and, in the extreme case, over the layer switcher. A solid fill keeps it legible instead of muddling two layers.
left-aligned with an icon
Centred text is right for the one-line loading chip and wrong for a two-to-six-line instruction. A CircleAlert glyph (already imported in MapExplorer.tsx) top-aligned in the gutter carries “problem” without relying on the red alone.
radius 12px, not 20px
The chip’s 20 px pill radius is for a single line. On a wrapped block it reads as a lozenge; 12 px reads as a card.
max-width 28rem
At 0.75rem that is roughly 72 characters — the top of a comfortable measure. The longest string lands in 2 lines on desktop. Wider would only trade line count for line length.
pointer-events: none
Verified: a pointer at the message’s centre reaches the map canvas.

The one residual, named. At 320 px with 200% text scale and the longest string, the message is 227 px tall in a 363 px map area, so it covers the layer switcher and spills about 28 px above the map’s top edge. There is no placement that avoids this — the message alone is 62% of the available height. It covers no control, it is click-through so the switcher underneath stays operable, and it clears on the next successful detection or view change. FR‑16 asks that neither the cluster nor the switcher be obscured; at this one combination only the switcher can yield, and it is the item with nothing to do with the failure.

one name, four views
The promise is identical everywhere: centre the map on me. On the three centre views the same press may also run a search, but only when both coordinate fields were empty — a condition the user cannot see. A name that promised a search would be a lie whenever the fields are already filled, and a name that changed with the view would make a screen-reader user relearn the control on every mode switch.
“Finding your location”
Matches the app’s own loading vocabulary (“Finding hotspots”, “Finding sightings”, “Finding nearby lifers”). A bare gerund reads oddly out of context and an ellipsis is announced inconsistently, so the sidebar’s visible “Locating…” is not reused verbatim as a name.
Label in Name
Does not constrain here: both states are icon-only with no visible text, so the accessible name is the only name and Voice Control has nothing else to match. Both stay short enough to speak. title mirrors the name, following SharePin.
aria-disabled, not disabled
Ratifying the Architect. Disabling a focused button drops focus to <body> in most browsers, which would break FR‑06 for the button just pressed.
busy is legible without motion
The app’s global reduced-motion block stops all animation, so the spinner freezes. The busy state therefore cannot rest on rotation: the glyph itself changes shape (a closed ring with a centre dot becomes an open arc) and takes --sr-accent, matching the sidebar’s spinner. Shape first, colour second, motion third.
05

The setup-required state

The one place the Architect left a visible button with nothing to centre.

On My Sightings with no eBird backup loaded, <SetupRequired> replaces the map while the cluster still renders above it. A press there detects successfully, arms panTarget, and — with no MapEffects mounted to consume it — does nothing observable. The Architect accepted this rather than reintroduce the data gate FR‑02 forbids.

Decision

The location button renders whenever a map is mounted. It is absent in the single branch where <SetupRequired> replaces the map (viewMode === 'sightings' && isSetupRequired).

why not leave it
A control that produces no observable result teaches the user it is unreliable. That is the exact lesson today’s pin button teaches, and the reason this feature exists. Shipping a second control that teaches it again would be self-defeating.
the permission cost
On a first press it can raise an OS location prompt for no benefit. In an app whose entire posture is privacy-first, asking for location it cannot act on is a real cost, not a cosmetic one.
why not disable it
A disabled control with no explanation is a dead end for everyone. The house rule is already to replace such a control with something honest rather than dim it — and here the honest replacement is already on screen: <SetupRequired> is the explanation, and it carries its own “Go to Settings” action.
FR-02 is preserved
FR‑02 exists so the button is not gated on the user’s data, and it is not: on Hotspots, Nearby Lifers and Media Targets the map renders even when isSetupRequired is true, and so does the button. The gate here is not “is there data” but “is there a map”. It is the same boolean that already governs the ternary, so it costs no new state.
flagged
QA‑02 as written tests the sightings + setup-required combination and would fail. It needs amending to the three centre views, which is where it can actually be observed. This is a deliberate amendment, not a silent deviation.
06

Motion

Two moments, both inside the house vocabulary already in globals.css — cubic-bezier(0.16, 1, 0.3, 1) under 200 ms, with an end state that is the resting state. The app’s global prefers-reduced-motion block collapses every animation to ~1 µs, so nothing is lost when it fires and no per-component reduced-motion query may be added (the Pin Share comment says so explicitly).
