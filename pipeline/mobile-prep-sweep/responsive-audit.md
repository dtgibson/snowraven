# SnowRaven — Responsive / Mobile-Friendliness Audit

**Date:** 2026-07-02 · **Scope:** every feature surface, pre-mobile-launch · **Method:** 13 parallel surface auditors → adversarial verification of each finding against the actual code + `globals.css` breakpoints (5 finder findings refuted and dropped).

## Summary

**71 confirmed issues** — 3 high, 20 medium, 48 low.

The v0.5.37 class-based responsive system held up well. Almost every confirmed issue is either code shipped **after** that sweep (the county overlay, the Completeness popup, the forecast panels, offline-maps settings) or falls in the two lenses that sweep never covered — **touch-target size** (~44px guideline) and **iOS-specific behavior** (sub-16px input auto-zoom). No systemic regression; a bounded, coherent fix set.

### Cross-cutting themes

1. **Map popups with no max-height / internal scroll (all 3 highs)** — the County Completeness popup and the sighting/target marker popups render tall content (progress bar + lists, or many stacked dates/links) with no height cap, so the bottom runs off a short phone screen unreachably.
2. **Touch targets (largest group)** — copy buttons, "Go to Settings →" links, disclosure toggles, segmented-control and legend-row buttons at ~15–30px tall against the ~44px guideline.
3. **iOS input focus-zoom (medium)** — form controls under 16px (place/coord/date/time, checklist ID, media facets, filter selects) trigger Safari's auto-zoom on primary interactions.
4. **Inline-style layout the conventions forbid (medium)** — non-wrapping inline-flex rows and inline grid/width declarations no media query can reach; they overflow or squeeze at 320px / 200% text scale.
5. **Fixed px widths vs rem content (low–medium)** — sticky columns, comparer cells, bar-row labels set in px don't track text scale.

## Findings

### County popups & Completeness

- **🔴 HIGH** `frontend/src/components/map/CountyLayer.tsx:349` — The Completeness-variant county popup has no max-height or internal scroll. A ready, birded county renders name + state + count row + progress block + up to 5 'Recently added' rows + up to 5 'Top targets' rows + two captions + the cache line — roughly 600px of content at 100% text scale inside a 220px-wide box. The popup is anchored bottom at the tap point and is clipped by `.maplibregl-map { overflow: hidden }` (maplibre default), and neither the Popup nor the inner div (line 350) caps height or scrolls.
  - *Phone impact:* On a 320x568 phone the map is calc(100dvh - 132px) = 436px tall (globals.css:684), so the full popup (~600px) cannot fit even when the tap point is panned to the very bottom edge — the top of the popup (county name link, count row, AND the close button, which is the only dismissal since closeOnClick={false}) is permanently clipped off the map and unreachable. On 390x844 (712px map) any tap in the upper half clips it. At 200% in-app text scale the content is ~1100px and clips on every phone.
  - *Fix:* Give the inner content div (line 350) a class defined in globals.css, e.g. `.sr-map-popup-body { max-height: min(48dvh, 24rem); overflow-y: auto; }` (dvh + rem so it holds at 200% text scale), and prefer a rem-based width cap (e.g. `maxWidth="min(15.5rem, 80vw)"`, the SightingsMap.tsx:71 vw-cap precedent) over the fixed 248px/220px so the box grows with the Text Size control instead of only growing taller.

- **🟠 MED** `frontend/src/components/map/CountyLayer.tsx:435` — The 'Counties in view' panel is `position:absolute; bottom:12; left:12; z-index:1050` inside the map container, and its width is min(232px, 62vw). It sits directly on top of the compact AttributionControl, which SnowMap.tsx:181-192 deliberately placed bottom-LEFT (F094) to keep it clear of the bottom-right FAB cluster; and on narrow phones the panel also reaches the FAB cluster itself: at 320px the panel spans x 12-210 while the fullscreen button spans x ~164-200 (cluster = right:16 + Filters ~94px + gap 10 + 36px button), both at z-index 1050 with the map subtree later in DOM, so the panel paints on top.
  - *Phone impact:* Whenever county boundaries are on and counties are in view (the overlay's normal state at zoom >= 4): (a) the attribution toggle is covered at ALL widths — taps land on the panel header, regressing the F094 fix and hiding the OpenFreeMap/OSM credit; (b) at 320-375px the collapsed panel header covers the bottom ~23px of the 36px fullscreen FAB (taps toggle the list instead of fullscreen), and with the list expanded (up to 62% of map height) the fullscreen button is fully occluded and unusable.
  - *Fix:* Reposition the panel out of both reserved corners — e.g. top-left under the NavigationControl, matching AtlasLayer's own 'blocks in view' disclosure at top:78/left:10 (AtlasLayer.tsx:268), or give it bottom clearance above the attribution ctrl (~bottom: 40px) plus a phone width cap that keeps it clear of the FAB cluster (e.g. max-width calc(100% - 170px) at <=640px, lifted to the existing .sr-county-inview class so a media query can reach it).

- **🟠 MED** `frontend/src/globals.css:859` — .maplibregl-popup-close-button is styled to font-size 1rem + padding 2px 8px on top of maplibre's unsized absolute default, yielding a ~23x32px touch target — and the county popup sets closeOnClick={false} (CountyLayer.tsx:349), so this button is the only way to dismiss it (no Escape handling, tapping the map does nothing).
  - *Phone impact:* On a phone the sole dismissal affordance for the county popup (and every other map popup) is a ~23px-tall target in the popup's top-right corner — well under the 44px guidance; mis-taps hit the county-name link (opens eBird in a new tab) or the map. Combined with the height-clipping finding, the button can also be scrolled/clipped out of reach entirely.
  - *Fix:* Enlarge the shared rule in globals.css: give .maplibregl-popup-close-button a min-width/min-height around 2.25-2.75rem (with padding, keeping the glyph size), optionally scoped under `@media (pointer: coarse)`. One CSS change fixes all popups app-wide.

- **🟠 MED** `frontend/src/components/map/CountyLayer.tsx:436` — The 'Counties in view' panel width is px-fixed (`min(232px, 62vw)`) while its row content is rem-sized, and the completeness value span (line 500) and metric value span (line 509) are flexShrink:0 with the name span at flex:1/minWidth:0 — so at 200% in-app text scale the panel does not grow but the fixed-shrink value column does.
  - *Phone impact:* At 200% text scale on a 320px phone the panel is 198px wide; a value like '1,234/2,345 · 53%' at effective ~23px tabular numerals needs ~160px+, so the flexShrink:0 span crushes the county name to a few pixels (rows become anonymous numbers) and can overflow the row into the list's internal clip. Violates the standing 'must hold at 200% in-app text scale' rule.
  - *Fix:* Size the panel in rem so it tracks the Text Size control: `width: 'min(14.5rem, 62vw)'` (14.5rem = 232px at 100%). Optionally let the value wrap at 200% by dropping flexShrink:0 in favor of a maxWidth, keeping fontVariantNumeric for alignment.

- **🟡 LOW** `frontend/src/components/map/CountyLayer.tsx:476` — Dense touch targets throughout the surface: the in-view row buttons are ~30px tall (padding '7px 8px' + 12.5px text, line 476), the disclosure header ~31px (line 447), and inside the popup the BirdName size-sm species links are ~16px-tall inline text links stacked with 4px gaps (CountyCompletenessPopup.tsx:162-199) with the 'Load completeness'/'Try again' button at ~31px (CountyCompletenessPopup.tsx:41).
  - *Phone impact:* On a phone, accurately tapping a specific species link (to open Species Detail) or a specific county row among 0.78125rem rows is fiddly; mis-taps select the adjacent row/species. All remain operable (full-width rows help), so this is polish rather than breakage.
  - *Fix:* Under `@media (pointer: coarse)` bump the lifted classes (.sr-inview-row already exists as a hook) to ~10-11px vertical padding, and give the popup list rows a slightly larger gap/line-height; keep desktop density unchanged.

- **🟡 LOW** `frontend/src/components/map/CountyLayer.tsx:349` — The popup hardcodes anchor="bottom", disabling MapLibre's dynamic anchor selection (used when anchor is omitted) that repositions a popup to stay within the map container.
  - *Phone impact:* On a 320px map a 248px-wide popup centered on the tap point is fully visible only when the tap lands in the central ~72px band; a county tapped near the left/right edge gets up to ~120px of the popup clipped by the map's overflow:hidden (recoverable by panning, since the popup tracks the coordinate — and the list-open path already flyTo-centers). Same pattern app-wide, but the county popup is the widest content-per-pixel case at 320px.
  - *Fix:* Omit the fixed anchor (or clamp longitude toward the viewport center before setSel) so MapLibre can pick left/right/top anchors near edges; verify the tip-color CSS already covers all anchor classes (globals.css:866-873 does).

- **🟡 LOW** `frontend/src/components/map/CountyLayer.tsx:419` — The 'Zoom in to see counties' chip occupies the exact same slot (bottom:12, left:12) as AtlasLayer's 'Zoom in to see atlas blocks' chip (AtlasLayer.tsx:248), and the 'Counties in view' panel (z 1050) also paints over the atlas chip (z 1) — both overlays can be active simultaneously since v0.5.47 keeps their boundary lines coexisting.
  - *Phone impact:* With atlas + county overlays both on at zoom ~4-6, the two role=status chips render exactly superimposed (unreadable doubled text), or the county panel completely hides the atlas hint — on a 320px map there is no free bottom-left space for either to escape to. Visual only (both are pointer-events:none / the panel is interactive).
  - *Fix:* Stack the bottom-left status chips in one shared flex slot (a small shared container component or a `.sr-map-status-stack` class both layers render into), or offset the county chip above the atlas chip; resolves together with the panel-reposition fix in the line-435 finding.

### Map markers & popups

- **🔴 HIGH** `frontend/src/components/map/TargetMarkers.tsx:92` — The target-location popup renders EVERY species in a location group with no slice cap and the popup content box has no max-height / internal scroll (base maplibre CSS and the globals.css .maplibregl-popup-content override both omit max-height/overflow). selGroup.map (line 95) walks all pins; each species block is ~50-70px tall (BirdName + favicons + tier badge + date + ChecklistLink).
  - *Phone impact:* A hotspot with many missing-media targets (8-12+ species is realistic) produces a 500-700px-tall popup. On a phone the non-fullscreen map is only ~calc(100dvh-132px) (~560px on an iPhone) and fullscreen is 100dvh; maplibre pans to fit but cannot when the popup exceeds the map height, so the top or bottom species — including their 'open checklist on eBird' links — are clipped off-canvas and unreachable. No scrollbar appears because the content box never scrolls.
  - *Fix:* Give the popup inner div a bounded height with internal scroll, e.g. style={{ minWidth: 200, maxWidth: 260, maxHeight: '60vh', overflowY: 'auto' }} (rem/vh, not px), mirroring the sidebar list panels. Optionally also slice to a sensible count with a '+N more' row as SightingMarkers/SightingsMap already do.

- **🔴 HIGH** `frontend/src/components/map/NearbyLiferMarkers.tsx:77` — Same unbounded-height popup as TargetMarkers: selLoc.lifers.map (line 80) renders every lifer at a location with no cap, and the inner div (minWidth:200, maxWidth:260) has no maxHeight/overflow. The shared .maplibregl-popup-content has no max-height either.
  - *Phone impact:* A location with many nearby lifers yields a popup taller than the phone map viewport; the map cannot pan far enough to reveal all of it, so the lowest lifers and their checklist links fall off-screen with no way to scroll to them.
  - *Fix:* Add maxHeight: '60vh', overflowY: 'auto' to the popup inner div (line 78), and/or slice the lifer list with a '+N more' row like SightingMarkers does.

- **🟡 LOW** `frontend/src/components/map/SightingMarkers.tsx:128` — Popup maxWidth is a fixed '260px' (px). The sibling SightingsMap.tsx (line 71) already uses the viewport-aware maxWidth="min(260px, 80vw)" pattern, but none of the Map Explorer popups (SightingMarkers 260, HotspotMarkers 260, TargetMarkers 280, NearbyLiferMarkers 280, AtlasLayer 240, CountyLayer 248) clamp to vw.
  - *Phone impact:* On a 320px viewport a 280px/260px popup plus its ~20px tip and the popup's own edge margins can leave the content box wider than the usable width when the anchor sits near a screen edge; maplibre nudges it inward but the fixed-width box still crowds the edges. Not broken (content wraps via sr-wrap-anywhere) but tighter than necessary on the smallest phones.
  - *Fix:* Adopt the SightingsMap pattern app-wide: maxWidth="min(260px, 80vw)" (and min(280px,80vw) for the target/lifer popups) so the popup shrinks on 320-360px screens instead of relying solely on maplibre's edge nudge.

- **🟡 LOW** `frontend/src/components/map/TargetMarkers.tsx:84` — On-map marker chips are ~20-22px tall (padding '3px 8px', fontSize 0.6875rem/11px, 1.5px border). Same for NearbyLiferMarkers (line 69) and the SightingsMap pin button 24x34 (SightingsMap.tsx line 64). All are well under the ~44px touch-target guideline for the tappable box.
  - *Phone impact:* The labeled target/lifer chips and teardrop pins are hard to tap accurately on a phone, especially where several markers cluster near the same spot; the small hit area increases mis-taps and mis-selection. There is a keyboard/sidebar 'in view' list as an alternative route, which mitigates but does not fix the direct-touch difficulty.
  - *Fix:* Increase the effective touch area without changing the visual chip: bump vertical padding (e.g. '6px 10px') so the chip clears ~34-44px, or add a transparent hit-slop (a larger invisible padded button wrapping the visible chip). Keep the visual size if desired via a pseudo-element/inset. Do not shrink further; 'Small' point size already reduces the GL circle to ~12px diameter.

### Map Explorer — chrome & sidebar

- **🟠 MED** `frontend/src/components/MapExplorer.tsx:2057` — The sidebar's width is an inline style — `width: 'clamp(240px, 28vw, 300px)'` — which (specificity 1,0,0) permanently beats the ≤640px media-query width `.sr-map-sidebar-overlay { width: min(282px, 90vw) }` in globals.css:924. On any phone the clamp resolves to its 240px floor (28vw < 240px below ~857px viewports), so the mobile Filters overlay renders 240px wide and the class's intended 282px is dead CSS. This is a direct violation of the 'responsive layout must be a class, never an inline style' convention: the code comment on the element even acknowledges the inline/class split for `display` but misses that `width` has the same conflict.
  - *Phone impact:* On a 320–430px phone the Filters overlay is 240px instead of the designed 282px — 15% narrower, ~208px of usable inner width. Every dense control inside (4-segment SegControls, the From/To date pair, legend rows) gets squeezed, aggravating the clipping findings below, and any future tweak to the mobile width in globals.css silently does nothing.
  - *Fix:* Remove the inline `width` and lift it into globals.css: give `.sr-map-sidebar-overlay` a base rule `width: clamp(240px, 28vw, 300px)` (preserving the 641–1024 tablet behavior) and let the existing ≤640 block's `width: min(282px, 90vw)` win on phones, per the lift-to-a-class convention. Keep flexShrink/border/background inline (non-layout).

- **🟠 MED** `frontend/src/components/MapExplorer.tsx:1342` — The Filters panel's Date Range row lays out the From/To native date inputs with an inline `style={{ display: 'flex', gap: 6 }}` instead of the shared `.sr-field-row` class. The conventions call out exactly this case: `.sr-field-row` exists because 'native date inputs can't shrink' and must stack at ≤480px — but an inline `display: flex` cannot be reached by that media query.
  - *Phone impact:* In the 240px mobile overlay (inner ~208px) each date input gets ~101px; a native date input needs ~106–148px to show mm/dd/yyyy plus its picker icon, so the year is clipped at 100% text scale and the fields are unusable at 200% in-app text scale (~140px needed each). The inputs stay tappable but the selected dates are unreadable.
  - *Fix:* Replace the inline `display:flex, gap:6` wrapper with `className="sr-field-row"` (keeping the inputs' `flex:1` / `minWidth:0`), so the pair stacks vertically at ≤480px like every other native date pair in the app. The Latitude/Longitude pair at line 987 could take the same class for consistency, though number inputs shrink acceptably.

- **🟠 MED** `frontend/src/components/map/MapSidebarUI.tsx:32` — SegControl segment buttons combine `whiteSpace: 'nowrap'`, `flex: 1`, a fixed px `height: 28`, and no min-width/overflow handling. Flex items' default `min-width: auto` means labels never shrink, so when the labels outgrow the sidebar the whole control overflows horizontally and is clipped by the sidebar's `overflow-x: hidden`. Worst instances: the county-shading metric control (Species / Checklists / Completeness, MapExplorer.tsx:1202 — v0.5.48+ code) at ~194px natural width and the Breeding Code control (All / Possible / Probable / Confirmed, MapExplorer.tsx:1362) at ~197px, against ~208px inner width in the 240px mobile overlay.
  - *Phone impact:* At 100% text scale the long SegControls just barely fit the 240px phone sidebar; at ~125% in-app text scale and above they overflow and the last segment ('Completeness', 'Confirmed', '50 mi') is progressively clipped invisible — failing the 'must hold at 200% in-app text scale' rule. The clipped segment remains focusable but can't be seen or reliably tapped. The 28px px-fixed height also leaves zero vertical headroom for 200% (23px) text.
  - *Fix:* Lift SegControl's layout to a class (e.g. `.sr-segcontrol`) with `flex-wrap: wrap` so segments fall to a second row when they can't fit (each button keeping `flex: 1 1 auto`), and replace `height: 28` with rem-based padding (`padding: 0.3em 4px`) so the control grows with text scale. Keep colors/border inline per convention.

- **🟡 LOW** `frontend/src/components/map/MapSidebarUI.tsx:170` — KeyNotice's 'Settings →' action is a bare text button with `padding: 0` and `fontSize: '0.6875rem'` (11px), giving a tap target of roughly 60×13px. This is the remediation affordance for a missing eBird key on three of the four map modes (Hotspots, Media Targets, Nearby Lifers).
  - *Phone impact:* On a phone, a ~13px-tall link is genuinely hard to hit with a thumb (below even WCAG 2.5.8's 24px floor, and far below the ~44px comfortable size) — a keyless user trying to reach Settings from the map will mis-tap the warning card around it.
  - *Fix:* Give the button real padding (e.g. `padding: '8px 10px', margin: '-8px -10px'` to grow the hit area without changing visual layout, or a minimum ~2.5rem-tall pill) while keeping the existing wrap-friendly `.sr-action-row`-style flex the KeyNotice container already has.

- **🟡 LOW** `frontend/src/components/MapExplorer.tsx:2066` — A cluster of 26×26px icon-only buttons in the mobile-critical paths: the Filters overlay's Close button (line 2066), the Crosshair 'Show on map' button in Targets-in-View rows (line 1865), and the compact HotspotLink in Nearest Unvisited rows (line 1602). All are px-fixed at 26px — above WCAG 2.5.8's 24px floor but well under the ~44px comfortable touch size, and they sit adjacent to other interactive elements in dense rows.
  - *Phone impact:* Fat-finger misses on the primary dismiss affordance of the mobile Filters overlay (mitigated by backdrop-tap and Escape) and mis-taps between the row button, crosshair, and external-link icon in dense sidebar lists.
  - *Fix:* Bump these to ~36–44px hit areas — either enlarge the buttons (the close button has room in its header row) or keep the 26px visual and add padding with negative margin so the touch target grows without shifting layout.

- **🟡 LOW** `frontend/src/components/MapExplorer.tsx:2041` — `sidebarOpen` is JS state but the overlay presentation is a ≤640px media query, and neither the backdrop render (line 2041) nor `.sr-map-backdrop` in globals.css (no media-query gate) is reconciled when the viewport crosses the boundary. Open the Filters overlay on a portrait phone, rotate to landscape (>640px, e.g. 812×375): the sidebar snaps to its in-flow desktop position (static, z-index auto) while the backdrop (absolute, z-index 1100) keeps rendering ON TOP of both the map and the sidebar, dimming and click-blocking the whole panel; the FAB cluster (including the fullscreen toggle) stays unmounted because `!sidebarOpen` is false.
  - *Phone impact:* After a portrait→landscape rotation with Filters open, the entire Map Explorer is veiled dark and inert-looking until the user taps the veil or presses Escape (both do still close it, so it self-recovers in one gesture).
  - *Fix:* Gate the backdrop by the same breakpoint in CSS — add `@media (min-width: 641px) { .sr-map-backdrop { display: none; } }` — so a stale `sidebarOpen` is harmless above the phone boundary (no JS resize listener, per the conventions).

### Weather & Forecast

- **🟠 MED** `frontend/src/App.tsx:777` — The checklist-ID input + 'Get weather' button row is a non-wrapping inline flex (`display:'flex', gap:8`) with the button fixed (`flexShrink:0`, `whiteSpace:'nowrap'`, px padding + fixed 15px icon). The button's label is rem-sized so it grows with in-app text scale, but the row never wraps or stacks, so the input (flex:1, minWidth:0) absorbs all the loss. Being inline styles, no media query can reach it (the exact anti-pattern the responsive conventions call out).
  - *Phone impact:* At 200% in-app text scale the button measures ~210px: on a 390px phone the input shrinks to ~80px, and on a 320px phone to ~13px — effectively unusable for typing/reviewing a checklist URL. No page-scroll leak (input shrinks), but the primary input on the tab is degraded to broken at the mandated 200% scale on small phones.
  - *Fix:* Lift the row to a class per conventions — `.sr-field-row` fits (inline controls that stack ≤480, button becomes full-width below the input); remove the inline display/gap and the nowrap/flexShrink from being load-bearing. Alternatively a small dedicated class that wraps the button under the input when it can't fit.

- **🟠 MED** `frontend/src/components/WeatherForecastPanel.tsx:68` — All form controls on this surface use sub-16px font sizes — `textInput` (place search, lat/lng number inputs, date and time pickers) is 0.84375rem ≈ 13.5px, and the App.tsx checklist input (line 794) is 0.875rem = 14px — while index.html's viewport meta has no zoom handling. iOS Safari auto-zooms the page when focusing any input with computed font-size < 16px.
  - *Phone impact:* On an iPhone, tapping the place search, latitude/longitude, date, time, or checklist-ID input zooms the whole page in; after dismissing the keyboard the user is left zoomed with horizontal panning and must pinch back out — jarring on every single lookup, and it happens on the tab's primary interaction.
  - *Fix:* In the ≤640 media tier, raise form-control font-size to 1rem (16px) via a shared class applied to these inputs (rem-based, consistent with the size-in-rem rule). Do NOT fix it with `maximum-scale=1` in the viewport meta — that disables pinch zoom and regresses accessibility.

- **🟡 LOW** `frontend/src/components/WeatherForecastPanel.tsx:93` — WeatherSummaryView's header row is a non-wrapping inline flex: an emoji span at 2.5rem (two glyphs for night results: condition + moon) beside the 2.1rem temperature block. Both are rem-sized (scale with in-app text scale); the temp token (e.g. '72°F') has no break opportunity and the row has no flex-wrap, and being inline styles no media query can add one.
  - *Phone impact:* At 320px + 200% text scale with a night result: emoji span ≈160px + 14px gap leaves ~34px in the ~208px content box for a ~148px-wide unbreakable temperature — the row overflows the result card by ~110px and extends ~60px past the viewport, leaking horizontal PAGE scroll (the conventions' cardinal sin, and a violation of the must-hold-at-200% rule). Day results at 320px/200% also overflow the content box (~34px) but stay inside the card padding.
  - *Fix:* Lift the header row to a class that allows wrapping (flex + flex-wrap, emoji first, temp block with .sr-min0) so the temperature block drops below the emoji when it can't fit; keep colors/gaps inline per conventions but move display/wrap into the class.

- **🟡 LOW** `frontend/src/App.tsx:729` — The 'Go to Settings →' buttons in both API-key warning banners are text-only buttons with `padding: 0` and 0.75rem text — a tap target roughly 14–16px tall (width helps only ≤480 where .sr-action-row-stack makes them full-width, but the height stays ~15px).
  - *Phone impact:* On touch, the navigate-to-Settings affordance is well under the ~44px target guideline in height; users with the key-not-configured banner (exactly the first-run mobile audience) will mis-tap it, hitting the inert banner instead.
  - *Fix:* Keep the visual text-link style but grow the hit area: add vertical padding (e.g. padding: '10px 0', optionally negative margin to preserve the banner's visual density) — padding is allowed inline per conventions.

- **🟡 LOW** `frontend/src/App.tsx:897` — The dense action buttons on this surface are 30px tall: the weather-output Copy (line 897), tide Copy (line 988), tide-override 'show anyway' (line 970), and the same pattern in WeatherForecastPanel (`copyBtn` line 59 and the override button line 485).
  - *Phone impact:* 30×~60px tap targets are below the ~44px guideline; on a phone the Copy action — the core deliverable of this tab (copy weather/tide into an eBird comment) — is fiddly to hit, especially next to the scrollable <pre> block that captures stray touches.
  - *Fix:* Bump these controls to ≥40–44px height in the ≤640 tier via a small shared class (desktop can keep the 30px density); or simply raise the constant height to 36–40px with padding since nothing depends on 30px.

- **🟡 LOW** `frontend/src/components/WeatherForecastPanel.tsx:504` — The 'Copy-ready block' disclosure is a bare `<summary>` with 0.75rem text and no padding — a ~15px-tall tap target that is the only way to reach the copy-ready output and its Copy button.
  - *Phone impact:* On touch the disclosure toggle is hard to hit; mis-taps land on the result card. Since the copyable block (the feature's main output) is behind it, the whole copy flow is gated on a sub-16px-tall control.
  - *Fix:* Add padding to the <summary> (e.g. padding: '10px 0'; padding may stay inline per conventions) to bring the hit area toward 44px while keeping the compact visual.

### Species Detail

- **🟠 MED** `frontend/src/components/SpeciesDetail.tsx:1377` — The comment body renders raw species-comment text with no wrap class: `<div style={{ fontSize: '0.84375rem', ... }}>{o.speciesComments}</div>`. There is no global overflow-wrap rule in globals.css, and SectionCard (speciesDetail/ui.tsx) has `overflow: hidden`, so a long unbroken token is silently clipped at the card edge. The v0.5.37 sweep added `sr-wrap-anywhere` to the location name one line above (line 1373) but missed the comment body itself.
  - *Phone impact:* On a 320-430px phone (~250-280px card content width), any pasted URL (Macaulay Library asset links, Google Maps links — common in real eBird species comments) or other long unbroken string overflows and is clipped invisibly by the card's overflow:hidden — the tail of the comment is unreadable and unreachable (no scroll).
