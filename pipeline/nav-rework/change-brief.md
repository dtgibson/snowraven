# Change Brief — Nav Rework

## What is changing

The app's main navigation, and only the navigation. Eleven destinations (ten data tabs plus Settings) need about 1,409px of horizontal strip, and the strip is swapped for a single dropdown the moment it would overflow — measured at roughly 1,457px with today's labels, which is why the website capture tooling had to be pushed to a 1,600px viewport to photograph a strip at all. An unmaximised laptop window, an iPad, a half-screen Mac window and every phone therefore get the dropdown, and the swap is all-or-nothing: eleven items or none. This replaces that one strip with a single responsive navigation over the same eleven destinations at three densities — a vertical sidebar on wide windows, an icon-only rail when width is tight, and a bottom bar of the first four destinations plus a More sheet at phone widths. Density is derived from available width in the same measured spirit as today's collapse, never from a fixed device check.

The user's saved order stays authoritative and flat: the sidebar renders it top to bottom with Settings last, exactly as the strip and dropdown do now, and any visual grouping is separation only, never a re-ordering. The phone bar's four favourites are the first four of that same saved visible order, so the existing reorder-and-hide setting already chooses them and nothing new is stored. Where the global sidebar and the Map Explorer's own 240–300px sidebar would both be expanded, the global nav drops to the icon rail — that is the width trade-off, resolved by density rather than by a preference. A collapse toggle, if the design keeps one, lives for the session; if it must survive a relaunch it joins the existing tab-layout document through its existing normalizer, never a new document.

**Out of scope, deliberately: the Cmd-K command palette.** A palette is a modal overlay with a text input that exists nowhere in the app today, driven by a global keyboard shortcut the app has never had — a capability a user can invoke that they could not before, on the New Feature side of the line — and its central question (navigate the eleven destinations only, or search species, checklists and actions?) is exactly what a PRD settles. It is a separate New Feature build, not dropped.

## Why now

Eleven destinations outgrew the horizontal strip. The collapse threshold sits above most real window widths, so the dropdown is the common case rather than the narrow-screen case it was designed as, and in the dropdown all eleven destinations are one scrolling list — genuinely scrolling on short and landscape viewports, where the menu is capped to the visible height. The interim options in the idea (an icon-only rung, or a More overflow on the existing strip) were considered and rejected as this run's answer: each is a stopgap inside the same horizontal model that the destination then has to undo, and the icon rail already delivers the icon-only density as one of the three tiers.

## User-facing impact

Substantial and intended — this is a visible change to the first thing every user touches, on macOS, Windows, iPhone, iPad, web and Pi. Wide windows (macOS, Windows, web, Pi, iPad landscape) gain a vertical sidebar and get back the vertical space the strip costs on every tab. The middle band — iPad portrait, small laptop windows, half-screen desktop windows — gets the icon rail instead of today's dropdown. Phone widths (iPhone, and any browser at or below 640px on any platform) get the bottom bar plus More sheet in place of the dropdown; the home-indicator inset applies on iOS only. Every destination stays reachable everywhere, and no destination is added, removed, renamed or hidden by default.

Three published surfaces state today's behaviour and must change in the same run: the Help documentation's description of the strip collapsing into a dropdown, the accessibility statement's keyboard-navigation paragraph (which names the main tab bar and its collapsed dropdown as the two roving-focus exceptions), and the README plus website. The website screenshots are captured at 1,600px specifically to clear the collapse threshold, so the capture tooling's justification and the shots themselves need revisiting. Nothing about data, privacy, network or providers changes.

## Scope

**Changes:** `frontend/src/components/TabNav.tsx` (and any new nav components beside it — new files are fine, they carry existing behaviour); `frontend/src/App.tsx` (the shell that hosts the nav, its inert wrapper, header composition); `frontend/src/globals.css` (nav classes and responsive tiers — layout in classes, never inline styles); `frontend/src/lib/mapPanelChrome.ts` (the measured chrome budget above the map panel no longer includes a tab strip at wide widths); `frontend/src/components/TabNav.test.tsx` plus new nav tests; the roving-group rows in `frontend/src/lib/tabOrderCoverage.test.ts`, whose file, attribute text and count must match the new markup; `docs/HELP.md`, `ACCESSIBILITY.md`, `README.md`, `website/` and its capture tooling; `frontend/src/lib/tabLayout.ts` only if a density field proves necessary; `CHANGELOG.md` and the version stamps at release.

**Does not change:** the destinations themselves — ids, labels (`TAB_LABELS` stays authoritative; `life-list` remains **Multimedia**) and the default order; the persisted tab-layout document's shape and key, and its storage path (the seam on desktop, localStorage on web and Pi) — the reorder-and-hide setting is reused, not replaced or migrated; the Settings reorder UI's behaviour, beyond copy if the phone favourites need explaining; which tab is active at launch, and the absence of URL routing or deep links in the app, so there is no routing behaviour to alter; the mounted-tab model, where tabs are hidden rather than unmounted and eight stay mounted; every tab's own content and data paths; the Map Explorer's own sidebar, its width clamp and its fullscreen overlay; the page as the scrollport, which the two sticky pinned-label bands depend on; the colour palette (existing `var(--sr-*)` tokens; any new token defined in both themes); and the backend, caches, network, providers and privacy posture — no new dependency, and the nav stays entry-chunk-light.

## Design pass

**Needed.** This is wholly a visual and interaction refinement of an existing surface. The Designer shapes: the sidebar at full density (width, visual grouping that does not fight the user's saved order, active state, where the brand header and the Settings row sit), the icon-only rail and how a destination is identified without its label, the phone bottom bar and its More sheet, and the width thresholds between the three. Constraints that hold throughout: colours from existing tokens in both themes, layout lifted to classes rather than inline styles, WCAG 2.1 AA at 320px and 200% in-app text scale, and every new button carrying an explicit place in the tab order because WebKit skips plain buttons on the shipped Mac, iPhone and iPad apps.

## Decisions touched

- **Responsive navigation: dropdown over bottom bar, overflow-driven collapse (2026-05-27) — partly REVERSED.** Its bottom-bar rejection rested on a bottom bar topping out at about five destinations when the app had eight; four favourites plus a More sheet is the mitigation that decision did not consider, and the destination count has since grown to eleven. Its second half — collapse by measured overflow, never a fixed breakpoint — is kept and extended to the new density tiers. The note that a future mobile app should inherit the dropdown is superseded.
- **Tab layout in localStorage, not server-side (2026-05-24)** and the **desktop tab-layout relaunch post-mortem (v0.3.30)** — touched, not reversed: same document, same key, same seam, reused as-is.
- **The measured Map Explorer chrome budget** — touched. The module measures rather than assumes, so it adapts, but its targets and its written reasoning both name a tab strip above the map.
- **The v0.5.77 capture-width note** — the 1,600px website capture width is load-bearing against the collapse threshold; that justification changes meaning when the strip goes away and needs rewriting rather than deleting.
- **The WebKit tab-order property (v1.0.16)** — not reversed and must be preserved: every button and link the app draws carries a literal tab-order entry apart from declared roving groups, and the guard's exception rows are bound to exact markup and counts.
- Two standing checks apply directly: an off-screen measurement node must sit under a clipped ancestor or it leaks horizontal page scroll on phones, and a `display: contents` wrapper has no box, so it can never be the thing a resize observer watches.

## What done looks like

Every one of the eleven destinations is reachable, identifiable and keyboard-operable at wide, medium and phone widths on all six platforms, with the user's saved order and hidden tabs honoured in all three densities and nothing stored that was not stored before. The all-or-nothing dropdown is gone, no window width leaves the navigation overflowing or unusable, and the Map Explorer keeps a usable map where both sidebars would otherwise compete. Help, the accessibility statement, the README and the website describe what the app now does, and the tab-order guard, the entry-chunk guard and the full suite are green.
