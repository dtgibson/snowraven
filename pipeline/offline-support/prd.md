# PRD — Offline Support
**Feature:** offline-support
**Date:** 2026-06-20
**Stage:** 2 — The Planner
**Source:** strategic-brief.md (approved)

## Feature Overview

Make SnowRaven a trustworthy field tool with no network: persist the vector map style **and bundle its glyphs/sprite** so maps mount and draw the user's local data layers on a cold offline start; let a user download a map region ahead of time and pan/zoom it offline with real street/terrain/label detail; resolve favicons and taxonomic sort offline (including a true first-ever run); replay previously-loaded weather/tide/checklist results across relaunch; and present honest "you're offline" messaging — distinct from "no API key" and from a server error — in both the desktop (Tauri) and web/self-hosted (Pi) runtimes.

## User Stories

- **US-01** — As a birder in a no-signal field location, I want every analytical tab and every map to open and show my own sightings, heatmap, and atlas, so that the app is usable the moment I open it offline.
- **US-02** — As a birder planning a trip, I want to download the map region I'm visiting while I still have wifi, so that I can pan and zoom that area with real street/terrain/label detail when I'm offline in the field.
- **US-03** — As a birder managing limited device storage, I want to see what regions I've downloaded and how much space they use, and remove ones I no longer need, so that I stay in control of disk usage.
- **US-04** — As a birder who opens the app for the first time on a flaky connection, I want bird names to sort taxonomically and show favicons without depending on a fresh eBird taxonomy fetch, so that even the very first offline run never falls back to A–Z plain-text names with no favicons.
- **US-05** — As a birder who looked at a checklist's weather, tide, or details earlier today, I want that same information to re-show when I reopen it offline, so that I don't lose what I already loaded just because the network dropped.
- **US-06** — As a birder offline, I want a clear, honest message that I'm offline (distinct from "no API key configured" and from a generic server error) whenever a live feature can't run, so that nothing looks broken and I know it will work again when I reconnect.
- **US-07** — As a self-hosted (Pi) user, I want favicons and taxonomic sort to keep working after I restart the backend without re-fetching from eBird, so that a server restart doesn't degrade the app.

## Functional Requirements

### Offline map foundation (Tier A — ships regardless of basemap mechanism)

- **FR-01** — The app shall persist, via the storage seam, the fetched-and-tuned vector map style JSON the first time it is successfully obtained, keyed by vector variant (today `positron`; the key tracks whatever base mechanism OQ-01 resolves to), so that the style survives an app relaunch. *(Verified: `fetchTunedBaseStyle` currently returns the tuned style but never persists it; `SnowMap`'s `cache` is in-memory only.)*
- **FR-02** — On first map mount in a session, the app shall attempt the storage-seam read of the persisted style and use its result **before** issuing any network style fetch; the network fetch shall be issued only if the storage read resolves empty (sequential, not in parallel — a parallel fetch defeats the offline goal). The seed is necessarily async, so a brief one-tick "Loading map…" state on first open is acceptable; the read shall run in `SnowMap`'s existing style `useEffect` ahead of `getVectorStyle`.
- **FR-03** — When a persisted style (plus bundled glyphs/sprite per FR-10) exists, the app shall mount `<MapGL>` and render all local-data child layers (sighting pins, heatmap, atlas blocks) **and** the vector base's labels and symbols with no network, so that the user's own data and a labelled base both draw offline. *(Note the scope boundary: a persisted style alone gives a mounted map whose vector TILES still come from the network; full street/terrain detail offline requires a downloaded region (Tier B). Tier A guarantees: the map mounts, local data layers draw, and labels/symbols render from bundled glyphs/sprite — not that base street tiles are present everywhere offline.)*
- **FR-04** — When no persisted style exists AND the network fetch fails (genuine cold-cache offline), the app shall show the existing "Map couldn't load" placeholder with a working Retry control, and shall not crash the app or any tab that hosts a map.
- **FR-05** — After a persisted style is loaded offline, the app shall, on the next map mount once connectivity is available, attempt a fresh online style fetch and replace the persisted copy on success, so that style tuning updates eventually propagate without blocking offline use. The persisted style itself carries **no freshness bound** (it is intentionally unbounded — base-style tuning changes rarely and a year-old style is still a usable base); only downloaded regions (FR-18) and taxonomy (FR-25) have freshness handling.
- **FR-06** — The style fetch shall remain a direct client-side fetch (the same posture as MapLibre's own tile fetches, which already bypass the transport seam in both runtimes); only the RESULT is persisted, through the storage seam. The seed-from-storage and persist paths shall behave identically in Tauri and web/Pi. On web/Pi, persistence and seeding require the local backend to be reachable (the storage seam is backend-served) — see FR-39a for the backend-down case.
- **FR-07** — Switching the base layer while offline shall keep the vector base mounted and shall not blank or crash the map. Because no durable raster tile cache exists (no service worker / tile store; MapLibre's in-memory tile cache is per-session and empty after relaunch), an offline switch to a raster base (Satellite / Topo / Trails) would render entirely blank tiles. Therefore: while offline, the raster base controls shall be disabled/greyed with the honest offline cue (consistent with FR-34/FR-37) rather than allowing a switch to a guaranteed-blank base. Switching between the persisted-style vector base and a downloaded-region vector base (and back) while offline, and entering/leaving region coverage mid-pan, shall keep the map mounted and shall not crash (see FR-17).
- **FR-08** — A `data-theme` (light/dark) change while offline shall re-bake the token-derived GL sprites (atlas hatches, pin sprites) from `--sr-*` CSS vars with no network fetch (the existing `MutationObserver` path). The vector base's land-cover tints are currently theme-independent fetch-time literals (`TINT_*` constants, identical for both themes) and are NOT re-tinted on theme change; this FR does NOT add offline vector-base re-tinting. (Making the vector base tints theme-dependent is out of scope — see Out of Scope.)
- **FR-09** — Persisting and seeding the style shall introduce no auto-firing network call on app load; the first online style fetch shall remain the existing lazy/idle-warmed, map-mount-triggered path, so that the no-auto-network-on-startup invariant holds.

### Offline basemap download & management (Tier B)

- **FR-10** — The app shall bundle the vector base's glyphs (font PBFs) and sprite sheet in-app as on-demand data assets, and shall rewrite the persisted style's `glyphs` and `sprite` URLs to point at the local bundled assets, so that the offline vector base renders labels and symbols with no network fetch to the tile provider. *(Verified gap: the OpenFreeMap style JSON references absolute `glyphs`/`sprite` URLs at `tiles.openfreemap.org`; `fetchTunedBaseStyle` rewrites neither, so without this the offline base is label-less and symbol-less even with FR-01 done.)*
- **FR-11** — The app shall let the user download a map region ahead of time (always user-initiated), and after a completed download shall let the user pan and zoom that region fully offline with real street, terrain, and label detail (not a blank/abstract base).
- **FR-11a** — All offline map tile downloading shall be gated behind an explicit Settings toggle ("Enable offline maps"), **default OFF**, persisted via the storage seam in both runtimes. With the toggle off, no map tile bytes shall be fetched or stored for offline use, the region-download UI is hidden/disabled with a cue pointing to the Settings toggle, and the app performs no automatic or background tile downloading. Turning the toggle off does not delete already-downloaded regions — it stops new downloads; existing regions remain usable and removable in the manager. This gate applies to **Tier B region tile downloads only**; it does NOT gate Tier A map-style persistence (FR-01) or the result-replay cache (FR-28..FR-34), which persist only already-fetched data (no tiles) and provide offline resilience with no bulk tile fetch.
- **FR-12** — Downloaded region tile data shall be stored locally durably so that a downloaded region survives an app relaunch. On desktop this uses a durable on-disk store (e.g. `tauri-plugin-fs` writing the region file under `AppLocalData/data/`, a path-based store separate from the typed two-slot `writeFile` adapter and from `settings.json`). The bundled glyphs/sprite from FR-10 are reused (not re-downloaded per region).
- **FR-13** — The app shall provide a UI surface to view all downloaded regions, listing for each region a human-readable name/extent and its on-disk size, plus a displayed total used by region downloads, so that the user can see what is downloaded.
- **FR-14** — The app shall let the user remove a downloaded region; removal shall reclaim that region's local storage and update the displayed total, so that the user can manage disk usage.
- **FR-15** — While a region download is in progress, the app shall show progress (at minimum a percentage or determinate-where-known indicator) and shall let the user cancel it. On cancel, no further tile requests shall be issued and the in-progress region shall be removed.
- **FR-16** — An interrupted, cancelled, or failed download (network drop, app close, error) shall be **cleanly discarded** (resume is out of scope for v1 — see OQ-06): a partial region shall never be listed as complete/available in the manager, never render as corrupt, and shall not block re-downloading the same region. (If the Architect chooses to support resume, that decision is recorded in OQ-06; absent that, discard is the committed behavior.)
- **FR-17** — When the user is inside the geographic extent and within the baked zoom range of a completed downloaded region while offline, the map shall serve that region's detail. Outside any downloaded region, OR above the region's baked max zoom (OQ-04), OR inside a region's extent but at a location the bake doesn't cover, the map shall fall back to the persisted-style behavior (Tier A) without crashing — local data layers still draw on whatever base is available, and over-max-zoom shows the region's content at its deepest baked zoom (over-zoomed) rather than blanking.
- **FR-18** — When storage lacks room to complete a download, the app shall fail the download gracefully with an honest "not enough storage" message and shall not partially corrupt existing downloaded regions, the replay store, or other app data (CSV/settings). Region-write storage and replay-store storage are **independent budgets**: a region write shall never evict or corrupt the replay store, the eBird/ML CSVs, or `settings.json`.
- **FR-19** — An expired or stale downloaded region (per the freshness policy in OQ-05) shall remain usable offline and shall be flagged as out-of-date in the management UI rather than silently deleted, so the user is never left with no offline base in the field; refresh is user-initiated and never automatic.
- **FR-20** — Region downloads are **desktop-first for v1**. The web/self-hosted (Pi) runtime cannot durably persist multi-hundred-MB region assets through any existing seam (the only blob path is the typed two-slot `writeFile`, capped at 50 MB on the backend; browser OPFS/IndexedDB quota for GB-scale regions is unreliable). On web/Pi the UI shall state this limitation honestly and shall not offer a region-download control that won't persist. (All OTHER offline UI — Tier A style persistence, taxonomy, replay, offline messaging — is dual-runtime per FR-40.)

### Taxonomy offline

- **FR-21** — The app shall ship a **bundled eBird taxonomy snapshot** as an on-demand data asset (like `ca-atlas-blocks.json` / `noaa-tide-stations.json`), carrying the full `byCode` map (all categories), name→code maps, order/sort data, and the `reportAs` sub-form map. This is a **committed dependency**, not optional: it is the only mechanism by which FR-22's first-ever-cold-start guarantee is satisfiable on both runtimes.
- **FR-22** — On a first-ever cold start with no network and no prior eBird taxonomy fetch, the app shall resolve favicons, taxonomic sort, and sub-form (`reportAs`) normalization for the user's species from the bundled snapshot (FR-21), so the first offline run never falls back to A–Z plain names with no favicons — in both Tauri and web/Pi.
- **FR-23** — On the desktop runtime, favicons and taxonomic sort shall continue to resolve offline from the persisted IndexedDB taxonomy across an app relaunch with no network, for the lifetime of the persisted copy (existing 7-day-TTL behavior), with the bundled snapshot as the floor when the cache is empty/expired.
- **FR-24** — On the web/self-hosted (Pi) runtime, the backend shall persist taxonomy across a process restart: it shall load the bundled snapshot at startup so `_ensure_loaded` returns populated maps with no eBird call, and (when an online fetch has succeeded) shall persist the fetched taxonomy to disk under `data/` and reload it on the next start, so a backend restart never blanks favicons/sort nor triggers a live eBird re-fetch to recover. *(Verified gap: `backend/routers/taxonomy.py` is process module-dicts only — `_loaded` flag, `_report_as`, etc. — with no disk persistence and no bundled snapshot; it re-fetches `ref/taxonomy/ebird` after every restart.)* This is a backend-internal cache plus a bundled asset; it needs no new transport route (so the dual-transport-route parity rule does not apply here).
- **FR-25** — The bundled taxonomy snapshot shall carry a versioned cache key and shall be superseded by a fresher successful online taxonomy fetch in both runtimes, so the annual Clements/eBird revision is picked up once online and the app is never silently pinned to a stale snapshot.
- **FR-26** — When taxonomy is genuinely unavailable (no bundled snapshot loadable, no persisted copy, no network — a degraded/edge state), consumers shall continue to degrade gracefully to plain names / A–Z sort (preserving today's try/catch contract) rather than erroring.
- **FR-27** — Taxonomy resolution shall remain a single coalesced, memoized load shared by all concurrent first-callers (no per-component refetch of the ~17k-entry taxonomy) in both runtimes, so offline-readiness does not multiply work or memory.

### Result replay (previously-loaded live results)

- **FR-28** — A weather block for a checklist that was successfully loaded online at least once shall re-show its last successful result when reopened offline, instead of re-failing.
- **FR-29** — A tide reading for a checklist/location that was successfully loaded online at least once shall re-show its last successful NOAA reading when reopened offline; the already-offline parts (nearest-station selection and too-far / outside-US classification from the bundled `noaa-tide-stations.json`, via haversine + US bounding boxes) shall continue to work with no network regardless of replay.
- **FR-30** — A checklist detail result that was successfully loaded online at least once shall re-show offline when reopened, instead of re-failing.
- **FR-31** — A replayed result shall be visibly marked as previously-loaded / possibly-stale (e.g. an "offline — showing the last loaded result" cue with the time it was loaded), so the user is never misled into thinking it is a fresh live reading.
- **FR-32** — Replayed results shall persist across an app relaunch via the storage seam (NOT the existing 90-second in-memory `networkCache`, which is per-session and must remain unchanged for its live-coalescing role). The replay store shall key each entry by the same derivation `networkCache` uses — path + sorted params, with `lat`/`lng` rounded to 5 decimals and comma-lists sorted (`networkCacheKey`) — so weather/tide/checklist-detail key by checklist id and the `…-at` variants key by rounded lat/lng/dt, and FR-34's "same key" is well-defined.
- **FR-33** — The replay store shall be bounded by an explicit entry cap AND byte cap (OQ-07); eviction shall be strictly oldest-loaded-first, and the most-recently-loaded entry shall always survive eviction so a just-loaded result is replayable on the next offline open.
- **FR-34** — A failed live fetch shall never overwrite or clear a previously-successful replay entry for the same key (errors are not cached — preserving the established never-cache-failures contract).

### Offline messaging & state

- **FR-35** — The app shall classify a live-feature failure into one of three distinct, non-collapsing states and surface the matching message wherever a live-only feature is invoked (weather, tide reading, Nominatim geocode/address search, Checklist Comparer, live nearby-bird overlays, update check): (a) **offline / connection-level failure** → an honest "you're offline" message; (b) **no API key configured** → the no-key message; (c) **server returned an error** (HTTP non-OK / 5xx / 4xx that isn't a missing-key) → a generic error message. The three must produce three different user-visible treatments.
- **FR-36** — Offline detection shall be conservative and failure-driven: a feature shall attempt its live path and classify a **connection-level rejection** (fetch `TypeError` / `tauriFetch` network error — no HTTP status) as "offline"; an **HTTP non-OK status** as a server error (or no-key, where the status/body indicates a missing key). Any pre-flight online/offline hint (e.g. `navigator.onLine`) is advisory for UI only and shall NOT hard-gate a request from being attempted when connectivity actually exists.
- **FR-37** — When a live feature is unavailable because the user is offline AND a replayed result exists (per FR-28..FR-30), the app shall prefer showing the replayed result with the staleness cue over showing only an offline error.
- **FR-38** — When a live feature is unavailable because the user is offline AND no replayed result exists, the app shall show the honest offline message in place of the feature, and shall not render a broken/empty control that looks like a bug. The no-replay surfaces — geocode/address search, Checklist Comparer, live nearby-bird overlays — have no replay path, so they always show the offline message when offline; an offline geocode in particular must read "you're offline", NOT "no matches" (the two are distinct, user-distinguishable states).
- **FR-39** — The update check shall distinguish three outcomes and never conflate them: (a) a **connection-level failure** (offline) → "couldn't reach the update server — you're offline"; (b) a **reachable-but-error** response → a generic update-check error; (c) **up to date**. The existing code reports **up_to_date = true on a GitHub 404** (verified at `versionService.ts` and `backend/routers/version.py`, where a 404 means "no release found"); this branch is the specific false-positive to fix — a 404 / no-release / unreachable response must NEVER be reported as "up to date". A connection-level failure already throws status 503 today; the offline message shall be derived by distinguishing that 503-class network rejection from an HTTP non-OK status.
- **FR-39a** — **(web/Pi only) Backend-unreachable is a distinct state from device-offline.** On web/Pi the storage seam, settings, persisted style, and replay all go through the local FastAPI backend; if that backend process is down while the device has connectivity, the user is not "offline" in any meaningful sense. The app shall, where it can distinguish them, message a dead local backend as "the local server isn't running" rather than "you're offline", and shall not claim the persisted-style/replay survive a backend-down state on Pi (FR-06/FR-32 persistence on web/Pi depends on the backend being reachable). On desktop (Tauri) there is no backend process, so this state does not apply.
- **FR-40** — Offline state and all new offline UI (staleness cues, offline/no-key/error messages, the update-check message) shall behave identically in the desktop and web/Pi runtimes. The only runtime-conditional difference is region download (desktop-first per FR-20) and the web/Pi backend-down state (FR-39a), both of which are surfaced honestly in the UI rather than failing silently.

### Settings-store foundation (new dual-transport capability)

- **FR-41** — The app shall add a **generic key/value settings store** so the storage seam can durably persist arbitrary keys (the persisted style, the replay index/entries, and any new UI settings) in both runtimes. On web/Pi this requires a new backend route family — `GET/POST/DELETE /settings/{key}` — writing to a JSON store under `data/` (mirroring `mapdefaults.py`), registered in `main.py`, with `/settings` already in the Vite proxy. *(Verified blocking gap: no generic `/settings/{key}` route exists today — only `/settings/keys`, `/settings/keys/{key_name}`, `/settings/map-defaults`, `/settings/files*`. `WebStorage.getSetting/setSetting` already call `/settings/{key}`, so today every generic-key write on web/Pi 404s and is silently swallowed by `.catch(()=>{})`. Tier-A style persistence, replay, and existing settings (`map-base-layer`, `tab-layout`, etc.) on web/Pi cannot work until this route exists.)*
- **FR-42** — The persisted style blob (and the replay store) shall be stored as their **own files/keys**, not merged into the single shared `settings.json`, to avoid a read-modify-write race or partial-write corrupting unrelated scalar settings (both `TauriStorage` and the backend do whole-file read-merge-write). The style blob is far larger than the scalar settings persisted today; isolating it bounds the blast radius of a bad write and the size of each whole-file rewrite.

### Privacy & documentation

- **FR-43** — The published `PRIVACY_POLICY.md` shall be updated in the same change to disclose: the basemap source change (whichever source OQ-01 selects), that ahead-of-time region downloads fetch tiles browser→provider (exposing IP + the chosen region's extent at download time), and that downloaded tiles plus the bundled glyphs/sprite are then stored locally and served with no further network calls. The style fetch remaining a direct browser→provider fetch (FR-06) shall be reflected in the Map Tiles disclosure.
- **FR-44** — The `Map Tiles` disclosure shall enumerate every tile/style/glyph/sprite host actually contacted by the code (the hosts in `lib/mapStyle.ts` plus any new own-hosted GitHub Releases/Pages surface from OQ-01), so the privacy statement stays a complete and accurate list. OQ-01's outcome materially changes this list and the `positron`-variant assumption in FR-01/FR-05.
- **FR-45** — `docs/HELP.md` (in-app help), `README.md`, and the `website/` showcase shall be updated in the same change to describe offline support: what works offline, how to download/manage a region (desktop), the staleness/offline cues, and the honest limits (which features stay online-only; region download desktop-only). `ACCESSIBILITY.md` shall be updated if any new offline UI changes the accessibility surface.
- **FR-46** — The version shall be bumped in **both** `frontend/package.json` and `src-tauri/tauri.conf.json` to the same value, and `CHANGELOG.md` shall be updated, as part of shipping this feature.

## Non-Functional Requirements

### Performance
- **NFR-01** — Seeding the persisted style from storage shall not regress first paint of non-map tabs; map work shall remain lazy/idle-warmed and off the initial render path. No synchronous storage read shall run on app boot for users who never open a map in a session. Budget: first contentful paint of the Statistics tab (cold boot, no map opened in session) stays within +30 ms of the pre-feature baseline (median of 5 runs, baseline = the commit immediately before this feature).
- **NFR-02** — Reading the persisted style and the replay store from the storage seam shall be coalesced and memoized so repeated consumers/maps in one session trigger exactly one disk read per key (matching the taxonomy coalescing in FR-27).
- **NFR-03** — A completed region download shall pan/zoom at >= 30 fps (frame time <= 33 ms p95 over a 5 s scripted pan) offline with zero tile network requests while inside the downloaded region.
- **NFR-04** — Region download and large storage reads/writes (style blob, region file, replay store) shall not block the UI thread; long operations run off the main thread or in chunks, and a scripted UI interaction (tab switch / button click) during the operation completes within 100 ms with main-thread long tasks (>50 ms) staying at/near zero.

### Compatibility
- **NFR-05** — Dual-transport parity: any new backend-served capability (the generic `/settings/{key}` store of FR-41) shall have a TypeScript service twin / storage-seam path (Tauri), a FastAPI route (web/Pi), AND its path prefix in `frontend/vite.config.ts` (`/settings` is already proxied). Backend-internal caches that need no new route (the taxonomy persistence of FR-24) are exempt from the new-route parity check but must still work in both runtimes. No capability may work in only one runtime by accident (except the explicitly desktop-first region download, FR-20).
- **NFR-06** — No new use of `localStorage` for anything that must survive a relaunch; all persisted offline state goes through the storage seam (TauriStorage `AppLocalData/data/` on desktop, the new `/settings/{key}`-backed WebStorage on web/Pi). Every TauriStorage write continues to `mkdir(DATA_DIR, { recursive: true })` first.
- **NFR-07** — Platform branching shall go through `isTauri()` only; no new direct `window.__TAURI_INTERNALS__` checks.
- **NFR-08** — Any new offline-base map-image/source code shall follow the established contract: register images unconditionally (not gated on `isStyleLoaded()`); keep a `styleimagemissing` net acting only on the component's own hardcoded image ids; key any `<Source>` whose id differs by branch so React remounts it; register the pmtiles (or chosen) protocol via `maplibre.addProtocol` inside the lazy map module, never in `App.tsx`'s static graph.

### Accessibility
- **NFR-09** — All new UI (region download manager, region list/remove, progress + cancel, offline/no-key/error messages, staleness cues, disabled raster-base cue) shall meet WCAG 2.1 AA: every control has an accessible name; status/error states use `role="status"`/`role="alert"` appropriately; offline state is conveyed by more than color; contrast is fixed at the token in both light and dark themes.
- **NFR-10** — New layout shall be responsive from ~320 px to large desktop using the established class vocabulary (no inline `display`/grid a media query can't reach), and hold at 200% in-app text scale with no horizontal page-scroll leak.
- **NFR-11** — Any new external link (provider attribution, "learn more about offline maps") goes through the shared `OutboundLink` / `ChecklistLink` / `HotspotLink` components, not a hand-rolled `<a target="_blank">`.

### Security & Privacy
- **NFR-12** — Any region id/extent or provider URL interpolated into a request or link shall be shape-validated and `encodeURIComponent`-wrapped (no raw user/external value into an href or fetch URL without validation), consistent with the app's id-guard posture; a malformed value renders plain / is rejected, never a raw injected URL.
- **NFR-13** — The privacy-first promise holds: this feature adds no analytics, telemetry, crash reporting, account, or new always-on third-party service. The only new network egress is user-initiated region downloads (plus the existing lazy style fetch and the new own-hosted style/glyph source if OQ-01 selects one), all of which are disclosed (FR-43/FR-44). The `website/` remains free of third-party requests.
- **NFR-14** — Stored offline data is the user's own derived/cached data on their device; no offline state is transmitted anywhere.

### Bundle-size
- **NFR-15** — MapLibre stays OFF the entry chunk (lazy + idle-warmed). No component reachable from `App.tsx`'s static import graph may statically import the offline-map / region-download / pmtiles machinery in a way that drags `vendor-maplibre` (or a large tile/pmtiles library) onto first paint. A fresh `npm run build` must still show `vendor-maplibre` absent from `dist/index.html`'s modulepreload. The pmtiles protocol registration and bundled glyph/sprite assets load only inside the lazy map chunk; re-confirm `chunkSizeWarningLimit` (currently 1100) still passes for the enlarged lazy map chunk.
- **NFR-16** — The bundled taxonomy snapshot (FR-21) and the bundled glyphs/sprite (FR-10) shall be on-demand data assets (like the atlas/tide assets), not statically imported into the entry chunk; their installed-size impact shall be stated and kept within budget (taxonomy target <= a few MB compressed; glyphs/sprite kept small).

## Out of Scope

- Offline satellite, topo (USGS), and trails (Waymarked) bases — provider terms forbid bulk pre-download and raster is too heavy; these stay online-only and, since no durable raster cache exists, the raster base controls are disabled offline (FR-07) rather than degrading to a blank tile.
- Making fundamentally-live features actually work offline: live weather (OpenWeather One Call), live tide readings (NOAA CO-OPS), geocoding (Nominatim), Checklist Comparer, live nearby-bird eBird overlays, and the in-app updater download/install. Offline behavior is limited to replaying a prior result (where one exists) plus honest messaging.
- Automatic or background tile downloading — region downloads are always explicitly user-initiated.
- **Resuming** an interrupted region download (v1 cleanly discards partials per FR-16; the Architect may add resume via OQ-06).
- **Region downloads on web/Pi** for v1 (desktop-first per FR-20).
- Theme-dependent re-tinting of the vector base offline (the `TINT_*` tints are theme-independent fetch-time literals; FR-08 covers only the token-derived GL sprites).
- A general-purpose service worker / PWA / full-app offline shell — none exists today; this feature introduces only the specific persisted-style + bundled-glyph/sprite + region-download + replay + generic-settings stores described.
- Bulk offline tiles from any third-party provider whose ToS forbids bulk download — only an own-hosted/licensed source is permitted as the offline base.
- Offline geocoded address search and offline live nearby-bird targets (depend on live third-party APIs; offline shows the honest message only).

## Open Questions

- **OQ-01 — Basemap mechanism** — Which offline vector-base mechanism does the Architect adopt? *Default if unanswered:* self-hosted PMTiles vector base on GitHub Releases (download-whole-file for offline; online HTTP-Range streaming as a bonus), glyphs+sprite bundled in-app (FR-10). Hard constraint regardless of choice: bulk offline tiles come from a source we are licensed to bulk-download (our own), never a third-party provider whose ToS forbids it. **This outcome materially changes FR-01's variant key, FR-05's "fresh online style fetch", and the FR-44 Map Tiles list — resolve before finalizing those specifics.**
- **OQ-02 — Region granularity** — County-level, whole-state, or zoom-capped? *Default:* **county-level chunks** (each typically tens of MB at the OQ-04 max zoom), with **whole-state as a coarser option** for users who want broad coverage; both under GitHub's ~2 GB per-asset limit. County granularity lets a user store only the counties they bird and maps onto how birders already organize geography (eBird county lists) and the county carried per sighting in their loaded data (see OQ-10). The Architect sizes against a real test extract; max zoom (OQ-04) remains the dominant size lever, composing with the chunk choice.
- **OQ-03 — Online streaming vs download-only** — Support online HTTP-Range streaming of the own-hosted base (bonus), or download-only for v1? *Default:* download-only is the required deliverable; range-streaming is a nice-to-have the Architect may include if it adds no first-paint or privacy cost.
- **OQ-04 — Max zoom for downloaded regions** — Maximum zoom baked into a region (drives file size vs. street detail and FR-17's over-max-zoom fallback)? *Default:* ~z14 (readable street + label detail for field use), chosen to keep per-region size within OQ-02's budget.
- **OQ-05 — Region freshness policy** — How long before a downloaded region is flagged stale, and any auto-refresh? *Default:* flag out-of-date after a generous fixed interval (single concrete number, e.g. 9 months) but never auto-delete and never auto-download (FR-19); refresh is user-initiated. The threshold must be a single constant and injectable for tests (reuse the codebase's session-now seam so QA can cross it deterministically).
- **OQ-06 — Interrupted-download: discard vs resume** — Is resume in v1, or clean-discard only? *Default:* clean-discard only (FR-16); resume is out of scope. If the Architect adds resume, fix the QA branch to the resumable outcome.
- **OQ-07 — Replay store budget & eviction** — Exact entry cap AND byte cap, and eviction policy? *Default:* a single concrete entry cap (e.g. 500) AND a byte cap (e.g. 4 MB), whichever is hit first, with strict oldest-loaded-first eviction; the most-recently-loaded entry always survives (FR-33). Threshold injectable for deterministic eviction tests.
- **OQ-08 — GitHub surface for hosting** — GitHub Releases (<=2 GB/asset, Range-capable CDN) vs GitHub Pages (<=100 MB/file)? *Default:* GitHub Releases, to allow per-state assets above 100 MB and to honor Range for the streaming bonus.
- **OQ-09 — Local PMTiles handoff per runtime** — How is the downloaded region file handed to MapLibre on desktop (a local file path via `convertFileSrc` / the asset protocol, or a blob), and is this reconciled with the addProtocol registration (NFR-08)? *Default:* desktop reads the region file from `AppLocalData/data/` and serves it to the pmtiles protocol via a local-file/asset-protocol URL; web/Pi region download is out of scope (FR-20), so no web handoff is needed for v1. Architect confirms.
- **OQ-10 — Region selection UX** — How does the user pick a region? *Default:* a curated list of named own-hosted regions, **surfacing first the counties where the user already has sightings** (derived from the county already present in their loaded data, per the Life List county backfill) so the common case is one tap; whole-state regions available as a coarser pick. A free-form draw-a-box / current-viewport gesture is out of scope for v1 unless the chosen mechanism makes it trivial.
