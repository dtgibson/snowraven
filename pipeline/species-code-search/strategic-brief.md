# Strategic Brief: Species Code Search

## What We're Building

Search (Cmd-K / Ctrl-K) and the shared type-to-find species picker also match a bird's four-letter code, so typing `yrwa` finds Yellow-rumped Warbler the way eBird Mobile users already type. A query that is exactly one of a bird's codes returns every bird in the user's backup that carries that code, and those rows lead the list ahead of ordinary name matches.

## Why Now

This is a direct request, not a roadmap item. Code-typing is a reflex for anyone who enters checklists on eBird Mobile, and today every species-finding surface in SnowRaven answers `amro` or `gbhe` with nothing. The change is unusually cheap to land everywhere at once: Search and all four species pickers already go through one matcher (`lib/speciesMatch.ts`), so one change reaches all five, and the codes are eBird's own data. The generator already downloads them and then throws them away in one function.

## The User Problem

A birder who logs on eBird Mobile types `amro`, `yrwa` or `cago` without thinking. In SnowRaven those queries match nothing, or match only when the letters happen to start a name (`mall` finds Mallard by accident, while `gbhe` finds nothing), so the birder has to stop and type the name. Enter opens the first result, and Search lists species alphabetically up to a cap of 50. So a code only helps if its bird leads the list.

## Success Criteria

- In Search, typing `yrwa` in any case, with any surrounding spaces, puts Yellow-rumped Warbler first among species when it is in the backup, and Enter opens it on Species Detail.
- A code that names several of the user's birds lists all of them, ahead of the name matches: `cago` gives Canada Goose and Cackling Goose, `nosh` gives Northern Shoveler and Northern Shrike, `trsw` gives Tree Swallow and Trumpeter Swan.
- Both code sets work: the banding codes (`amro`, `anhu`, `yrwa`, `mall`) and eBird's common-name codes (`cago`, `rodo` for Rock Pigeon, `mywa` for Yellow-rumped Warbler).
- Forms are reachable by their own codes, and the parent's code finds them too. `auwa` finds Yellow-rumped Warbler (Audubon's) if the user has recorded it, and `yrwa` lists the user's Yellow-rumped Warbler forms along with the species.
- Under Search's 50-species cap, a code match is never pushed off the list by name matches.
- A query gives the same set of matches in every species picker (the Select species picker on Species Detail, the Calendar's species filter, the Map Explorer's Species filter on My Sightings, and the Filter by species picker in Statistics' weather section) as it does in Search. In each picker the code matches lead the list after the "All species" row where there is one, and Enter picks the first of them.
- For any query that is not exactly a code, the matches and their order are the same as today on every surface.
- The first time Search or a picker opens, it never waits for the code data. Name matching works at once, destinations are never held up, and a failure to load the code data leaves name matching exactly as it is today, with no new message.
- No new third-party request, no new endpoint or host, and no request moved between components. Search still works offline and needs no API key. The entry chunk does not grow (`entryChunk.test.ts` stays green).

## Scope

- A build-time code asset, generated from eBird's taxonomy. It is bundled with the frontend and loaded lazily (a dynamic import) on every platform. It carries `comNameCodes` and `bandingCodes` for every taxon entry that has any, and it gets fail-closed generator guards plus a test that pins it to the snapshot version.
- The one shared matcher in `lib/speciesMatch.ts` gains code matching (exact equality of the whole code) and a shared ranking rule: rows that match a code first, then everything else, each in the order that surface already uses. Search (`lib/paletteRows.ts`) and `SpeciesCombobox` both use it. The shared layer owns loading the codes, so the four call sites wire nothing up, and a fifth picker would get codes automatically.
- Joining the user's backup names to their codes, in memory, derived from the already-loaded parse.
- `docs/HELP.md` is updated wherever it describes species matching. That is the Search section (including its "listed alphabetically by common name" sentence, which stops being true) and the picker passages under Map Explorer, Species Detail, Calendar and the Statistics weather picker. `palettePublishedClaims.test.ts` is updated in the same change. These are written without a stop.
- The usual version bump and CHANGELOG entry at ship.

## Out of Scope

- eBird's `sciNameCodes` (four letters from the scientific name) and the six-letter scientific codes. Typing part of a scientific name already works.
- Matching part of a code or the start of one. `yr` does not match YRWA.
- Any visible change to result rows. No code badge and no "matched by code" label.
- Species outside the user's backup. Search and the pickers list only birds the user has recorded, and that stays true.
- Other species filters that do not use the shared matcher. These include the Media Targets target-species search box in the Map Explorer (`MapExplorer.tsx` `filteredManualSpecies`) and the Checklists comment search. If wanted, the target-species box is a follow-on for the roadmap.
- The backend, `/taxonomy/codes`, the desktop live taxonomy fetch, the IndexedDB `CACHE_KEY`, and the backend snapshot twin. None of them changes.
- Editing eBird's codes in any way, whether adding, removing or re-ranking them.
- `README.md`, `website/`, `appstore/LISTING.md` and `PRIVACY_POLICY.md`. None of them has a Search passage since website-readme-copy-pass, and nothing here changes what the app sends anywhere. The App Store What's New line is drafted at ship time and held for the user's approval.

## Key Decisions

1. **The codes are eBird's, used as published.** A row matches the codes eBird publishes for that row's own taxon entry, from `comNameCodes` and `bandingCodes` together. Both fields are required. On their own, banding codes cover only 2,253 of 11,167 species, and `comNameCodes` covers 9,644. Together they give every one of the 11,167 species at least one code. The familiar North American codes (YRWA, AMRO, MALL) are the banding codes. For the same species, `comNameCodes` holds eBird's other codes (Yellow-rumped Warbler: MYWA; Canada Goose: CAGO, where the banding code is CANG). This follows the house rule that eBird answers taxonomy questions (as with countability and `reportAs`).
2. **Every row that carries the code is returned.** Codes collide, which is why every match counts. Across species, 2,694 of the 10,098 distinct codes name more than one species. Within the 2,253 species that have banding codes, 314 codes collide. Every collision among the user's own birds is shown.
3. **Matching is exact, case-insensitive equality on the trimmed query.** All codes are A to Z. All but six are four letters, and those six (EMU, KEA, TUI on two entries, MAO, OU) are each the bird's own name. So any 2-to-4-letter query is checked against the codes, with no prefix matching and no separate length rule.
4. **Ranking has one rule in one place.** Rows that match a code come first, then the existing name and scientific-name matches, with no row listed twice. Within each group the surface keeps its own order: Search's `compareSpeciesName`, which stays the same on every platform, and each picker's upstream order. Search's cap of 50 applies after ranking. Two consequences are accepted and stated. (a) A query that is also an English word and a code puts that bird first, and the name matches still follow. Measured against common group words, `wren` (Wrentit, Wrenthrush), `dove` (Dovekie), `crow` (Crested Owl), `swan` (three Neotropical antbirds) and `ibis` (Ibisbill) are affected; `teal`, `duck`, `gull`, `hawk`, `tern`, `rail`, `loon` and others are not codes. (b) Hybrids carry both parents' codes, so a user holding `Cape May x Yellow-rumped Warbler (hybrid)` sees it ahead of Yellow-rumped Warbler in Search's alphabetical order for `yrwa`. Keeping one ordering rule is worth that rare case.
5. **Forms use their own codes.** Each of the 4,120 `reportAs` entries carries all of its parent's codes and adds its own (Audubon's: AUWA), so keying on the row's own entry gives forms both kinds for free. A row whose exact name the snapshot does not publish (a name from an older revision) falls back to the codes of its normalized parent name. If that does not resolve either, the row matches by name only. Re-exporting from eBird fixes it.
6. **The data ships as its own lazy frontend asset, not inside the snapshot or a backend field.** On web and Pi the frontend never loads `ebird-taxonomy.json` (the backend serves `/taxonomy/codes`). Joining through `/taxonomy/codes` would add a request to Search, and Search's documented property is that it makes none. A bundled asset loaded like any other lazy chunk keeps every platform the same and needs no endpoint. The asset is keyed so the frontend can join a backup name without the snapshot (lowercased published common name to codes). Its measured cost is **about 619 KB raw / 151 KB gzip** for all taxon entries that have codes, or 339 KB / 101 KB for species only. For comparison, the existing snapshot is 1.74 MB / 464 KB gzip. Taking the all-entries version is what makes `auwa` work. The Architect may find a denser encoding. A budget materially above about 200 KB gzip comes back as a flag.
7. **"Costs nothing at runtime" is true per keystroke, not overall.** Each keystroke adds one hash lookup of the normalized query and a membership test inside the existing single pass over the index. That stays linear in the size of the index, constructs no `RegExp`, and the query reaches only equality and `includes`. The one-time costs are parsing the asset on first use, a join over the user's distinct names (one hash lookup each), and the bytes in point 6 added to every build. The schema declares both new scans, the one over typed text and the one over backup names, with this linearity argument. It also names the `.claude/rules/security.md` glob the build adds for any new `lib/` file that scans backup text.
8. **Lookups keyed by external strings use a `Map` or `Object.hasOwn`, never a bare `obj[key]`.** Backup names and typed queries both reach the lookup, and the `constructor`/`__proto__` precedent is in `taxonomyService.hostileKeys.test.ts`. Hostile-key rows are owed on both the name side and the query side.
9. **Generation follows the snapshot's annual revision.** The code asset is derived in the same run as `ebird-taxonomy.json`, as `ebird-countability.json` already is. That way an annual Clements revision refreshes all of them together. The asset carries the snapshot's `version`, and a test fails when the two disagree, like the splits-and-lumps asset. Guards fail closed: the build stops on too few entries, a species with no code, or a code outside `^[A-Z]{2,4}$`. Verified 2026-10-08: the five maps derived from today's live taxonomy are exactly equal to the shipped snapshot (`version` 2027, `generated` 2026-06-20). Regenerating now therefore changes nothing in the existing assets except the `generated` stamp. If eBird's live taxonomy has moved past the snapshot by build time (the annual update usually lands in late October), the codes must not be generated from a newer revision than the snapshot. The generator should check this rather than assume it, and a mismatch means the full annual-revision procedure (`.claude/rules/bird-names.md`) or a stop.
10. **The joined codes live in memory and die with the parse.** They follow `lib/speciesIndex.ts`'s `WeakRef` pattern, with no persisted document and no `clearDerived.ts` row (the v1.0.20 boundary in CLAUDE.md). The asset itself is build-time data, so the bundled-asset trust rule applies: guards run at build time and in CI, not at runtime.
11. **Accessibility and names are unchanged by construction.** No new controls, rows, labels or announcements are added. Rows still render as today, and WCAG 2.1 AA at 320px and 200% text holds because nothing visual moves. Surfaces are named from `TAB_LABELS` (Species Detail, Calendar, Map Explorer, Statistics), never from component names.

### What the code says (verified 2026-10-08, so the Planner need not re-derive it)

- **Where the codes are dropped:** `scripts/build-ebird-taxonomy.mjs` `deriveBundle()` fetches `api.ebird.org/v2/ref/taxonomy/ebird` (17,891 entries, each carrying `comNameCodes`, `bandingCodes` and `sciNameCodes`) and keeps only `bySci`, `byCom`, `byOrder`, `byCode` and `reportAs`. Its two twins derive the same five maps: `fetchTaxonomyOnline()` in `frontend/src/lib/tauri/taxonomyService.ts` and `_derive_from_taxonomy` in `backend/routers/taxonomy.py`. None of the shipped files (`frontend/src/assets/ebird-taxonomy.json`, `backend/staticdata/ebird_taxonomy.json`) carries a code.
- **Search:** `lib/paletteRows.ts` `buildPaletteRows` normalizes the query once, filters the index with `matchesSpeciesQuery`, sorts with `compareSpeciesName`, and cuts at `SPECIES_CAP = 50`, which sets `speciesTruncated`. The index is `lib/speciesIndex.ts` (`{name, sciName}` from the backup, in memory). The cap line in `lib/paletteCopy.ts` ("Showing the first 50 matches") stays true.
- **Pickers:** `components/SpeciesCombobox.tsx` (options `{name, sciName?}`, "already sorted upstream", plus an optional "All species" row that always comes first). It has exactly four call sites: `SpeciesDetail.tsx`, `Calendar.tsx`, `MapExplorer.tsx` (My Sightings Species filter) and `WeatherStatsSection.tsx`. `components/targets/TargetsCountyPicker.tsx` is a county picker, and `NamedBirdTickList.tsx` is not a species search. Neither is in scope.
- **The matcher:** `lib/speciesMatch.ts` (`normalizeSpeciesQuery` + `matchesSpeciesQuery`) imports nothing and stays off the entry graph only because its consumers do. It must stay off. The existing extraction note ("do not improve a shipped predicate while extracting it") still applies to the name half, which must behave exactly as it does today.
