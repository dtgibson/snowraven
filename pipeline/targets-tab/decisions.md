## 2026-09-26 — Frequency source (Stage 1, user decision)
eBird's percent-of-checklists frequency is not available through the API (the bar-chart download redirects to the Cornell SSO login). The user chose BOTH sources and asked that the tab "be clear about what is live data and what is probability": probability comes from the county's eBird bar-chart file the user downloads and imports (monthly default, year-round); live comes from the eBird API (reported on N of the last 30 days, last report, distance) and is never shown as a percent. Acceptance anchor from the user: Lincoln's Sparrow in Alameda reads 3.29% year-round on their eBird Targets page.

## 2026-09-26 — Window default is Any time (Case 1 correction to the PRD)
FR-53 and the brief's Scope line defaulted the Day / Week / 30 days / Any time window to 30 days. Changed to **Any time**. The user's idea makes the window an optional filter ("distance to last sighting if available (filterable by day, week, month)"), and a 30-day default would silently hide seasonal targets that are absent this month, which contradicts a year-round probability sort. The window still narrows the list exactly as FR-53 specifies when the user picks Day, Week or 30 days.

## 2026-09-26 — Stage 4 design notes (The Designer, first direction; logged for the record, not deviations from the design system)
1. **Two kinds, two shapes.** Probability and live are separated four ways at once, none of them color: (a) two labelled column groups on desktop and two labelled blocks per row on a phone, each headed PROBABILITY / LIVE with a glyph (Percent / Radio) and a source line naming where the figure comes from ("eBird bar chart, Alameda, CA, 1900-2026" against "eBird API, last 30 days"); (b) the figures themselves take different forms: a percent with its sign under a continuous share bar (a proportion) against a sentence with a count and its window ("Reported 12 of the last 30 days") under thirty discrete day ticks (a count); (c) every probability header and sort name carries "%" and the source range, every live cell carries the window and never a percent (FR-36, FR-42, FR-58), in visible text and accessible names alike; (d) a hairline divides the two groups in the table. 4. **Inter is kept.** The doctrine's display-face rule yields to `pipeline/design-system.md`, which pins Inter / system-ui as the house type; the mockup must read as SnowRaven, not as a new product. `weft-design-lint` reports clean on the file.

- **Budgets.** `DAY_OBS_MAX_BYTES = 10_000_000` UTF-16 code units of `JSON.stringify(species)` summed (the house unit; keys and envelopes outside it; one sole oversized newest entry allowed). In bytes that is ~1.0-1.05x for real eBird records (only `locName` can be non-ASCII) and at most ~1.4x, so the on-disk document is ~10-11 MB and fits `settingskv.py`'s 16 MiB cap; stated residual: three adversarial 5,000-record entries with 512-code-unit non-ASCII names would 413 on web/Pi, best-effort, mirror stays live. `DAY_OBS_MAX_ENTRIES` 300 → 3,000 so the payload budget is the constraint that binds: at the measured 20-31 KB per busy day 10 MB is 320-490 days, and a 300 cap would have bound at under 1 MB of quiet (~3.4 KB) days; 3,000 is where the count cap stops binding before the budget for any day above ~3.3 KB and becomes the backstop on near-empty envelopes it is meant to be.

**The measuring-point chooser (FR-51a, QA-53a), with these differences from the spec, each deliberate:**
1. **No place name for the Default Location.** The stored Default Location is coordinates only (the earlier build's recorded deviation), so the line reads "Distances from your Default Location." without "(Oakland)", and the chooser's sub-line reads "Set in Settings" rather than "Oakland, set in Settings".
2. **"Places in this list" is built from every pool species' last report, not only the rows on screen.** design-spec 2a's text says "the rows currently on screen"; the approved mockup (`renderAnchorPop(rows(c))`, unfiltered) and PRD FR-51a ("every location named by the county's loaded live data") build it from the whole county's live data, and a narrowing filter must not remove the places a user would re-anchor to. A place without coordinates cannot be measured from and is left out.
3. **A click outside returns focus to the trigger only when it left focus nowhere.** A click on another control keeps that control's focus; a click on blank page would strand focus on `<body>`, so it goes back to the trigger. Escape, a choice and a successful search always return it.
4. **The slider's description is a hidden plain-text twin of the status line**, not the line itself: the line now holds the trigger, whose accessible name would be spliced into any description computed from the line's subtree. Read out of the real accessibility tree in both engines: the trigger is `button "Distances are measured from your Default Location. Change"`, the slider's description "Distances from your Default Location.".
5. **Busy states are `aria-disabled`, not native `disabled`**: My location while it locates and the Search button while a search runs, so a press never throws focus to `<body>` inside the dialog. The Search button is native-disabled only while the field is empty.
6. **The chooser's non-offline failure line is "Location search failed. Try again."** Map Explorer's line tells the user to enter coordinates, which the chooser does not offer; the miss line and the offline line are the shared ones word for word.
7. **Map Explorer's `AddressSearch` was extracted to `components/AddressSearch.tsx` + `lib/placeSearch.ts`** (the spec's "extracted to a shared component so the two cannot drift"). Map Explorer's register renders its shipped markup unchanged. The shared logic gained two things Map Explorer now also gets: the Nominatim answer is validated (a body that is not a list, a non-object result, or coordinates that are not finite and in range read "No location found" rather than handing on NaN, or, for a non-list body, a TypeError the offline classifier could read as "you're offline"), and a press while a search is outstanding sends nothing (Enter in the field could previously send a second request). `maps.md` and `security.md` gain the two new files in their `paths`, since `maps.md` gated the code at its old home.
8. **The no-anchor trigger's accessible name is its visible text, "Choose where to measure from".** design-spec 2a gave it "Choose where distances are measured from", which does not contain the visible words, so a voice-control user saying what is on screen would miss it (WCAG 2.5.3 Label in Name).
