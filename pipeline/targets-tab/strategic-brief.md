# Strategic Brief — Targets Tab

## What We're Building
A new **Targets** tab, placed after Calendar, that turns a US county into a sortable target list over the user's own record: species that would be **lifers**, species the user has recorded but still has **no photo, audio or video** of, and species the user has recorded but has **no breeding code** for. Each type has its own on/off toggle. The list carries two kinds of frequency, kept visibly distinct: **probability**, eBird's own historical percent-of-checklists frequency (this month and year-round) from a bar-chart file the user downloads from ebird.org for that county and adds to SnowRaven; and **live**, what the eBird API reports now with the user's key (reported on N of the last 30 days, last report, distance). Sorts: this month's eBird frequency (default when the county has a file), year-round eBird frequency, live 30-day count, distance to the last report, alphabetical, taxonomic, with a Day / Week / 30-day / Any-time window on the last report.

## Why Now
Every ingredient already exists in the app and none of them is joined: the all-time county species list (`/map/county-species`, cached 30 days for the Completeness metric), the life-list subtraction Nearby Lifers uses, the missing-media rule Media Targets uses, the breeding-code aggregation the Breeding Codes tab uses, and the shared Day/Week/30-day window. The county Completeness popup shipped a deliberately unranked five-species "targets" floor at v0.5.54 with a data-source decision left open on the roadmap; this feature makes that decision and gives the answer a surface of its own. It is the user's next pick from the inbox, and it is what a birder planning a county day actually wants from eBird's Targets page but cannot get: media and breeding gaps beside lifers, in one list, over their own files.

## The User Problem
A birder heading to a county asks three questions eBird answers only one of: what could be a lifer here, what have I seen but never photographed or recorded, and what have I never confirmed breeding. eBird's Targets page answers the first, ranked by bar-chart frequency, and knows nothing about media or breeding codes. Today in SnowRaven the same birder pieces it together across three tabs and a map radius, with no county frame and no ranking by how findable a species is right now.

## Success Criteria
- Choosing a US county the user has birded renders the county's species pool before any network call, with Lifer / Photo / Audio / Video / Breeding badges per species and the alphabetical and taxonomic sorts working offline from the cached pool.
- With an eBird key, the live 30-day count, the last-reported date and the distance to that report fill in progressively with a visible progress line.
- With the county's eBird bar-chart file added, every row shows eBird's frequency for the current month and year-round, the default sort is this month's eBird frequency, and the year-round figure reproduces eBird's Targets page: against the user's real Alameda file, Lincoln's Sparrow reads 3.29% year-round.
- The two kinds are unmistakable everywhere they appear (a user-directed requirement): the probability columns and sorts name their source and date range ("eBird, Alameda, 1900–2026, September" / "year-round") and carry the percent sign; the live measure is a plain count ("reported 12 of 30 days") with its date, never a percent; a screen reader hears the same distinction in the column and sort names.
- A county without a file still lists every target with the live measure and the distance, alphabetical and taxonomic sorts; the two eBird-frequency sorts are shown as unavailable with a one-line prompt to add that county's file and a link that opens the county's eBird bar chart page in the system browser.
- Adding a file downloaded for a partial month or year range shows the range it covers; year-round is offered only when all twelve months are present; a file whose name carries a different county's region code is refused with a plain reason and the county's existing file is left as it was; removing a county's file returns the county to the no-file state.
- Turning a type toggle off removes exactly that type; a species carrying two types (media and breeding) stays while either toggle is on; lifers never appear as media or breeding targets.
- Setting the window to Week hides every species whose last county report is older than seven days, using the same predicate as Map Explorer's Time Range, and on the day after a spring-forward transition it counts calendar days correctly.
- The county chosen is remembered across relaunches on that device; a first visit opens on the county with the most checklists in the backup.
- The tab sits after Calendar for a user on the default layout; a user with a custom saved layout keeps that layout, with Targets appended.
- Every bird name renders through `<BirdName>`; WCAG 2.1 AA holds at 320px and 200% text; all color through `var(--sr-*)` tokens; keyboard and screen-reader users can change county, toggles, sort and window.
- No eBird call is made without a key; a 429 anywhere slows every eBird call through the shared gate; a county with no key or offline shows the pool from cache with an honest one-line status, never a spinner.

## Scope
- New configurable tab `targets` (label **Targets**, own icon) after `calendar` in `DEFAULT_TAB_ORDER`, with the one-generation default migration described in Key Decisions.
- County picker over the user's **US** birded counties (from the backup's State/Province + County, joined to an eBird region code through the county geometry). Default: most checklists; last choice persisted through the `storage` seam.
- Species pool: the county's all-time species-level list from the existing `/map/county-species` route and `countyCompletenessCache` (shared store, no second copy).
- Three target types, each with a toggle (all on by default):
  - **Lifer** — pool species whose normalized name is not in the user's recorded set (the Nearby Lifers subtraction, plus the code-level subtraction `completenessTargets` already does).
  - **Media** — pool species the user HAS recorded that lack at least one of Photo / Audio / Video in the ML export (Map Explorer's Media Targets rule), with the same Photo / Audio / Video type chips (AND). A user with no ML export sees the Media toggle disabled with the reason.
  - **Breeding** — pool species the user HAS recorded with no breeding code on any observation (the `BREEDING_CODES` set the Breeding Codes tab aggregates), with a two-position threshold: **Any code** (default) or **Confirmed** (tiers 3–4, `CATEGORY_CODES.confirmed`).
- Two frequency kinds, both in scope and never conflated:
  - **Probability (eBird frequency)** — from a per-county eBird bar-chart file the user downloads while signed in on ebird.org (bar chart page → Download Histogram Data, named like `ebird_US-CA-001__1900_2026_1_12_barchart.txt`) and adds from that county's view. Two figures per species: **this month** (the current calendar month's percent of checklists) and **year-round** (the sample-size-weighted share across the file's periods, so it matches eBird's Targets figure). Shown with "%", the source and the file's date range.
  - **Live (eBird API)** — the measured "reported on N of the last 30 days" from a per-day sweep of eBird's historic observations for the county (30 calls on first visit), plus last reported date, place and coordinates. Shown as a count with its window, never as a percent. Cached durably per (county, day) so a revisit costs only the missing days; gated, paced and 429-honoring under the shared eBird gate; registered with `clearDerived.ts`.
- Sorts: **eBird frequency, this month** (default when the county has a file), **eBird frequency, year-round**, **Live 30-day count** (default when it has none), **Distance** to the last report (from the saved Default Location or Use my location, disabled when neither exists or the report has no coordinates), **Alphabetical**, **Taxonomic** (the pool's eBird order). The two eBird-frequency sorts are unavailable without a file, with the prompt and the bar-chart-page link (`openExternalUrl`).
- Window on the last county report: Day / Week / 30 days / Any time (default Any time), through the shared `isWithinWindow`.
- Per-row: name, type badges, eBird frequency this month and year-round (when a file exists), live count ("12 of 30 days"), last reported date, place, distance; a row tap opens Species Detail for recorded species.
- Bar-chart file import per county: add, replace, remove; the file is a new stored user-file kind through the stored-file refusal registry, the `storage` seam on both transports and the `filesChanged` epoch (constraints in Key Decisions). Partial month or year ranges are shown as the range covered; year-round only when all twelve months are present.
- The `isWithinWindow` DST fix (round in place of floor) and the flipped parity fixture row, in this change.
- `docs/HELP.md` section for the tab, including how to download a county's bar-chart file from ebird.org; `PRIVACY_POLICY.md` gains the new eBird request kind (a per-day county species query) and the statement that the imported eBird file stays on the device; a one-sentence website/README PROPOSAL for user approval.
- Version bump (patch) and CHANGELOG entry.

## Out of Scope
- Fetching eBird's bar-chart data from ebird.org on the user's behalf (it is login-gated and 302s to the Cornell SSO; the user downloads the file), and deriving a year of frequency from the API (365 per-day calls per county stays rejected).
- Month ranges other than the current month for the probability sort (a month picker), and a probability sort for a county with no file.
- Syncing bar-chart files through iCloud (device-local in v1; see Key Decisions).
- Non-US counties, states, hotspots, or a radius as the region; multi-county lists.
- "County lifers" (species new to the county but already on the life list) as a fourth type; the Completeness popup already serves that and its ranking upgrade is a separate item.
- Breeding-season filtering or joining the California Breeding Bird Atlas overlay.
- CSV/clipboard export of the list; per-species month bars; a Targets home-screen widget.
- Re-ranking the Completeness popup's five-species floor from this data (it can consume the new source later through the existing `completenessTargets` seam; not in this build).
- Any change to the Calendar, Map Explorer or Breeding Codes surfaces beyond the shared-predicate fix.

## Key Decisions
- **Two frequency kinds, user-decided ("do both, and be clear about what is live data and what is probability"), and the UI keeps them apart.** The official API 2.0 has no frequency endpoint, and eBird's bar-chart download (`ebird.org/barchartData?...&fmt=tsv`) 302-redirects to the Cornell SSO login, so it cannot be fetched with the API key or on the user's behalf. **Probability** therefore comes from a bar-chart file the user downloads while signed in and adds per county: eBird's own percent of checklists reporting the species, per period, with a Sample Size row per period. This month = the current calendar month's figure; year-round = the sample-size-weighted share across all periods, which is what reproduces the Targets page (acceptance check: Lincoln's Sparrow, Alameda, 3.29% year-round against the user's real file; the Architect confirms the exact derivation against that file). **Live** comes from `data/obs/{regionCode}/historic/{y}/{m}/{d}`, one record per species reported in the county on that day, so 30 calls yield an exact "reported on N of the last 30 days" plus each species' most recent report (date, place, coordinates). The single `recent?back=30` call was rejected as the sole live source (presence without gradation); the 365-call annual sweep stays rejected (the file answers year-round properly). **Copy rule:** the probability figures carry "%" and name their source and date range ("eBird, 1900–2026"); the live measure is a count with its window and never a percent; sort names say which kind they are; the distinction is in the accessible names, not only in color or position. Default sort is this month's eBird frequency when a file exists, the live count when none does.
- **The bar-chart file is a NEW stored user-file kind, one per county, and inherits every stored-file rule.** It goes through the refusal registry (`lib/uploadGuard.ts` `refuseByFilename` / `refuseByContent`, header detection bounded by `MAX_HEADER_CHARS`), the `storage` seam on both transports, and the `filesChanged` epoch; a failed status lookup is UNKNOWN, never EMPTY; the parser runs over untrusted text, so `.claude/rules/security.md`'s linearity rule applies and the scan is declared in the schema with its argument. **Device-local, not iCloud-synced** (default recommendation, adopted): iCloud Sync covers the two data files only, and syncing a third kind would change the iCloud scope statement and `PRIVACY_POLICY.md`; a county's file is small and re-downloadable, so the cost of device-local is one download per device. **County attribution** comes from the view the import happens in; a filename carrying a region code (`ebird_US-CA-001__...`) that disagrees with that county is refused with a plain reason, and a filename without one is accepted on the view's county. **Ranges:** the file's month and year range is parsed and shown; year-round is offered only when all twelve months are present; a narrowed year range labels the probability with that range. **Removal** returns the county to the no-file state and bumps the epoch. **Derived data:** the parsed frequency table is derived from a user file and keyed on a county the user chose, so if it is persisted anywhere it gets a `clearDerived.ts` row and a `cacheInventory` pairing; the recommended shape is to re-parse from the stored file on load and persist no derived document, in which case no row is owed and the file's own delete is the teardown. **Known risk for the Architect:** species names in the file join the pool through the app's existing `normalizeSpeciesName` and `/taxonomy/codes` resolution; a name eBird has since renamed, a subspecies row, or a spuh/slash row can fail to join, so unmatched rows are counted, surfaced in the file's status line, and never dropped silently.
- **Cost and pacing.** 30 gated calls on a county's first visit (roughly 5–8 s at the 150 ms floor), cached durably per (regionCode, day) in the `countyCompletenessCache` pattern (validated at the write chokepoint, entry and payload budgets, FIFO, offline stale reads) so tomorrow costs one call and a revisit today costs none. The new route joins `EBIRD_GATED_PATHS` on both transports with the shared 429 mapper; the sweep owns its own pass-scale pacing in the tab's controller (the projects-sweep precedent), never inside gate policy. The pool renders before any network call so the tab is never blank behind the sweep. The cache is keyed on counties the user has birded, so it registers in `clearDerived.ts` with a `cacheInventory` row.
- **Target definitions reuse the app's, against the whole record, and are disjoint by construction.** Lifer = not recorded anywhere (Nearby Lifers' `normalizeSpeciesName` set + `completenessTargets`' code subtraction). Media and Breeding apply only to recorded species, so a lifer never carries a media or breeding badge; a recorded species can carry both. Media uses Map Explorer's missing-any-of-three rule and its Photo/Audio/Video chips; Breeding uses the `BREEDING_CODES` set (F and H included, matching the Breeding Codes tab) with an optional Confirmed threshold from `CATEGORY_CODES`. No parallel definitions.
- **DST: fix `isWithinWindow` here (round, not floor) and flip the `widgetRows.parity.test.ts` declared-difference row to agreement.** This tab is the function's fourth consumer; leaving the roadmap's one-line fix out would ship a third surface with the known day-after-spring-forward miscount. The change reaches Nearby Lifers, Media Targets and the hotspot 7-day count, all in the direction the widgets already take. Architect: confirm `calendar-overlays` and `launch-splash-screen` touch neither `lib/nearbyLifers.ts` nor that fixture before landing.
- **Tab order migration follows CLAUDE.md's one-generation rule.** `PREVIOUS_DEFAULT_TAB_ORDER` becomes the 1.0.19–1.0.36 order (the one this change replaces) and the pre-1.0.19 constant is retired; the new default inserts `targets` after `calendar`; saved CUSTOM layouts are kept verbatim with `targets` appended by the existing missing-tab step (so a custom layout gets Targets last, not after Calendar, by the standing rule); nothing writes back at read time. `ConfigurableTab`, `TAB_LABELS`, `tabIcons.tsx`, App.tsx's lazy import, prefetch list and mount block, and every tab-enumerating guard (`tabOrderCoverage`, tabLayout tests) are in the Architect's file list.
- **County scope is US-only by mechanism, not preference.** eBird region codes derive from the county geometry's GEOID (`deriveCountyRegionCode`), which exists for US counties only; the picker joins the backup's `countyKeyFromState` keys to geometry `name`/`stusps`, loaded lazily so maplibre and the geometry stay off the entry chunk. Counties that fail the join are listed as unavailable with the reason rather than silently omitted.
- **Distance anchor reuses the app's location seam**: the saved Default Location, with Use my location (`lib/location.ts`) as the override, the same two Nearby Lifers uses. No new permission prompt, no new location storage.
- **Concurrent-build overlap.** `launch-splash-screen` (at testing) very likely touches `App.tsx`; `calendar-overlays` (at design) owns `Calendar.tsx` and may add settings keys. This build's `App.tsx` edits are additive only (one lazy import, one prefetch entry, one mount block) and it does not touch Calendar files or the `icloud-sync` settings object; the Architect rebases onto whichever lands first and re-runs the tab guards.
- **Published surfaces.** `docs/HELP.md` updated in the same change, including the ebird.org download steps; `PRIVACY_POLICY.md` must stay true and gains two sentences, shown to the user before they land: the per-day county query in the eBird bullet, and that an imported eBird bar-chart file is stored only on the device (and is not part of iCloud Sync); website and README receive one proposed sentence for the user's approval, never an append; no em dashes in any published copy. The user gets a live tailnet look at the built tab against their real data, with their real Alameda file, before the deploy gate.
- **Alignment.** Local-first over the user's own two files, calls device-to-provider with the user's key, alongside eBird rather than replacing it (the media and breeding types are exactly what eBird's Targets cannot do). No founding decision is strained.
