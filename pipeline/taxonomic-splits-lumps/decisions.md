# Decisions - Taxonomic Splits and Lumps

## Stage 4 - The Designer (2026-09-30)

Design system status: established (`pipeline/design-system.md`); this feature designs within it with zero new tokens and zero new component patterns. The deviations below are deliberate and small; the Chronicler folds any pattern worth keeping back into `design-system.md` at Stage 9 rather than this stage editing it.

1. **A hand-drawn direction glyph instead of lucide `Split` / `Merge` in the event badge and list rows.** The user asked that the glyph "split in the same direction the flowchart does". Lucide's `Split` and `Merge` are both drawn vertically and read against the wide layout's left-to-right flow, and lucide has no horizontal fork. The badge glyph is therefore a three-stroke (split) or two-stroke (lump) inline SVG on the lucide grid (24 viewBox, stroke 2.2, round caps, `currentColor`, `aria-hidden`), fanning out or converging to the right, and rotated 90deg by CSS on the phone tier so it turns with the stacked chart. Lucide `Split` stays as the feature icon on the control tile and the section header, where it identifies the feature rather than a direction. This is the icon rule's "clarify or create hierarchy" applied with a shape the library does not carry; it adds no dependency.

2. **A `breakAfterSlash` opt-in on `<BirdName>`.** At 320px and 200% text, a slash name ("Eastern/Western Warbling Vireo") inside a chart node broke mid-word ("Wester|n") because nothing offers a break after "/". The section renders slash entries through BirdName with a new default-off prop that inserts `<wbr>` after each "/" in the common name. The text content and accessible name are unchanged (`<wbr>` contributes no character), every shipped surface stays byte-identical, and the alternative, a mid-word break on the one surface that shows slash names prominently, was rejected on the mockup. The bird-names rule ("every user-facing bird name renders through BirdName") is why this lives on the shared component rather than as a local name renderer.

3. **Marker wording "No reports under this name" over "Not in your data".** Offered to the user, approved. After a lump the retired parents (Common Redpoll, Hoary Redpoll) hold no rows under their names in a current export even though the birder plainly saw redpolls; "not in your data" would read as a false claim about the birder's history. The marker states the literal fact about the file. FR-18's meaning ("the user holds no rows under this entry") is unchanged.

4. **After-side order is eBird's taxonomic order with the user's species marked in place, not moved first.** Offered to the user, approved. Keeps the chart faithful to the asset's order (FR-01, schema I9) and consistent with every other species order in the app; the accent tint and the "Your species" marker make the user's node findable without re-sorting.

5. **One-track count bar.** The first mockup drew the reassigned and recorded-since shares as two abutting fills, and the user saw the hairline of track that shows at their subpixel seam. The bar is now one track filled with the reassigned colour and a single right-aligned accent fill for the recorded-since share; there is no seam to draw. Reinforcement only; both numbers are text.

6. **Connectors are CSS pseudo-element hairlines, not SVG, and the stub offset tracks the text scale.** A measured SVG would need JS geometry on every resize and text-scale change; pseudo-elements let each node's own height decide the geometry. The first draft pinned the stub at 20px and the name line-height at 20px, which made two-line names touch at 200%; the shipped rule is `--lin-stub: calc(10px + 0.55rem)` with the name at line-height 1.3. On the phone tier the rail's hairlines extend 8px across the grid's row gap on each side and the multi side's end segments stop at the node edge, so the line is continuous with neither a gap nor a doubled overlap (the two defects the review round found).

7. **The text equivalent is visually hidden, not a visible duplicate.** The chart's nodes are already rem-sized text in reading order, so a visible twin would put every fact on screen twice; the Planner's visible list precedent answers a chart whose marks are not text. The graphic is `aria-hidden` and a `.sr-only` paragraph set carries every fact (QA-22 parity). The mockup's "Text equivalent" preview toggle exists only so the user could read it.

8. **The stale-export state is per backup.** `event.predates` is a fact about the whole file, so with an older backup every event of that update shows the note at once; the mockup's export-date toggle demonstrates that state and is not a per-species control.

## Stage 5 - The Engineer, QA fix errand 1 (2026-09-30)

1. **A species' chain is its own line of descent, not the connected component (FR-11, FR-15; QA-11, QA-15).** schema.md 6.5 closed a species' events over the chain links in BOTH directions at once, which is the whole connected component, so a daughter inherited its sibling's later change and a lump's co-parent inherited its partner's earlier split. In the committed asset a backup holding only Palawan Crow listed "Split 2024; Split 2023" and rendered the 2024 split of Slender-billed Crow, with a sentence dating a reassignment that never touched Palawan Crow records. The PRD's word is "touches" and the PRD governs: `buildTaxonomyHistoryIndex` now walks each matched entry's own line, backward through before sides and forward through after sides, and never turns around onto a sibling branch. **The source of the defect was schema.md 6.5's wording**, carried into the code and into a unit test that asserted the sibling behaviour ("Gamma Bird ... Lump 2024"); that test now asserts the opposite, with the Palawan Crow shape and the lump co-parent as regression rows. The real two-event line (Sunda Crow: the 2023 split, then the 2024 split of the kept Slender-billed Crow) still stacks earliest first.
2. **The chart stacks on a narrow EVENT as well as a narrow viewport (QA-32).** Between 641 and ~740px at 200% text the three-column chart had sides of 77 to 122px and its markers, counts and partition labels were clipped by the card. `.sr-lin-event` is now a named inline-size container, and `@container sr-lin (max-width: 21em) or (max-width: 420px)` carries the <=640 tier's stacked-chart declarations, locked identical by `lib/splitsLumpsCss.test.ts`. 21em is about a sixth above the measured first clip (an event ~18em wide); 420px is the 100%-text floor. Measured: 0 of 360 configurations clip (320 to 900px, 100/150/200%, Chromium and WebKit, text ink against the card and against each node); with the container removed from the built CSS the same probe reproduces the defect at 660/700/740px, 200%, in both engines.
3. **Every visible bird name in the section opts into `breakAfterSlash` (QA-32).** The sentence's quoted slash name ("European/African/Eastern Red-rumped Swallow") ran 4.64px past the card at 320px / 200%; it, the linked chart names and the list rows now pass the prop, which is a no-op on a name without a "/".

## Stage 5 - The Engineer, QA fix errand 2 (2026-09-30)

1. **A retired name also matches the earlier update that created its code, and counts once per event (FR-07, FR-16, FR-18, FR-19; QA-16, QA-18, QA-19).** schema.md 6.2's tier 0 matched a retired common name to before-side entries only. Some names are an after-side entry of one covered update and a retired before-side entry of the next, so rows under them were never counted on the earlier update's entry. Four such names exist in the committed asset (Slender-billed Crow `slbcro1`, Macquarie Parakeet `recpar23`, North Papuan Pitta `pappit2`, South Papuan Pitta `pappit1`), all created or kept by a 2023 split and retired in 2024, and only a backup exported between those two updates carries them. The rule now: **a row under a retired name matches the before entry of the update that retired it AND, by code, the after entry of every earlier covered update whose after side carries that code; at any one event the after entry wins, so the row sits on exactly one entry per event.** Each event's partition and its "predates" reading then follow from the row's side at that event: a 1 March 2024 Slender-billed Crow row is "recorded since" at the 2023 split and predates only the 2024 update. The match is by code because the after entry carries today's name, which can differ from the export's ("South Papuan Pitta" in the export is the 2023 entry now shown as "Papuan Pitta"). Implemented as `midChainTier0` in `frontend/src/lib/taxonomyHistory.ts`, called from tier 0 in `resolve`.
2. **Stated limit, the same kind as the Cory's Shearwater limit in schema.md 6.2, which is unchanged.** At an update that KEPT the name (Slender-billed Crow in 2023), a backup exported BEFORE that update carries the same name, and such a row is read as an export made after it: it lands on the kept after entry, and that event does not read as predating. The name alone cannot separate the two exports. Cory's Shearwater is untouched by this change because its before name is not retired, so tier 0 never fires for it.
3. **Regression rows** (`taxonomyHistory.test.ts`, describe "a name current after one update and retired at the next"): a synthetic chain (Beta Bird, created in 2023 and lumped in 2024, with rows either side of the 2024 date); the Macquarie Parakeet shape; the Slender-billed Crow kept-name shape, alone and with the Palawan Crow sibling present; and the renamed South Papuan Pitta matched by code. Mutation-checked: reverting tier 0 to the before entries alone turns 5 rows red; dropping the one-entry-per-event rule turns 2 red. The four real species were also checked against the committed asset through the real entry point (a throwaway test, not committed): each lands on its 2023 after entry and its 2024 before entry, the 2023 events no longer read as predating, and the 2024 events still do.
4. **The declared scan changed, and this item first said it had not (corrected at the security review, L2).** The row pass is unchanged: it still visits every row once and does the same work per row. But `midChainTier0` is new per-key work (once per distinct tier-0 key, bounded by the asset), and QA fix errand 1's `lineageEvents` had already moved the chain walk from once per asset to once per affected key. Both are linear in the rows. schema.md 6.6 now declares both, and `taxonomyHistory.test.ts` has a timing leg where every row is its own affected key.

## Stage 5 - The Engineer, security fix errand (2026-09-30)

1. **Site marks only on a current code (security review L1; FR-23).** The chart gave every linkable after-side node the eBird and Birds of the World marks. I5 deliberately admits an after code that a LATER covered update retired, and the committed asset carries three: `slbcro1`, `recpar23` and `pappit2`. Their Birds of the World pages return 404, and a backup exported between the 2023 and 2024 updates reaches them. `EntryView` now carries `current`, computed in `buildTaxonomyHistoryIndex` from the asset alone: **a code is current when the latest update that carries it has it on an after side.** Under I5 and I6 that is exactly "a species in the snapshot", and `taxonomyHistoryAsset.test.ts` holds it to the snapshot over every entry of the committed asset. **The Auditor's suggested test, "no later update carries it on its before side", was not used, because it is wrong for a kept code:** Red-crowned Parakeet (`refpar4`) and Papuan Pitta (`pappit1`) sit on a 2024 lump's before side AND its after side, are still species, and would have lost valid links. The derivation, not the generator, carries it because the derivation already builds the chain maps, and a runtime rule held to the snapshot in CI needs no change to the asset or its checker. `LineageNode` lost its side-based `current` prop and reads `entry.current`. Mutation-checked: treating every after entry as current turns 4 rows red; the shorter rule turns 3 red, including the component row's `refpar4` leg; a component that ignores `current` turns exactly the component row red.
2. **The declared-scan record caught up with the QA fixes (security review L2).** schema.md 6.6 gains rows for `midChainTier0` and for the per-affected-key lineage walk, with their bounds, and a corrected measurement note. Errand 2's item 4 is corrected in place above. The timing guard gains a leg where every row is its own affected key over the real asset: half match by scientific name, half are case variants of the retired "Slender-billed Crow", so tier 0 and `midChainTier0` run at volume. It uses the same-run quotient (under 9x from 10k to 40k rows) with an explicit timeout as a backstop, and non-vacuity assertions that every row is an affected key and both halves are present. A quadratic injected into per-key resolution turns this leg red and leaves the two older legs green, which is the gap the Auditor named.
3. **The PR description states the network posture in the durable form (I2).** "Makes no request" became "no third-party request, no new endpoint or host, and no request moved between components", noting that on web and Pi the chunk comes from the user's own server like every other chunk. HELP and the CHANGELOG keep their wording, which matches the shipped Subspecies and Search wording. I1 is accepted as is.
