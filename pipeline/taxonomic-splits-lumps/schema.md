# Schema - Taxonomic Splits and Lumps

**Feature:** taxonomic-splits-lumps
**Date:** 2026-09-30
**Stage:** 3 - The Architect
**Source:** prd.md (approved), strategic-brief.md (approved)
**Path:** Incremental

## Architect assessment - Incremental

`pipeline.config.json` exists and is complete, so the config step is skipped. SnowRaven has no
database; its data layer is the user's eBird backup parsed in memory, a family of storage-seam
documents, and a small family of **bundled build-time assets** (`ebird-taxonomy.json`,
`ebird-countability.json`, `us-counties.json`, `noaa-tide-stations.json`, `ca-atlas-blocks.json`),
each with a developer-run generator under `scripts/` and a CI guard. This feature adds a new
member to that asset family plus its generator and guard, and a new in-memory derivation over
the parsed backup. It persists nothing, adds no storage-seam document, no backend route, no
transport path, and no request. Not frontend-only, because a committed data artifact with a
build pipeline and a trust boundary is data-layer work; not migration, because nothing existing
is remapped. (Running hands-off: declared here rather than confirmed in chat.)

---

## 1. The design in one paragraph

A committed JSON asset, `frontend/src/assets/ebird-taxonomy-history.json`, holds one dated
event per species-level split or lump, keyed on eBird species codes with scientific and common
names on both sides, generated by `scripts/build-taxonomy-history.mjs` from Cornell's annual
eBird/Clements integrated checklist (the per-row change annotation and its "text for website"
sentence) joined against the eBird taxonomy file of that year and the year before. It is
dynamically imported on Species Detail's first ready state, so it rides its own chunk. A pure
module `lib/taxonomyHistory.ts` matches the backup's merged species keys to event entries in
three tiers (retired-name identity, current code, asset-name fallback), tallies every row once
with an on-or-before / after partition against the update's published date, and walks the event
chain. Nothing is stored; the index is a `useMemo` keyed on the observations array, the loaded
asset and the page's existing `/taxonomy/codes` result.

## 2. Two measured findings that shape the matching (read before section 6)

Both measured against the bundled snapshot `frontend/src/assets/ebird-taxonomy.json`
(`version` "2027", generated 2026-06-20, 17,891 codes, 11,167 species, 1,173 names carrying
a `/`).

**2.1 eBird recycles a split parent's code.** `warvir` is now the slash "Eastern/Western Warbling
Vireo"; `whimbr` is "Hudsonian/Eurasian Whimbrel"; `corshe` is "Cory's/Scopoli's Shearwater". A
lumped daughter's code becomes a subspecies group: `comred` is now "Redpoll (Common)" with
`reportAs redpol1`. And sometimes the parent code is **kept by the nominate daughter**: `houwre`
is "Northern House Wren" (2024 split). Cornell states codes are "not necessarily stable with
respect to taxonomic concepts". Consequences: a before-side code can never be forbidden from
resolving in the current snapshot (it may be a slash, a group, or a daughter); a code that is on
both sides of one event is assigned to the **after** side; and the species-only `bySci`/`byCom`
maps the app resolves through never return a retired code, so before-side entries are reached
by name, not by code (section 6.2).

**2.2 The existing sciName-first bridge lands a pre-split export on the nominate daughter.**
`bySci["vireo gilvus"]` is `eawvir1`, Eastern Warbling Vireo. An export made before October 2025
carries "Warbling Vireo / Vireo gilvus", and the page's `fetchTaxonData` batch would resolve
every one of those rows to the Eastern daughter's code. Under FR-06 read literally, the species
is affected (correct) but its rows land on the after side as "reassigned by eBird" (wrong: that
export predates the update, and FR-19 could never fire because "no current code" is never
true). The success criterion in the brief, "a backup exported before an update matches the
before side and is labelled as predating it; nothing is silently mismatched", and FR-19 itself
require a refinement: **a merged key equal to a before-side common name that eBird has retired
matches that before-side entry, and only then does code resolution run.** A retired common name
cannot appear in an export made after the update (eBird rewrites every row under the current
taxonomy), so its presence is direct evidence, and it is the one signal the bridge erases.
Section 6.2 states this as tier 0. It is a refinement of FR-06/FR-07's order, not a new matching
rule: the names compared are the asset's own (FR-07's names), and the case it adds is exactly
the FR-19 case the PRD wants detected. Recorded for the gate in the hand-back trace.

## 3. The history asset

### 3.1 Location, loading, no backend twin

- **File:** `frontend/src/assets/ebird-taxonomy-history.json`. Minified JSON, one line, keys
  sorted by the generator so a no-op regeneration is byte-identical (the countability
  precedent).
- **Consumed only by the frontend**, through a dynamic `import()` in
  `frontend/src/lib/taxonomyHistoryAsset.ts` (section 7.2). On web/Pi the FastAPI server serves
  `frontend/dist/` as static files, so the chunk reaches the browser exactly as every other
  frontend chunk does. **No backend twin, no route, no transport branch, nothing in
  `vite.config.ts`'s proxy.** The taxonomy snapshot ships twice only because
  `backend/routers/taxonomy.py` computes `/taxonomy/codes` server-side on web; this asset is
  never read by a route, so `backend/staticdata/` is untouched. The `no third-party request, no
  new endpoint or host, no request moved between components` posture is therefore true on all
  targets by construction: the only HTTP a web/Pi session makes for this feature is the fetch of
  a static chunk from the user's own server, the same class of request that loads the tab.
- **Trust boundary (NFR-02):** a Vite-inlined JSON import is a build-time asset, not a persisted
  runtime cache; malformed JSON fails the build, and a user cannot change the document without
  changing the code that reads it. Defenses are build-time (section 4, fail-closed generator) and
  CI-time (section 5). No runtime per-entry validation. The loader performs one structural
  presence check (`Array.isArray(mod.default?.events)`) only so FR-28 has a signal.

### 3.2 Shape

TypeScript types live in `lib/taxonomyHistory.ts` and are the contract; the JSON is their
literal form. Field names are short because the file ships.

```ts
export interface TaxonomyHistory {
  /** Asset schema version. A different value is a load failure (FR-28), never a migration. */
  v: 1
  /** `version` of the bundled taxonomy snapshot every current-side code was resolved
   *  against ("2027" today). CI asserts equality with the snapshot (section 5). */
  snapshot: string
  /** ISO date the generator ran. Provenance only. */
  generated: string
  /** The input files the generator read, by basename, in year order. Provenance only. */
  inputs: string[]
  /** Every update the asset covers, ascending. Derived by the generator from the events it
   *  produced (FR-02): an update with zero events is NOT listed, so coverage never claims a
   *  year the generator could not read. */
  updates: HistoryUpdate[]
  /** Derived: first and last of `updates`, or null when `updates` is empty. Carried so a
   *  consumer never re-derives it and CI can assert it equals min/max (FR-02, FR-05). */
  coverage: { earliest: HistoryUpdate; latest: HistoryUpdate } | null
  /** Ascending by `published`, then by the before side's first scientific name, so the file is
   *  deterministic and a chain reads in date order without a sort at runtime. */
  events: HistoryEvent[]
}

export interface HistoryUpdate {
  /** eBird/Clements update year, e.g. 2025. */
  year: number
  /** The day eBird announced the update complete on ebird.org (OQ-02), YYYY-MM-DD. The
   *  partition date of every event in this update. */
  published: string
}

export interface HistoryEvent {
  kind: 'split' | 'lump'
  /** Denormalized from `updates` so a consumer holds one object per event. CI asserts every
   *  event's (year, published) pair is a member of `updates`. */
  year: number
  published: string
  /** A split has exactly one; a lump has two or more (FR-01). */
  before: HistoryBeforeEntry[]
  /** A split has two or more; a lump has exactly one (FR-01). */
  after: HistoryEntry[]
  /** Slash taxa the split created (FR-01). Always present; empty for a lump and for a split
   *  that created none. Never a spuh (PRD Out of Scope). */
  slashes: HistoryEntry[]
}

export interface HistoryEntry {
  /** eBird species code as of the update year (after/slash) or the year before it (before).
   *  Matches SPECIES_CODE_RE from lib/speciesCode.ts. */
  code: string
  /** Scientific name exactly as the eBird taxonomy file of that year prints it. */
  sci: string
  /** Common (PRIMARY_COM_NAME) exactly as the eBird taxonomy file of that year prints it. For
   *  after/slash entries CI asserts equality with the snapshot's byCode[code]. */
  com: string
}

export interface HistoryBeforeEntry extends HistoryEntry {
  /** true when `com` is NOT a species common name in the current snapshot (lowercase compare
   *  against byCom). Computed by the generator, re-asserted by CI. This is the tier-0 gate in
   *  section 6.2: only a retired common name is evidence of a pre-update export. */
  retired: boolean
}
```

Illustrative JSON for one event (the 2025 Warbling Vireo split, names as the eBird taxonomy
prints them; the Engineer must generate rather than hand-type this):

```json
{"kind":"split","year":2025,"published":"2025-10-31",
 "before":[{"code":"warvir","sci":"Vireo gilvus","com":"Warbling Vireo","retired":true}],
 "after":[{"code":"eawvir1","sci":"Vireo gilvus","com":"Eastern Warbling Vireo"},
          {"code":"wewvir2","sci":"Vireo swainsoni","com":"Western Warbling Vireo"}],
 "slashes":[{"code":"warvir","sci":"Vireo gilvus/swainsoni","com":"Eastern/Western Warbling Vireo"}]}
```

Note the before code and the slash code are the same string. That is eBird's data (finding
2.1), not a generator error, and the derivation never keys a before entry by code.

### 3.3 Invariants (the generator refuses to emit, and CI re-asserts, every one)

| # | Invariant | Owner |
|---|---|---|
| I1 | `v === 1`; `snapshot` equals the bundled snapshot's `version` | generator writes, CI asserts |
| I2 | Every event has `kind` in {split, lump}, integer `year`, `published` matching `/^\d{4}-\d{2}-\d{2}$/` and a real calendar date, and (year, published) is a member of `updates` | both |
| I3 | split: `before.length === 1 && after.length >= 2`; lump: `before.length >= 2 && after.length === 1`; `slashes.length === 0` for a lump | both |
| I4 | Every entry has non-empty `code`, `sci`, `com`; `code` matches `/^[a-z0-9-]{2,16}$/` (the app's `SPECIES_CODE_RE`, measured: real codes are 2 to 8 chars) | both |
| I5 | Every after-side code is a species in the snapshot (a value of `byCom`) and its `com` equals `byCode[code]`; every slash code is a key of `byCode`, NOT a species, its `com` contains `/` and equals `byCode[code]` | both |
| I6 | A before-side code that is a species in the snapshot must appear as an after-side code of the same event (the kept-code case, finding 2.1); otherwise the before side is not retired and the event is malformed | both |
| I7 | `retired === !Object.hasOwn(snapshot.byCom, com.toLowerCase())` for every before entry | both |
| I8 | Within one event no two entries on the same side share a code; before and after codes may coincide only per I6 | both |
| I9 | `updates` ascending by `published`, unique years; `coverage` equals its first/last or null when empty; `events` sorted as stated; every year in `updates` has at least one event | generator derives, CI asserts |
| I10 | Committed file size `<= HISTORY_MAX_BYTES(updates.length)` (section 3.4) | CI |
| I11 | No U+FFFD anywhere; the file parses as UTF-8 JSON | both |

### 3.4 Size bound (FR-05)

Estimate, from the measured 2025 annotation counts (55 `split` + 29 `split; range` + a
handful of `split; groups added` / `split; concept change` daughter rows, 27+ `lump` survivor
rows): about 40 split events and 30 lump events per update. A minified entry is ~75 bytes
(code 8, sci to 33, com to 63 measured maxima; typical far shorter); a split event with one
parent, two or three daughters and up to one slash is ~360 bytes, a lump ~300 bytes. So
**~25 KB per covered update**, ~75 KB for the first ship's three updates, ~300 KB if coverage
ever reaches 2013.

Declared in the CI test as a formula over the asset's own `updates.length`, so it grows with
coverage deliberately and never needs a hand edit at the annual refresh:

```ts
/** 64 KiB per covered update (2.6x the measured ~25 KB estimate) plus 16 KiB of envelope,
 *  with an absolute ceiling so a generator that emits a whole taxonomy still fails. */
export const HISTORY_BYTES_PER_UPDATE = 65_536
export const HISTORY_BYTES_ENVELOPE = 16_384
export const HISTORY_BYTES_CEILING = 1_048_576
export const historyMaxBytes = (updates: number) =>
  Math.min(HISTORY_BYTES_CEILING, HISTORY_BYTES_ENVELOPE + HISTORY_BYTES_PER_UPDATE * updates)
```

The constants live in `lib/taxonomyHistoryAsset.ts` and the test imports them (never
re-spells them). The bound is on the committed file's byte length (`Buffer.byteLength` of the
raw file), not on a gzip figure. The asset is off the entry chunk, so this bound is a
garbage-detector, not a first-paint budget.

## 4. The generator

### 4.1 Location and inputs

- **Script:** `scripts/build-taxonomy-history.mjs` (CLI entry, node built-ins only, no
  dependencies, same class as `build-ebird-taxonomy.mjs`). Its pure core lives in
  `scripts/lib/taxonomyHistoryDerive.mjs` (parse, join, derive, validate; no `process`, no
  `fs`, no app imports) so a vitest suite can import and mutation-test it (QA-02, QA-04).
- **Inputs directory:** `scripts/taxonomy-history-input/`, **gitignored** (add
  `scripts/taxonomy-history-input/` to `.gitignore`). Cornell's files are ~4 to 11 MB each,
  are Cornell's data, and are re-downloadable; the committed artifact is the output, exactly
  as the countability and taxonomy snapshots are committed without their API responses. A
  `scripts/taxonomy-history-input/README.md` (committed; the directory's only tracked file,
  un-ignored with `!scripts/taxonomy-history-input/README.md`) lists the required files, their
  Cornell download page, and the fact that the developer downloads them **in a browser**
  (birds.cornell.edu answers automated clients with a Cloudflare 403; measured 2026-09-30).
- **Files per covered update year Y**, named by the developer to this convention (the script
  refuses any other name, so provenance is unambiguous in `inputs`):
  - `clements-integrated-vY.csv`: the "eBird/Clements integrated checklist vY" CSV. Supplies
    the change annotation, the "text for website" sentence, the previous-year sort key, and
    the category. **Only the CSV form is accepted**; when Cornell's CSV is unavailable, the
    developer exports the XLSX to CSV (UTF-8) by hand and names it the same way.
  - `ebird-taxonomy-vY.csv`: the eBird taxonomy file for Y (`eBird_taxonomy_vY.csv` from the
    same download page, or the API's `ref/taxonomy/ebird?version=Y&fmt=csv`, which answered
    without a key for 2025 in this investigation). Supplies codes, names and categories for
    the after side and the slash taxa.
  - Plus `ebird-taxonomy-v(P).csv` for P = the eBird update immediately before the earliest
    covered Y. Supplies the before side's codes and names for the earliest event year. Every
    other year's before side comes from the previous covered year's taxonomy file.
- **Also read:** the committed `frontend/src/assets/ebird-taxonomy.json`, for I1, I5, I6 and I7.
  The generator never fetches; it does not read `EBIRD_API_KEY`.

Column handling is **header-driven by name, never by position**, because the layout moved
every year (measured: 13 to 17 columns, `species_code` present from v2023 only, the concept id
present in 2023 and 2025 but not 2024, a `v2024b` suffix in the change/text headers). Required
integrated columns, matched case-insensitively after trimming: `category`,
`English name`, `scientific name`, `/^clements v\d{4}[a-z]? change$/`,
`/^text for website v\d{4}[a-z]?$/`, and a previous-sort column `/^sort[ _]v?(\d{4})$/` whose
year is not the file's own. Required taxonomy columns (Cornell layout or the API layout):
`SPECIES_CODE`, `CATEGORY`, `PRIMARY_COM_NAME` or `COMMON_NAME`, `SCI_NAME` or
`SCIENTIFIC_NAME`. A missing required header is a fail-closed exit naming the file and header.
`species_code` and `taxon concept ID` in the integrated file are **not used**: the first is
absent before 2023 and the second is absent in 2024, so neither can be the join.

CSV parsing is a hand-written RFC 4180 reader in `taxonomyHistoryDerive.mjs` (quoted fields,
doubled quotes, embedded newlines; the `range` and `text for website` cells carry all three),
with a leading BOM stripped. Any U+FFFD in a name cell is a fail-closed exit (a Latin-1 file
read as UTF-8), never a silent mis-name.

### 4.2 Derivation, per covered year Y (with P = previous eBird update year)

Let `taxY` and `taxP` be the taxonomy files indexed by code and by lowercase scientific name
(species category only for the sci index; all categories for the code index). Let `intY` be the
integrated file's rows with `category === 'species'`.

**Join.** Each `intY` species row joins to `taxY` by lowercase scientific name (species
scientific names are unique within a year; the generator asserts this and fails closed on a
duplicate). Apostrophes are normalized U+2019 to U+0027 for the join key only; **emitted names
always come from the taxonomy file**, never from the integrated file's `English name`, so the
asset carries the strings eBird exports carry.

**Split rows.** An `intY` species row whose change cell contains the token `split` (word match,
case-insensitive; the cell is free text such as `split; range`, `split; groups added`) is a
daughter. Its parent is resolved two independent ways and both must agree where both answer:

1. *Previous-sort link.* The row's previous-sort cell, when non-empty, names a row of the
   previous integrated file (`clements-integrated-vP.csv`, required when any daughter in Y has
   a non-empty previous sort; measured: 23,532 of 23,558 resolvable v2025 rows link this way,
   blank on 312 genuinely new rows). If that row is a species row, its taxonomy entry in `taxP`
   is a parent candidate. If it is a group or subspecies row it contributes nothing (a daughter
   promoted from a group links to the group).
2. *Text mention.* Every `taxP` species whose scientific name occurs in the "text for website"
   cell as a whole binomial (word-bounded, case-insensitive) is a parent candidate **unless**
   that scientific name is also a species in `taxY` under the same code (it is then a
   daughter's own name being mentioned, not the parent). Measured on 2025: "Polytypic Whimbrel
   Numenius phaeopus ... is split into ... Eurasian Whimbrel Numenius phaeopus ... and ...
   Hudsonian Whimbrel Numenius hudsonicus" yields the single candidate `whimbr` (phaeopus was
   `whimbr` in 2024 and is `whimbr5` in 2025, so the same-code exclusion does not remove it);
   the Warbling Vireo text yields `warvir` alone (swainsoni was not a 2024 species).

The candidate set (union, keyed by `taxP` code) must have **exactly one** member; zero or two
or more is a fail-closed exit naming the row and every candidate. Daughters are then grouped by
parent code (never by identical text, which 2023's "X is split from Y" phrasing does not
provide). A group with fewer than two daughters fails closed (FR-04). The event's before entry
is the parent from `taxP`; after entries are the daughters from `taxY`.

**Slash taxa of a split.** From `taxY`, every `CATEGORY === 'slash'` row whose scientific name
parses as `Genus e1/e2[/e3...]` where `Genus` equals every daughter's genus and every epithet
is some daughter's epithet, **and** whose code is either absent from `taxP` or equal to the
parent's code (finding 2.1). Zero or more; absence is not a failure. Any other slash (a
pre-existing one, a spuh, a slash spanning a non-daughter) is excluded.

**Lump rows.** An `intY` species row whose change cell contains the token `lump` is the
survivor (after side, from `taxY`). The before side is the union of:

1. the survivor's own previous identity: its previous-sort row's `taxP` species entry (usually
   the same code, sometimes re-coded: measured `impcor1` to `impcor6`), or when the
   previous-sort is blank, the `taxP` species with the survivor's scientific name; and
2. every `taxP` species whose scientific name occurs in the text cell as a whole binomial and
   which is **not a species in `taxY`** (retired), e.g. "Monotypic Maghreb Owl Strix mauritanica
   is lumped with polytypic Tawny Owl Strix aluco, as Tawny Owl Strix aluco" yields
   `tawowl3`; the three shags of the Imperial Cormorant lump yield three entries.

Deduplicated by code. Fewer than two before entries is a fail-closed exit (FR-04). A row whose
change cell carries both `split` and `lump` (measured: 4 rows in v2024) is processed under both
rules; if either half fails, the run fails closed naming the row.

**Published date.** A constant table in `taxonomyHistoryDerive.mjs`, `UPDATE_PUBLISHED`,
maps year to the day eBird announced that update complete on ebird.org, each row carrying its
source URL in a comment and a `measured` / `assumed` mark. A covered year with no row, or a
row marked `assumed`, is a fail-closed exit: an assumed date must be verified and its mark
changed before the year can ship. Measured as of this document: 2025 `2025-10-31`,
2024 `2024-10-22`, 2023 `2023-10-24`, 2022 `2022-11-01`, 2021 `2021-09-08`, 2019 `2019-08-21`,
2018 `2018-08-17`, 2017 `2017-08-18`, 2013 `2013-10-14`; 2014 to 2016 assumed from search
snippets only. No eBird update was released in 2020. FR-02's "never hand-typed" governs
coverage; the date of an update is a published fact the spreadsheets do not carry, so a cited
table is the honest source, and the generator refuses to run on an unverified row.

**Coverage.** `updates` is derived from the years for which events were produced, ascending.
The generator requires the covered years to be **consecutive eBird updates** (2020 is the one
known gap, held in `YEARS_WITHOUT_UPDATE = [2020]`); a hole in the provided inputs is a
fail-closed exit, so "covers 2023 to 2025" is literally true of every update between.

### 4.3 Complete fail-closed list (QA-04 fixture rows)

Missing or unrecognised input file name; missing required header; U+FFFD in a name cell;
duplicate species scientific name within a taxonomy file; an integrated species row that joins
to no taxonomy row; a split daughter with zero or more than one parent candidate; a split
group with one daughter; a parent whose code is a current species not among its own
daughters (I6); a lump with fewer than two before entries; a lump before entry that is still a
species in `taxY`; an after-side code missing from the bundled snapshot, or present with a
different common name (I5); a slash code missing from the snapshot or present as a species;
a covered year with no `UPDATE_PUBLISHED` row or an `assumed` one; non-consecutive covered
years; a year that produced zero events (the developer removes it from the inputs; silence is
not coverage); an output that fails any of I1 to I11 on re-read. Every exit is non-zero, names
the offending row or file, and **writes no output**: the generator serialises to memory,
validates the serialised object against the same invariant checker CI uses (exported from
`taxonomyHistoryDerive.mjs`), and only then writes the file.

`coverage` states it to the user; whichever year fails closed is simply not covered, and the
UI's coverage statement says so. Never hand-type an event to extend the range.

### 4.5 Annual refresh

Joins the release-time snapshot re-run: after `build-ebird-taxonomy.mjs` writes the new
snapshot, the developer adds the new year's two files and re-runs
`node scripts/build-taxonomy-history.mjs`. I1 makes the pairing mandatory: a fresh snapshot
under a stale `snapshot` field turns CI red, exactly as `countableForms.test.ts` does for the
countability artifact. Document the step in `build-ebird-taxonomy.mjs`'s header comment and in
the input README.

## 5. CI guards

### 5.1 `frontend/src/lib/taxonomyHistoryAsset.test.ts` (QA-01, QA-02, QA-05)

Reads the committed asset and the committed snapshot with `readFileSync` (the countability
guard's shape) and asserts I1 through I11 from section 3.3 by calling the **shared invariant
checker** imported from `scripts/lib/taxonomyHistoryDerive.mjs` **and** re-asserting the load-
bearing rows independently in the test body (I1, I5, I7, I9, I10), so a checker weakened in
the script cannot pass the test by itself. The size assertion reads `historyMaxBytes` from the
loader module rather than re-spelling the constants. Mutation rows (each verified red, then
restored byte-identical): a re-spelled `snapshot`; one after-side code changed to a retired
one; one `retired` flag flipped; `coverage.latest` moved; a split with one daughter; an
event whose `published` is not in `updates`; the file padded past the bound.

If importing `scripts/lib/*.mjs` from the frontend vitest root is refused (Vite's `fs.allow`
covers the dev server, and out-of-root ESM imports are expected to work in vitest, but this is
measured on the first run, not assumed), the fallback is a copy of the checker under
`frontend/src/lib/taxonomyHistoryInvariants.ts` imported by both, with the script reaching it
through a relative `import()`; the test then pins the two byte-identical.

### 5.2 `frontend/src/lib/taxonomyHistoryGenerator.test.ts` (QA-02, QA-03, QA-04)

Drives `deriveHistory(inputs)` from `taxonomyHistoryDerive.mjs` over small in-memory CSV
fixtures (strings in the test, never real Cornell data): a two-update fixture yields exactly
that coverage; a zero-event input yields the stated empty coverage; the QA-03 chain fixture
(A splits X into Y and Z; B lumps Y with W into V) produces two dated events with Y an

## 6. The derivation: `frontend/src/lib/taxonomyHistory.ts`

Pure. No React, no I/O, no `Date.now()`, no `transport`, no `storage`. Imports
`normalizeSpeciesName` and `isNonCountableForm` from `speciesUtils` (NFR-07: the shared fold
and the shared countability predicate, nothing local) and `SPECIES_CODE_RE` from
`speciesCode`.

### 6.1 Inputs

```ts
export interface HistoryCodeLookup {
  /** The page's existing `/taxonomy/codes` result (`taxonMap` in SpeciesDetail.tsx), keyed
   *  by the name AS SENT (raw and normalized names are both sent). Read only through
   *  Object.hasOwn: a species name out of the CSV is an external-string key (security.md
   *  v1.0.22; `taxonCodeFor` in the same file is the shape NOT to copy). Empty when the
   *  batch failed or has not landed (offline web/Pi): only the name tiers then apply. */
  codes: Readonly<Record<string, string>>
}

export function buildTaxonomyHistoryIndex(
  observations: readonly ObservationEntry[],
  history: TaxonomyHistory,
  lookup: HistoryCodeLookup,
): TaxonomyHistoryIndex
```

The index builds its own merged-key to first-scientific-name map inside its single row pass
rather than taking the page's `sciNameMap`, so its memo depends on neither `mergeSubspecies`
nor `taxonOrders` (NFR-03: once per backup, asset and codes, never on a mode flip).

### 6.2 Matching a merged key to entries (the FR-06 / FR-07 / FR-19 contract)

Per distinct merged key `k` (= `normalizeSpeciesName(o.commonName)` over countable rows),
with `sci` = the first scientific name seen under `k`, in this order, **stopping at the first
tier that yields any entry**:

- **Tier 0, retired-name identity (finding 2.2, enables FR-19):** every before entry whose
  `retired === true` and `com.toLowerCase() === k.toLowerCase()`. Index:
  `Map<lowerCom, entryId[]>` over retired before entries only.
- **Tier 1, current code (FR-06):** `code = Object.hasOwn(lookup.codes, k) ? lookup.codes[k]
  : undefined` (the merged key is always sent by `fetchTaxonData`); if defined and passes
  `SPECIES_CODE_RE`, every after entry with that code, and every before entry with that code
  **on an event where no after entry has it** (finding 2.1: structurally near-empty, kept so
  FR-06's "either side" is literally implemented). Slash entries are never matched by key
  (FR-08).
- **Tier 2, asset names (FR-07):** only when tier 1 yielded no code at all. First the exact
  pair (`sci`, `k`) against every entry's (`sci`, `com`) lowercased; then `sci` alone (an
  ambiguous sci, which a split leaves on the nominate daughter and its parent, prefers after
  entries, then before); then `k` alone. Scientific name wins over a conflicting common name
  (QA-07) because the pair and sci steps run first.

A key matching nothing is not affected. The result per key is `entryId[]` (small: at most one
entry per event, in practice one to three). Within one event a key maps to at most one entry
(tier 0 stops before tier 1; tier 1 prefers after over before; tier 2's precedence is total),
which is what makes "the user's species marked in the lineage" a single marker per event.

**Stated limit:** a split whose nominate daughter keeps the parent's exact common name (before
`com` not retired, I7 false) cannot be told apart from a post-update export by name, so tier 0
never fires for it and FR-19 cannot be detected; rows dated before the update then show as
reassigned by eBird on the after side, which is what eBird's conversion did to the nominate
share anyway. The generator emits `retired: false` for such an entry and the section shows it
without the predates label.

### 6.3 The row pass (one pass, every row visited once)

```
for each row o:
  if isNonCountableForm(o.commonName):
    e = slashByRawName.get(o.commonName)          // exact raw name (FR-08 exception)
    if e: tally(e, o.date)
    continue                                        // hybrids, spuhs, other slashes: nowhere
  k = normalizeSpeciesName(o.commonName)            // forms roll up (FR-08)
  ids = entriesByKey.get(k)                         // resolved lazily on first sight of k
  for id of ids: tally(id, o.date)
```

`tally(id, date)`: `count += 1`; `if (date <= event.published) onOrBefore += 1`
(lexical compare of `YYYY-MM-DD` strings, the page's own date-filter convention at
`SpeciesDetail.tsx:444`; a row dated exactly on the published date is on-or-before, FR-16).
`after` is derived as `count - onOrBefore`, so the partitions sum exactly by construction
(FR-16, QA-16). **Accepted limit, stated:** the parser does not validate the date cell, so a
malformed date sorts wherever lexical order puts it, identically to the tab's own filters
(FR-25 same-content-by-any-route); eBird writes `YYYY-MM-DD` on every row.

The first sight of a key resolves it through 6.2 and caches the `entryId[]` (or an empty
array) in `entriesByKey`, so resolution runs once per distinct key, not per row.

### 6.4 Output

```ts
export interface TaxonomyHistoryIndex {
  coverage: TaxonomyHistory['coverage']
  /** Merged keys that matched at least one entry, in first-seen order; the list control
   *  intersects sortedSpeciesList with this (FR-11 order). */
  affected: ReadonlyMap<string, AffectedSpecies>
  /** Every event, with per-entry tallies attached. Index-addressable by eventIndex. */
  events: readonly EventView[]
}

export interface AffectedSpecies {
  key: string
  /** Every event that touches the key, DIRECTLY (6.2) or through the chain (6.5), in date
   *  order ascending. The list shows these most recent first (FR-11); the section shows
   *  them earliest first (FR-15). */
  events: readonly { eventIndex: number; kind: 'split' | 'lump'; year: number; direct: boolean }[]
}

export interface EventView {
  kind: 'split' | 'lump'
  year: number
  published: string
  before: readonly EntryView[]
  after: readonly EntryView[]
  /** Only the slashes the user holds rows under (FR-14): count > 0. */
  slashes: readonly EntryView[]
  /** FR-19: some before entry has count > 0 and every after entry has count === 0. Per event,
   *  independent of the selected species. */
  predates: boolean
}

export interface EntryView {
  code: string
  sci: string
  com: string
  /** Rows matched to this entry in the full backup (FR-09, FR-16). 0 = "not in your data". */
  count: number
  onOrBefore: number
  after: number
  /** The merged key whose rows matched this entry, for the selected-species marker
   *  (FR-14) and for linking through the page's selection path (FR-23); null when count
   *  is 0 or the entry is a slash (a slash is never a selectable species). Where two
   *  distinct keys match one entry (structurally possible only through tier 2), the first
   *  seen wins for linking and both keys' rows are counted. */
  speciesKey: string | null
  /** Added at the security review (L1): true only for an after-side entry whose code is
   *  still a species after every covered update, the one kind of entry that may carry the
   *  eBird and Birds of the World marks. Decided from the asset alone: a code is current
   *  when the latest update that carries it has it on an after side (I5 and I6 make that
   *  equal to "a species in the snapshot", and CI holds it to the snapshot). */
  current: boolean
}
```

Absence is expressed inside the objects (`count: 0`, `speciesKey: null`, `coverage: null`),
never as a `null` field on a member: this index does not join the stats worker bundle, but the
house rule is followed anyway so it could.

`lineageFor(index, key): AffectedSpecies | null` is a `Map.get`; the section renders
`index.events[eventIndex]` for each and marks the entry whose `speciesKey === key`.
`predates` and the FR-19 rule "show no after partition" are the section's concern: the
derivation always carries both partitions, because an export made inside eBird's multi-week
conversion window can legitimately hold a retired name with a row dated after the published
day, and hiding the number is a presentation decision the PRD makes, not a fact the data layer
should erase.

### 6.5 Chain (FR-03, FR-15)

At index build, over the asset alone (O(events x entries), tiny): for each event E and each
after entry a of E, every LATER event F with a before entry of the same code links E to F
(`next[E] += F`, `prev[F] += E`); a same-event code coincidence (finding 2.1) is not a link
because the years are equal. A species' `events` are the closure of its directly matched
events over `prev` and `next`, sorted by `published`. `direct` marks which events the user's
rows matched; chain-only events render with their own tallies (which may all be zero, then
every entry shows "not in your data"), so the reader follows the lineage while the counts stay
honest.

### 6.6 Declared scans over user-file content (CLAUDE.md, `.claude/rules/security.md` v1.0.23)

| Scan | Where | Input | Shape and bound |
|---|---|---|---|
| Row pass | `buildTaxonomyHistoryIndex`, 6.3 | every row's `commonName`, `date` | Per row: one `isNonCountableForm` (two `Set.has` on the raw string plus the shipped shape predicate, linear in the name), one `normalizeSpeciesName` (memoized, linear scan, 128-char key bound), one `Map.get` on the raw or merged name (hash of the string, linear in its length), and per matched entry one lexical string compare against a 10-char constant (bounded by the shorter operand). No nested scan, no regex, no `includes` / `indexOf` / `find` in the loop. Total O(sum of row string lengths) |
| Key resolution | first sight of a key, 6.2 | the merged key and its first scientific name | One `Object.hasOwn` on `lookup.codes`, one `SPECIES_CODE_RE` test on a value the seam already bounded, up to four `Map.get`s on lowercased strings (`toLowerCase` linear in the key). Once per distinct key, so at most once per row and in practice far fewer |
| Retired-name resolution (`midChainTier0`, added at QA fix errand 2) | key resolution, tier 0 only | a merged key equal, ignoring case, to a retired before-side name | Runs only when tier 0 matches, once per distinct key. Per call: for each matched before entry, one `Map.get` on its code and one date compare per after entry carrying that code, then one pass keeping one entry per event. Bounded by the asset (the entries that share one code), never by the file. A file multiplies tier-0 keys only through case variants of a retired name, each its own key, so the total is O(distinct tier-0 keys x that bound), at most one call per row |
| Lineage walk (`lineageEvents` and the affected loop, added at QA fix errand 1; replaces 6.5's once-per-asset closure) | after the row pass, once per AFFECTED key | each affected key's matched entry ids | Per matched entry, one forward and one backward walk over the asset's chain. Each event is visited at most once per direction (`fwdSeen` / `bwdSeen`) under a strictly monotone date test, so the walk terminates even on a cyclic asset. Then one sort of that key's events. Per key O(events + entries) of the asset, plus a sort bounded by the events. Total O(distinct affected keys x that bound): linear in the rows, because a key costs at most one row |
| Chain maps and current codes (`withBefore` / `withAfter`, `currentAfterCode`) | once per index build | none (asset only) | O(events x entries); asset bounded by 3.4 |

No scan over raw CSV text; every input is a parsed field. Every native search the pass relies on
is a hash lookup or a bounded compare; there is no `indexOf` whose end is the end of the whole
string. **Measurement duty for the Engineer (security.md's method):** time
`buildTaxonomyHistoryIndex` through its real exported entry point at 10k, 20k and 40k rows of
the reference export shape and require roughly 2x per doubling; and run a hostile leg where
every row carries a 4,000-character common name and a 4,000-character date, which must scale
the same way. **Corrected at the security review (L2):** both legs hold 5 to 7 distinct names,
so they never exercise the per-key rows above at volume. A third leg makes every row its own
affected key over the real asset (half tier 2, half case variants of a retired name, so tier 0
and `midChainTier0` too), 10k against 40k rows, held to the same quotient. The Auditor measured
the distinct-key path at 14, 25, 58 and 118 ms for 10k, 20k, 40k and 80k rows.

**Memory:** the index retains per entry three integers and one key reference, per distinct key
one small array of entry ids, and nothing per row. Bounded by entries x keys, never by rows.

### 7.2 The loader: `frontend/src/lib/taxonomyHistoryAsset.ts`

```ts
let pending: Promise<TaxonomyHistory | null> | null = null
export function loadTaxonomyHistory(): Promise<TaxonomyHistory | null> {
  pending ??= import('../assets/ebird-taxonomy-history.json')
    .then((m) => (isHistoryShape(m.default) ? (m.default as TaxonomyHistory) : null))
    .catch(() => null)
  return pending
}
```

## 8. Persistence: none

- No storage-seam document, no setting, no cache, no `localStorage`, no `docChains` link, no
  `CACHED_GET_PATHS` or `EBIRD_GATED_PATHS` change, no replay entry, no iCloud scope change,
  no `PRIVACY_POLICY.md` change.
- The index is an in-memory derived value keyed on a user data file and held in component
  state. Per CLAUDE.md it is **outside `clearDerived.ts` by design** (every registry row is an
  on-disk document ending in `storage.deleteSetting`, and `cacheInventory.test.ts` would go red
  for a store that does not exist). What terminates it when the file is deleted is stated at
  the definition site: the memo's `observations` dependency changes on the new load and the
  old index becomes unreachable; a `SpeciesDetail` tab is never unmounted, so the index lives as
  long as the current backup does, which is the same lifetime `subspeciesIndex` has today.
- The loaded asset (`history`) is session-scoped and not keyed on user data; it is the same
  object for every backup.
