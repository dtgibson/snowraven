### 8. The web/Pi saved copy: the mechanism chosen

**Stamp the disk twin with the bundled snapshot's `version`, and use it offline only when the stamps match.** Every live fetch is saved with `version` set to the version of the snapshot this build ships (read from `backend/staticdata/ebird_taxonomy.json` at the first floor load, `""` when that file is absent). `_load_floor` prefers the disk twin only when its `version` equals the bundled snapshot's; otherwise the bundled snapshot serves. The existing `version` field carries the stamp, so the file shape is unchanged.

Why this and not a fetch date:

- **It is the desktop's rule, exactly.** The desktop keys its saved copy by `CACHE_KEY`, so bumping `taxonomy-v2027` to `taxonomy-v2028` stops it reading copies saved under the old counter. Equal stamps give the web/Pi backend the same behaviour from the same hand-bump, with no edit to the backend at the annual revision.
- **No clock.** A Pi with no real-time clock can stamp a wrong date; a version stamp cannot be wrong that way.
- **Equality, not "greater than".** On a downgrade (an older release over a newer saved copy) the older bundled snapshot serves offline until the next online fetch. That is also what the desktop does, and it needs no number parsing.

The three behaviours the brief asked for:

1. **A fetch that differs rewrites the twin** (a fetch the router accepts; one it refuses is never saved, see the audit fixes below). `_saved_copy_differs` replaces `_disk_version`: it re-reads the twin and returns true when it is absent or unreadable, carries another `version`, or holds any of the five maps unequal to the fetch. Only then is `_persist` (write-temp-then-rename, unchanged) called, so an unchanged fetch still writes nothing.
2. **A newer bundled snapshot beats an older saved copy offline**, by the stamp rule above. A twin written by any earlier build carries `version: ""`, so after this ships it never matches and the bundled snapshot serves until the next online fetch restamps it. On this Mac that copy's maps equal the 2025 snapshot today, so nothing a user sees changes.
3. **A server older than seven days re-fetches.** `_fresh_until` (monotonic clock, `_MAX_AGE_S` = seven days, the desktop's `SEVEN_DAYS_MS`) is set by every load. Once past it, the next request re-runs the load under the same coalescing lock, keeping the maps already in memory as its floor. The monotonic clock is deliberate: a Pi that sets its wall clock from the network after boot neither triggers nor postpones a refresh.

Kept: the same `ref/taxonomy/ebird` call from the same component, no new endpoint, host or route, the coalescing lock and its mandatory second check, fail-to-floor, write-temp-then-rename, and `DATA_DIR` from `datadir.py`. `PRIVACY_POLICY.md` needs no change: no request is added, moved or sent anywhere new; the existing request simply repeats once a week on a long-running server.

Two smaller decisions, each with its reason:

- **A failed seven-day refresh waits another seven days.** A refresh fails when eBird does not answer, answers with an error status, or answers 200 with a body that is too short or cannot be turned into maps (the last two since the audit fixes below). The maps in memory keep serving, and the clock restarts, rather than retrying on every request: each attempt can take 30 s or longer (the timeout is per phase), so a per-request retry would stall every page of an offline server. The cost is that a server offline at its refresh misses an update for one more week. A shorter retry would need a second constant; not earned yet.
- **`_fresh_until` starts at infinity.** The parity tests (`test_taxonomy_collapse_parity.py`) inject maps by setting `_loaded = True` directly. With a zero start, a Mac up for more than seven days (the monotonic clock counts from boot) would have sent those tests to the network and to the real `data/` directory. Starting at infinity means maps injected that way never age; every real load sets a finite deadline. The new tests' fake clock starts at the real `time.monotonic()`, so the deadline they leave behind is in the real future for any later test.

Known limitation: the seven-day refresh runs inside the request that finds the maps expired, as the first load already does, and every taxonomy request that arrives while it runs (`/taxonomy/codes`, `/map/county-species`, `/checklists/{checklist_id}`) waits for it, not only the one that triggered it. The coalescing lock bounds the fan-out: however many requests wait, they share one fetch. It happens at most once a week: every load, and every failed refresh with maps to fall back on, sets the next deadline seven days out on the server's monotonic clock, and a client can only be the first request after that deadline, never bring it forward. Online the wait is seconds. The fetch's `timeout=30.0` is httpx's per-phase timeout (connect, read, write and pool, 30 s each), not a bound on the whole download, so a connection that keeps trickling bytes can hold the refresh longer than 30 s. A background refresh would remove the wait, and `asyncio.wait_for` around the fetch would give a true total deadline; neither was asked for, and the Auditor accepted the residual (security report, F4).

**Declared read (security.md, Improve-lane form).** `_saved_copy_differs` adds one read of the app-written disk twin per successful load and one comparison of two parsed documents, linear in their size, with no loop driven by a number in the file. Measured on the real 1,737,479-byte snapshot on this Mac: 9.9 ms to parse one file, 1.8 ms to compare five equal maps (best of 7). `_load_floor` now parses both files at a cold start where it parsed one. It is not user-file content (no export text is scanned) and no new scan over user data is added.

### 13. F1: the refresh's `try` covers the builder and the apply

- The plausibility check (section 14), `_derive_from_taxonomy` and `_apply_snapshot` now run inside the same `try` as the fetch. A 200 the router cannot turn into maps therefore takes the failed-refresh path: the loaded maps keep serving, nothing is saved, and the next attempt waits seven days (`.claude/rules/security.md`, v1.0.29).
- **One shape beyond the report's list, and why the fix reaches `_apply_snapshot`.** A form (any category but species) whose `comName` is a non-string truthy value (measured with `5`) passes `_derive_from_taxonomy`, then raised in `_rebuild_by_com_all` inside `_apply_snapshot`, after the five maps had been replaced. Moving only the derive call would have left that shape on F1's loop with the maps half-replaced. `_rebuild_by_com_all` is now `_by_com_all_for(by_code)`, a pure function named after the desktop twin `byComAllFor`, and `_apply_snapshot` calls it before it clears any map, so a bundle that cannot be applied leaves the loaded maps exactly as they were. The inversion and its last-wins order are unchanged, so every well-formed bundle and the floor path behave as before; a hand-edited floor with such a name now falls to the other source without touching the maps first. Likelihood is low: eBird's names are strings, and `null`, the plausible malformed value, never raised there because `if name` skips it.
- The cold-start case closes with the same move: with no floor at all, a malformed 200 raises and leaves `_loaded` false, as a failed fetch with no floor does.
- **Found, not fixed.** A body whose values have the wrong type but derive and apply cleanly is accepted and saved. Measured in scratch: a form whose `reportAs` is a list loads without error, and `resolve_species` and `collapse_to_species_list` then raise `TypeError` for that code at request time. That is one fetch a week, not F1's loop, and the desktop twin accepts the same body. Closing it means a per-field type check on both transports, which neither the brief nor the report asked for.

### 14. F2: a plausibility floor before anything is applied or saved

- `_MIN_ENTRIES = 100` sits beside the fetch, with a comment naming its twin: `fetchTaxonomyOnline` in `frontend/src/lib/tauri/taxonomyService.ts` refuses a non-array or fewer than 100 entries. The backend refuses the same response the same way (not a list, or `len < 100`) inside the `try`, so it is a failed refresh. On a refresh the maps are kept and nothing is saved over the good copy; on a first load with a floor, the floor serves; with no floor, the load raises as before. eBird publishes some 17,900 entries, so this is a sanity floor, not a tight bound. The desktop's rule was matched, as the brief asked, rather than the report's alternative of a fraction of the bundled snapshot's count, which would also vanish when the snapshot is absent.
- The two declarations are compared, not restated: the F2 row reads the TypeScript source with comments stripped and asserts that its one `taxonomy.length < N` figure equals `_MIN_ENTRIES` as shipped.
- The constant is read at call time, so test fixtures can patch it down to 1 (refusing only an empty list), because their fake taxonomies hold one to nine entries. The patch is in the isolation fixtures of the three files that drive the live fetch: `test_taxonomy_router.py`, `test_checklists_router.py` and `test_checklists_projects_route.py`. - Declared read (security.md, Improve-lane form): the check is a type test and a `len()`, constant time, and adds no scan. The reverse map moved earlier in `_apply_snapshot`; it is still one pass over `byCode`.
