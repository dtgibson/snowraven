## Tide Timezone Parse

### What this does

`_epoch_min` in `backend/services/tide.py` converted NOAA `lst_ldt` wall-clock
strings with a naive `datetime(y, mo, d, h, mi).timestamp()`, which resolves in
whatever zone the **server process** runs in. The same string therefore read
differently on two machines, and on a server whose own clock crossed a daylight
saving transition between two tide times the error reached a shipped figure: the
checklist tide rendered `Water level: 1.0 – 5.0 ft` where the correct range is
`1.5 – 4.5 ft`. The desktop twin `epochMin` (`frontend/src/lib/tide.ts`) already
used `Date.UTC` and was correct, so the two transports disagreed.

This converges the backend on the explicit form already used twice in this repo
(`services/tz_clock.py`'s `gmt_epoch`, and the TS `epochMin`): an anchored
ASCII-digit-class regex hoisted to a module constant, `tzinfo=timezone.utc`, and
a `ValueError` guard. The false "Calendar-correct epoch-minutes" docstring is
replaced with one stating the contract the code actually has.

Three defects close, only the first of which the brief predicted:

1. **Server-zone dependence.** The reading is now identical in every process
   zone, and equals the TS twin's.
2. **A Unicode-digit parity hole.** The old pattern used `\d`, which in Python
   matches every Unicode decimal digit while the TS twin's `\d` is ASCII-only.
   `٢٠٢٦-09-12 22:41` parsed to a real instant on the backend and to `0` on the
   desktop. This is the v0.5.54 twinned-guard character-class rule; the explicit
   `[0-9]` class closes it.
3. **An uncaught raise.** The naive call raises `ValueError: year 0 is out of
   range` near the calendar's start, and `compute_tide_reading` sits *outside*
   the routes' `try`, so a malformed NOAA body was a plain-text 500. It now
   returns `0.0`. (The broader "route `try` covers the builder" repair for the
   two `/at` handlers stays on ROADMAP and is not touched here.)

### How to test

```sh
# Before/after, under two zones. Both lines must now agree.
cd backend && for z in UTC America/Los_Angeles; do TZ=$z .venv/bin/python -c "
from services.tide import _epoch_min, compute_tide_reading
h=[{'t':'2026-11-01 01:00','v':0.0,'type':'L'},{'t':'2026-11-01 03:00','v':6.0,'type':'H'}]
r=compute_tide_reading('2026-11-01 01:30','2026-11-01 02:30',[],[],h,{'id':'X','name':'X'},1.0)
print('$z','span_min=',_epoch_min('2026-11-01 03:00')-_epoch_min('2026-11-01 01:00'),'level=',round(r.level_min,2),round(r.level_max,2))"; done

cd backend && TZ=UTC .venv/bin/python -m pytest tests/ -q
cd backend && TZ=America/Los_Angeles .venv/bin/python -m pytest tests/ -q
cd frontend && npx vitest run src/lib/tideEpoch.parity.test.ts src/lib/tide.test.ts
```

**Cross-transport parity.** `frontend/src/lib/tideEpoch.fixture.json` is
generated by an env-gated test driving the shipped `epochMin`
(`SR_GEN_TIDE_EPOCH_FIXTURE=1`), never hand-written, per the v1.0.29 rule. Both
`tideEpoch.parity.test.ts` and `backend/tests/test_tide_epoch_parity.py` drive it.

**Two twin divergences are pinned, not omitted.** Measured: `Date.UTC` rolls an
impossible calendar value over and maps years below `0100` into the 1900s, where
the Python twin returns `0.0`. These three rows ride in a `divergent` list
asserted on both sides, because a fixture of conforming strings cannot see one
twin raising where the other returns a value. None is a shape NOAA can emit.

**Deliberate carve-outs, stated in the test file so they are not "fixed" later.**
`_epoch_min` matches a *prefix* (`re.match`, no `$`) because the TS twin does;
`re.fullmatch` here would break parity, so this is not the v0.5.87 anchor rule
going unapplied. And there is no linearity timing row: the pattern is anchored
and fixed-width, so a hostile string fails inside 16 characters and a timing
fixture could not be made to fail against a revert. A structural row guards the
shape instead, and cannot flake.

**No bundle change, measured rather than asserted.** Three files were added
under `frontend/`, which Tailwind's auto source detection scans, so the built CSS
was A/B'd: `md5 91ae90a4f503b450b82e28c5c8b6ca5a`, 112,607 bytes, byte-identical
with the new files present and genuinely moved aside (the move was verified: 0
remaining, 3 in the holding directory), with a passing determinism control.

**A deferred decision is recorded, not silent.** The UTC form does not give true
elapsed time across the *station's* own DST transition. That scoping is ratified
with its evidence, reversal condition and exact fix in
`pipeline/tide-timezone-parse/decisions.md`; it is owed a `DECISIONS.md` and
`ROADMAP.md` entry at closeout.

### Changelog entry for the bundled release

No version bump in this build by design: it is one of five in a bundled Spool
release taking a single four-file bump. The line this build is owed, under
`### Fixed`:

> - Tide water levels no longer depend on the time zone of the server the app
>   talks to. On a server whose own clock crossed a daylight saving change
>   between two tide times, a checklist's tide could report the wrong water
>   level range (for example 1.0 to 5.0 ft instead of 1.5 to 4.5 ft). The web
>   and Raspberry Pi backend now reads NOAA times exactly as the desktop app
>   already did.

## Convention Flags

- A twinned helper pair records the inputs the two sides genuinely read
  differently in a `divergent` list inside the shared fixture, asserted on both
  sides, rather than restricting the fixture to inputs that agree. Omitting them
  makes a partial parity claim read as total; pinning them turns a future
  convergence or drift into a red row that names the decision record.
- When a shell harness moves files aside to measure a build A/B, it asserts the
  move happened (count the files at both ends) before trusting the comparison.
  An unquoted `$VAR` holding several paths does not word-split in zsh, so the
  `mv` fails, the "before" build is really the "after" build, and the harness
  reports IDENTICAL for the one reason that proves nothing.
