## Weather/tide Planner

### What this does
Adds a second action to the Weather tab's Predict form, **Plan sunrises and sunsets**, which builds a plan from now to the end of the weather forecast for the place already picked: every sunrise and sunset still ahead, each with its local time, the predicted tide height and trend, the high and low on either side, and the forecast weather in force (hourly for the first two days, then the day's summary, labeled exactly as Predict labels one). It renders as one horizontally scrolling chart on the location's own time axis plus a per-day list that carries every figure the chart draws. Both transports (FastAPI and the desktop TypeScript services) gain twinned range routes, `GET /weather/plan` and `GET /tide/plan`, whose builders are fixture-locked to byte-identical output; the merge runs once, on the client, for live, replayed and overridden plans alike.

### How to test
1. Backend: `cd backend && .venv/bin/python -m pytest tests/ -q` (438 pass; the new files are `test_weather_plan.py`, `test_tide_plan.py`, `test_weather_tide_plan_parity.py`, `test_tz_clock_parity.py`).
2. Frontend: `cd frontend && npm run typecheck && npm run lint && npx vitest run --maxWorkers=1 && npm run build`. The build must emit `PlanChart-*.js` and `vendor-recharts-*.js` as lazy chunks with neither in `dist/index.html`'s modulepreload (`entryChunk.test.ts` asserts it post-build).
3. Manually, in the built web app (`cd backend && .venv/bin/uvicorn main:app --port 1621`, open http://localhost:1621): Weather tab, press **Predict**, search a coastal place (e.g. "Del Monte Beach, Monterey"), press **Plan sunrises and sunsets**. Expect the status "Building the plan for ..." then a region named "Weather and tide plan" with the header, the station line (once), the chart, the legend, one day heading per forecast day, and the closing note. Scroll the chart sideways with the wheel, a drag, or arrow keys after tabbing to it.
4. Check each honest state: an inland place (e.g. "Panoche Valley") shows the too-far notice and **Show it anyway**, which fills the tide in without a second weather request; a non-US place shows the outside-US notice; remove the OpenWeather key in Settings and the action shows "API key not configured..."; go offline after a plan loaded and repeat the action to see the plan with the "Offline: showing the last loaded result" cue.
5. Confirm Predict's single-moment result and Current are unchanged: press **Get forecast** with a date two days out and see the `FORECAST · DAILY` pill and the ", forecast for that day" suffix exactly as before.

### Notes for reviewer
- The revised design (D4-12 to D4-18; Stage 5 D5-20 to D5-25): the mouse drag follows the pointer one to one under pointer capture with no snapping anywhere; a wide tier (641px and up) widens the Weather card to 1080px only while a plan is on screen (the card's width lifted to `.sr-weather-card`, everything else in it held at 476px by `.sr-weather-narrow`), gives the chart a day-header lane and a 220px plot, adds a Days in view control (1 / 3 / 7 / All, persisted as `planDaysInView` through the storage seam), and flows the list into two columns above 760px of region width; two day buttons in the legend row work on both tiers. The phone tier is DOM-identical to the shipped build apart from those two spec'd legend and snap-marker deltas (`planPhoneRender.test.tsx`).
- After the audit: both builders run inside their route's `try` on both transports (a semantically malformed provider body is a 502 / `unavailable`, never a 500 or a false "offline"), `composePlan` type-checks every printed field of a replayed half and drops a malformed entry rather than throwing, and the bundled station ids are pinned to `^[A-Za-z0-9]{7}$` (D5-17 to D5-19).
- After QA attempt 1: each day in the list now carries a "Tides:" line naming every high and low the chart draws on that day (the event brackets alone missed turning points that fell between two events), and a sky reading keeps only its glyph and clock unbreakable so the disclosure fits at 320px and 200% text scale (D5-15, D5-16).
- The tide span is derived from `now` and the location alone (schema D2), never from the forecast, so the override reproduces it without the weather; both NOAA range requests carry `time_zone=gmt` and land on the epoch axis; `/tide/at` and `fetch_tides` are byte-unchanged.
- `GET /tide/plan` and `getTidePlan` refuse without an OpenWeather key on purpose (schema D6): a tide half without the weather spine is not a plan, and this is what makes "zero NOAA requests without a key" structural.
- Deviations from the schema, each recorded in `decisions.md`: `PLAN_CURVE_MAX` is 448 rather than 432 (a fall-back day makes the nine-day span 434 samples, and the cap must sit above the largest conforming shape); a boundary day's partial daily cell carries the local clock it begins at in `local` rather than the day's noon, so the list's "from {time}" wording never computes a time in the UI; the halo contrast guard asserts "over each band, fill or halo clears 3:1" rather than "halo vs night 3.2:1 on dark", because on dark the halo is the night ground itself (the spec's stated dark figure was the halo-vs-day ratio).
- The chart's hour ticks on a DST day are placed by the day's own length from the document (every US zone changes its clock at 02:00, before 6 AM), which is arithmetic on document values, not a timezone conversion.
- The scroll container is the tab stop (`role="img"`, `tabIndex 0`); its child is `aria-hidden` and `inert` with `accessibilityLayer={false}` on the chart. Wheel and touch scrolling on an inert child hit-test to the scroller itself; that is the one claim here that only a browser can settle, so it is flagged for the Tester.
- The parity fixture (`weatherTidePlan.fixture.json`, ~1.1 MB) is generated by an env-gated vitest file (`SR_GEN_PLAN_FIXTURE=1 npx vitest run src/lib/weatherTidePlan.fixtureGen.test.ts`) from the shipped TS builders; the Python twin reproducing it from the same raw bodies is the parity claim.
- Predict's daily-summary wording is extracted to `lib/forecastLabels.ts` and imported by both surfaces; the single-moment result renders the same bytes (`WeatherForecastPanel.plan.test.tsx` asserts them).
