SnowRaven · Improve lane · Stage 2

Uniform Map FABs

One row of map furniture on all four Map Explorer views. Three discs of one diameter, one gap, one surface, one optical glyph weight, and a third disc whose glyph names the pin it commands.

1 · The family fix

Today the row is ragged. It should not be.

The share and locate discs reach the phone touch posture; the fullscreen disc stays at a fixed 36px at every width and every text scale. At 320px with 200% text scale the gap is at its worst: two 88px discs beside a 36px one. Hover any disc, and tab through them.

This change consumes almost all the horizontal slack in the cluster. Measured, not calculated. At 320px and 200% text scale the three discs plus two 10px gaps measure 284.00px, and the Filters pill's own row measures 139.14px, so the disc row is now the binding one. The cap is max-width: calc(100% - 32px), which resolves against the padding box of .sr-map-content: at a full 320px content box that is 288px and the slack is 4px. Anything that narrows that box reduces the slack one-for-one. On this page the specimen carries a 1px border, so the cap computes to 286px and the real slack is 2px, which is exactly the sort of difference that makes this a measurement and not a sum. Today the same row is 232px with 56px to spare.

The failure mode is bounded, because flex-wrap and justify-content: flex-end already handle it: if the row does not fit, the fullscreen disc wraps to its own line. Nothing goes off screen. Pre-approved escape hatch if the app measures short: drop the cluster's column gap to 8px in the ≤640 tier while keeping row-gap: 10px, which buys 4px and doubles the margin. Do not cap the disc below 2.75rem; that is the touch-target posture.

Measure the element box against its container's content box, never document.scrollWidth: a left overflow on an absolutely positioned element never extends scroll width, so a scrollWidth check will certify a broken build.

2 · My Sightings

Unchanged, except that the fullscreen disc joins the family

The flag still drops and moves the share pin. Press it to see the "holding a pin" tint.

3 · Hotspots

The new disc: a teardrop, because that is the pin it opens

On the three centre views the pin is the draggable search centre, and it is a teardrop. The FAB is a picture of it. Press the teardrop to open the same popup the pin opens; press again to close.

4 · Nearby Lifers

Open, and the disc says so

The accent tint here is carried by aria-expanded, not aria-pressed. Same visual, different property, different meaning: the flag's tint means "this map is holding a pin", this one means "the popup is open". They can never be on screen together, because a view is either My Sightings or a centre view.

5 · Media Targets

The state most likely to be missed: no centre set yet

On a first visit both coordinate fields are empty, so there is no pin and nothing to copy. The disc stays, dashed and disabled. It holds the row's shape, it stays focusable so a keyboard user can read what to do, and it never sets a centre, because that would re-run the search.

7 · The shared base

One base, two size modifiers, and a source order that matters

.sr-map-locate-btn is the third hand-written copy of the same eleven declarations. It becomes one base class. The semantic classes survive as state hooks only.

/* 1 */ .sr-map-fab            display, align, justify, padding, flex, background,
                          color, border, radius, cursor, shadow, transition
/* 2 */ .sr-map-fab svg        width/height: var(--sr-fab-glyph)
/* 3 */ .sr-map-fab:hover      background: var(--sr-surface-subtle)
/* 4 */ .sr-map-fab--std       --sr-fab-glyph: 1.0625rem;  2.25rem  (2.75rem @640)
        .sr-map-fab--compact   --sr-fab-glyph: 0.9375rem;  1.875rem (2.5rem  @640)
/* 5 */ .sr-share-drop-btn[aria-pressed="true"]
        .sr-map-locate-btn[aria-disabled="true"]
        .sr-map-center-share-btn[aria-expanded="true"]
        .sr-map-center-share-btn[aria-disabled="true"]
A base plus a modifier puts two same-specificity rules on one element, so source order decides. .sr-map-fab and .sr-map-fab--std are both (0,1,0), so the base must come first. The concrete regression this can introduce is at step 3 against step 5: .sr-map-fab:hover and .sr-share-drop-btn[aria-pressed="true"] are both (0,2,0) and both set background. Put the state rules above the base block and a hovered, pinned button silently loses its green tint, which no value diff would catch.
Per the repo's v0.5.81 convention this extraction needs a cascade-competitor scan at build time. It must cover every stylesheet the bundle emits, not only globals.css: SnowRaven also ships vendor-maplibre-*.css, and these buttons live inside a map container. Test the rightmost compound of each selector, and record the @layer as well as the specificity, since Tailwind preflight's * { padding: 0 } and its button border reset compete directly with the base. This is a class-to-class move, so specificity is unchanged at (0,1,0): the scan proves the new shared rule cannot be outranked, it does not repair a specificity drop. Say that in the test's own comment.
The glyph rule is not a tidy-up. Lucide's size={17} renders a px attribute, so a phone FAB grows 44px to 88px at 200% text scale while its glyph stays 17px. A glyph's unit must match its box's unit, or the ratio breaks at scale. Both go to rem and the ratio becomes scale-invariant by construction rather than correct at the one scale someone sampled. Keep the size props as the no-CSS fallback; CSS wins over presentational attributes.

Every colour on this page is an existing --sr-* token read from frontend/src/globals.css. No new token is introduced. Specimen sizes use calc(n × --fs) only to model three root font sizes inside one document; the shipped rule is plain rem.
