## upload-origin-table-wrap-copy

### What this does

Four confirmed defects, one fix. On the web/Pi backend, a state-changing request that a browser sends from another site is now refused with 403 before routing (so nothing is read or written): every browser write must carry the app's own `X-SnowRaven-Request: 1` header, which a page on another site cannot add, `POST /settings/{key}` requires `application/json`, and every response carries `X-Frame-Options: DENY`, `Content-Security-Policy: frame-ancestors 'none'`, `X-Content-Type-Options: nosniff` and `Referrer-Policy: strict-origin-when-cross-origin`. On every platform, the Targets Species cell wraps a long scientific name at phone widths instead of widening the table, and two Settings sentences now say where things are really saved (Appearance, per platform; Bar-chart files, "this server" on web/Pi).

### How to test

1. Backend: `cd backend && .venv/bin/python -m pytest tests/ -q` (all pass). The new `tests/test_browser_protections.py` sends each deployment shape the brief names, with the headers a current browser actually sends there (no `Sec-Fetch-*` to a plain-HTTP address that is not loopback), with and without the app header, against every write route.
2. Cross-site refusal by hand, with the backend running (ideally on a throwaway `SR_DATA_DIR`): `curl -i -X POST -H 'Origin: https://evil.example' -H 'Content-Type: application/json' -d 'true' http://localhost:1620/settings/sr-origin-check` returns `403 {"detail":"Request refused: not sent by SnowRaven's own page."}` and writes nothing, and so does `-H 'Origin: http://localhost:1620'` (a browser-shaped request without the app header); adding `-H 'X-SnowRaven-Request: 1'` to that second command returns 200, and so does the command with no Origin at all, which is how curl and the Node tooling call it (then `curl -X DELETE http://localhost:1620/settings/sr-origin-check` to remove it). A multipart upload to `/settings/files/ebird` with a foreign Origin is refused the same way. A preflight from Vite's default dev origin is refused too: `curl -i -X OPTIONS -H 'Origin: http://localhost:5173' -H 'Access-Control-Request-Method: POST' -H 'Access-Control-Request-Headers: x-snowraven-request' http://localhost:1620/settings/theme` returns `400 Disallowed CORS origin` with no `Access-Control-Allow-Origin`.
3. Headers: `curl -I http://localhost:1620/` shows the four headers.
4. The app still works: under `./start.sh`, under `npm run dev` (Vite proxy) at `http://localhost:5173` and at the Mac's LAN address (`npx vite --host 0.0.0.0`), and on a Pi reached by LAN name or IP over plain HTTP, upload a backup, save a setting (for example the Text size), and remove a file. Each should succeed. After upgrading a server, reload any tab that was open before the upgrade: a tab still running the old bundle sends no header and its saves are refused until it is reloaded.
5. Targets: open the Targets tab at 320px wide with Settings, Appearance, Text size 200%, on a county whose list includes Yellow-headed Blackbird or Bonaparte's Gull. The table does not scroll sideways; the scientific name wraps under the common name.
6. Settings, Appearance: with no saved choice, pick Dark. On web/Pi the prompt reads "Your preference will be saved on this server and used by every browser that opens SnowRaven here."; in the desktop app, "Your preference will be saved in this app's settings on this device."
7. Settings, Bar-chart files on web/Pi reads "No bar-chart files are saved on this server." (or "Saved for N counties on this server.").

### Notes for reviewer

- **Mechanism (decisions.md 4, replacing 1):** a required request header. `WebStorage` (every POST and DELETE) and `WebTransport.post` send `X-SnowRaven-Request: 1`, declared once in `frontend/src/lib/appRequestHeader.ts` (no imports, entry-chunk safe) and once in `backend/main.py` (`APP_REQUEST_HEADER`), with a backend row comparing the two. The backend refuses a POST, PUT, PATCH or DELETE that came from a browser (it carries `Origin` or `Sec-Fetch-Site`) without the header. A page on another origin cannot add a custom header without a CORS preflight, and the backend's CORS admits no origin (`DEV_ORIGINS = ()`, so `allow_origins=[]`), so it refuses every such preflight. It used to admit `http://localhost:5173`, which let any page served on Vite's default port (another project's dev server) pass the preflight, add the header, write and read the stored API keys (audit M1, fixed here); the app's own dev page is same-origin through the Vite proxy and never preflights, so removing the entry costs nothing. `CORSMiddleware` stays so a foreign preflight still gets an explicit 400. Nothing compares Host, Origin or `X-Forwarded-Host` any more, which is what broke at QA: Chromium and WebKit send no `Sec-Fetch-*` header to a plain-HTTP address that is not loopback, so the old Origin-vs-Host fallback was the only check on a LAN Pi and on a dev page opened by LAN address, and it refused the app's own writes there and behind a Host-rewriting nginx. Requests with no `Origin` and no `Sec-Fetch-Site` (curl, TestClient, Node `fetch` in `website/tools`, which sends `Sec-Fetch-Mode` only) pass.
- **Known limits, each stated at its definition in `backend/main.py`:**
  - The guarantee rests on CORS, here and in any proxy in front: any origin added to `allow_origins`, or a proxy that answers preflights itself, lets the pages it admits write.
  - A tab still running a pre-fix bundle sends no header and is refused until reloaded.
  - L1 (Low, pre-existing): DNS rebinding passes the guard, since an attacker hostname re-pointed at the server is same-origin and nothing checks Host.
  - I1 (Informational, accepted): an unhandled exception's 500 comes from Starlette's `ServerErrorMiddleware` and carries none of the four headers (body is a fixed "Internal Server Error").
- **`frontend/vite.config.ts` now sets `server.cors: false`.** Vite 8's dev server answers a CORS preflight itself for any `localhost` or `127.0.0.1` origin and echoes the requested headers, so the backend's CORS never saw it. Measured in Chromium and WebKit: with the default, a page on `http://localhost:8766` added the header and wrote through the dev proxy (200, file on disk); with `cors: false` the preflight reaches the backend, is refused (400), and nothing is written. The app's dev page is always same-origin with Vite (Tauri dev loads `devUrl` directly; HMR is a WebSocket, which `server.cors` does not govern), so it never preflights. A backend row pins the setting with comments stripped.
- **Middleware order is load-bearing** (`backend/main.py`): `SecurityHeaders` is outermost, so a CORS preflight answer and the guard's 403 carry the headers; the guard sits outside CORS. The unhandled-exception 500 sits outside this stack (I1, under Known limits).
- **`nosniff` cannot break a load:** Vite's module scripts and workers already require a JavaScript MIME type, Python's `mimetypes` types `.js`/`.mjs` as JavaScript and `.css` as `text/css` (one test reads the running host's answer, so CI checks Linux), and the map's `.pbf` glyphs are fetched as bytes, which `nosniff` does not govern. No MIME registration was needed.
- **`settingskv`** now answers 415 for any non-JSON content type before reading the body; `test_non_json_body_rejected_422` became a 415 row over `text/plain`, form, multipart and no type (each carrying a valid JSON body), plus a 422 row for invalid JSON sent as JSON.
- **Targets CSS** is three rules in the established 640px tier, scoped to `.sr-tg-name` like the Breeding Codes and Rainbow Connection repairs. The shared `.sr-birdname-sci` is untouched, and the built CSS differs from HEAD's by exactly those three rules (rule-by-rule diff, utilities identical). The 1.0.47 Last report hang (F4) is untouched; its rows pass unchanged.
- **Mutation-checked:** backend mutations of the header guard (Origin dropped as a browser marker, `Sec-Fetch-Site` dropped, `Sec-Fetch-Mode` added as one, presence-only header check, guard never refuses, DELETE left out of the unsafe methods, CORS wildcard, the `http://localhost:5173` CORS entry restored (four rows red), header renamed on one side, Vite `cors: false` deleted, commented out, or set true) each turn at least one row red; the guard moved inside CORS stays green, because CORS passes every non-preflight request through and a preflight is a safe method the guard ignores, so no input separates the two orders. A header removed from `deleteApiKey`, `setApiKey`, `deleteAllBarChartFiles` or `WebTransport.post` each turns its row red. From the first round, still standing: the headers-middleware order, one security header dropped, two `settingskv` arms, and 12 frontend mutations (each CSS rule deleted, `break-word` for `anywhere`, selector renamed, rules moved to top level, shared rule changed, the old Appearance sentence, swapped branches, `here` reverted, server word everywhere, the BirdName wrapped in a span) each turn at least one row red; restores verified by hash.
- **Built-app check (scratch probe, not committed):** the Targets tab served from the built `dist` with a stubbed backend, 320 to 420px in 10px steps at 100/150/200%, Chromium and WebKit: 66/66 configurations measured, table and page scroll 0, no box or text ink past the cell (worst 0.02px), favicons inside the cell, every 24px hit target unclipped, and the scientific name wrapping in 20 configurations. The same dist with HEAD's stylesheet reproduces the brief exactly (74px of table scroll at 320px/200%, 34px at 360px) in both engines. Promoting it into `website/tools/verify/` would be a `website/` change, which this build was told not to make.
- **One captured fixture string moved on purpose:** `settingsOffIos.fixture.json`'s web entry now reads "saved on this server" in the Bar-chart files status; Windows and Mac entries are as captured.
