# PRD: Visited Hotspots in Search
**Feature:** visited-hotspots-in-search
**Date:** 2026-11-13
**Stage:** 2, The Planner
**Source:** strategic-brief.md (approved)

## Feature Overview

Search (the Cmd-K overlay) gains a third group of results, after Destinations and Species: the locations in the user's own eBird backup, matched by name. Choosing one opens the **Hotspot Reports** tab (`hotspot-reports`) on that location's report. The feature ships only in a form that passes the five responsiveness gates of the brief (NFR-01 to NFR-05); if no form passes, it does not ship (FR-03).

Requirement IDs below are this feature's own. A requirement of a shipped feature is cited by its folder (for example `command-palette FR-29`, `hotspot-reports FR-10`). Default wordings are given so two engineers build the same thing; the Designer may restyle a default wording but not change what it states. "The tab" means the Hotspot Reports tab; "the tab's picker" means its Location picker. "A location" always means one Location ID in the loaded backup, a public eBird hotspot or a personal location alike (Open Question 1).

**How to read this document across the outcome ladder.** Sections A to F and H to J hold for whichever form ships. Section G holds the three form-specific requirements; exactly one of FR-33, FR-34 and FR-35 applies, and the schema names which. FR-03 is the fourth outcome.

## User Stories

> **US-01** As a birder who thinks in places, I want to type part of a place name into Search and open my record there in one step from any tab, so that I do not have to open Hotspot Reports, open its picker, type and choose.

> **US-02** As a birder with two places that share a name, I want Search to tell them apart and open the one I chose, so that I never land on the wrong report.

> **US-03** As a birder who uses Search for tabs and birds, I want destinations and species to behave exactly as they do today and Search to feel no slower, so that nothing I rely on moves or lags.

> **US-04** As a birder with a very large or unusual backup, I want Search to stay responsive and to say when it is showing only some of the matching places, so that a big file never freezes the overlay or hides a cut.

> **US-05** As a birder with no backup saved, a backup still being read, or a backup that would not load, I want Search to say which of those is true for places as it does for species, so that I am never told to import a file the app can already see.

> **US-06** As a birder without an eBird key, or offline, I want every place in my backup to be findable in Search, so that reaching my own records never depends on eBird answering.

> **US-07** As a keyboard or screen reader user on a phone-width screen at large text, I want the new results to be reachable with the arrow keys, announced with enough to tell namesakes apart, and readable without sideways scrolling, so that Search works for me as it does today.

## Functional Requirements

### A. The ship gate and the outcome ladder

> **FR-01** The feature shall ship in the first of these forms that passes all five gates NFR-01 to NFR-05, tried in this order: (1) the **full form** (FR-33), (2) the **deferred form** (FR-34), (3) the **threshold form** (FR-35). Each form is measured against the same five gates with the same fixtures, engines and method (NFR-06). No gate is advisory, none may be dropped, and no number in them may be loosened by any builder; only the user may change one. The form selected, the figures that selected it and the figures that ruled out any earlier form shall be written into `schema.md` and into the run's `decisions.md`.

> **FR-02** The measurements shall be taken three times, each recorded. (a) **The Architect, first,** on the pure functions in both engines, before any design or build work; the figures go into `schema.md` beside each declared scan as its cost per draw and per re-draw (NFR-09). This is the first go or no-go. (b) **The Engineer,** in the built app in Chromium and in WebKit, recorded in `decisions.md`. (c) **QA,** who judges NFR-01 to NFR-05 on the recorded figures before the deploy gate, together with a live look at the built app on a cap-sized synthetic backup (NFR-18). If (b) or (c) finds a gate failing for the selected form, the run returns to the Architect for the next form on the ladder, and the requirements of this document apply to that form; the failing figures are kept in `decisions.md`. A failure is never resolved by re-stating a gate.

> **FR-03** **Does not ship.** If no form passes, the run shall stop at the stage that measured it. The measured figures for every form tried, per gate and per engine, go to the user. Nothing from the run is merged to `main`, no version is bumped, no changelog entry, tag or release is made, no Help or in-app text changes ship, and no held copy is applied. The pipeline folder keeps the brief, this document, the schema and the figures as the record. The run resumes only on the user's decision.

> **FR-04** None of the following is an acceptable way to pass a gate, in any form: indexing or offering only some of the backup's locations without saying so; leaving out personal locations to reduce the count; delaying, debouncing or capping destinations or species; any network request; a persisted index. If the Architect finds that a persisted index is the only passing form, that finding goes to the user as a decision (it would be a new durable store keyed on file content, with a `clearDerived.ts` row and a privacy-policy sentence) and is not built in this run.

### B. Which locations Search knows

> **FR-05** Search's locations shall be exactly the tab's locations (`hotspot-reports FR-10, FR-11`): a location is one distinct Location ID cell of the loaded backup, 1 to 16 code units, compared exactly as parsed; which location a row counts at is decided by its checklist's first row in file order; a checklist whose first row carries no usable Location ID is offered nowhere; a row with an empty Submission ID changes nothing. For every backup, the set of Location IDs Search can offer shall equal the set `buildLocationIndex` yields, in both directions. The Architect either derives both from one shared rule or keeps a second derivation and proves the equality over a generated corpus whose first rows are the failure returns (an empty file, a file with no usable Location ID, a file whose every Submission ID is empty). A second derivation owes its symmetric difference against `buildLocationIndex` in both directions, measured, not argued.

> **FR-06** For each location Search shall hold only what a row shows and what the request carries: the Location ID; the name, read through the tab's bound (200 code units, no lone surrogate at the cut) with the truncation recorded; and the place label in the tab's form ("County, ST", "County", "ST" or empty, through the tab's bounded County and State/Province reads). Name and place are those of the location's first checklist in file order, as on the tab (`hotspot-reports FR-12, FR-13`). For every location, the name and the place label Search shows shall equal the ones the tab's picker shows for the same Location ID.

> **FR-07** The location data shall be derived in memory from the shared parse (`loadEbirdObservations`) and from nothing else: no second read of the file, no request, no stored document. It shall be derived at most once per loaded file, and only after Search has been opened; a session that never opens Search performs none of this derivation, at launch, on a file load, or while any tab (the Hotspot Reports tab included) is open. It shall not outlive the parse it came from (NFR-04). Search shall not read the tab's own index from the tab, because the tab may not be mounted.

### C. Location results

> **FR-08** Location results shall be a third group, after Species, in the same single ordered result list Search has today, under their own group heading (default "Locations"; the final word is the Designer's and must be true of a personal location, so it is never "Hotspots"). The heading is not a result: it is not selectable and the arrow keys never land on it. The group and its heading are rendered only when the group has at least one row, or when FR-20 puts a backup-state sentence under a heading.

> **FR-09** With an empty query, or a query that is empty after trimming (whitespace only), Search shall show no location rows: destinations only, exactly as today. Opening Search never lists locations before something is typed.

> **FR-10** A location shall match when the normalized query (trimmed and lowercased, the normalization Search already applies once per keystroke) is a substring of the location's shown name, lowercased. The shown name is the bounded name; for a location whose name is empty it is the tab's placeholder wording (default "Unnamed location"), so an unnamed location can be found by typing part of that wording. The written ellipsis of a truncated name is not matched. County, state or province, the place label and the Location ID are not matched. There is no fuzzy matching, no accent folding and no ranking by relevance. The query never becomes a `RegExp`. A query longer than a named bound matches no location; the bound is enforced inside the matching function and the query input itself is unchanged (default: the name bound, since no bounded name can contain a longer query, so the bound changes no result).

> **FR-11** Location rows shall be ordered by name, then by place label, then by Location ID in code-unit order, with unnamed locations after named ones. The order shall be total and shall depend only on the set of locations, never on their order in the file, so two runs over the same backup and a run over the same rows shuffled give the same order. Which string comparison orders name and place (locale compare, as the tab's picker; or code-unit, as Search's species) is the Architect's choice inside the gates, stated in the schema with the reason (Open Question 3).

> **FR-12** At most a fixed number of location rows shall be rendered: a named constant of its own that the file cannot change (default 50, the species cap's value; the Architect or Designer may set another fixed value). The cap applies after ordering, so the rows shown are the first matches in FR-11's order. When more locations match than are shown, one non-selectable line shall say so (default "Showing the first {cap} locations. Keep typing to narrow them."), built from the constant in the copy module so the sentence and the cut cannot disagree. The line shall directly follow the location rows in reading order and be programmatically associated with that group, so that when the species cap line also shows, a reader can tell which group each line is about. The arrow keys never land on it. Destinations are never capped; the species cap and its line are unchanged (FR-16).

> **FR-13** Each location row shall show, as escaped plain text: the location's shown name (the bounded name with a written ellipsis when it was cut, or the placeholder when it is empty), and its place label when it has one. It shall show no kind mark (hotspot or personal), no checklist count, no link and no other control: a row is a plain `role="option"` element with nothing interactive inside it, so `HotspotLink` is never rendered in a row. The row's accessible name shall contain the shown name, the place label when present and the Location ID when FR-14 shows it, in that order. Whether a location row carries a glyph is the Designer's choice.

> **FR-14** Where two or more locations in the backup share both name and place label, each of those rows shall also show its Location ID as plain text, so namesakes are told apart first by place and then by ID. The rule is evaluated over the whole backup, not over the rows a query happens to match, and is the tab's rule: for every location, Search shows the Location ID exactly when the tab's picker shows it for that location (`hotspot-reports FR-21`). Two namesakes are always two rows and each opens its own report.

> **FR-15** Name edge cases. (a) A name longer than the bound is shown cut with the ellipsis and matched on the bounded text only. (b) An empty name is shown and matched as the placeholder (FR-10). (c) A name made only of whitespace is shown as the tab shows it and cannot be matched by any query, because a trimmed query always holds a non-space character; this is an accepted limit for a hand-built file, recorded in `decisions.md` with what would reverse it. (d) A name equal to `__proto__`, `constructor` or any other `Object.prototype` member name, and a Location ID of that shape, are ordinary locations: listed, matched and opened like any other. (e) A name is never used to build a DOM id, an ARIA reference or a selector (FR-19).

> **FR-16** Destinations and species shall behave exactly as they do today. For every query that matches no location: the destination rows, the species rows, their order, the species cap and its line (wording and presence), and the result Enter opens when nothing is highlighted are identical to the shipped build's. For every query: destinations still render in the first commit on open, before any read of the backup; species matching, code ranking and the species cap are untouched; and the Alerts inbox row is untouched. Nothing that is first today stops being first.

### D. Keyboard, pointer and assistive technology

> **FR-17** The Up and Down arrow keys shall move the highlight through the whole list, crossing from species into locations with no extra keystroke, stopping at the ends without wrapping, as today. The highlighted row is scrolled into view. Enter opens the highlighted row, or the first row of the list when nothing is highlighted, which is a location only when no destination and no species matched; with no rows Enter does nothing and Search stays open. A pointer press on a location row chooses it. Escape, the Close button, the backdrop and a second press of the key combination are unchanged.

> **FR-18** A change to the rows that the user did not type shall never move the highlight onto a different result. When location rows join an open search (FR-34), they are added after every existing row, so an existing highlight keeps its row and Enter's target among existing rows does not change. When the species rows change under a highlighted location row (the species-code data arriving, `species-code-search FR-25`), the highlight either stays on the same location or is cleared; it never lands on another row. Every query change resets the highlight, as today.

> **FR-19** Every DOM id and ARIA reference for a location row (the option id, `aria-activedescendant`) shall be built from the row's position in the list plus the overlay's per-instance prefix, never from a name, a place or a Location ID. The location group shall be exposed to assistive technology as a labeled group of options inside the existing listbox. The feature adds no tab stop: the query input and the Close button remain the overlay's only two, and no location row, heading or cap line is focusable. No new live region is added; state sentences use the overlay's existing status region (FR-20).

### E. What Search says about the backup

> **FR-20** Species and locations come from one backup, so they share one backup state and one sentence, shown through the overlay's existing always-mounted status region and never created together with its first message. (a) **Reading:** while the shared read is in progress, the shipped sentence, unchanged ("Reading your eBird backup."). (b) **No backup saved:** default "Searching species and locations needs your eBird backup. Upload MyEBirdData.csv in Settings → Default Files → eBird Backup." (c) **A saved backup that would not load:** the shared `EBIRD_BACKUP_LOAD_ERROR` constant, unchanged and imported from where it lives. The heading shown over such a sentence shall not name species alone (default "Species and locations"). Destinations work in all three states. Exactly one of these sentences, the no-match sentence (FR-22), or none is shown at a time.

> **FR-21** A file-status read that fails is unknown, never empty: it shall show sentence (c) of FR-20 and never sentence (b), for locations as for species. This holds on web and Pi, where the status read is a request to the user's own server that can be unreachable.

> **FR-22** The no-match sentence ("Nothing matches that search.", unchanged) shall be shown only when the query is non-empty, the backup has loaded, every half that will answer this query has answered, and no destination, species or location matches. It shall never be shown while location results for the current query are still pending (FR-34). In the threshold form it shall never be shown for a query shorter than the minimum; FR-35 gives the sentence for that case.

> **FR-23** Replacing or clearing the eBird backup while Search is open shall reach it at once, with no relaunch and no reopen: location rows from the previous file leave in the same update that species rows from it leave, the state returns to "reading" and then to the new file's answer, and Search never offers a location from a file that is gone. This relies on the data-file epoch the overlay already follows.

> **FR-24** A backup that loads and holds no location (FR-05 leaves nothing) produces no location rows and no sentence of its own; FR-22 applies as for any query that matches nothing.

> **FR-25** If the location data cannot be derived from a backup that loaded, destinations and species shall keep working, no location row shall be shown, and Search shall show sentence (c) of FR-20 for the location half under the location heading. The failure is never reported as "no backup" and never as "nothing matches". If the Architect shows the derivation cannot throw for any parse the shared cache can hand back, a test that injects a throwing derivation still proves this behavior.

### F. Opening the report

> **FR-26** Choosing a location row shall close Search through its one close path and show the Hotspot Reports tab with that location's report, from any tab, including from the Hotspot Reports tab itself and including when the tab has not been opened yet in this session (it mounts and loads as it does on a first visit). Keyboard focus after the close follows the overlay's shipped rule unchanged (`command-palette FR-12`): back to the control Search was opened from, or to the main content when that control is gone or hidden. Focus never lands on the document body.

> **FR-27** A location row shall open the Hotspot Reports tab even when the user has hidden that tab in Settings, exactly as a species row opens Species Detail when that tab is hidden (`command-palette FR-29`; Help says so for species today). Hiding a tab removes it from the navigation and from Search's destinations (`command-palette FR-18`, unchanged); it does not remove the user's locations from Search. The hidden set is not changed by the visit, and the tab does not become a destination.

> **FR-28** Choosing a location while a map is fullscreen shall end with the Hotspot Reports tab visible, no fullscreen map covering it and page scrolling not locked. For the Map Explorer's fullscreen the choice collapses it first, as the species route does, so returning to the Map Explorer later does not show a fullscreen map. For an expanded embedded map (Species Detail, Named Birds, Statistics) the outcome shall equal what choosing a species row produces from the same state today. Choosing a location never leaves the app in a state the species route cannot reach.

> **FR-29** The route into the tab shall be one App-level, single-use request carrying only the Location ID. (a) It is held until the tab's ready phase holds an index, then consumed exactly once and cleared; it is never applied twice and never re-applied on a later file change. (b) If a second location is chosen before the first request is consumed, the later one wins. (c) If the tab settles in its setup-required or load-error phase instead of ready, the request is dropped, the tab shows that phase as it would on any visit, and no message about the request is shown. (d) Consuming a request never switches the active tab: if the user has moved to another tab before it is consumed, they stay there, and the report is the one shown when they return. (e) The Location ID in the request is used only as a `Map` lookup key against the tab's index.

> **FR-30** A report opened from Search shall behave as one chosen in the tab's picker (`hotspot-reports FR-24, FR-25`): the picker's value shows that location's shown name, the tab's existing polite live region announces the location once (its name with its species and checklist totals), and every part of the report renders by the tab's own rules. The region is in the accessibility tree, empty, in a commit before the message. The report's header shall be in view without the user scrolling. Choosing the location that is already selected leaves the report as it is and announces it once. The tab builds its location index at most once per loaded file, as today, and never because of a Search selection: a selection from Search costs the tab what a picker selection costs.

> **FR-31** When the requested Location ID is not in the tab's index (the backup was replaced between the choice and the consumption, and the new file lacks that location), the tab shall show its overview with nothing selected, with no error message and no announcement, and the request is cleared. It never shows a different location's report in answer to the request.

> **FR-32** Apart from accepting the request, the Hotspot Reports tab is unchanged: its picker (matching, order, window, namesake rule), its overview, its report, its copy and its requests. Location names elsewhere in the app (Checklists, Species Detail, map popups) keep their current links and gain no route to the tab.

### G. Form-specific requirements (exactly one applies)

> **FR-33** **Full form.** Location results are produced for every keystroke from the first character, in the same synchronous result build as destinations and species, and after a file load they join an open search in the same update in which species results join it.

> **FR-34** **Deferred form.** The location data is prepared separately from, and after, the species results of an open search, so species rows and typing never wait on location work. Location rows join the open search when the data is ready, with no need to close and reopen, under FR-18 (added after existing rows) and FR-22 (no no-match sentence while they are pending). While they are pending and no other row or sentence is shown for a non-empty query, the reading sentence of FR-20 (a) is shown. The only visible difference from the full form is that gap on the first open after a file load: once the data is ready, in that open and in every later open for the same file, location results for a keystroke render in the same update as its species results. A design in which location results lag species results on every keystroke is not this form (Open Question 5).

> **FR-35** **Threshold form.** Locations are matched only when the normalized query is at least a minimum length, a named constant the Architect sets from the measurement at 2 or 3 code units (never more than 3). Below it Search shows no location rows. Help states the minimum (FR-37), and the constant, not a typed number, feeds every sentence that names it. For a non-empty query shorter than the minimum that matches no destination and no species, Search shows a threshold-aware sentence in place of FR-22's (default "Nothing matches so far. Locations are searched once you have typed {n} characters."). This form may also join late as FR-34 allows; the schema says whether it does. The gates are measured as written, with the ordinary-match and no-match queries at least the minimum long.

The unnamed-location placeholder is the tab's own constant, single-sourced, not a second copy. The Search control's label in the navigation ("Search") is unchanged. No string holds an em dash (U+2014); spelling is American; the tab is named "Hotspot Reports" from `TAB_LABELS`, never from a component name.

> **FR-37** `docs/HELP.md`'s **Search** section shall be updated in the same change as the feature, to state as properties: that Search reaches the locations in the user's own eBird backup, hotspots and personal locations alike, and only those; that a location is matched on its name, anywhere in it, ignoring capitals, and not on its county, state or Location ID; what a row shows and how namesakes are told apart; that choosing one opens Hotspot Reports on that place, even when that tab is hidden; the order of the three groups and of location rows; that the location list stops after a fixed number with a line saying so (the number itself is not written in Help, as for species); that the arrow keys cross all three groups; the backup-state messages as changed by FR-20; that replacing or clearing the backup reaches open location results too; and, in the threshold form only, the minimum length. The Help guards in `lib/palettePublishedClaims.test.ts` move with the prose: the Search passage keeps every existing row, and gains rows holding the location claims to the code (the location cap's value does not appear in the prose; the hidden-tab sentence; the matched field).

> **FR-39** `README.md`, `website/`, `appstore/LISTING.md` and what is written into App Store Connect, `PRIVACY_POLICY.md` and its `website/privacy.html` twin, and the F-Droid listing text are not changed by this feature: none describes Search's results, nothing is persisted and no request is added, so no sentence in them becomes untrue. The App Store "What's New" text and the three Fastlane changelog files are prepared as a held patch in the pipeline folder and applied only after the user has read the exact wording and said yes. No screenshot set is regenerated, because no tab is added.

## Non-Functional Requirements

> **NFR-01 (Gate R1, Typing):** Measured: the whole synchronous result build for one keystroke (destinations, species with code ranking, locations) at the realistic cap, over a one-character query, an ordinary match and a no-match, beside the same build with locations removed. Pass: the location half adds at most 4 ms (a quarter of a frame) and the total stays at or under 16 ms, in both engines. If the build without locations is already over 16 ms on this fixture, that is reported as a separate finding about the shipped overlay and the feature is judged on the 4 ms alone.

> **NFR-02 (Gate R2, First open):** Measured: main-thread CPU the feature adds to the first Search open after a file load, at the realistic cap. Pass: at most 50 ms (the long-task line) in both engines, none of it before destinations have painted. Later opens and later keystrokes cause zero location derivations, counted by a spy. A session that never opens Search does no location work at all: none at launch, on a file load, or on another tab.

> **NFR-03 (Gate R3, Hostile files):** Measured: every new scan over file text, at doubling sizes, including a leg in which every row is its own location. Pass: linear by the house method (at most 2.2x per doubling). Rendered location rows are capped by a named constant the file cannot change, with a visible cap line. Names are length-bounded before matching and before render. At 150,000 distinct locations the location half of a keystroke costs no more than the species half costs at 150,000 distinct species in the same run, so the worst case is no worse in kind than what ships today.

> **NFR-04 (Gate R4, Load and memory):** Measured: the entry chunk, and the heap the location data retains. Pass: nothing new on the entry chunk (`entryChunk.test.ts`). The location data becomes unreachable when the parse it came from is replaced or cleared, asserted by test, with the argument written at the definition site (the species index's strong-reference memo is not a precedent here: a hostile file can make this data 150,000 records with long names). Retained heap at the realistic cap is recorded and at most 5 MB; the hostile figure is recorded with the bound that limits it.

> **NFR-05 (Gate R5, What ships today):** Measured: destinations, species results and the backup states. Pass: with locations present, destination and species rows, their order, the species cap line and Enter's choice of the first row are unchanged for every query that matches no location; destinations still render in the first commit; the existing overlay suites stay green. The only existing assertions that may be edited are those that pin, word for word, a string FR-36 changes; each such edit is listed in `decisions.md`. No other existing row is edited to fit.

> **NFR-06 (Measurement method):** Fixtures: the **realistic cap** is 150,000 rows, 3,000 species, 2,000 locations (the `hotspot-reports` schema's shape); the **hostile shape** is 150,000 rows with every row its own location. Engines: V8 and JavaScriptCore for the pure functions, Chromium and WebKit for the built app, all on the developer Mac. Timing is CPU time through `frontend/src/test/cpuTiming.ts` with nothing else compiling. Committed guards are quotients, counts and structural assertions; a deliberately expensive guard states its own timeout. Every recorded figure names its fixture, engine and whether it is a first call or a best-of.

> **NFR-07 (Network):** No third-party request, no new endpoint or host, and no request moved between components. Search itself asks for nothing: over a full open, type and choose cycle the overlay's modules make no request beyond the existing file-status read and shared file read, which on web and Pi are existing calls to the user's own server and whose count per open is unchanged. Choosing a location opens a tab that may make its existing requests (the hotspot classification with the user's key, the taxonomy codes batch, map tiles once a located place is shown) exactly as choosing that location in the tab's picker does; Search adds a route to them, not a request. The Vite proxy, the backend routes, `CACHED_GET_PATHS`, the Tauri content security policy and the Tauri HTTP permit are unchanged. Requests a system component makes from the app's process are in scope of this statement; the feature causes none.

> **NFR-08 (Nothing persisted):** The feature writes nothing: no stored document, no setting, no `localStorage` value, no recent-search or remembered-location value. There is therefore no `clearDerived.ts` row, `cacheInventory.test.ts` is unchanged and green, and no privacy-policy sentence is owed.

> **NFR-09 (Declared scans and linearity):** The scans this feature adds over user-file text are, at least: the location pass over the observations (per draw: once per loaded file; per re-draw: none); the per-keystroke match over bounded names; and the ordering of locations or of matches. Each is declared per FR-41 and is linear by the house method, or n log n for a sort with the limit derived from the rows it actually sorts. Any native search is bounded to the bounded string it searches, and the hostile corpus carries the delimiter-absent case for each. No loop is driven by a number read from a cell. No de-duplication or grouping over file text uses a nested scan.

> **NFR-10 (Hostile keys and identifiers):** Every table keyed on file text (Location IDs, Submission IDs, names) is a `Map`, or is read through `Object.hasOwn` at the point of use. No DOM id, ARIA reference or selector is built from file text. File text reaches the page only as escaped React text; no location row builds an `href`.

> **NFR-11 (Accessibility):** WCAG 2.1 AA holds for the overlay with location results present. The grouped-listbox structure, the single active descendant, the two-tab-stop invariant (asserted with zero location rows and with the cap's worth) and the focus containment are as shipped. The status region is in the accessibility tree before its message and is never hidden while idle. The highlighted row has a non-color cue as today. A claim about the accessibility tree is read from a real engine's tree in Chromium and WebKit, not from jsdom. No screen reader announcement is claimed in published prose beyond what has been verified.

> **NFR-12 (Layout):** At 320px width and at 200% in-app text scale, in both themes, in Chromium and WebKit: no horizontal scroll of the page or the panel; a location row with a 200-unit unbroken name and the longest place label stays inside the panel; where a row must shorten, the name gives way before the place label and the Location ID, so namesakes stay distinguishable; both cap lines, the group heading and each state sentence wrap rather than clip. The measurement uses the longest strings a state can produce, not a fixture's typical ones, and any size threshold taken from the mockup is re-measured in the built app.

> **NFR-13 (Theming):** Every color comes from a `var(--sr-*)` token defined in both themes; no hardcoded color. Any hover look on a row keeps the shipped overlay's behavior and adds no new touch-hover defect.

> **NFR-14 (Platforms and compatibility):** The feature behaves as specified on every shipped target: Mac, Windows, iPhone, iPad, Android, web, and Raspberry Pi. It uses no runtime API beyond those already cleared for the shipped targets and the Android WebView floor; any other needs the explicit availability check `security.md` requires.

> **NFR-15 (Determinism):** For one backup, the location rows and their order are the same on every run on one platform and do not depend on file order (FR-11). If the Architect chooses locale compare, the schema states that order can differ between engines' collations as the tab's picker order already can, and the namesake rule still equals the tab's on each platform.

> **NFR-16 (Bundle):** No new module joins `App.tsx`'s static import graph, and the Hotspot Reports tab stays lazy. If Search reuses any module of the tab, the schema shows that the overlay's chunk does not pull the tab's report, map or maplibre code, and `entryChunk.test.ts` gains a row for each new off-entry module. No new npm or Rust dependency.

> **NFR-17 (Prose):** Help, in-app copy and any held copy contain no em dash, use American spelling, state properties rather than counts, name surfaces from `TAB_LABELS`, and write platform lists with the serial comma.

> **NFR-18 (Verification and the device boundary):** Verification is by automated tests plus a live look at the built app before the deploy gate, on a cap-sized synthetic backup, in Chromium and WebKit; what that look finds goes back to the Designer. Agents work on the developer Mac and its simulators only. Every timing figure is from the developer Mac, and the gates carry headroom for that. The one check that needs a phone is FR-43, performed by the user. A browser probe of the built app on the web or Pi preview answers every eBird-backed path it is not measuring inside the browser, and counts those requests, before it loops over configurations.

## Out of Scope

- Hotspots the user has never birded, and any eBird lookup started from Search. That is the Map Explorer's Hotspots view.
- Hotspot or personal marks on Search rows, and filtering Search to public hotspots only. Both need the hotspot classification, a network answer Search does not start (Open Question 1).
- Matching on county, state or province, place label or Location ID. A state name would match most of a backup at three letters and bury the other results.
- Ranking location matches (prefix first, most visited first, nearest first). Rows are in FR-11's order only.
- A checklist count, species count or any other figure on a Search row.
- Checklists, named birds, counties or dates in Search. One new result kind per feature.
- Opening a report from location names elsewhere in the app (Checklists, Species Detail, map popups).
- Remembering the chosen location across launches, recent searches, or any stored value.
- Changes to the Hotspot Reports tab beyond accepting the request (FR-32), including its picker's two-scans-per-keystroke note (`hotspot-reports` schema 12.5) and how it shows a whitespace-only name.
- A persisted location index (FR-04).
- A design in which location results lag species results on every keystroke (Open Question 5).
- Any change to how destinations or species are matched, ordered, capped or worded, beyond the strings FR-36 names.
- `README.md`, `website/` (other than the version stamp), `appstore/LISTING.md`, `PRIVACY_POLICY.md` and the F-Droid listing text. If a later stage wants a sentence there, it is a held proposal of at most one sentence for the user's yes.
- New App Store or website screenshots. No tab is added.
- Any physical-device measurement by an agent.

## Open Questions

1. **Should Search list personal locations, or public eBird hotspots only? (For the user; carried from the brief.)** "Visited hotspots" can be read either way. *Default if no answer before Stage 5:* every location in the backup, hotspots and personal locations alike, which is the set Hotspot Reports reports on and the only reading Search can serve with no network answer. The requirements keep a later public-only reading a small change: Search's set is defined in one place (FR-05), rows carry the Location ID and the region cells the classification reads, and a filter over those rows from the passively read classification would touch FR-05, FR-13 and the Help sentence about needing no key, and nothing else.

2. **A location result opens Hotspot Reports when that tab is hidden (FR-27).** Settled here on the Species Detail precedent; the alternative was to hide location results while the tab is hidden. *Default:* FR-27 as written. The user may reverse it; the change would be one condition on the location group and one Help sentence.

3. **Which comparison orders location rows (FR-11).** The tab's picker uses locale compare; Search's species use code-unit comparison so order is identical on every platform. *Default:* the tab's picker order, so the two lists of the same places read the same and the namesake rule is shared outright; the Architect may choose code-unit order if the measurement or cross-platform determinism favors it, and says why. Either way FR-14's parity with the tab holds.

4. **The location cap's value (FR-12).** *Default:* 50, the species cap's value. The Architect or Designer may set another fixed value from the measurement or the layout; it is never derived from the file.

5. **Location results that lag on every keystroke.** The brief's deferred form allows a gap only on the first open after a file load. If the measurement passes only with location results arriving after species results on every keystroke, that is a visible behavior the brief did not approve. *Default:* not adopted; the ladder moves to the threshold form, and the finding goes to the user with its figures.

6. **The group heading word (FR-08) and whether a location row carries a glyph (FR-13).** *Default:* "Locations", no glyph (species rows carry none). The Designer decides both.

7. **The threshold form's sentence for a short query that matches nothing (FR-35).** *Default:* "Nothing matches so far. Locations are searched once you have typed {n} characters." Applies only if that form ships.

8. **`ACCESSIBILITY.md` (FR-38).** It is not on CLAUDE.md's list of surfaces that wait for the user's approval, and it must stay true. *Default:* extend the one sentence about the arrow keys in the same change, with no other edit; if the user prefers to read it first, it joins the held patch.

9. **What a failed later measurement does (FR-02).** The brief names who measures and when, not what a failure at the Engineer's or QA's measurement triggers. *Default:* the run returns to the Architect for the next form on the ladder; no gate is re-stated.
